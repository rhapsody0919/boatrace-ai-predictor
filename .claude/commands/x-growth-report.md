# X集客状況レポート（自アカウント投稿実績＋競合定点観測＋サイト送客効果）

Xは`docs/operation/x-operations-playbook.md`で最も運用に力を入れているチャネルであり、アルゴリズム調査（`docs/reference/x-algorithm-and-growth-notes.md`）・投稿設計ルール・リプライ戦略まで詳細に確立されている。にもかかわらず、本スキルは2026-09-05時点まで「インプレッション・いいね数を見て終わる」という浅い定点観測に留まっていた。2026-09-05の改訂で本来のKPI（サイト送客）測定と運用ルール遵守チェックを追加したが、ユーザーから「まだあらゆる観点を網羅できていない」という指摘を受け、2026-09-06に再改訂した。

`/growth-report`・`/growth-pdca`がSearch Console/GA4（検索流入・ブログ側）を扱うのに対し、このスキルは**Xというプラットフォーム自体のパフォーマンスと、Xが本来のKPIであるサイト送客にどれだけ貢献しているか**を扱う。X APIは契約していないため、Chrome in Claudeで実際の画面を開いて数値を読み取る方式と、GA4 Data API（契約済み、`i18n-demand-report.js`と共通）を組み合わせる。

**役割分担（重複実装を避けるため必読）**:
- Xプラットフォーム側の仕組み・アルゴリズム自体の深掘り調査は本スキルの範囲外にはしていない（`/channel-algorithm-research`は現状`youtube|tiktok|note`のみ対応でXは未対応のため、`x-algorithm-and-growth-notes.md`の維持は引き続き本スキルのステップ4.5が担う）
- 他チャネル（TikTok/note/SEO）との**資源配分の判断**は`/growth-monthly-summary`（月次）の役割。本スキルは「Xが十分な投資対効果を出せているか」の単体診断に留め、配分の意思決定はそちらに委ねる（ステップ5.5参照）
- 提案した施策の「戦略メモ」DB登録後の**採用・却下の意思決定**はsns-hub管理画面「戦略メモ」タブが担う（週次デフォルト採用方式、ステップ7参照）。本スキルはinsightを登録するところまでが責務

**本スキルが答えるべき問い（実行前に自問する）**:
1. Xは`x-operations-playbook.md`の絶対厳守事項・運用ルール通りに運用できているか（Plan通りにDoできているか）
2. Xは本来のKPI（ブログ・サイトへの送客、ブランド想起）にどれだけ貢献しているか（Xのインプレッションが増えても、サイトに人が来ていなければ意味が薄い）
3. `x-algorithm-and-growth-notes.md`の仮説（火〜木9-11時、視聴維持率50%目標等）は自社データで裏付けられつつあるか
4. 前回提案した施策は実行され、効果が出たか。過去に同じ施策を試して失敗していないか
5. 直近の数値の動きは「単発のブレ」か「継続的な傾向」か（2点比較では判断できない）
6. 投じている時間・工数に見合うリターンが出ているか
7. フォロワーは増えているとして、それは「量」だけでなく「質」も伴っているか

## 実行手順

### 0. 前回提案した施策の実施・効果検証（必須、最初に行う）

PDCAの「C→A」を閉じるための最重要ステップ。**新しいデータを集める前に**、直近の`data/analysis/x-growth/report-*.json`（またはmemory）に残っている「前回の提案」を確認し、以下を明示する。

- 前回提案した施策（投稿時間帯変更、フォーマット変更等）は実際に実行されたか
- 実行された場合、その後の投稿実績に変化が見えるか（今回集めるデータと突き合わせる）
- 実行されていない場合、なぜか（判断が保留された/優先度が下がった等）を記録する
- 前回「小施策」として`sns_strategy_insights`に登録したinsightが、その後`active`（週次デフォルト採用）になったか`retired`（却下）になったかを確認できる場合は明記する（sns-hub管理画面「戦略メモ」タブの履歴ビューで確認可能。「採用後どれだけ実際の下書き生成に参照されたか」も表示される設計のため、見れる場合はそれも報告に含める）

過去レポートが無い初回実行時はこのステップをスキップし、その旨を明記する。

### 0.3 失敗パターンの学習ループ（必須、2026-09-06新設）

同じ施策を「新しい提案」として繰り返し出してしまうリスクを防ぐ。`docs/operation/sns-marketing-strategy.md`（意思決定ログ）を確認し、以下を行う。

- 直近で提案しようとしている施策の候補（ステップ6で固まる前の仮説段階でよい）が、このファイルに「試したが撤回/失敗した」と記録されている施策と重複していないか照合する
- 重複している場合、**前回と同じ理由で失敗する可能性が高いか、状況が変わって再挑戦する価値があるかを明示的に判断してから**提案する（無条件に再提案しない、無条件に永久却下もしない）
- ファイル全体を毎回読むのは重いため、目次的に「◯月◯日: ◯◯を試して◯◯という理由で撤回」という一文が拾える箇所を優先的に確認する（例: マスコット9本のスケジュール圧縮、時制表現バグ、福岡5R→若松2R差し替え等の既存の教訓セクション）

### 0.5 運用ルール遵守チェック（必須）

`x-operations-playbook.md`にどれだけ精緻なルールを定めても、実際に守れているかを検証しなければPDCAの「Plan通りにDoできたか」が確認できない。以下を実行する。

```bash
node scripts/analysis/x-operations-compliance-report.js --days=30
```

このスクリプトは`data/analysis/x-posts/history.json`から機械的に以下を検出する:
- **1日4本の投稿上限**（動画＋ブログ告知＋引用リツイート合計、playbook「X投稿頻度・型選定ロジック」）の超過日
- **同一記事の重複告知**（2026-08-31/09-01に実際に発生した問題の再発検知。マスコットA/B/Cテストで同一素材を異なるキャラで使うケースは意図的なため誤検知しない設計）
- **型の3連続**（直近投稿で同じ型が3回続いていないか）
- 型別の平均インプレッション（`metrics`が記録されている投稿のみ、母数警告は下記ステップ2参照）

上限超過・重複告知が検出された場合、**なぜ起きたか**（誰も明示的に決めずなし崩し的に増加した、記録漏れ等）を推測せず、`data/analysis/x-posts/history.json`のnotesフィールドや直近のセッション記録から実際の経緯を確認してから報告する。

**データ品質の注記が出た場合**（`postedAtTime`未記録等）: 次回以降の投稿記録に時刻を追記する運用改善を、今回の「次の施策」に含める。

Chrome in Claudeで`https://x.com/kyouteiboatai`を開き、直近の投稿（目安5〜10件）を確認する。

**2026-09仕様変更への対応**: 個別投稿の詳細アナリティクス画面（視聴完了率・プロフィールクリック数等）は「Unlock advanced analytics with X Premium」という課金誘導表示に変わり、無料では見れなくなったことを2026-09-05に確認した（X Premium非契約が前提、`x-operations-playbook.md`「判断基準の再検討タイミング」参照）。この制約下では以下で代替する:

- **プロフィール画面の「直近7日間インプレッション」集計値**（無料で見える）を主指標にする
- フィード上に表示される投稿ごとのビュー数・いいね数・リポスト数・返信数（無料で見える）を記録する
- 詳細アナリティクスが引き続き見れる場合（Premium契約後、または仕様が再変更された場合）は、視聴完了率・離脱ポイント・トラフィックソースも記録する。**毎回まず1件試しにクリックして、詳細画面が見えるかどうかを確認してから記録方針を決める**（仕様は頻繁に変わるため、決め打ちしない）

記録する項目:
- 投稿日時・内容の概要（動画/テキストのみ/ブログ告知/引用リツイート等の種別、A/Bテストがあればどのバリエーションか）
- ビュー数・いいね数・リポスト数・返信数
- （見れる場合のみ）詳細アナリティクス各項目
- フォロワー数・フォロー数・投稿総数の現在値（プロフィール画面）

**フォロワーの質の簡易チェック（2026-09-06新設）**: フォロワー数の増減だけでは「量」しか見えない。フォロワー一覧を数十件サンプリングし、以下を確認する。

- bot・エンゲージメントpod的なアカウント（フォロー数だけ極端に多い、投稿が機械的、アイコン未設定）の混入率を目視で概算する
- ボートレース・競艇関連のbio/投稿を持つアカウントがどの程度の割合か（無関係な業種アカウントばかりが増えている場合、量の増加が質を伴っていない兆候）
- 判断基準: 母数が少ない段階（フォロワー100人未満目安）でこの比率を厳密な数値として出すのは時期尚早。「明らかにbotと分かるものが◯件見つかった」程度の定性的な記述に留める

結果を`data/analysis/x-growth/report-{日付}.json`に保存する（構造: `{generatedAt, followerCount, followingCount, totalPosts, followerQualityNote, previousActionsReview: {...}, postsSampled: [...], summary: {...}, nextActions: {...}}`）。専用スクリプトは無い（X APIが無いため）。Writeツールで直接書き込む。

**フィールド名の注意（2026-09-06追記）**: 過去レポートで`totalPosts`が`totalPostsCounter`という別名で保存されていた時期があり、後述のトレンド判定スクリプトでN/A表示になる不具合の原因になった。**必ず`totalPosts`のキー名で統一する**。

### 1.5 サイト送客への貢献度を測る（必須・最重要）

`x-operations-playbook.md`が明記する本来のKPI（「Xがどれだけ伸びたかよりも、ブログ・サイトへの送客・ブランド想起にどれだけ寄与したか」）を測る。

```bash
node scripts/analysis/x-referral-report.js --days=30
```

このスクリプトはGA4 Data APIから以下を取得する:
- **Organic Social全体**のセッション数（Xに絞る前の母数、他のSNS経由との比較用）
- **X経由（`sessionSource`が`t.co`/`x.com`/`twitter.com`と完全一致）**のセッション数・新規ユーザー数・コンバージョン数
- X経由の**着地ページ内訳**（どの記事・機能が実際にXから読まれているか）
- **日別推移**（Xの投稿本数・型の変化と時系列で突き合わせて解釈する）

**解釈の注意点**:
- X経由セッションが0またはごく少数の場合、「Xが機能していない」と即断せず、以下を切り分ける: (1)そもそもリンク付き投稿が少ない、(2)X公式アプリ内ブラウザ経由だとリファラーが欠落しGA4で計測されないケースがある、(3)GA4のセッション定義（同一ユーザー30分ルール）による過小計上
- 着地ページに`/admin/*`等の管理画面が含まれる場合、それは開発者自身のアクセスの可能性が高くノイズとして注記する（一般ユーザーの流入と混同しない）
- Organic Social全体とX経由がほぼ同数であれば、「Xが実質的に唯一の機能しているSNS流入チャネル」であることを意味する。他のSNS（TikTok等）が別のKPI（動画プラットフォーム内での認知）を主目的にしているなら問題ないが、混同しない

**このステップの結果が思わしくない場合**（X経由セッションが少ない・伸びていない）、ステップ6の統合分析で最優先の論点にする。フォロワー・インプレッションが伸びていても送客がゼロなら、Xの投資対効果そのものを問い直す必要がある。

### 1.7 複数時点のトレンド判定（必須、2026-09-06新設）

ステップ3（過去レポートとの比較）は前回との2点比較に留まっており、「前回だけたまたま悪かった/良かった」のか「継続して悪化/改善している」のかを区別できない弱点があった。以下を実行する。

```bash
node scripts/analysis/x-trend-summary.js
```

`data/analysis/x-growth`・`data/analysis/x-referral`の直近5レポートを並べ、フォロワー数・投稿総数・X経由セッション数それぞれについて「改善/悪化が何回連続しているか」を機械判定する。3時点未満の指標は「データ不足」と出るため、断定的な傾向判断をしない（母数警告と同じ考え方）。

**解釈**: 2〜3回以上同方向の連続が出ている指標は、単発のブレではなく構造的な傾向として扱い、ステップ6の施策検討で優先度を上げる。逆に前回比較（ステップ3）で大きく動いていても、このトレンド判定で「横ばい」「データ不足」と出た場合は、過剰反応した施策変更をしない。

### 2. 判断基準（しきい値）— 分析を「なんとなく」で終わらせないために

数値を見て終わりにせず、以下を基準に「注目に値する差か、ただのばらつきか」を判定する。

- **母数が少ない段階（投稿10件未満）の警告**: この段階での「動画とテキストどちらが強いか」等の比較は、統計的に意味のある結論を出すには早すぎる。傾向として言及してよいが、断定はしない
- **外部基準（2026-08-22調査より）**: 同ジャンルの類似アカウント（ボートレース日和、フォロワー2.9万人）の通常投稿は表示回数3,000〜4,300件、価値提供型の突出投稿は49万件。直接競合@KAIPREDICTOR（1ヶ月・71フォロワー）は880ビュー水準。フォロワー規模が近づいてきたらこの水準と比較する
- **内部基準（自アカウントの推移が十分に貯まってから）**: 直近5〜10投稿の中央値をベースラインとし、そこから明確に外れた投稿（2倍以上／半分以下）を「なぜそうなったか」の分析対象にする
- **アルゴリズム仮説との照合**（`x-algorithm-and-growth-notes.md`参照）: 個別の投稿の伸び悩みを「なんとなく内容が悪かった」で済ませず、以下の一次情報ベースの仮説と照合する
  - 視聴維持率は50%地点（動画尺の半分）まで届いているか。届いていなければ「冒頭2〜3秒に核心を前倒しする」設計の問題として扱う
  - その投稿の前後2〜3時間以内に自分の別の投稿が無いか（連投による自己競合）
  - 通報・大量ミュートを招くような表現が無かったか（ネガティブシグナルはアカウント全体の評判を毀損するため、単発の低調より優先度が高いリスクとして扱う）
- **コスト対効果の視点（2026-09-06新設）**: 施策の良し悪しをリターンの絶対量だけで判断せず、投じたコストと対比する。目安（厳密な時間計測は不要、体感でよい）:
  - リプライ・引用リツイート戦略: 1件あたりの下書き作成〜承認のやり取りにかかる時間 vs 得られたインプレッション・フォロワー転換
  - 動画制作: 1本あたりの制作時間（Remotion設定・レンダリング・チェック） vs 視聴数・エンゲージメント
  - 「時間をかけた割に伸びていない型」と「軽い工数で一定の反応がある型」を区別し、後者へのリソース再配分を施策候補に含める

### 4. 競合アカウントの定点観測（頻度: 月1回目安、毎回はしない）

競合アカウントの投稿傾向は短期間で大きくは変わらないため、**毎回リサーチし直さない**。前回調査から1ヶ月以上経っている場合のみ、以下を実施する。

- 前回調査対象アカウント（`sns_marketing_phased_strategy_2026_08_22`memory参照）のプロフィールを再訪問し、フォロワー数・投稿頻度・フォーマットに変化が無いか確認する
- **直近1ヶ月でバズった投稿（自分の中央値の5倍以上）があれば、個別に開いて「なぜ伸びたか」を`x-algorithm-and-growth-notes.md`の枠組み（推し活/体験談/問いかけの有無、リプライ数の多さ、投稿時間帯）で分析する**
- 新規に伸びているアカウントが無いかWebSearchで軽く確認する
- X公式のベストプラクティス・アルゴリズムに関する新しい発表が無いか確認する（`business.x.com/en/basics/organic-best-practices`、X公式ブログ、`github.com/xai-org/x-algorithm`のコミット履歴等）

前回調査から1ヶ月未満の場合は「前回調査済み、変化なしと仮定」と明記してこのステップを省略してよい。

### 4.5 アルゴリズム知見の鮮度チェック（頻度: 実行のたびに軽く確認）

`docs/reference/x-algorithm-and-growth-notes.md`はXアルゴリズムが2026年1月に全面刷新されて以降、複数回の追加調査で更新されてきた一次情報ベースの知識ベースである。`/channel-algorithm-research`は現状`youtube|tiktok|note`のみ対応でXは対象外のため、Xのアルゴリズム知見の維持は引き続き本ステップが担う。

- ファイルの最終更新（追記日）から1ヶ月以上経っていれば、`github.com/xai-org/x-algorithm`の直近コミット・関連ニュースをWebSearchで軽く確認し、大きな変更（重み表の変化、新機能等）が無いか確認する
- 変更を発見した場合、`x-algorithm-and-growth-notes.md`に確度（一次情報/業界分析/未確証）を明記した追記を行い、`x-operations-playbook.md`の該当ルールに影響が無いか確認する
- 1ヶ月未満なら「鮮度確認済み、変化なしと仮定」と明記して省略してよい

### 5. 下書き・投稿キューの消化状況

```bash
grep -c "^- \[ \] 投稿済み" note-articles/tweet-drafts.md
```

加えて、動画投稿用のキャプション下書きファイル（`sns-video-studio/captions/x-*-video-captions.md`等、プロジェクトによってファイル名は変わる）があれば同様に未消化件数を確認する。未消化が多い場合は他の施策より優先度を上げて報告する（`/growth-pdca`と同じ方針）。

**リプライ・引用リツイート戦略の実行率**: `sns-video-studio/x-reply-sent-log.md`があれば、直近7〜30日の送信件数を確認し、`x-operations-playbook.md`の目標（1日10〜20件）に対する実行率を算出する。この施策は4週間ごとに継続/縮小/拡大を判断する設計のため、前回判定から4週間以上経過している場合は必ずこの判断を行い、結果を`docs/operation/sns-marketing-strategy.md`の意思決定ログに追記する。

- 実行率が低い場合、原因を「対象探しのコストが高い」「承認フローが重い」等、具体的なボトルネックまで特定する（「頑張ります」で終わらせない）
- 相互フォロー数の推移も可能なら記録する（`BidirectionalFollowReplyWeightBoost`+15.0の活用度合いの代理指標、`x-algorithm-and-growth-notes.md`参照）

### 5.5 他チャネルとの資源配分（軽量診断のみ、2026-09-06新設）

本スキルの範囲は「Xが単体で十分な投資対効果を出せているか」の診断までとし、TikTok/note/SEOとの資源配分の最終判断は`/growth-monthly-summary`（月次）に委ねる。以下の軽量チェックのみ行う。

- `data/analysis/growth-monthly-summary/summary-*.json`の最新ファイルの生成月を確認し、当月分が無ければ「月次サマリー未実行、資源配分の判断は`/growth-monthly-summary`で行う」と明記する
- ステップ1.5（サイト送客）の結果が悪く、かつステップ1.7のトレンド判定で「悪化が継続」と出ている場合は、「Xへの投資配分を見直すべきか」を大施策候補として挙げ、最終判断は月次サマリーに委ねる旨を明記する

### 6. 統合分析・次の施策（アクションプラン形式、2026-09-06改訂）

ステップ0〜5.5の結果を統合し、次の投稿・運用施策を**実行可能なアクションプラン**として提示する。単に施策を列挙するだけでなく、以下の表形式で出力する。

| 優先度 | 施策 | 担当 | 期限目安 | 完了判定基準（次回ステップ0で検証する内容） |
|---|---|---|---|---|
| 1 | （例）投稿時間を21時→20時に変更 | Claude（即実行） | 次回投稿から | 次回レポートで20時台投稿の平均ビュー数を比較 |

担当は「Claude（即実行）」「ユーザー承認待ち」「ユーザー判断が必要」の3種から選ぶ。**次回このスキルを実行する際にステップ0で検証できるよう、完了判定基準は後から実行有無・効果を判定できる粒度で書く**。

**優先順位付けの原則**: 以下の順に論点を扱う。上位の問題を放置したまま下位の施策（投稿時間帯の微調整等）を提案しない。

1. **運用ルール違反**（ステップ0.5）: 1日4本超過・重複告知等、決めたことが守れていない状態はまず是正する
2. **サイト送客がゼロ・低迷**（ステップ1.5）: Xの本来のKPIが機能していないなら、フォロワー・インプレッションの改善より優先して原因を特定する
3. **継続的な悪化傾向**（ステップ1.7）: 単発のブレではなく複数回連続の悪化が出ている指標は早めに手を打つ
4. **仮説との乖離**（ステップ2・4.5）: 視聴維持率50%未達・投稿頻度過多等、確立した知見に反する運用が続いているなら是正する
5. **コスト対効果の悪い施策の縮小**（ステップ2）: 工数の割にリターンが薄い型・活動があれば縮小候補にする
6. **通常のPDCA施策**（投稿時間帯・型の比重・キャプション調整等）

- 小施策（即実行）の例: 投稿時間帯の見直し、キャプションのハッシュタグ調整、反応の良かった投稿フォーマットの横展開、history.jsonへの`postedAtTime`追記開始、重複告知防止のための投稿前チェック追加
- 大施策（提案のみ）の例: 新しい動画フォーマットの開発、TikTok解禁の判断、マスコットキャラの勝者確定・統一、X Premium課金の再検討（判断基準は`x-operations-playbook.md`参照）、Xへの資源配分見直し（`/growth-monthly-summary`に委ねる）

**提案前チェック（ステップ0.3の失敗パターンと必ず突き合わせる）**: ここで挙げる施策が`sns-marketing-strategy.md`に「過去に試して撤回」と記録されているものと重複していないか、最終確認してから提示する。

### 7. 提案した小施策をinsightとしてDBに登録する（Phase 2）

SNSマーケティングハブPhase 2（改善案の自律立案ループ、`docs/design/sns-hub-phase2-pdca-loop/`）の入力として、ステップ6で挙げた「小施策（即実行）」を`sns_strategy_insights`テーブルに`status='proposed'`で構造化して登録する。既存の`data/analysis/x-growth/report-{日付}.json`への保存は維持したまま、追加で行う（ADR 0027）。

**登録後の意思決定フロー（2026-09-06追記、正確な仕様を反映）**: 登録したinsightは即座に採用されるわけではなく、sns-hub管理画面「戦略メモ」タブに`status=proposed`（要判断）として表示される。**週次サイクル内にユーザーが却下操作をしなければ、次のサイクル開始時に自動的に`status=active`へ昇格する**（デフォルト採用・拒否権レビュー方式）。却下された場合は`status=retired`になり、理由が`decision_note`に記録される。本スキルの責務は登録までであり、採用・却下の判断はsns-hub側に委ねる。

- 各「小施策」1件につき1レコードを`createInsight`（`scripts/lib/snsStrategyInsights.js`）で登録する
  - `platform`: `'x'`
  - `language`: `'ja'`（本スキルが観測しているのは日本語アカウントのみのため。英語アカウント開設後は別途判断する）
  - `format`: 施策が特定の型に限定される場合はその型名、全体に関わる施策なら`null`
  - `insightText`: 施策の内容（例:「投稿時間を21時→20時に変更する」、次回生成に注入してそのまま参照できる粒度で書く）
  - `evidence`: 根拠となった数値・観測（例:「直近10投稿の中央値と比較し20時台の投稿がインプレッション2倍」）
  - `source`: 競合観測由来なら`'external-research'`、自アカウント実績由来なら`'own-metrics'`
  - `researchMethod`: `'x-growth-report-skill'`
- 「大施策（提案のみ）」はinsight化しない（人間の戦略判断を要するため、次回生成へ自動反映すべきではない）
- 登録は専用スクリプトが無いため`node -e`等の一時的なコードで行ってよい
- 過去に蓄積済みの`data/analysis/x-growth/report-*.json`にまだinsight化されていない小施策が残っていれば、このステップで遡って登録してもよい
- `scripts/lib/snsStrategyInsights.js`が現在のブランチに存在しない場合（マージ漏れ等）は、このステップを省略し「Phase 2コードが見つからないため未実施」と明記する。ブランチが古いまま無理に実装し直さない

## 解釈の注意点

- Xのインプレッション数は投稿後24〜48時間で大きく伸びが止まる傾向があるため、投稿直後（数時間以内）の数値だけで判断しない
- フォロワー数が少ない段階（1万人未満目安）は母数が小さく、数件のバズ投稿で平均値が大きく歪むため、中央値や個別投稿の傾向も併記する
- 「インプレッションが低い」原因が投稿内容なのか投稿頻度なのかタイミングなのかを切り分ける（`docs/operation/sns-posting-operations.md`の運用フローと照らし合わせる）
- Xの投稿詳細アナリティクス画面が何らかの理由で開けない場合（権限・課金・UI変更等）は、代替手段（ステップ1参照）で計測した旨を明記し、精度が落ちることを報告に含める
- `x-algorithm-and-growth-notes.md`にある数値（「◯倍」等）の多くはSEO目的のマーケティングブログが情報源であり、一次情報（`param.rs`実測）と乖離することがある（例: 「リプライはいいねの27倍」という通説は実際は10倍程度）。報告時は確度（一次情報/業界分析/未確証）を意識し、断定的な数値を鵜呑みにしない
- 取得したデータは自己判断で重要度を絞り込まず全て報告に含める（`.claude/CLAUDE.md`「調査・分析結果の報告原則」）。「特筆すべき動きが無い」というデータも省略しない
