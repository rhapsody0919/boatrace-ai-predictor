---
description: SDD Step 1 — docs/design/{機能slug}/spec.md を対話形式で作成する
argument-hint: "<機能slug（kebab-case）> [Linearチケット番号 例: BOA-140]"
---

引数 `$ARGUMENTS` はスペース区切りで「機能slug（kebab-case、必須）」「Linearチケット番号（任意）」を受け取る（例: `venue-comparison-widget BOA-140`）。以降このコマンド内で `{slug}` は1語目、`{ticket}` は2語目（あれば）を指す。

`docs/design/{slug}/spec.md` を対話形式で作成する。次の手順で進めること。

このコマンドは**大きい・曖昧さが残る新機能**向け。小さく仕様が明確な Linear チケットは `/implement` で直接実装した方が速い。迷ったら「仕様を書き下さないと設計判断を誤りそうか」で判断する。

手順
1. `{ticket}` が渡されていれば該当 Linear チケット（`node scripts/linear-cli.js get {ticket}` 等）の説明・受入基準を読む。関連する `docs/proposal/` や既存分析結果（`data/analysis/`）があれば読む。
2. 未決定点を洗い出す。自分で読んで列挙せず、`spec-ambiguity-detector` サブエージェントに依頼文（チケット本文・関連資料のパス）と下記5カテゴリを渡して列挙させる。依頼を読んだ本人が洗い出すと自分の解釈に固着するため（`.claude/agents/spec-ambiguity-detector.md` 参照）。コードやドキュメントで答えが出るものは質問にしない
3. 洗い出した点を振り分けて質問する
   - **既定値で成果物が変わらない、または既定値で問題ない点**: 質問せず既定値を採用し、spec.md に「既定値で決定」と根拠を書く
   - **確認が要る点**: 依存関係の上流（種別 → スコープ → 機能要件 → 非機能要件）から順に聞く。互いに依存しない質問は AskUserQuestion で最大4問まとめて聞き、上流の回答で選択肢が変わる質問だけ回答を待ってから聞く
   - 各質問に**推奨回答とその理由**を付ける（推奨を第1選択肢に置く）。判断材料の無い「どうしますか」だけの質問はしない
   - 質問の基準は「解釈が違うと成果物が変わるか」。変わらない点は聞かない。全観点を網羅するために質問を増やさない
4. 回答を反映する。答えられない項目は推測で埋めず「未確定（いつ・誰が決めるか）」として記録する。
5. 全カテゴリが埋まる、または残りが未確定として確定したら spec.md を生成し、未確定事項の一覧を再掲する。

洗い出しで必ずカバーするカテゴリ（全て質問するという意味ではない。既定値で決まるものは手順3で質問を省く）

A. **種別** — UI機能（画面・コンポーネントが関わる） / データ・分析機能（バッチスクリプト・分析ロジックのみ、画面変更なし）。UI機能なら次の `/step1-screens` に進む。データ・分析機能なら screens はスキップし `/step2` へ進んでよい
B. **機能要件** — 各要件に優先度と、テスト可能な受入基準
C. **スコープ** — やること / やらないこと（特に「やらないこと」）
D. **非機能要件** — 該当する場合は数値で（例: モバイル表示崩れなし・320px〜、SEO要件、既存回収率を悪化させない 等）。該当しなければ「なし」と明記
E. **制約・前提** — 既存コンポーネント再利用の可否（`.claude/rules/component-reuse.md` 参照）/ データ源（Supabase テーブル・外部スクレイピング等）/ 法的制約（投票は日本国内在住・20歳以上のみ、AI予測は結果を保証しない旨のディスクレーマー要否）/ 「競艇」使用禁止等の用語ルール

不明点を推測で埋めることは禁止。

spec.md の構成
- 冒頭: 種別（UI機能 / データ・分析機能）、対応する Linear チケット（あれば）
- 機能要件（優先度・受入基準つき）/ スコープ（やる・やらない）
- 非機能要件（数値、または「なし」）/ 制約・前提
- 既定値で決定した事項（項目ごとに採用した既定値と根拠。ユーザーが後から覆せるように残す）
- 未確定事項（項目ごとに「いつ・誰が決めるか」）
