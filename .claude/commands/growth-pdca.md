# 集客状況PDCA（網羅分析→施策立案→実行）

Search Console・GA4・競合（kyoteibiyori）動向・キーワード需要を横断的に分析し、次に打つべき施策を立案する。
`/growth-report`・`/i18n-growth-report`が「定点観測レポート」に留まるのに対し、このスキルは**分析結果から具体的な施策を立案し、小さな施策はその場で実行する**ところまでを担う。

「集客を分析して」「集客状況どう？」等の自然言語依頼でもこのスキルを起動する。

## 実行手順

### 0. ブランド一貫性チェック（リブランド・大型施策の直後のみ、該当する場合は必須）

2026-08-22追加。リブランド（BoatAI→龍神レーダー等）や大型施策の直後は、Search Console/GA4の**数値だけを見ていても検出できない技術的な取りこぼし**が起きやすい。実際に2026-08で、title/meta/構造化データ/sitemap/全ブログ記事は移行済みだったにもかかわらず、SNS共有時のプレビュー画像（`og:image`）だけが半年以上前の旧ブランド表記のまま放置されていた実例がある（Claudeが手順書を離れて自主的に監査したことで発覚。定型手順に無いと再現性が無い）。

該当する変更（リブランド、ドメイン変更、主要導線の大幅刷新）の直後に本スキルを実行する場合は、以下を確認してから1に進む。該当しない通常の定点観測では省略してよい。

- `<title>`・`meta description`・OGP（`og:title`/`og:image`/`twitter:image`）・構造化データ（JSON-LD）が最新の表記になっているか（`grep`で旧表記を横断検索）
- OGP画像等のラスター画像に旧表記がテキストとして焼き込まれていないか（コード検索では発見できないため、Readツールで画像を直接目視する）
- SNSアカウントのハンドル名・プロフィールが最新か（変更するかは別途ユーザー判断だが、現状把握はしておく）
- sitemap.xmlが最新か、再送信済みか（`node scripts/submit-sitemap.js`）

### 0-B. 大施策の月次棚卸しレビュー（2026-08-26追加、前回提示から1ヶ月以上経過した候補がある場合のみ）

大施策（被リンク獲得、新機能開発、大規模コンテンツ拡充等）は「提案のみ、実行はユーザー判断」という設計上、提示後の意思決定サイクルが無いまま候補が蓄積し続ける問題があった。実際、被リンク獲得施策（`/blog`・`/about`・`first-mark-prediction-guide`等）は2026-08-20頃から毎回のレポートで同じ「候補」として出てくるだけで、着手・見送りの意思決定が一度もされないまま放置されていた（2026-08-26、8人パネル議論で発覚）。

`data/analysis/growth-pdca-major-initiatives.json`に大施策の提示履歴を記録し、**前回提示（`lastProposedDate`）から1ヶ月以上経過している候補があれば**、このステップで一覧を再提示し、ユーザーに「着手する／見送る／保留継続」の判断を仰ぐ。1ヶ月未満の候補は今回は省略してよい（growth-pdca自体を高頻度で実行するため、毎回催促すると意思決定疲れを招く）。

- 判断が出たら`status`を更新する（`in_progress`＝着手、`rejected`＝見送り、`deferred`＝保留継続）。着手が決まった大施策で新機能を伴う場合はLinearチケット化する（VUPループと同じ運用）
- ステップ6で新たに大施策候補を提示する際は、このファイルに`title`・`firstProposedDate`・`lastProposedDate`・`status: "proposed"`・関連ページ一覧を追記・更新する
- 過去レポートが無い（ファイル自体が無い）初回実行時はこのステップをスキップし、新規に検出した大施策候補をファイルに書き込むところから始める

### 1. Search Console（先行指標）

```bash
node scripts/analysis/search-console-report.js
```

`data/analysis/search-console/report-{日付}.json`と過去レポートを比較し、日割りトレンド・トップクエリの順位変動・新機能記事/`/winning-technique`の検索状況・会場ガイド（`/venues`配下）の状況を確認する。詳細な解釈手順・注意点は`/growth-report`を参照。

このスクリプトは以下2つの追加分析も出力する（2026-08-20追加、天才マーケッター視点でのスキル改善時に導入）。

- **指名検索（ブランド名クエリ）比率**: 全クリックに占めるブランド名検索の割合と、旧ブランド（BoatAI系）・新ブランド（龍神レーダー系）の内訳・前回比を出力する。指名検索比率が高いサイトほど、リブランドや検索順位の変動が事業インパクトに直結するため、この比率自体の推移を毎回必ず確認する。2026-08のBoatAI→龍神レーダー移行期は特に、新ブランド検索の立ち上がりと旧ブランド検索の減衰ペースを注視する（新ブランドの検索ボリュームがゼロから積み上がるまでの過渡期は指名検索経由の流入が一時的に落ち込むリスクがある）
- **CTR-vs-掲載順位ギャップ**: 順位から期待されるCTR目安（業界一般値の概算）と実際のCTRを比較し、「タイトル/メタディスクリプション改善候補」（順位相応なのにCTRが低い＝スニペットの問題）と「権威・被リンク不足の可能性」（CTRは高いのに順位が低い＝コンテンツは検索意図に合っているが権威不足）を自動で分類する。前者は`title`/`meta description`の即時改善（小施策）に直結し、後者は被リンク獲得や関連コンテンツ拡充（大施策）の判断材料になる。**この2つの区別を必ず行動の起点にする**（同じ「順位が低い」でも処方箋が全く違うため）
- **ページ×クエリのクロス集計**（2026-08-22追加）: 上記「タイトル/メタディスクリプション改善候補」に挙がった上位5ページについて、実際にどのクエリで表示されているかを紐付けて出力する。これが無いと「たぶんこの検索意図だろう」という当てずっぽうでtitleを書き換えることになる（実際に過去そうしていたことがあり、後から確認すると意図とズレたリライトをしていたケースがあった）。**title/meta description改善（小施策）を実行する前に必ずこの内訳を確認する**
- **候補として提示する前に変更履歴を確認する**（2026-08-24追加）: 「タイトル/メタ改善候補」に挙がったページは、提示・着手する前に必ず`git log -- src/data/blogPosts.js`（対象ファイル）でtitle/description関連の直近コミットを確認する。CTRが低いままでも「未対応」なのか「対応済みで反映待ち」なのかを区別せず「新規候補」として提示し、ユーザー承認まで得てから発覚した実績がある（`exhibition-run-guide`が2026-08-22に一度改善済みだったのに2026-08-24のレポートで再度「新規候補」として提示してしまった）。Search Consoleの反映には数日〜1〜2週間かかることがあるため、直近（目安1〜2週間以内）にtitle/description変更のコミットがあるページは候補から外すか、「◯月◯日対応済み・反映待ちのため様子見」と明記する

### 2. GA4（多言語利用状況含む）

```bash
node scripts/analysis/i18n-demand-report.js --days=30
```

言語別PV・チャネル別流入・国別内訳を確認する。詳細な解釈手順は`/i18n-growth-report`を参照。

**日本語ページ自体の流入チャネル内訳**も出力される（2026-08-22追加）。Search Consoleはオーガニック検索しか見えないため、「オーガニック検索の表示回数は落ちているが全体PVは伸びている」ような乖離が起きた際に、実際にどのチャネル（Direct/Organic Social/Referral等）が変化しているのかをここで検証する。検証せずに「他チャネルが埋め合わせているはず」と推測だけで報告しない。

前回チェック日以降に追加された新規項目のみを抽出する（前回チェック日はmemory `vup_feature_analysis_skill.md`を参照）。boatAI未実装かつ既存データで実現可能な候補が無いか確認する。`docs/proposal/competitor-kyoteibiyori/`の実装優先度メモも参考にする。

### 4. 競合のシェア・権威動向（share of search・被リンク簡易チェック）【必須、省略時は報告に明記】

2026-08-20追加。自サイトの指標だけを見ていると「市場全体が縮んでいるのか、自サイトだけがシェアを落としているのか」を区別できない。特に自サイトの指標が悪化している回（今回のようなオーガニック検索減少局面）ほど、このステップを飛ばした状態で「リブランドが原因」「コンテンツが弱い」等の自己診断をしてしまうリスクが高い。

**時間の都合で省略する場合でも、このステップだけは実行するか、実行しない場合は最終報告に「ステップ4は未実施」と明記する**（2026-08-22追加。過去に時間の都合で暗黙にスキップし、報告書に痕跡が残らなかった実績があるため）。市場要因を切り分けないまま自サイトの問題だと断定するのが最悪の結果になる。

**Share of searchスナップショット（WebSearch）**: コアクエリ（Search Consoleのクリック上位から、ブランド名を含まない一般語を3〜5個選ぶ。例:「ボートレース予想サイト」「ボートレースAI予想」「競艇AI予想」）についてWebSearchを実行し、上位5件のドメインを記録する。結果は`data/analysis/serp-snapshots/snapshot-{日付}.json`に`{query, date, topDomains: [...]}`の配列として保存し（Writeツールで直接書き込む、専用スクリプトは無い）、直近の過去スナップショットと比較して以下を確認する。

- 自サイト（boat-ai.jp）の順位・有無の変化
- 新規参入ドメイン・順位上昇ドメイン（アフィリエイト系比較サイトが伸びているか等）
- 上位ドメインの顔ぶりが固定化している（既存プレイヤーが強すぎる）か、流動的（新規参入の余地がある）か

過去スナップショットが無い場合は「今回分を保存、次回から比較可能」と明示する（`reportComparison.js`と同じ前回比較パターンに揃える）。

**対象クエリのローテーション（2026-08-26追加）**: 2026-08-20の導入以降、「ボートレース予想サイト」「ボートレースAI予想」「競艇AI予想 無料」の3クエリで固定運用してきたが、同じクエリだけを見続けると新たに伸びている検索需要・新規参入者を見落とすリスクがある（8人パネル議論で指摘）。`data/analysis/serp-snapshots/`の最新スナップショットの`date`を確認し、**前回のクエリ見直しから3ヶ月以上経過していれば**、Search Consoleのクリック上位クエリを再確認し、対象クエリの入れ替え・追加を検討する（既存クエリを完全に捨てるのではなく、傾向が安定していれば維持し、新たに伸びているクエリを1〜2個追加する形でよい）。3ヶ月未満の場合は既存クエリのまま実行し、その旨明記する。

**被リンク簡易チェック（重要な制約あり、実測困難）**: Ahrefs/Moz/Semrush等の被リンク専門ツールは契約していない（`/codex-review`見送りと同じ理由でコスト対効果が見合わないと判断、`docs/operation/sdd-and-codex-review.md`参照）。当初「WebSearchの`site:{ドメイン}`検索でインデックス済みページ数を比較する」簡易プロキシを検討したが、2026-08-20の実地検証で`site:`演算子がWebSearchツール経由では期待通りに機能しない（無関係な結果が混入し、対象ドメインに絞り込めない）ことを確認した。そのため、この方法での定量比較は**現状できない**。

上位ドメインが「個人ブログ的な小規模サイトか、複数記事・カテゴリ構造を持つ本格的なメディア/アフィリエイトサイトか」を、通常のWebSearch結果のタイトル・スニペットの傾向（記事数の多さを示唆する表現、更新頻度、サイト構造）から**定性的に**推測する程度に留める。精密な被リンク数・ドメインオーソリティが必要になった時点で、有料ツール導入をユーザーに相談する。

### 5. キーワード需要調査（コア + 地域密着）

WebSearch等で以下2軸を調査する。

**コアキーワード軸**: 「ボートレース AI予想」等の既存コアクエリ（Search Consoleのtop queries）周辺の関連キーワード・検索トレンドを調査し、コンテンツで拾えていない需要が無いか確認する。

**地域密着キーワード軸**: 24会場（桐生・戸田・江戸川・平和島・多摩川・浜名湖・蒲郡・常滑・津・三国・びわこ・住之江・尼崎・鳴門・丸亀・児島・宮島・徳山・下関・若松・芦屋・福岡・唐津・大村）それぞれについて、「{会場名} 観光」「{会場名} 周辺」「{会場名} グルメ」等、ボートレース目的に限らない検索需要を調査する。目的は、ボートレース会場周辺に来ている観光客等が検索から会場ガイド（`/venues/{slug}`）に辿り着ける導線を強化すること。既存の会場ガイドコンテンツと突き合わせ、観光情報が薄い・キーワードカバレッジが弱い会場を特定する。全24会場を毎回調査すると重いため、Search Consoleのimpressionsが伸びている会場や、直近未調査の会場から優先的に数会場ずつ回す。

**再開時期の目安（2026-08-26追加）**: 会場ガイド全会場化プロジェクト（memory `venue_guide_expansion_project`、2026-07-27完了）の効果測定チェックポイントが**2026-10-27頃**に設定されている。地域密着キーワード軸はこのチェックポイントに合わせて本格的に再調査するのが効率的なため、それまでは`growth-pdca`実行のたびに毎回省略してよい（優先度低のまま据え置く）。省略する際も「地域密着キーワード軸は2026-10-27の会場ガイド定点確認まで据え置き中」と一言明記し、単に触れずに終わらせない。

### 6. 統合分析・施策立案

**報告前の確認**: ステップ1〜5で取得したデータ（Search Console・GA4の多言語別数値・VUP動向・share of search・キーワード需要）は、自己判断で重要度を絞り込まず全て報告に含める（`.claude/CLAUDE.md`の「調査・分析結果の報告原則」参照）。「動きが無い」データも省略せず明記する。特に多言語（en/zh-TW/ko）のPVデータは、日本語側の変化にフォーカスするあまり報告から漏らした実績がある（2026-08-25）ため要注意。

上記5つに加えて、note/X投稿の消化状況（`grep -c "^- \[ \] 投稿済み" note-articles/tweet-drafts.md`、詳細は`/growth-report`参照）を必ず確認する。技術的なSEO施策をいくら積み上げても、実際に発信されなければ認知は拡大しない。未消化件数が多い場合は、他の施策より優先度を上げて報告する（2026-08-22追加、天才マーケッター・エンジニア・ビジネスマンでの議論より——技術指標は揃っているのに一番効くはずのレバーだけが計測不能だった反省）。

**X自体のパフォーマンス（インプレッション・いいね数・フォロワー推移・競合動向）は本スキルの対象外**（2026-08-23追加）。このスキルはSearch Console/GA4（検索流入・ブログ側）のPDCAに特化しており、Xのプラットフォーム自体の集客PDCAは`/x-growth-report`が担当する。X運用の定点観測が必要な場合はそちらを実行する。

これらを踏まえ、次の施策を立案する。

**施策の優先順位付け（インパクト×工数、2026-08-20追加）**: 複数の施策候補が出た場合、感覚的に列挙するだけで終わらせず、以下の2軸（各3段階）で必ずマッピングしてから提示する。

| 軸 | 高 | 中 | 低 |
|------|----------|----------|----------|
| インパクト | 表示回数上位ページ・複数ページ横断で効く | 単一ページ・中程度のimpressions | 表示回数が少ないページのみ |
| 工数 | 新規設計・複数ファイルにまたがる | 数ファイル・既存パターン踏襲 | 1ファイル程度の軽微な変更 |

優先順位は「インパクト:高×工数:低」→「インパクト:高×工数:中」→「インパクト:中×工数:低」の順に倒す。同格の場合は「タイトル/メタ改善候補」（ステップ1のCTRギャップ分析由来のもの）を優先する。効果検証までのリードタイムが短く、正誤の判定がしやすいため。

**小施策（即実行）の例**:
- 既存ページのtitle/meta description改善（特にステップ1のCTRギャップ分析で「タイトル/メタ改善候補」に挙がったページ）
- 内部リンク追加
- 既存記事への軽微な追記（観光情報の追加等）
- sitemap反映漏れの修正

即実行の場合も`.claude/CLAUDE.md`の開発フロー（ブランチ作成→実装→セルフレビュー→PR作成）は省略しない。「即実行」は着手前のユーザー承認を待たないという意味であり、レビュー・マージ確認プロセスをスキップする意味ではない。マージ確認はサマリー+確認観点を添えて都度提示する（`feedback_merge_confirmation_summary`参照）。

**大施策（提案のみ）の例**:
- 新機能開発 → `/analyze-vup-feature`→`/create-vup-ticket`のVUPループに乗せる
- 新規ブログ記事の執筆
- 会場ガイドへの大規模な観光コンテンツ拡充
- 被リンク獲得施策（ステップ1のCTRギャップ分析で「権威・被リンク不足の可能性」に挙がったページ、ステップ4の簡易チェックで規模差が裏付けられたページ向け。具体的な獲得手段の検討はユーザー判断を仰ぐ）

大施策は具体案を会話で提示し、実行はユーザー判断を仰ぐ。新機能はLinearチケット化（VUPループと同じ運用）。

### 7. 提案した小施策をinsightとしてDBに登録する（2026-09-02追加）

ブログ/noteチャネル別パイプラインRoutine（`docs/operation/sns-pipeline-blog.md`・`sns-pipeline-note.md`、`docs/design/sns-topic-gate/`）が次回のネタ選定・執筆時に参照できるよう、ステップ6で挙げた「小施策（即実行）」を`sns_strategy_insights`テーブルに構造化して登録する。`/x-growth-report`ステップ7・ADR 0027と同じパターン（`sns_drafts`のplatform列と同様、`sns_strategy_insights`のplatform列にも`'blog'`/`'note'`を含め既存の値との重複・enum制約は無い）。

- 各「小施策」1件につき1レコードを`createInsight`（`scripts/lib/snsStrategyInsights.js`）で登録する
  - `platform`: `'blog'`（note向けにも当てはまる施策は`'note'`でも追加登録、両方に有効な場合は`null`）
  - `language`: `'ja'`
  - `format`: 特定の記事カテゴリ・タブに限定される施策はその名前、全体に関わる施策なら`null`
  - `insightText`: 施策の内容（例:「会場ガイド記事には観光情報セクションを厚めに書く」、次回生成に注入してそのまま参照できる粒度で書く）
  - `evidence`: 根拠となった数値・観測（例:「◯◯記事のCTRが掲載順位相応の期待値の1.8倍」）
  - `source`: `'own-metrics'`（Search Console/GA4実績由来）または`'external-research'`（競合・キーワード需要調査由来）
  - `researchMethod`: `'growth-pdca-skill'`
- 「大施策（提案のみ）」はinsight化しない（人間の戦略判断を要するため）
- 登録は専用スクリプトが無いため`node -e`等の一時的なコードで行ってよい

## 判断基準（小 / 大）
- 小 = 1ファイル程度の軽微な変更、既存パターンの踏襲、リスクが低いもの
- 大 = 新規ページ・新規機能・新規コンテンツ作成、設計判断を伴うもの
- 迷ったら大側に倒して提案に留める

## 解釈の注意点（`/growth-report`・`/i18n-growth-report`から継承）
- 30日ローリングウィンドウのため、直近の施策効果と過去の減衰が混ざる。施策公開日と照らして解釈する
- Search Consoleデータは2〜3日の反映ラグがある
- 悪化トレンドでも新施策公開から2〜4週間はSEO効果の判定期間として扱い、早計な戦略変更をしない
- 報告は良い数字も悪い数字も正直に。判断が必要な悪化（コアクエリの順位2位以上の下落等）は明示する

## 実行頻度の目安（2026-08-26追加）
Search Consoleデータの反映ラグ（2〜3日）を踏まえると、**前回実行から中1日以上空いていない場合、新規に取得できるデータはほぼ前回と同じである可能性が高い**。ユーザーから明示的に依頼された場合は実行を断らないが、以下を実行前に一言添える。

- `data/analysis/search-console/report-*.json`の直近ファイルの日付を確認し、前回実行から中1日以上空いていなければ「前回実行から日が浅く、Search Console側の反映ラグにより新規データがほぼ同じ可能性がある」旨を報告冒頭に明記した上で実行する
- 定点観測目的で日次実行したいという要望が続く場合は、フルステップ（0〜6）ではなく、変化が出やすいステップ（1のSearch Console日割りトレンドのみ等）に絞った簡易実行を提案する

## 月次統合サマリーへの誘導（2026-08-26追加）

`data/analysis/growth-monthly-summary/`の最新ファイルの日付を確認し、前回の月次サマリーから1ヶ月以上経過している（またはファイル自体が無い）場合は、統合分析の最後に「そろそろ`/growth-monthly-summary`で月次の振り返りをしませんか」と一言提案する。SEO/X/TikTokの実績を横断して事業ゴールへの進捗を確認する場は、このスキル単体では担わないため。
