# デザイン・音楽の反復作り込み

ビジュアル（画像・動画コンポーネント）やBGMを、複数案の提示→人間のフィードバック→再生成のループで作り込みます。`docs/reference/brand-kit.md`のギャラリー構築（note ヘッダー・アイコン・CTAシーン・カバー画像等）で実際に機能してきたプロセスをスキル化したものです。

**この作業はsns-hub UI上では行いません**。Claude Codeとの対話の中で完結させ、確定した内容だけを成果物（`brand-kit.md`・実コンポーネント）に反映します（2026-09-04、UI上に同等の仕組みを作るより既存の対話ベースのループを再利用する方が二重投資を避けられるとユーザーと合意）。

## 引数
- `$ARGUMENTS`: 作り込む対象（例: `note ヘッダー画像`, `X動画CTAシーンのBGM`, `YouTubeサムネイルの見出しレイアウト`）

## 実行手順

### 1. 前提確認（既存資産の把握）

- `docs/reference/brand-kit.md`の該当セクション（チャネル別ギャラリー）を必ず確認する。同種の対象で過去に採用・却下された実例があれば、それを出発点にする（ゼロから発想しない）
- 対象がBGMの場合、現時点でギャラリーにBGM専用セクションが無ければ、この作業の中で新設してよい（下記4.参照）
- 対象コンポーネントの現在の実装（例: `sns-video-studio/remotion/src/*CM.jsx`、`DataQuoteCard.jsx`）を読み、変更の起点を把握する

### 2. 目的の明確化

- ユーザーからの依頼に具体的な不満点・方向性が含まれていればそれを起点にする
- 不明瞭な場合（「もっと良くして」等）は、着手前に一言で確認する。曖昧なまま複数案を作ると手戻りが大きいため、方向性だけは先に合わせる

### 3. 複数案の生成（1案だけで進めない）

- 最低2案、可能なら3案を並行して用意する。単一案の微調整より、方向性が異なる複数案を比較する方が良い結果に繋がりやすい（brand-kit.mdの過去の採用実績が示すパターン）
- ビジュアル: HTML/Remotionコンポーネントとして実装し、`remotion still`または既存のスクリーンショット取得手順でレンダリングする
- BGM: 候補曲を選定し、対象シーンに合わせた短尺クリップとしてレンダリングする（著作権フリー楽曲のみ、`sns-video-producer-prompt.md`絶対厳守5と同じ制約）
- 一時ファイルはスクラッチパス配下に置く

### 4. 提示・フィードバック取得

- 各案をスクリーンショット（ビジュアル）または生成したクリップの説明（BGM、実際に聴けるファイルパスも添える）と共に提示する
- 選択肢が明確な場合はAskUserQuestionで選ばせる。自由記述の指摘の方が適切な場合はそのまま聞く
- 却下された案も**理由と共に**記録しておく（5.でギャラリーに残すため）

### 5. 反復

- フィードバックを反映して再生成し、4.に戻る。満足のいく案が出るまで繰り返す
- 同じ指摘を繰り返させない。前回のフィードバックは次の案に必ず反映する

### 6. 確定・反映

承認が得られたら、その場で以下を両方行う（後日まとめない）:

1. **`docs/reference/brand-kit.md`のギャラリーに追記**: 採用案（理由込み）・却下案（理由込み）を、既存エントリと同じ形式で記録する。BGMの場合、既存の「チャネル別ギャラリー」に新規セクションを設けてよい
2. **実装への反映**: 対象コンポーネント・ドキュメントに実際に変更を適用する

### 7. 後片付け

- スクラッチパスの一時ファイル（採用しなかった案含む）を削除する
- 変更をコミットする（対象がgit管理下のファイルの場合）

## 制約

- ビジュアル・音楽どちらも実在の素材のみを使う（環境依存の絵文字、著作権不明の楽曲は不可）
- 新しいロゴ・紋章・独自デザイン言語を発明しない。既存の`brand-kit.md`トークンから逸脱する提案をする場合は、逸脱する理由を明示した上でユーザーに確認する
- 将来的にRemotion以外の生成手段（外部の生成AI動画サービス等）に切り替わっても、このスキルの手順（複数案→FB→反映→ギャラリー記録）自体は生成手段に依存しないため、そのまま使える設計にしている。3.の「生成方法」の部分だけ差し替えればよい
