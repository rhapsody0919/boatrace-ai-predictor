# SDDフロー詳細ルール（DB設計・長時間実装時の規律）

`docs/design/`配下の編集時のみ自動読み込みされる。SDDフロー自体（`/step1-spec`〜`/step4`）の概要はプロジェクトCLAUDE.mdの「仕様書駆動開発」参照。

## DB設計はER図をDDLから機械生成する（2026-09-15〜、グローバル設定の図解ルールのDB特化版）
グローバル設定の「新しい設計・仕様を検討する際は...図を使って理解を揃える」というルールは、DBスキーマのカーディナリティ（1:N、N:N等）を表現するER図の使用までは明記していない。このプロジェクトはSupabaseスキーマ変更が頻繁なため、DB特化のルールとして以下を追加する。

**天才エンジニア視点レビュー（2026-09-15）で確認した経緯**: 当初「実装前にER図を手で描く」ルールを検討したが、このプロジェクトが既に何度も学んでいる「散文ルールはコンテキスト圧迫下で読み飛ばされる」パターンを再生産するリスクが高いと判明。正の情報源である実際のDDL（`docs/db-migration/`）から逆算する機械生成方式に変更した。

- `/step2`で`docs/design/{slug}/plan.md`のデータ設計に新規テーブル、または既存テーブルとの新規リレーション（外部キー）を1つでも書いたら、対応する`docs/db-migration/`のマイグレーション案作成後に`node scripts/maintenance/generate-er-diagram.js {slug}`を実行し、出力されたmermaid `erDiagram`ブロックをplan.mdに貼り付ける（マイグレーションファイルのヘッダーコメントに`docs/design/{slug}/plan.md`等の参照を書く既存慣習に依存して該当DDLを自動検出する）
- `npm run verify:er-diagram`（`scripts/maintenance/verify-plan-erd.js`）が、新規テーブル・新規リレーションを導入するDDLを持つのにER図が無いplan.mdを横断検知する。**PR時にQuality Gates CI（`npm run verify:ci`）が自動実行する**（ADR-0072）。手元で先に確かめたい場合は `npm run verify:er-diagram`
- DB全体の俯瞰図は個別機能単位ではなく`docs/reference/database-design.md`の「テーブル関係図」を参照（`mcp__supabase__list_tables`で本番稼働中スキーマから機械生成、2026-09-15作成）。生きたスキーマから生成する方式を採用しているのは、DDL履歴の積み上げではDROP TABLE・RENAME等を正しく追えないため

## データ取得を含む機能は「完了の定義」を必ず適用する（2026-09-19〜）
外部サイトを取得してDBに書き込む機能のSDDでは、`/step3`で作るtasks.mdに`.claude/rules/data-acquisition.md`「完了の定義」（件数・タイミング・継続監視）の3行テンプレートを各データ項目に含める。plan.mdの実行基盤は同ファイル・[ADR-0066](../../docs/adr/0066-scraping-execution-consolidation-to-vercel.md)（Vercel Functions + Vercel Cron）に従う。コードのマージではなく本番DBの実測で完了を判定する。

## SDD実装が長時間・複数セッションに及ぶ場合の再開規律（2026-09-15〜）
`/step4`はタスク完了ごとに`docs/design/{slug}/tasks.md`のチェックボックスを更新する設計だが、長時間の実装セッションでは会話の圧縮・脱線により「本当は未完了のタスクを完了したつもりで進めてしまう」「圧縮後に前の続きのつもりで一部タスクを読み飛ばす」という抜け漏れが起きうる（2026-09-15、SDDで丁寧に設計しても実装が長引くと当初計画の完成度に届かないという課題を受けて追加）。これを会話の記憶ではなく`tasks.md`という実体に依存する形に寄せる。

- 会話が圧縮された直後、または別セッションでSDD実装を再開する際は、直前の会話の記憶を信用せず、必ず`docs/design/{slug}/tasks.md`を読み直してから続行する。`/step4`を都度呼び出す運用が最も安全（次の未完タスクを`tasks.md`から機械的に特定できるため）
- 1タスクが独立して大きい・複数ファイルにまたがり後のタスクと文脈を共有しない場合は、そのタスク単位で`spawn_task`または別セッションに切り出す（プロジェクトCLAUDE.md「セッション内のスコープ管理」の判断基準と同じ）。1つのセッションに全タスクを詰め込んで長時間化させない
- 全タスク完了後、`/create-pr`に進む前に`tasks.md`の全チェックボックスと実際のコミット・コードを突き合わせる完了監査を行う（詳細は`/step4`のコマンド定義を参照）。「会話でやった記憶がある」ではなく、ファイルと実コードの対応で機械的に判定する

## 実装着手前に天才エンジニアの独立レビューを必ず挟む（2026-09-23〜）
`/step3`でtasks.mdまで書き上げた時点の設計は、**同一セッションが自分で測った数値・自分で読んだコードだけを根拠にしている**。同じ推論プロセスで書かれた仕様・設計・タスクを同じセッションが読み返しても、前提そのものの誤りは見つからない。2026-09-23、`analysis-visualization-upgrade`（phase a）で実際にこれが起きた: `/step1-spec`〜`/step3`をすべて通した設計に対し、独立エージェントのレビューで33件の指摘が出て、そのうち**仕様の数値の前提が誤っていたもの（Fの符号正規化の効果を逆に記述、集計窓「730日／直近1年」が実データでは295日しかない、事前集計のキー設計がグレードの交絡を無視）が含まれ、設計をtasks.mdまで書き上げてから巻き戻す手戻りが発生した**。

- **`/step3`のtasks.md作成が完了し、`/step4`の実装に着手する前に、Agent toolで独立したエージェント（天才エンジニア視点）にレビューを依頼する。これは省略可能な任意ステップではなく、`/step4`の事前条件とする**
- 渡すもの: `docs/design/{slug}/` の spec.md・screens.md・plan.md・tasks.md と、関連するADR・マイグレーション案のパス。「結論を見せた上での批判的検証」なので、こちらの根拠（実測SQL・読んだコードのパス）も併せて渡す
- 依頼する観点は最低限この4つを明示する。「レビューして」だけだと文体・粒度の指摘に流れる
  1. **仕様に書かれた実測値・統計値を、自分で同じクエリを実行して再現できるか**（本プロジェクトのSDDで実際に壊れたのはここ。数値の再現を最優先で依頼する）
  2. **前提として引用した既存コードの挙動が、実際のコードと一致しているか**（「この関数は既に取得済み」「クエリは+0本」等の主張の裏取り）
  3. **設計のキー・粒度・集計窓が、実データの分布に対して妥当か**（交絡因子の見落とし、母数が実質0になるセル、窓の定義が複数箇所で食い違っていないか）
  4. **失敗モード**（エラーの握りつぶし、キャッシュの残留、監視の空振り、ロールバック時に残る状態）
- 指摘は鵜呑みにしない。**一次情報（実DB・実コード）で自分で再現してから採否を決める**。再現できたものは設計に反映し、再現できなかったものは反論を明記して残す（グローバル設定「セカンドオピニオン検証」の手順3と同じ）
- 完了報告（tasks.md確定時・PR時）には「自分の結論」「レビューでの指摘」「指摘への対応（採用/反論）」の3点を必ず含める
- この手順は`.claude/CLAUDE.md`「重要な意思決定・分析のセカンドオピニオン検証」（事業判断向け）とは別物。あちらは対象が後戻りしにくい事業判断に限られるが、こちらは**SDDフローを通した全機能が対象**（設計をtasks.mdまで書き上げてから巻き戻す手戻りのコストが、レビュー1回のコストより明確に大きいため）
