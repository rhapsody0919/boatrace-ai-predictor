# レビュー→修正サイクル（洗い出しと修正の分離・再現テストでの固定）

AIレビューの指摘は、繰り返しても0に収束しない。原因は3つある。1回のレビューで一部しか見つからない（小出し）、修正が新しい問題を生む、観点によって判定が揺れる。とくに3つ目は構造的なもので、「指摘0件」を終了条件にすると終わらない（[npaka「AIデバッグはなぜ収束しないのか」](https://note.com/npaka/n/n557fb948c3cf)、BOA-464）。そこで、洗い出し・検証・修正を別の工程に分け、実在を確認した指摘はテストで固定し、揺れる判断を再現できる基準に置き換える。

## 全レビュー共通: 修正した指摘は再現テストで固定する

`/code-review` 等の指摘を修正するときは、次に従う（「実装完了後の自動レビュー」の手順3）。

1. **修正前に実在を検証する**。再現手順・実データ・コードの呼び出し経路で、本当に起きるかを確かめる。起きない指摘は理由を付けて破棄する（PRコメントに残す）
2. **修正と同じPRで再現テストを追加する**。修正前は落ち、修正後は通るもの。置き場所は内容で選ぶ
   - UI挙動: `e2e/`（Playwright）
   - レイアウト: `e2e/layout.spec.js`
   - パーサー・集計・スクリプト: `scripts/maintenance/verify-*.js`（`verify-registry.json` に登録）
3. **テスト化しない例外**は次の3つだけ。PRコメントに「テスト化しない理由」を書く
   - 文言・見た目の好み
   - コメント・命名などの非機能的な指摘
   - テスト基盤が無く、追加コストが修正コストを大きく上回るもの
4. **同じ指摘が2回目に出たら修正をやめる**。コードは変えず、なぜ繰り返し指摘されるかを原因分析する（前提の食い違い、呼び出し側の保証が不明瞭、仕様未定義など）。分析結果を仕様・コメント・テストのどれかに固定してから直す
5. PRコメントのレビュー結果は「指摘 → 検証結果 → 修正コミット → 追加テスト（または理由付きの例外）」の対応で書く

## 新しいUI/UXの追加フロー

### 対象

新しいページ・分析タブ・主要コンポーネント（新しい導線や表示単位を持つもの）。

次は対象外で、従来フローのままとする。
- 「実装前の要件確認」の低リスクカテゴリ
- 既存UIの部分修正（ボタン1個・表示項目1つの追加など）

### フロー

```
[設計]     8人パネルで「ボートレースファンにどの形で提供するのが最適か」を議論
            → モック → ユーザー承認（CLAUDE.md「実装前の要件確認」）
[実装]
[Phase1 洗い出し] 独立サブエージェント・修正禁止・固定観点で1パス
[Phase2 検証]     各指摘が実在するか確認。誤った指摘は理由付きで破棄
[Phase3 振り分け] 重大度で行き先を決める（下表）
[Phase4 修正]     振り分けで「このPR」になったものをまとめて修正＋再現テスト
[Phase5 回帰確認] build / E2E / layout / verify:ci
                  ＋修正に起因する新規問題だけを見る再レビュー
                  同じ指摘が再発したら → 修正をやめて原因分析（上記4）
[完了]
```

- **8人パネルは仮説を出す用途**: 同じモデルのロールプレイなので、偏りを共有している。案の幅を広げるには有効だが、ファンにとって最適であることの証明にはならない。検証はモック承認とリリース後の実データで行う
- **Phase1は設計に関わっていないサブエージェントで行う**。設計・実装したコンテキストで自己採点しない。長いセッションでの指示遵守率低下も避けられる
- **Phase1のプロンプトには次の3点を明示する**
  - 修正しない
  - 下の固定観点を全部見終わるまで探索を止めない
  - 各指摘に重大度（P0〜P3）と再現手順を付ける
- **Phase1の固定観点**
  - ファン視点のUX（初見で何のデータか分かるか、次に何をすればいいか）
  - レイアウト（375/768/1024/1440/1920px）
  - データ正確性（集計を含む場合は `data-accuracy-verifier`）
  - i18n区分と `t()` 経由
  - a11y（コントラスト・`translate="no"`）
  - コード（`/code-review`）
- **洗い出しは1パスで閉じる**。「全て出し尽くす」までは繰り返さない。網羅性は固定観点で担保する

### 振り分け

| 区分 | 行き先 |
|---|---|
| P0 / P1 | このPRで修正＋再現テスト |
| 実在を確認したP2 | このPRで修正＋再現テスト。量が多くPRが膨らむ場合は起票して別PR |
| P3・好みの問題 | 1チケットにまとめて起票するか、理由付きで破棄 |

起票するのは「このPRでは直さないもの」だけ。このPRで直す指摘は起票しない（PRコメントに記録する）。

### 終了条件

「指摘0件」は条件にしない。次を全て満たしたら完了とする。
- P0/P1が0件
- 実在を確認したP2は修正済みで、再現テストで固定されている（または起票済み）
- build / E2E / layout / verify:ci が全て緑
- 再発した指摘は原因分析済み
- 「ファン評価あり」の作業では、下の「ファン評価ループ」の終わる条件も満たしている

## ファン評価ループ

### 対象

新しいページ・タブ・主要な表示の追加や変更のうち、オーケストレーターが作業を振るときに「ファン評価あり」と指定したもの。指定が無いものには適用しない。

### 位置づけ

- **「指摘0件を終了条件にしない」との関係**: ファン視点の判定は観点による揺れが特に大きいので、0件を待たず、下の「上限つきの収束条件」に置き換える
- **上の「新しいUI/UXの追加フロー」との関係**: ファン評価ありの作業では、Phase1の固定観点のうち「ファン視点のUX」をこのループが担う（Phase1のプロンプトからは外し、二重に見ない）。Phase1のその他の観点（レイアウトの機械検知・データ正確性・i18n・a11y・コード）はPhase1〜5のまま。このループはPhase5の後、PRのCIが緑になってから回す

### 手順

```
[前提] 実装済み・PRのCIが緑・Vercel Preview URL が出ている
[周の開始] boatrace-fan-reviewer を毎回新しく起動する
           渡すのは Preview URL・変更の要約・対象幅だけ。前の周の結果は渡さない
[検証]     各指摘が実在するか確認（上の「全レビュー共通」1）。誤った指摘は理由付きで破棄
[振り分け] P0/P1・実在するP2 → このPRで修正＋再現テスト（全レビュー共通 2・3）
           （P2が多くPRが膨らむ場合は、上の振り分け表と同じく起票して別PRにしてよい）
           P3 → 起票してループから外す（周をまたいで1チケットにまとめてよい）
[判定]     終わる条件を満たせば終了。満たさなければ修正をpushし、CIが緑になってから次の周へ
```

- 毎回新しく起動するのは、前の周の指摘を知ると「直ったか」の確認に視野が狭まるため。同じ理由で、周をまたいだ比較（同じ指摘の再発判定）は依頼元が行う

### 終わる条件

- **P0/P1が0件で、かつ新しく実在するP2が出ない周が1回あったら終了**
- **上限は3周**。上限に達して残った指摘は、オーケストレーター経由でユーザーの判断に回す
- **同じ指摘が2回出たら修正をやめて原因分析する**（上の「全レビュー共通」4と同じ）

### 限界

同じモデルのロールプレイなので、ファンの評価そのものではなく仮説にすぎない（8人パネルと同じ）。このループを通ったことは「ファンにとって分かりやすい」ことの証明にならない。最終判断はユーザーの確認と、公開後の実データ（GA4・Search Console等）で行う。

### 報告

PRコメントに次を書く。

- 1行目: `ファン評価: N周、P1をx件修正、P3をy件起票`（P0・P2を修正した場合も同じ形で足す）
- 周ごとの表

| 周 | 指摘（重大度・観点） | 検証結果 | 対応（修正コミット＋再現テスト / 起票チケット / 破棄理由） |
|---|---|---|---|
