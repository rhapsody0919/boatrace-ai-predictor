# 分析ワークフロー・ルール

## 目標
各会場で「回収率100%超え」のルール・条件を統計的に発見し、厳選型のモデルを構築する。

## 分析ステップ
1. **データ収集**: Supabaseから過去データを取得
2. **条件探索**: 回収率100%超えの条件を統計的に探索
3. **ルール検証**: 発見したルールの信頼性を検証（サンプル数、期間）
4. **モデル化**: ルールを `src/services/ruleMatchService.js` に組み込み

## 分析PDCA

```
仮説立案 → データ分析 → ルール発見 → 検証 → 本番適用 → 結果確認 → フィードバック
```

分析結果は `data/analysis/venue-{コード}/` に保存。保存形式は `.claude/templates/analysis-docs.md` を参照。

## データ精度の検証（新規データ・分析機能追加時、必須）

新しい集計ロジック・分析機能（新統計、ランキング、傾向表示等）を追加する際は、`.claude/CLAUDE.md` の
実装完了後の自動レビューフローの一環として、以下をコードレビューとは別の視点で必ず行う。
見た目やコードスタイルが正しくても、集計ロジック自体の誤り（スケール不一致、JOIN漏れ、期間ズレ、
NULL除外漏れ等）は気づかれにくいため、意識的に切り分けて検証する。

1. **実データでのスポットチェック**: 実際のレース・選手・モーター等を2-3件手動で抽出し、
   集計結果とDBの生データを直接突き合わせて一致することを確認する（`node -e` での即席クエリでよい）
2. **妥当性の機械的チェック**: 比率の合計が100%に近いか、件数が母集団と矛盾しないか、
   異常な偏り（全件が1カテゴリに集中する等）が無いかを確認する
   （2026-07-28: `volatility_score` の分布集計で閾値のスケール不一致により全件が「High」に
   誤分類されるバグが実際に発生した。この手のチェックで発見できる）
3. **可能なら独立した別経路での再計算**: 別クエリ・別スクリプト・既存の類似集計との突き合わせで
   同じ指標が一致するか確認する
4. 実装者本人のセルフチェックだけで終わらせない。規模の大きい分析機能では、コード品質チェックとは
   別に「データが正しいか」だけを見る検証パスを設ける。
   `data-accuracy-verifier` サブエージェント（`.claude/agents/data-accuracy-verifier.md`）がこの役割を担う
   （`.claude/commands/implement.md` の並列サブエージェント検証パターンに準ずる）

## モデル・統計分析の検証（比較・選択・評価を含む分析）

2026-10-02 のデータサイエンス体制レビューで、事前登録が結果と同じコミットに入っていて事前性を示せない、test の使い回し、分析の定義と本番の定義の照合が無い、数値の限定条件が落ちて誤って中継される、が見つかったため。

1. **事前登録は単独でコミットして push してから分析を回す**。結果のコミットには事前登録コミットの SHA を書く。事前登録の前に `second-opinion-reviewer` で方法論を1パス見る（時点・リーク・test の使用履歴・ベースライン・指標とファンに見える差の対応）
2. **test は分析をまたいで使い回さない**。どの期間を何回見たかを分析の記録に残す。使い回した場合は spec の限界として明記する
3. **分析で選んだ定義（Python 等）と本番の定義（SQL・JS）は、本番データで照合するスクリプトを作り、毎晩の検査に載せてから公開する**。画面に出す推定量は、評価した推定量と同じものにする（違うなら同じデータで評価し直して記録する）
4. **分析コードと結果は master に残せる形にする**（scratchpad のパスは環境変数にする）。結果 JSON にはデータの行数・最大日・内容ハッシュを入れ、縮小版なら `scale`（例 `sample2000`）を必ず入れる
5. **数値には出典を付ける**。報告・文書・中継の数値は「値／指標／A−B（比較対象）／母集団・部分集合／期間（cal・test）／データ版／結果 JSON のパス#キー」の形で書く。出典の無い数値は「未検証」と書いて扱う
