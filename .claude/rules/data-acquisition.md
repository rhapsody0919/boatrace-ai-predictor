# データ取得機能の実装ルールと完了の定義

複数のセッションが並行してデータ取得を実装した結果、「コードはマージ済みだが本番DBが空」「成功扱いだが0件書き込み」「一度も実行されていない月次ジョブ」が見逃された（2026-09-19の実測）。コードのマージを完了とせず、**本番データの実測で完了を判定する**。

## 1. 実行基盤（[ADR-0066](../../docs/adr/0066-scraping-execution-consolidation-to-vercel.md)）

- 新規のデータ取得は**Vercel Functions + Vercel Cron**で実装する。新規にGitHub Actions・cron-job.orgへ取得ジョブを追加しない（既存の旧基盤ジョブは、移行が完了するまでの暫定）
- 移行完了までの暫定として残る旧基盤のジョブが、結果をmasterへコミットして`git push`する場合は、素の`git push`ではなく`scripts/maintenance/push-with-retry.sh`経由にする（masterの更新と競合してもrebase＋リトライで成功させ、コンフリクト時は失敗させる。BOA-360）
- Cronは共通ラッパ（認証・排他（リース）・冪等・0件エラー・リージョン）経由で実装する
- 並走期間（新旧基盤の併存中）の二重書き込みは、取得元（source）列で区別する
- マイグレーション番号は、着手時とPR作成前に`origin/master`の最大番号を確認する（重複はCIで機械検査する予定）
- Vercel Cronは「UTC固定・リトライ無し・best-effort・まれに重複配信」。次を満たす設計にする
  - cron式はUTCで書き、JSTの運用時間帯をコメントで併記する
  - upsertで冪等にする（重複配信で壊れない）
  - 各実行で「本来取得済みであるべき窓のうち、未取得のもの」も再処理する（catch-up。未配信の自己修復）
  - 1回の呼び出しで処理する対象を分割し、関数の最大実行時間内に必ず終わる粒度にする
- 過去分の一括取得（バックフィル）は、手動実行のCLI（`scripts/maintenance/`）で行う。取得ロジックは定期実行と共有し、二重実装しない
- 変更の無い行は書かない（条件付きupsert）。取得のたびに全行をUPDATEしない。WAL・Disk IO・dead tupleの増加の原因になる
- 新規の取得・バッチは、書き込み行数×行サイズの見積りと、Disk IO予算への影響をspecに書く。本プロジェクトのSupabaseは小さい計算リソースで、Disk IO Budget枯渇の警告が出た実績がある（2026-09-19）
- 書き込み件数が0件の実行を「成功」として扱わない。期待件数が0でない限り、0件はエラーとして記録・通知する

## 2. 完了の定義（3つ全てを満たして初めて完了）

### A. 件数: 過去のバックフィルを含む期待件数が、本番に入っている

- tasks.mdに、対象期間・対象テーブル・**期待件数と算出根拠**（例: レース数×6艇）を書く。期待件数の分母からは、開催中止・出走取消（`cancellation_status='confirmed'`等）を除外して算出し、除外した件数も報告する
- 完了報告に、本番DBの**実測クエリと結果**（期間×会場別の充足率）を添付する。コード・テストの結果だけで完了としない
- 充足率は原則99%以上。未達は、理由（中止レース・欠場等）を件数付きで説明する
- 過去分を遡って取得できないデータは、「取得開始日以降のみ」と明記してユーザーの承認を得る

### B. タイミング: 可変データが、ユーザーが見る時点で取得済みである

対象は、レースの進行に応じて値が変わる、または取れる時間が限られるデータ（展示・オッズ・直前情報・気象・結果 等）。

1. データ種別ごとに「取得すべき窓」と「許容遅延」を、specで定義する（[ADR-0057](../../docs/adr/0057-odds-capture-frequency-and-full-grid-scope.md)・[ADR-0058](../../docs/adr/0058-data-refresh-frequency-optimization-principle.md)の4つの問いを適用する。オッズは60/30/15/10/5/0分前の6窓）
2. **各行に取得時刻を保存する設計にする。** 取得時刻が残らないデータは、タイミングを検証できないため不可。行に取得時刻列が無いテーブルは、先に取得時刻列（`scraped_at`）を追加するマイグレーションを行い、追加日以降の行で実測する
3. **土日を含む直近7日**の実測で、レースごとの「締切（発走）時刻−取得時刻」の分布を出し、各窓の充足率を完了報告に添付する。窓内取得率は「窓の中心±3分以内に1件以上取得できたレースの割合」と定義する。欠落率は2%以内（BOA-313の基準）
4. 早朝・閑散日だけの実測は根拠にしない

### C. 継続監視: A・Bの指標が自動で計測され、逸脱を検知できる

- 件数の充足率、窓内取得の充足率、**0件のテーブル**を、DBの実測から自動計測する（`exhibition-gap-monitor.yml`と同じ方式を、データ種別ごとに汎用化する）
- 閾値を超えたら、既存のSlack通知に流す
- 監視自体が失敗した場合も検知できるようにする（監視が動いていることを確認する）
- 未実行、または最終成功からの経過時間が想定を超えたジョブを検知する
- 取得ステップに`continue-on-error: true`を付けて、ジョブ全体を成功に見せない。ステップ別の成否を集計する
- 大量書き込み（バックフィル・全件更新）の前後で、ダッシュボードのDisk IO消費を確認し、完了報告に含める

## 3. tasks.mdのテンプレート

データ取得を含む機能のtasks.mdには、各データ項目ごとに次の3行を必ず入れる。

```
- [ ] 本番実測: 期待件数（算出根拠: …）に対し、過去分を含めて充足率99%以上であることを実測クエリで確認する
- [ ] タイミング実測: 可変データは、土日を含む直近7日で窓内取得率（窓の中心±3分以内）を実測する（欠落率2%以内）
- [ ] 継続監視: 上記指標が日次で自動計測され、閾値超過でSlack通知されることを確認する
```

`/step3`でtasks.mdを作成するときも、この3行を各データ項目に含める。
