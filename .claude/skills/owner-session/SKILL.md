# オーナーと対話するセッションの決まり

旧 `.claude/CLAUDE.md` と `.claude/rules/session-start-checks.md` から、作り手に要らない決まりを移した（2026-11、T1。ZB03 で rules を消した）。置き場は窓口の手順を分ける票で決め直す。作り手の決まりは `AGENTS.md`。

## セッションの始めの確認（旧 session-start-checks.md）

セッション開始時に次を実行し、**結果をこのセッションの最初の応答で報告する**。

```bash
node scripts/maintenance/session-start-check.js
```

1回の実行で次を集める。

| 項目 | 何を見るか |
|---|---|
| `xVideo` | X の本日の投稿本数が目標に達しているか |
| `racerNews` | 選手ニュースの要確認（自動投入されなかった候補） |
| `growthSkills` | `/x-growth-report` の最新レポートが1週間以上前か（`/note-growth-report` は止めている。note の noindex は 2026-11-01 に解除済みで、11/4 からの毎日1本が1週間たつ 11/11 から戻す。2026-11-03 オーナー決定、`docs/knowledge/note.md`） |
| `pendingInsights` | 戦略メモ（`sns_strategy_insights`）の承認待ち |
| `qualityBacklog` | Linearの `content-quality` ラベルの古いもの2〜3件 |
| `visualAssetAge` | 90日以上更新されていない視覚素材 |
| `deprecatedTerms` | 廃止済み用語の残存件数 |
| `contentIndexCoverage` / `missingContentIndex` | トレーサビリティ索引の欠落・形式エラー |
| `schemaSnapshot` | 本番スキーマの写し `docs/reference/schema-snapshot.json` が7日以上古い（または本番と食い違う）か。食い違いは台帳 `APPLIED.md` で写しの後に適用済みになったファイルで見る（本番には接続しない） |

**該当が1件以上あれば、ユーザーから話しかけられるのを待たずに最初の応答で提示する。**
「いいえ」または反応が無ければその日はスキップし、催促しない。

各項目を確認したあと実際に何をするか（投稿の作り方・承認の取り方・型の選び方）は
[`content-ops.md`](../../rules/content-ops.md) にある。そちらは `public/blog/**`・`note-articles/**`・
`sns-video-studio/**` 等を編集するときに読み込まれる。

この確認は対話のセッションだけが回す（以前は常時の rules だったが、作り手の起動で node_modules の無い worktree でも回り、max-turns を食ったため移した。T4）。

## 調査・分析の報告

調査・分析タスク（集客系のコマンドに限らず全般）では、**取得したデータは自己判断で重要度を絞り込まず全て報告に含める**。「特筆すべき動きが無い」「横ばい」というデータも省略せず、その旨を明記する。取得したのに報告しなかった情報は、ユーザーから見れば「調査されなかった」のと同じ。一部だけ深掘りしたい場合も、まず全項目を並べた上で「特にAが重要」と扱う。

### 「議論して」のファンパネル
ユーザーが「議論して」と依頼したら `discussion-panel` skill（`.claude/skills/discussion-panel/`）の手順に従う。熱血ボートレースファン4人（20代・30代の男女）だけで議論する。

### 重要な意思決定・分析のセカンドオピニオン検証
単一セッション内の自己検証では、同じ推論のバイアスから逃れられない。後戻りしにくい判断ほど、別の視点で批判的に検証する。

**対象**: 後戻りが困難、または投資規模が大きい事業判断・戦略転換に限る（例: リブランディングの可否判断、集客戦略の大転換、大規模新機能のGo/No-Go判断、アーキテクチャの大幅変更）。定例分析や軽微な相談は対象外。迷ったら「この結論が外れていた場合の手戻りコストが大きいか」で線引きする。ファンパネル（同一セッション内のロールプレイ）とは別物で、両方使う場合はファンパネルで結論をまとめた後にこちらを行う。

**手順**:
1. 一次情報（コード・ドキュメント・実データ）に基づき結論・推奨案をまとめる
2. 別ベンダーの Codex に、結論・根拠・使用したデータをそのまま渡して批判的検証を依頼する（codex プラグインの `codex:rescue` で渡す。鍵・会話記録は渡さない）。Codex が止まっているとき（プラグインが使えない、Codex の接続が切れている）だけ、代わりに `second-opinion-reviewer` サブエージェントに依頼する
3. 指摘のうち妥当なものは結論に反映し、妥当でないものは反論を明示した上で残す
4. 最終報告には「自分の結論」「セカンドレビューでの指摘」「指摘への対応（採用/反論）」の3点を必ず含める

※結論を見せた上での批判的検証であり、独立した再導出ではない。第一セッションが検討しなかった観点の完全な捕捉は保証しない。

### サブエージェントの使い分け
役割が固定で繰り返し使うものは `.claude/agents/` に定義を置き、毎回プロンプトで書き下ろさない。定義があるものはそれを使う。

| 定義 | 用途 | 呼ぶタイミング |
|------|------|---------------|
| `spec-ambiguity-detector` | 依頼文だけを見て「決まっていない点」を列挙する | **実装方針を考える前**（下記「実装前の要件確認」） |

| `acceptance-test-writer` | UI機能の受け入れE2Eを spec.md・screens.md だけから書く（plan/tasks/src は読まない） | `/step3`完了後、`/step4`着手前（UI機能のみ） |
| `data-accuracy-verifier` | 集計結果が実データと一致するかだけの検証 | 実装完了後の自動レビュー2番（新規の集計・分析機能を含む場合） |
| `content-qa` | ブログ記事の公開前品質チェック7観点 | 記事の新規公開・改稿前 |

上の11（`data-scientist` 以下）は、定義に書いた `docs/knowledge/` の話題ファイル（一覧は `docs/knowledge/README.md`）を最初に読み、答えの最後に「知見ノートに足す行」を出す。呼んだ側が話題に合うファイルへ書き写す（1行1知見、日付と根拠つき、鍵・個人情報は書かない）。知見の正本は `docs/knowledge/` の1か所で、写しを作らない。ファンの知見は `docs/knowledge/fan-reactions.md` を `discussion-panel` が読む。note は当面ノート（`docs/knowledge/note.md`）だけで担当を置かない。`boatrace-fan-reviewer`・`content-qa`・`design-reviewer`・`data-accuracy-verifier`・`user-proxy-reviewer`・`mock-diff-checker` も、定義に書いた話題ファイルを最初に読む。`spec-ambiguity-detector`・`acceptance-test-writer`・`second-opinion-reviewer` は独立性のために読む範囲をわざと絞っているので、話題ファイルを足さない。

いずれも読み取り専用（`acceptance-test-writer` のみ `e2e/acceptance/` に書く）で、修正は親セッションが行う。定義に無い一回限りの調査は、Agent tool へ直接プロンプトを渡す。

**Agent Teams機能（`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`）は使わない**。理由は2つ:

1. **デスクトップアプリで非対応**。公式ドキュメント（`code.claude.com/docs/en/desktop`）が「coordinated teams … are available in the CLI, not in Desktop」と明記している。本プロジェクトの運用はデスクトップのCodeタブが中心
2. **worktree隔離ルールと衝突する**。teammateは自動でworktree分離されず、Agent tool呼び出しで `isolation` を渡すとteammateではなく通常のサブエージェントとして起動する（＝teammateとworktree隔離は排他）。「新規タスクは必ずworktreeで隔離する」というGit安全策を優先する

この環境変数を有効にすると、Claudeが名前を付けたサブエージェントが勝手にteammateとして起動するようになるため、`.claude/settings.json` には置かない。並列作業が要る場合はサブエージェント（親が統合）か、独立セッション＋`SendMessage`（cross-session messaging、設定不要）を使う。

## 重要な制約

- モバイル実機でのテストは不可能。ユーザーに確認を依頼する
- Codex に記録を渡さない: Codex の `/import`・`codex-plugin-cc` の `/codex:transfer` は使わない（`~/.claude/projects/` の会話記録に平文の鍵が残る）。誤って `/import` を開いたら全ての選択を外して閉じる（旧 AGENTS.md から移した、ZB03③ 2026-11、オーナー yes 11/12。作り手は `/import` を回せない）

### Linear MCPが認証切れの場合は`scripts/linear-cli.js`にフォールバック
Linear MCP（`.mcp.json` の公式リモート MCP サーバー）はユーザーのブラウザ経由の OAuth 認証で、Claude Code のセッションからは再認証できない（`.env.local` の `LINEAR_API_KEY` とは別物）。MCP の呼び出しが認証エラーになったら、都度ユーザーに確認せず `LINEAR_API_KEY` を使う `scripts/linear-cli.js` に切り替えて続ける。

```bash
node --env-file=.env.local scripts/linear-cli.js get BOA-123
node --env-file=.env.local scripts/linear-cli.js update BOA-123 "Done" "PR #999マージ済み"
node --env-file=.env.local scripts/linear-cli.js create "タイトル" "説明"
```

- `update`の状態名は完全一致（大文字小文字は無視）が必要。不明な場合は該当チームのworkflow状態一覧を先にGraphQLで確認してから指定する（BOAチームの主要状態: `Backlog`/`Todo`/`In Progress`/`Done`/`Canceled`/`Duplicate`）。一致しないと`In Progress`相当の状態に誤って変更されるため、状態名を推測で決め打ちしない
- MCP接続自体の再認証（ユーザー側の対応）が必要な場合のみユーザーに案内する

### フロントエンド変更の確認は自己完結させる（絶対ルール、例外なし）
**「`npm run dev`」という文字列をユーザー向けの文章に書くこと自体を禁止**する。

- **ユーザーに`npm run dev`を打たせる・打つよう示唆する文言は一切書かない**（「ローカルで`npm run dev`後〜」のような一文も禁止）。UI変更が発生したら、頼まれる前にClaude自身がdevサーバーを（`run_in_background` で）起動し、確認後は停止する
- ブラウザでの確認はPlaywright（プロジェクト依存関係）で自己検証する
  - DOM出力（`document.title` / `meta[name="description"]` / `link[rel="canonical"]` 等）をスクリプトで取得して照合する
  - スクリーンショットを撮り、Read toolで読み込んで視覚的にも確認する
  - Node解決の都合上、確認スクリプトはプロジェクト直下（node_modules配下）に一時的に置く必要がある場合がある。**検証後は必ず削除する**
- ユーザーへの確認依頼は、Playwrightで完結できないもの（モバイル実機、視覚的な好み・UXの主観判断等）に限定する
- ユーザーがローカル環境で自分の目で確認したい場合は、Claude自身が起動したdevサーバーのURLを提示した上で、**必ず箇条書きで**何を確認すればよいかをリストアップする：①アクセス先の正確なURL・操作手順（例: `/winning-technique?tab=extrend`を開く、どのボタンを押すか）、②確認項目（新旧の違い、期待される表示内容、崩れていないか等）。「動作確認してください」のような曖昧な依頼で済ませない
- UI変更を伴うタスクのマージ確認・完了報告では、ユーザーから「ローカルで見たい」と言われる前に、上記（起動済みのURL＋箇条書きの確認項目）を最初から本文に含めておく

### 実装前の要件確認（ユーザーの想定とのズレ防止）
- 既存機能の修正・追加依頼で、影響範囲が1ファイルに閉じない、または挙動が変わる場合は、**実装方針を考える前に `spec-ambiguity-detector` へ依頼文をそのまま渡し**、決まっていない点を列挙させる。そのうえで「こう理解した」を一言で復唱し、ユーザーの認識とズレが無いか確認してから実装する
  - **自分で復唱するだけでは足りない**。依頼を読んだ本人が復唱すると自分の解釈に固着する。依頼文だけを渡した別エージェントに判定させる構成で、SWE-bench Verified の情報欠落版で resolve rate が +14.6〜22.2pt 改善したという実測がある（[arXiv 2603.26233](https://arxiv.org/html/2603.26233)）
  - **確認が要る点が2つ以上あればタスクを分割する**。曖昧点が1個なら最高30%成功、2個で8%、3個でほぼゼロという実測がある（[arXiv 2607.00711](https://arxiv.org/html/2607.00711)）。「必要なら聞いて」と書くだけでは効かない
- **低リスクカテゴリは復唱・事前確認を省略し、確認なしで着手してPR作成まで進めてよい**: typo修正、文言1箇所の変更（規約・法務・事業判断に影響しないもの限定。ユーザーが個別に「様子見」等と保留判断した内容は対象外）、Linearチケット起票、ブログ記事の軽微な修正（誤字・数値更新・リンク修正等、記事の主張や構成を変えないもの）。この定義は「実装完了後の自動レビュー」のマージ確認でも共通して使う
- 迷ったら「要件をどう解釈したか一文で言えるか」で判断する。一意に言えない・複数の解釈がありうる、または設計判断・挙動変更を伴う場合は復唱する
- 大規模・曖昧さが残る新機能は復唱では足りないため、`/step1-spec` からのSDDフローを使う
- **大規模な新機能（SDDフロー対象）は、実装着手前にモック・サンプルを見せてユーザーの承認を得る**。spec.md確定後、`/step1-screens`の画面設計を経て実装に入る前に、実際の見た目（Artifactでのモックアップ、または簡易な画面キャプチャ等）を提示し、イメージと合っているか確認してから本実装に進む
- **UI/UX に要る統計検証は、見せ方・設計を決める前に必ず実施する**（全開発共通）。画面に出す材料（指標・データ）ごとに、効き目（着順・結果との関係）・母数・言える範囲を、`data-scientist` サブエージェントで先に確かめる。その結果を踏まえてファンパネル・モック・spec に進む。「効き目は未確認」と注記して出す案を先に作らない。データが足りず判定できないときは、その事実と必要な量（件数・日数）をユーザーに出し、出すか待つかを決めてもらう。統計のやり直しは3回まで
  - 検証の結果をリポジトリに残すまでを1つの作業とする（AGENTS.md「PR の決まり」の知見の候補）。サブエージェントの「残すファイルの一覧」（スクリプト `scripts/analysis/`・結果 `data/analysis/`・読み物 `docs/`）を PR にし、`docs/knowledge/stat-findings.md` に1行1知見で追記して、はじめて「検証済み」と扱う

### セッション内のスコープ管理
関連する追加依頼が積み重なると、1つのセッションが当初の目的から離れた広い範囲を抱え込みやすい。

**この切り分けはユーザーに判断させない。Claude側が下記の機械的な基準で即座に判断し、確認を挟まず実行した上で、やったことを一言報告するだけに留める**（「①このまま続ける②spawn_task③別セッション、どれがいいですか」のような選択を迫らない）。

**長さによる判断は自動で促される。** セッションの編集回数が20回を超えると、PostToolUseフック（`.claude/hooks/track-session-progress.sh`）が現在の推定遵守率と下記の選択肢をその場で出す。以降10回ごとに再通知する。**指示遵守のオッズは関数を1つ生成するごとに約5.6%低下する**（Claude Code 1,650セッション・16,050観測、[arXiv 2605.10039](https://arxiv.org/abs/2605.10039)）。同じ研究で、CLAUDE.mdのサイズ・指示の位置・ファイル構成・矛盾の4変数はいずれも遵守率に有意差を与えないことが示されており、**効くのは1セッションで生成する量を減らすことだけ**。

**判断基準（性質で機械的に決まる）**:
- **今のタスクの結果に今すぐ使う調査・検証か** → Agentで同一セッション内で実行する（例: 結論への批判的検証、独立観点のレビュー、探索作業のコンテキスト節約）
- **今すぐ手が回らないが自己完結して着手できる別スコープの改善点か**（気づいたバグ、ついでに直したい既存の不備、大きな設計課題の種等） → `spawn_task`で切り出す。「今の会話とは別の話だ」と気づいた瞬間に切り出すのがデフォルト動作
- **触る対象が別ディレクトリ・別リポジトリか、または元の依頼と目的が別物で今の会話のコンテキストを圧迫する規模か** → 新しいworktree・新しいセッションで着手する

**確認が必要になる場面はこれだけに絞る**（それ以外は実行してから事後報告する）:
- 実行そのものが後戻りしにくい・費用や外部影響が伴う（マージ・投稿・購入等、下の「確認のバッチ化」で確認必須とされているもの）
- 依頼が今の会話の続きなのか全く新しい話なのか、Claude自身で判断がつかない

### 小さなスコープの作業中に「実は大きな設計判断が必要」と気づいた場合
今困っている問題は応急処置としてまず完了させる（止血が先）。大きな設計検討を理由に今の作業を止めない。都度「大きい方を先にやるか」を聞かない。

- 完了報告に「これは応急処置であり、根本的な設計は別途検討が必要」と明記する
- 気づいた大きな設計課題は、その場で深追いせず`spawn_task`または`docs/proposal/`への記録で明示的に残す。ユーザーが後から「今すぐ大きい方をやりたい」と言えばそちらを優先する
- 再発性・影響範囲の兆候（同じ問題が2回目以降発生している、複数箇所に影響する、車輪の再発明になりそう等）が強い場合のみ、「これは個別修正ではなく`/step1-spec`からのSDDフローで俯瞰設計すべき規模かもしれない」と一言添えて判断を仰ぐ

   - 連続してタスクをこなす場合も、通常カテゴリは都度サマリー付きで確認を求める
   - **例外**: 窓口は、下の「マージしてよい範囲」の段階0に当たる PR に限り、自分の判断でマージしてよい。段階1・2の扱いも同節に従う

ユーザーがモック（Artifact 等）を承認したら、その作業のセッションは承認した見た目の画像（375px と 1440px）を `docs/design/{slug}/mock/` に保存し、同じ場所の `APPROVED.md` に承認日・承認のメッセージ（要旨）・承認範囲（画面・コンポーネント）を書いて、設計の PR に入れる。画面の PR は CI が緑になった後に `mock-diff-checker` を1回通し、結果を PR コメントに書く。窓口の段階0（下の「マージしてよい範囲」）はこれを条件にする。

## マージしてよい範囲（承認の3段階、旧 orchestrate の skill の4節。hq を閉じて窓口へ移した、BOA-1710）


ユーザーの承認がボトルネックにならないよう、承認を3段階に分ける。

### 自動マージ（オーナー 2026-11-23。段階0の A〜G より先に見る）

オーナーは「マージしてよいか」を PR ごとに聞かれない。次を全部満たした PR は、PR を作ったセッションが auto-merge を付け（`node scripts/maintenance/ryujin-maker-token.js -- gh pr merge` に PR 番号と `--auto --squash`）、GitHub が緑で入れる。窓口の手もオーナーの手も要らない。

1. 壊れていない: 必須の check（e2e・verify・ml-tests）が全部緑
2. 試験・守りを弱めていない: `guard-weakening` が緑（赤なら、その理由が「弱めていない」と窓口が差分で確かめられた物だけ通す）
3. ファンにとって問題なく使いやすい: 画面が変わる PR は、設計に関わっていないサブエージェント `boatrace-fan-reviewer` の評価で P0・P1 が0。PR のコメントに「ファン評価: N周、P0 0・P1 0」と書く。画面が変わらない PR は飛ばす
4. GitHub の守る場所（`.github/CODEOWNERS` に当たるパス）を触らない。触る PR は GitHub がオーナーの承認を求める

pr-lane の heavy（H5 を含む）は、上の1〜4を満たせばこの道で入れてよい（H5 の e2e の spec を足す・直すだけの変更は 2 で見る）。
**3周で P0・P1 が0にならなければ、直すのをやめてオーナーに判断を仰ぐ**（指摘・直した物・残った理由を推奨つきで）。同じ指摘が2回出たら原因を分析する。

この道に乗らない物（オーナーが決める）: 新しい機能を作るか・最初のモックの承認・本番 DB のスキーマや RPC の変更とデータの削除・お金と鍵・`.github` と守りの仕組みそのものの変更・事業と法務とブランドの表記。

### 段階0: 窓口がマージし、事後に報告する

次のいずれかに当たり、条件をすべて満たす PR。

- A. 画面が変わらない PR: CI の必須の check が全部緑で CLEAN（承認待ちだけが理由の BLOCKED を含む。`.claude/commands/merge-pr.md` を参照）、pr-lane.js が light、マージ順の制約を守っている。LLM の審査は無い（D2、2026-11-06）
- B. 画面が変わる PR のうち、ユーザーが承認したモック・仕様の実装であるもの。A の条件に加えて次をすべて満たす
  - 承認したモックの画像が `docs/design/{slug}/mock/`（承認日つき）にあり、mock-diff-checker（`.claude/agents/mock-diff-checker.md`）が Preview（`claude/*` は Preview が無いので、PR の head で起動した手元の dev サーバー。作業ツリーの HEAD が PR の headRefOid と同じで未コミットの変更が無いことを確かめて SHA を渡す）と並べて「承認範囲内」と判定した
  - 受け入れ E2E が「存在して」緑（無い PR は B に当たらない）
  - 差分が承認範囲（spec に書かれた画面・コンポーネント）の外を触っていない
  - 新しい数値・集計の表示を含まない
  - 共通コンポーネント（Header・LanguageSwitcher・`src/components/race/` の共通部分）・ルーティング・URL 構造・i18n の区分を触っていない
  - 文言に事業・法務・ブランドの語（競艇、的中率、回収率、誇大表現。4言語とも）が新しく入っていない
- C. 画面が変わる PR のうち、見せ方を新しく決めない不具合の修正。A の条件に加えて次をすべて満たす
  - 本来の動きに戻す・崩れを直す・文言の誤りを正すもので、新しい表示項目・配色・並び順・文言の方針を決めていない（はみ出し、折り返し、金枠の誤り、内側スクロール、訳語の誤り等）
  - 修正前は落ち、修正後は通る再現テストが同じ PR にある
  - 修正前と修正後の画面を比べた結果（スクリーンショットか実測値）が PR にある
  - user-proxy-reviewer が「通る」と判定した
  - B の最後の4条件（新しい数値・集計の表示を含まない、共通コンポーネント等を触らない、事業・法務・ブランドの語を入れない、承認範囲の外を触らない）を満たす
  - 新しい画面、本番 DB への書き込みを伴うもの、.claude の変更は C に当たらない（段階2）。BOA-271 は下の D・E で扱う
- D. docs だけの PR（BOA-271 を含む）。A の条件に加えて、変更が `docs/` 配下と `*.md` だけで、画面・コード・CI の変更が無い。`.claude/` 配下の md は D に当たらない（段階2）
- E. 再現テストを同じ PR に含む障害修正（BOA-271 を含む）。A の条件に加えて次をすべて満たす
  - 修正前は落ち、修正後は通る再現テストが同じ PR にある
  - 画面の見せ方（表示項目・配色・並び順・文言の方針）と、表示する数値の判断（集計・算出の定義）を変えない
  - .claude・CI ゲート・permission の変更、本番 DB への書き込みを伴わない
- F. ブログ記事の掲載・改稿。変更が `public/blog/`・`src/data/blog-posts/`（翻訳のメタの `en/`・`ko/`・`zh-TW/` を含む。#1699 で移った先）・`public/images/blog/`・`docs/content-manifests/`（記事の審査記録、契約 docs/operation/content-pr-contract.md）・`public/blog-charts/`（記事の図のデータ、ADR 0098）だけの PR。画像は別の名前で足す（差し替えはオーナーが行う）。A の条件に加えて次をすべて満たす
  - content-qa（`.claude/agents/content-qa.md`）・wording-editor・ファンのレビュー（boatrace-fan-reviewer か discussion-panel）・seo-marketer の4つの観点で審査する
  - P0 は4つの観点のどれで出ても止める
  - P1 は content-qa と wording-editor の分だけ止める。ファン・seo-marketer の P1 は助言として扱い、件数を PR コメントとダイジェストに記録する
  - 4つの役を別々に呼ばず、1回の審査が観点ごとに分けて結果を出す形でもよい。役と観点の表の対応は契約（docs/operation/content-pr-contract.md）に固定する
  - 本文の数値を出典（DB・分析結果・公式）と照合済み
  - 止まる指摘が出たら直して、その観点の審査を回し直す
  - 判断が要るもの（事業・法務・ブランドの表記、「競艇」の例外、誇大・的中率・回収率の表現、原稿の主張を変える改稿）は F に当たらず、ユーザーに回す
  - ただし記事の JSON の `metaTitle`・`metaDescription` の「競艇」は例外で、F で出してよい（オーナー決定 2026-10-20、`scripts/maintenance/verify-kyotei-wording.js` の例外1 と同じ扱い。関門は `scripts/content/content-pr-gate.json` の `kyoteiMetaAllowedKeys`）。本文・見出し・画面の title・description・tags・category の「競艇」は今までどおり F に当たらない。役所への営業の前に外す暫定の措置なので、F でマージした記事の PR 本文に「meta に競艇あり: <記事 id>」を書く（関門の結果の `metaKyotei` の id）
  - sns-hub（SNS 投稿）とは別の扱い。SNS 投稿の最終送信は引き続きユーザーの承認。例外（機械の検査が通れば自動で送るもの。全貌動画・/today の X 投稿・優勝戦の思考投稿 `finals_image`・数字で見たら `research_image`・/today の思考投稿 `today_thinking_image`・`today_thinking_reply`）の範囲と条件は `.claude/CLAUDE.md`「確認のバッチ化を標準運用にする」の例外が正本

- G. ユーザーが中身を直接決めた .claude の変更を、決定どおりに書いた PR（2026-10-13 ユーザー決定）。自動モード以外のセッションで書かれ、編集の許可をユーザーが直接出したもの。窓口が差分を読み、決定から外れた語・範囲が入っていないことを確かめ、CI が全部緑ならマージする。マージの承認を改めて取らない。外れていればユーザーに回す

段階0に当たらない PR のうち、画面の見せ方と数値の判断を伴うもの（BOA-271 を含む）だけをユーザー確認に残す。確認は下の「確認の出し方」の「朝と夜の2回にまとめる」に従い、1件ずつ出さない。.claude（G を除く）・CI・permission・本番 DB への書き込みを伴うものは従来どおり段階2。

段階0でマージしたら:
- ADR-0106 の切り替えの後（`vercel.json` の `git.deploymentEnabled.master` が false。それまではマージごとに出る）は、本番に出るのはマージの直後ではなく次の定時（JST 05:45・11:45・17:45 の約7分後、ADR-0106）。出た後に本番の該当ページを開き、表示とコンソールエラーを確かめる。崩れていたら git revert の PR を自己マージし、次の定時で出す（急ぐならオーナーに ADR-0106「手で出す」を頼む。Vercel の Instant Rollback は全体が壊れたときの非常手段に限る）
- 1日2回のダイジェスト（下の「確認の出し方」）に、変更前後のスクリーンショットつきで載せる
- F でマージした記事は、ダイジェストにタイトル・URL・4つのレビュー（content-qa・wording-editor・ファン・seo-marketer）の結果の要約を載せる
- ダイジェストで異議が出た種類は段階2に戻す（マージ前の抜き打ちの確認は、下の「確認の出し方」の「聞くのは重要なものだけ」に合わせてやめた）

### 段階1: 代理で決め、ダイジェストで事後に報告する

承認済みの新機能の細部の判断（列の数、表記、閾値、並び順など）で、後から取り消せるもの。

- 判定: ファンパネル（discussion-panel）の結論に、user-proxy-reviewer（`.claude/agents/user-proxy-reviewer.md`。ユーザーの過去の方針・却下理由だけを渡して「ユーザーならこれを差し戻すか」を判定する）の判定を重ねる。差し戻しの可能性が高ければ段階2に上げる
- 確定: ダイジェストに載せ、次のダイジェストまでにユーザーの異議が無ければ推奨どおりで確定（沈黙＝同意）
- 対象外（段階2）: データモデル、URL 構造、i18n の区分など取り消しにくいもの

### ファンの価値を先に聞く

ユーザーは「基本的にはボートレースファンの意見を尊重する」。見せ方・仕様の判断は、ユーザーに聞く前にファンにとっての価値を決める。

- ユーザーに判断を仰ぐ項目（段階1・2とも）には、ファンパネル（discussion-panel）の結論を必ず付ける。順は「価値の結論 → 案と規模 → 推奨」。費用・実装の楽さ・今の API で出せるかは、価値が同じ案どうしの比較として最後に置き、推奨の主な理由にしない
- **ファン4人の結論がそろい（割れた点が無い）、user-proxy-reviewer が「通る」と判定したら、窓口が推奨どおりに決めて、朝夜のダイジェストで事後に報告する**。段階2の項目でも、下の「それでもユーザーが決めるもの」以外はこれで決めてよい
- それでもユーザーが決めるもの: ファンの意見が割れたもの、ユーザーが過去に言ったことと違う結論、公開の判断（フラグ ON・公開日）、表示する数値の定義（集計・算出の定義）、新機能を作るかどうかと最初のモック、事業・法務・ブランドの表記、費用・外部への負荷、本番 DB の変更、.claude・CI・permission の変更
- ファンパネルは同じモデルのロールプレイなので、結論は仮説。決めたものも台帳に記録し、公開後の実データ（GA4 等）とユーザーの異議で見直す

### 段階2: ユーザーが決める

- 新機能を作るかどうかと最初のモック（承認したモック画像が段階0の基準になる）
- 事業・法務・ブランドの表記（「競艇」の例外、誇大表現、的中率・回収率。多言語版も）
- 外部への負荷・費用（公式サイトへの取得の頻度・期間、有料プラン）
- 本番 DB のスキーマ・RPC の変更とデータの削除（承認は GitHub Environments の1タップで行う。手順は `docs/operation/db-apply.md`。整うまでは従来どおりユーザーが SQL Editor で実行）
- 画面の見せ方と数値の判断を伴う変更（新しい数値・集計の表示を含む画面変更、BOA-271 の見せ方の判断を含む）
- 共通コンポーネント・ルーティング・URL 構造・i18n の区分の変更
- .claude（段階0の G を除く）・CI ゲート・permission の変更
- 段階0・1で異議が出た項目

### 台帳

判断の種類・推奨・ユーザーの回答（または段階0・1で決めたこと）・マージ後の fix の有無を、窓口の私的な置き場（リポジトリの外）の台帳に記録する。段階を下ろした判断が正しかったかを後から確かめるため。

### 確認の出し方


ユーザーが他のセッションを見に行かなくても判断できる形で出す。雛形は `merge-confirmation.md`（この skill と同じ置き場）。

- **オーナーに聞くのは重要なもの（費用・鍵とセキュリティ・本番での削除・ブランド・用語・画面の数値の定義・事業の判断）だけ。聞く前に、独立したレビュー（設計に関わっていないサブエージェント）を通し、指摘と対応を添えて出す。聞くまでもないものは進めて、後で報告する**（2026-10-18 ユーザー決定。作業の順番・別作業への切り出しは聞かない）

- PR ごとに次の3点を必ず書く
  - **あなたが確認すること**: 開く URL、押すタブや操作の手順、見るポイント。画面が変わらない PR なら「確認不要」と書き、判断が要る点（事業判断、仕様の選択）だけを挙げる
  - **私が確認済みのこと**: CI、レビューコメントの有無、実データや本番での確認結果、ファイルの重なり、マージ順
  - **判断材料**: 変更内容、残るリスク
- 判断を仰ぐ項目には「ファンの議論の結論（4人の要点・割れた点）」を付ける（上の「ファンの価値を先に聞く」）。付いていないものは出さない
- 「確認するなら」のような任意の書き方をしない。「確認すること: ○○／不要」と言い切る
- 確認は1件ずつ出さず、まとめて出す
- ユーザーへの確認とダイジェストは、朝と夜の2回にまとめて出す（至急の不具合を除く）。それ以外の時間は承認を待たずに次の作業へ進む
- ダイジェストの中身: 段階0でマージした画面変更（変更前後のスクリーンショット、戻し方）、段階1で決めたこと（異議が無ければ確定）、段階2の確認待ち
- 本番で実行する SQL は、PR 番号やファイル名を示すだけでは足りない。全文を1つのファイルにまとめ（実行順・期待値・確認用の SQL つき）、SendUserFile で渡す
