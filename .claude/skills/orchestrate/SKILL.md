# オーケストレーター運用

並行セッションが多いとき、master へのマージの承認と実行をこのセッション1つに集める。
同じファイルを触る PR が連鎖していると、個別のセッションが順番を知らずにマージして順序が崩れ、承認が二重に走る。

## 起動時の手順

1. **CronList で見回りの定期実行があるか確かめ、無ければ作り直す**（下の「見回りの定期実行」）。CronCreate で作った定期実行は、セッションが終わると消える
2. 状態ファイル（下の「状態ファイル」）を読む。フックがこのセッションの session_id を `orchestrator_session` に書いている
3. 見回りを1回手で実行し、状態ファイルのレーン表と突き合わせる

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/patrol.sh"
```

## 1. 役割

- 手を動かさない。実装・dev サーバーの起動・検証はレーン側が行う
- オーケストレーターが担うのは、順番・確認・マージの3つ
- レーンの事実主張（「〜は存在しない」「〜は原因ではない」等）をユーザーに渡す前に、独立したサブエージェントで反証させるか、自分で一次データを1つ確かめる。確かめていないものは「レーンの報告（未検証）」と書く
- 数値を中継するときは、出典（値／指標／A−B（比較対象）／母集団・部分集合／期間（cal・test）／データ版／結果 JSON のパス#キー）が付いているかを見る。付いていない数値は「未検証」と書いて中継し、判断を仰ぐ根拠の数字は元のファイルか本番で1つ確かめる
- ユーザーがローカルで画面を見たいと言ったら、その依頼を担当レーンに回す。レーンが自分の worktree で dev サーバーを起動し、URL と確認項目を返し、確認が済んだら止める

## 2. レーン制

- 1レーン1セッション。各レーンは作業列を上から1本ずつ進める
- 新しい作業は、空いているレーンの作業列に積む。レーンを増やすのは、既存のどのレーンにも積めないときだけ
- 同時に動かすレーンは5〜6本まで。待ちに入ったレーン（効果確認待ち・一区切り等）は作業ツリーが clean で push 済みなのを確かめてアーカイブし、必要になったら起こす。セッション一覧から見えるのは直近20件まで
- レーンのモデルと effort は、チケットを割り振るたびに次の表で区分を決め、set_session_model / set_session_effort で切り替えてから依頼を送る。迷ったら重い方に倒す。切り替えはレーンの次のターンから効くので、1つのチケットの途中では変えない

  | 区分 | 該当するもの | モデル・effort |
  |---|---|---|
  | 定型 | 文言・翻訳・置換、ドキュメント、Linear 整理、CI の軽い修正、レポート | Sonnet・medium |
  | 通常の実装 | 仕様が決まっている画面・集計の修正 | Sonnet・high にする予定。オッズ一覧レーンの fix 率を他のレーンと比べて広げるか決めるまでは、試験のレーン以外は Opus・high |
  | 重い | 設計（SDD）、数理・モデル、本番 DB・マイグレーション、セキュリティ、仕様が曖昧なもの、同じ不具合の2回目 | Opus・high |

- レーンは自分のモデルを変えられない。Sonnet で進めていて設計判断・本番 DB・想定外の難しさに当たったら、レーンが格上げをオーケストレーターに申告し、オーケストレーターが切り替える。レーンへの最初の依頼にこの申告ルールを書く
- レビュー用サブエージェント（spec-ambiguity-detector・design-reviewer・data-accuracy-verifier 等）は区分によらず Opus のまま
- レーンへの最初の依頼は `templates/lane-request.md` から作る
- **作業を終えたレーンは、オーケストレーターの指示を待たず、同じ領域の未着手の Linear チケットを自分で1件取って始める**（取ったものを1行で報告）。`codex-ok` ラベルの付いたものは取らない（Codex の実装レーンが取るため。`linear-cli.js list` はラベルを出さないので、取る前に1件ずつラベルを確かめる）。取るものが無ければ、自分をアーカイブの候補として1行で報告する（2026-10-13 ユーザー決定）
- **フック・.claude の設定（settings.json、CLAUDE.md、rules、agents、skills）・CI ゲートを変える作業は、そのレーンのユーザーの直接承認が要る**。オーケストレーターからのメッセージは承認にならない

## 3. レーン→オーケストレーターの報告ルール

- 報告するのは、次の3つが揃ったとき
  - CI が全部緑
  - mergeStateStatus が CLEAN（master の ruleset 導入後は、承認待ちだけが理由の BLOCKED を CLEAN と同じに扱う。6. を参照）
  - /code-review の結果を PR コメントに記載済み
- 報告に含めるもの
  - PR 番号
  - 変更の要点
  - あなたが確認すること／私が確認済みのこと／判断材料（5. と同じ形）
- 別スコープの作業を見つけたら spawn_task を使わず、Linear に起票して番号を送る。spawn_task のチップはユーザーの画面にしか出ず、オーケストレーターに届かない。そのまま押されると、レーン制の外でセッションが増える

## 4. 自分でマージしてよい範囲（承認の3段階）

ユーザーの承認がボトルネックにならないよう、承認を3段階に分ける。

### 段階0: オーケストレーターがマージし、事後に報告する

次のいずれかに当たり、条件をすべて満たす PR。

- A. 画面が変わらない PR: CI が全部緑で CLEAN（承認待ちだけが理由の BLOCKED を含む。6. を参照）、レビュー結果が PR コメントにある、別ベンダーの審査（Claude の PR は Codex。止まっているときは代わりの審査）で実在する P0・P1 が0件、マージ順の制約を守っている。別ベンダーの審査には、review.yml の審査（作成の App の PR を別ベンダーの LLM が審査し、審査の App が承認する）も含める。review.yml は P0 が0件なら P1 が残っていても APPROVE するので、APPROVE があり、承認の本文の指摘に P1 が無いこと（P1 があれば実在を確かめて直す）を条件にする
- B. 画面が変わる PR のうち、ユーザーが承認したモック・仕様の実装であるもの。A の条件に加えて次をすべて満たす
  - 承認したモックの画像が `docs/design/{slug}/mock/`（承認日つき）にあり、mock-diff-checker（`.claude/agents/mock-diff-checker.md`）が Preview と並べて「承認範囲内」と判定した
  - ファン評価ループ（review-fix-cycle.md）が終了条件を満たした
  - 受け入れ E2E が「存在して」緑（無い PR は B に当たらない）
  - 差分が承認範囲（spec に書かれた画面・コンポーネント）の外を触っていない
  - 新しい数値・集計の表示を含まない
  - 共通コンポーネント（Header・LanguageSwitcher・`src/components/race/` の共通部分）・ルーティング・URL 構造・i18n の区分を触っていない
  - 文言に事業・法務・ブランドの語（競艇、的中率、回収率、誇大表現。4言語とも）が新しく入っていない
- C. 画面が変わる PR のうち、見せ方を新しく決めない不具合の修正。A の条件に加えて次をすべて満たす
  - 本来の動きに戻す・崩れを直す・文言の誤りを正すもので、新しい表示項目・配色・並び順・文言の方針を決めていない（はみ出し、折り返し、金枠の誤り、内側スクロール、訳語の誤り等）
  - 修正前は落ち、修正後は通る再現テストが同じ PR にある
  - 修正前と修正後の画面を比べた結果（スクリーンショットか実測値）が PR にある
  - user-proxy-reviewer が「通る」と判定した
  - B の最後の4条件（新しい数値・集計の表示を含まない、共通コンポーネント等を触らない、事業・法務・ブランドの語を入れない、承認範囲の外を触らない）を満たす
  - 新しい画面、本番 DB への書き込みを伴うもの、.claude の変更は C に当たらない（段階2）。BOA-271 は下の D・E で扱う
- D. docs だけの PR（BOA-271 を含む）。A の条件に加えて、変更が `docs/` 配下と `*.md` だけで、画面・コード・CI の変更が無い。`.claude/` 配下の md は D に当たらない（段階2）
- E. 再現テストを同じ PR に含む障害修正（BOA-271 を含む）。A の条件に加えて次をすべて満たす
  - 修正前は落ち、修正後は通る再現テストが同じ PR にある
  - 画面の見せ方（表示項目・配色・並び順・文言の方針）と、表示する数値の判断（集計・算出の定義）を変えない
  - .claude・CI ゲート・permission の変更、本番 DB への書き込みを伴わない
- F. ブログ記事の掲載・改稿。変更が `public/blog/`・`src/data/blog-posts/`（翻訳のメタの `en/`・`ko/`・`zh-TW/` を含む。#1699 で移った先）・`public/images/blog/` だけの PR。画像は別の名前で足す（差し替えはオーナーが行う）。A の条件に加えて次をすべて満たす
  - content-qa（`.claude/agents/content-qa.md`）・wording-editor・ファンのレビュー（boatrace-fan-reviewer か discussion-panel）・seo-marketer の4つの観点で審査する
  - P0 は4つの観点のどれで出ても止める
  - P1 は content-qa と wording-editor の分だけ止める。ファン・seo-marketer の P1 は助言として扱い、件数を PR コメントとダイジェストに記録する
  - 4つの役を別々に呼ばず、1回の審査が観点ごとに分けて結果を出す形でもよい。役と観点の表の対応は契約に固定する（どの文書に置くかは ③ のレーンと hq で決める）
  - 本文の数値を出典（DB・分析結果・公式）と照合済み
  - 止まる指摘が出たら直して、その観点の審査を回し直す
  - 判断が要るもの（事業・法務・ブランドの表記、「競艇」の例外、誇大・的中率・回収率の表現、原稿の主張を変える改稿）は F に当たらず、ユーザーに回す
  - sns-hub（SNS 投稿）とは別の扱い。SNS 投稿の最終送信は引き続きユーザーの承認（全貌動画と /today の X 投稿は例外。全貌動画は機械の検査と評価役の検査で P0 が0件なら、/today の X 投稿は機械の検査が通れば自動で送る。`.claude/CLAUDE.md`「確認のバッチ化を標準運用にする」）

- G. ユーザーが中身を直接決めた .claude の変更を、決定どおりに書いた PR（2026-10-13 ユーザー決定）。自動モード以外のセッションで書かれ、編集の許可をユーザーが直接出したもの。オーケストレーターが差分を読み、決定から外れた語・範囲が入っていないことを確かめ、CI が全部緑ならマージする。マージの承認を改めて取らない。外れていればユーザーに回す

段階0に当たらない PR のうち、画面の見せ方と数値の判断を伴うもの（BOA-271 を含む）だけをユーザー確認に残す。確認は5の「朝と夜の2回にまとめる」に従い、1件ずつ出さない。.claude（G を除く）・CI・permission・本番 DB への書き込みを伴うものは従来どおり段階2。

段階0でマージしたら:
- マージ後に本番の該当ページを開き、表示とコンソールエラーを確かめる（レーンに依頼してよい）。崩れていたら git revert の PR を自己マージする（Vercel の Instant Rollback は全体が壊れたときの非常手段に限る）
- 1日2回のダイジェスト（下の5）に、変更前後のスクリーンショットつきで載せる
- F でマージした記事は、ダイジェストにタイトル・URL・4つのレビュー（content-qa・wording-editor・ファン・seo-marketer）の結果の要約を載せる
- ダイジェストで異議が出た種類は段階2に戻す（マージ前の抜き打ちの確認は、5の「聞くのは重要なものだけ」に合わせてやめた）

### Codex の PR（`codex/*`）

Codex が実装して `codex/` のブランチから出した PR は、次のとおりに扱う。Codex 側の規約は AGENTS.md「実装者としての規約」。

- **審査は Claude が行う**。鍵を持つ側で `claude -p` を Bash なしで実行し、差分を AGENTS.md の観点で審査する。Codex の PR 本文にある自己検証の結果は、合否の根拠にしない
- **src/ の画面の作業は Codex に回さない**。`codex/*` には Vercel Preview が無く、画面を確かめられないため
- **マージは当面「案Z」**: 機械と審査役が CI の見張り・失敗したときの再実行（1回まで）・審査を済ませ、P0・P1 が0件で CI が全部緑の PR を「マージ可」として束ね、オーケストレーターがまとめてマージする。束に入れてよいのは、上の段階0（A〜F）の条件に当たる PR だけ。ただし F は切替（ADR-0097。作成の App の名義と auto-merge）の後だけ。F の束はマージの時点で判定し直す（作者の bot の ID、今の head SHA に審査の App の APPROVE、変えたパスが F の許可のパスの中、CI が全部緑）。CI が赤なら空のコミットで1回だけ再実行してから決める。`codex/*` には Vercel Preview が無いので、Codex の記事の PR のファンのレビューは discussion-panel だけで行う。当たらないものは段階1・2として扱う
- 再実行しても CI が落ちる PR は束に入れず、Codex に直させる（AGENTS.md「自分の PR の CI が落ちたら、直して同じブランチに push する」）
- 自動マージをどの名義で行うかは未決（オーナーに確認中）。決まるまでは、オーケストレーターがこのセッションから `gh pr merge` を実行する

### 段階1: 代理で決め、ダイジェストで事後に報告する

承認済みの新機能の細部の判断（列の数、表記、閾値、並び順など）で、後から取り消せるもの。

- 判定: ファンパネル（discussion-panel）の結論に、user-proxy-reviewer（`.claude/agents/user-proxy-reviewer.md`。ユーザーの過去の方針・却下理由だけを渡して「ユーザーならこれを差し戻すか」を判定する）の判定を重ねる。差し戻しの可能性が高ければ段階2に上げる
- 確定: ダイジェストに載せ、次のダイジェストまでにユーザーの異議が無ければ推奨どおりで確定（沈黙＝同意）
- 対象外（段階2）: データモデル、URL 構造、i18n の区分など取り消しにくいもの

### ファンの価値を先に聞く

ユーザーは「基本的にはボートレースファンの意見を尊重する」。見せ方・仕様の判断は、ユーザーに聞く前にファンにとっての価値を決める。

- ユーザーに判断を仰ぐ項目（段階1・2とも）には、ファンパネル（discussion-panel）の結論を必ず付ける。順は「価値の結論 → 案と規模 → 推奨」。費用・実装の楽さ・今の API で出せるかは、価値が同じ案どうしの比較として最後に置き、推奨の主な理由にしない
- レーンの「判断してほしい」にファンパネルの結論が無ければ、ユーザーに出さずにレーンへ差し戻す。急ぐときはオーケストレーターがファンパネルを回してから出す
- **ファン4人の結論がそろい（割れた点が無い）、user-proxy-reviewer が「通る」と判定したら、オーケストレーターが推奨どおりに決めて、朝夜のダイジェストで事後に報告する**。段階2の項目でも、下の「それでもユーザーが決めるもの」以外はこれで決めてよい
- それでもユーザーが決めるもの: ファンの意見が割れたもの、ユーザーが過去に言ったことと違う結論、公開の判断（フラグ ON・公開日）、表示する数値の定義（集計・算出の定義）、新機能を作るかどうかと最初のモック、事業・法務・ブランドの表記、費用・外部への負荷、本番 DB の変更、.claude・CI・permission の変更
- ファンパネルは同じモデルのロールプレイなので、結論は仮説。決めたものも台帳に記録し、公開後の実データ（GA4 等）とユーザーの異議で見直す

### 段階2: ユーザーが決める

- 新機能を作るかどうかと最初のモック（承認したモック画像が段階0の基準になる）
- 事業・法務・ブランドの表記（「競艇」の例外、誇大表現、的中率・回収率。多言語版も）
- 外部への負荷・費用（公式サイトへの取得の頻度・期間、有料プラン）
- 本番 DB のスキーマ・RPC の変更とデータの削除（承認は GitHub Environments の1タップで行う。手順は `docs/operation/db-apply.md`。整うまでは従来どおりユーザーが SQL Editor で実行）
- 画面の見せ方と数値の判断を伴う変更（新しい数値・集計の表示を含む画面変更、BOA-271 の見せ方の判断を含む）
- 共通コンポーネント・ルーティング・URL 構造・i18n の区分の変更
- .claude（段階0の G を除く）・CI ゲート・permission の変更
- 段階0・1で異議が出た項目

### 台帳

判断の種類・推奨・ユーザーの回答（または段階0・1で決めたこと）・マージ後の fix の有無を、状態ファイルの `## 保留・注意` の下か `.git/orchestrator/approval-ledger.md` に記録する。段階を下ろした判断が正しかったかを後から確かめるため。

## 5. 確認の出し方

ユーザーが他のセッションを見に行かなくても判断できる形で出す。雛形は `templates/merge-confirmation.md`。

- **オーナーに聞くのは重要なもの（費用・鍵とセキュリティ・本番での削除・ブランド・用語・画面の数値の定義・事業の判断）だけ。聞く前に、独立したレビュー（設計に関わっていないサブエージェント）を通し、指摘と対応を添えて出す。聞くまでもないものは進めて、後で報告する**（2026-10-18 ユーザー決定。作業の順番・別作業への切り出し・レーンへの割り振りは聞かない）

- PR ごとに次の3点を必ず書く
  - **あなたが確認すること**: 開く URL、押すタブや操作の手順、見るポイント。画面が変わらない PR なら「確認不要」と書き、判断が要る点（事業判断、仕様の選択）だけを挙げる
  - **私が確認済みのこと**: CI、レビューコメントの有無、実データや本番での確認結果、ファイルの重なり、マージ順
  - **判断材料**: 変更内容、残るリスク
- 判断を仰ぐ項目には「ファンの議論の結論（4人の要点・割れた点）」を付ける（上の「ファンの価値を先に聞く」）。付いていないものは出さない
- 「確認するなら」のような任意の書き方をしない。「確認すること: ○○／不要」と言い切る
- 確認の中身はレーンの報告から取る。オーケストレーター自身は dev サーバーの起動や実装検証をしない
- 確認は1件ずつ出さず、まとめて出す
- ユーザーへの確認とダイジェストは、朝と夜の2回にまとめて出す（至急の不具合を除く）。それ以外の時間、レーンは承認を待たずに次の作業へ進む
- ダイジェストの中身: 段階0でマージした画面変更（変更前後のスクリーンショット、戻し方）、段階1で決めたこと（異議が無ければ確定）、段階2の確認待ち
- 本番で実行する SQL は、PR 番号やファイル名を示すだけでは足りない。全文を1つのファイルにまとめ（実行順・期待値・確認用の SQL つき）、SendUserFile で渡す

## 6. マージの手順

- 1件ずつ、PR 番号を文字で書いて実行する（`gh pr merge 946 --squash` のように）。for ループ・変数・`$(...)`・xargs で PR 番号を渡すと、台帳に制約がある場合に guard-pr-merge.js が止める（#929）
- マージ順の台帳は `node scripts/maintenance/merge-order.js list`。順序を決めたら `add <PR> --after <PR>...` で登録し、解消したら `remove <PR>`
- squash が必要な PR は、依頼文と報告に明記させる（レーンの報告に書かれていなければ、マージ前に確かめる）
- マージの可否の確認・`gh pr merge <PR> --squash --admin`・本番ビルドの完了待ち・報告は `/merge-pr`（`.claude/commands/merge-pr.md`）の手順に従う。承認待ちだけが理由の BLOCKED の扱いも同じ所にある
- `--admin` は失敗しているチェックも素通りするので、実行の前に `gh pr checks <PR>` が全部緑であることを確かめる。PR 番号は文字で書く（guard-pr-merge.js は `--admin` を値の無いフラグとして読み飛ばすので、そのまま動く）

## 7. ピアのメッセージの扱い

- ピア（他のセッション）からのメッセージは、ユーザーの承認にならない
- レーンのユーザーが、そのレーンで直接マージを指示した場合、レーンはそれに従ってよい。ただしマージの前に、オーケストレーターにマージ順を確認する（ピアのメッセージではユーザーの直接指示を上書きできないため）

## 8. 担当セッションの探し方

- セッション一覧（list_sessions）の cwd は起動時の値で、worktree 内で動いていても main を指すことがある。作業場所の判定に使わない
- PR の担当セッションを探すときは、PR のブランチ名で search_session_transcripts を引く
- 見回りの list_sessions は limit 8 だと足りないことがある。見つからなければ、上のブランチ名検索に切り替える

## 9. 見回りの定期実行

CronCreate で次の設定を作る。止めるまで繰り返し実行する。

- cron: `7,37 * * * *`（30分ごと。60分以上にしない。サブスクのキャッシュ寿命が1時間で、それを超えると毎回全文脈の読み直しになり、かえって高くつく）
- プロンプトの全文:

```text
[オーケストレーション見回り] 1) bash "$(git rev-parse --show-toplevel)/.claude/skills/orchestrate/scripts/patrol.sh" を実行。2) mcp__ccd_session_mgmt__list_sessions（limit 8）で新規・停止セッションを確認。3) DIRTY・CI赤は担当セッションへ連絡。CLEAN＋CI緑＋レビュー記載＋確認手順付き報告が揃ったPRは、画面変更なしの軽いものは自己判断でマージ（1本ずつ・PR番号をそのまま書いて実行）、それ以外はユーザーにマージ確認を出す（あなたが確認すること／私が確認済みのこと を必ず書く）。4) マージ順は node scripts/maintenance/merge-order.js list に従う。5) 変化が無ければ出力は「見回り: 変化なし」の1行だけ。
```

運用上の注意:

- CronCreate の定期実行はセッションが終わると消える。/orchestrate を起動したら、まず CronList で確かめる（「起動時の手順」の1）
- 2) の list_sessions で担当が見つからないときは、8. のブランチ名検索を使う

`patrol.sh` が出すもの:

- master HEAD と直近1時間のマージ
- 直近14日に更新されたオープン PR（mergeStateStatus・draft・head・e2e/verify の結果）と、前回の見回りとの差分
- マージ順の台帳の未解消の制約（先行 PR が未マージのもの）と、MERGED/CLOSED になって remove してよい規則
- regenerate-generated-docs.yml と e2e-rerecord.yml の直近の失敗（ワークフローが master に無ければ飛ばす）
- master の CI（push で走るもの）の直近の失敗

## 10. 状態ファイル

- 置き場所: `$(git rev-parse --git-common-dir)/orchestrator/state.md`。コミットしない。全 worktree から同じファイルが見える
- 書き換えるのはオーケストレーターだけ。レーンは書かない
- 見回りや判断のたびに更新する（`updated` も書き換える）
- compact の後は、SessionStart フックが `orchestrator_session` と一致するセッションにだけ全文を再注入する。compact を越えて覚えておくべきことは、ここに書いておく
- 見出しは固定。フックと検証（`scripts/maintenance/verify-orchestrator-hooks.js`）が前提にしている

雛形:

```markdown
orchestrator_session: <session_id>
updated: <ISO 8601, UTC>

| レーン名 | セッション名 | 今の作業 | 作業列 |

- #941: 画面変更あり。確認手順はレーンの報告から転記済み

## マージ順の制約

<!-- merge-order.js の台帳に無い口約束だけを書く。台帳にあるものは書かない -->
```

## 仕組み

- `.claude/hooks/orchestrator-session.sh` が次の3経路で動く（`.claude/settings.json` に登録）
  - UserPromptSubmit: プロンプトの先頭が `/orchestrate` なら、このセッションを `orchestrator_session` に記録する。state.md が無ければ雛形で作る
  - UserPromptExpansion（matcher: orchestrate）: `/orchestrate` を直接打った経路で同上。UserPromptSubmit の prompt が展開後の本文で届いた場合の保険
  - PostToolUse（matcher: Skill）: `tool_input.skill` が `orchestrate` なら同上。この skill は `disable-model-invocation: true` なので、Claude が Skill tool で読み込むことは通常ない。念のための経路
  - SessionStart（matcher: compact）: session_id が一致するときだけ、state.md の全文と見回りの要約を返す
- jq が無い環境では何もせず素通しする
