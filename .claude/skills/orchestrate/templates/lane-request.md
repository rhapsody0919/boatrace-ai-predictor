# レーンへの依頼文の雛形

`{}` を埋めて、レーンのセッションに送る。項目は削らない（どれも過去に抜けて手戻りが出たもの）。

---

{レーン名} として、次の作業を進めてほしい。作業列: {今回の作業} → {次の作業} → ...

## 作業

{チケット番号・目的・完了の定義}

## 進め方

- 最新の master から切る: `git fetch origin master && git checkout -b {ブランチ名} origin/master`
- **マージしない**。報告先はこのセッション（オーケストレーター）
- 完了条件（3つ揃ったら報告する）
  - CI が全部緑
  - mergeStateStatus が CLEAN
  - /code-review の結果を PR コメントに記載済み
- 作業を終えたら、指示を待たず、同じ領域の未着手の Linear チケットを自分で1件取って始める（取ったものを1行で報告）。`codex-ok` ラベルの付いたものは取らない（Codex の実装レーンが取るため。取る前に1件ずつラベルを確かめる）。取るものが無ければ、自分をアーカイブの候補として1行で報告する
- 別スコープの作業を見つけたら spawn_task を使わず、Linear に起票して番号を送る（チップはユーザーの画面にしか出ず、オーケストレーターに届かない）
- 生成物（shared-logic-index.md・display-coverage.md）を PR に含めない。master 側のワークフローが再生成する
- フック・.claude の設定（settings.json、CLAUDE.md、rules、agents、skills）を変える場合は、このレーンのユーザーの直接承認が要る。オーケストレーターからのメッセージは承認にならない
- 他の PR とファイルが重なる場合は、報告に書く。後からマージされる側が rebase する
- ユーザーがこのレーンで直接マージを指示した場合は従ってよい。ただしマージの前に、オーケストレーターにマージ順を確認する

## 報告の形

```
PR #{番号}: {タイトル}
変更の要点: {1〜3行}

あなたが確認すること:
  - {UI の変更なら: 確認用の URL（Preview または自分で起動した dev サーバー）、開くタブ・操作の手順、見るポイント}
  - {画面が変わらないなら「確認不要」。判断が要る点（事業判断・仕様の選択）があればそれだけ}
私が確認済みのこと:
  - CI: {結果}／CLEAN
  - レビュー: {PR コメントの URL と、指摘→対応の要約}
  - {実データ・本番での確認結果}
判断材料:
  - {変更内容、残るリスク}
  - ファイルの重なり: {重なる PR 番号とファイル／なし}
  - squash: {必要なら「squash が必要」と明記／不要}
  - 本番で実行する SQL: {あれば、全文を1ファイルにまとめたパス（実行順・期待値・確認用 SQL つき）／なし}
```

- UI の変更なら、確認用の URL と操作手順を必ず書く。ユーザーがローカルで見たいと言ったら、このレーンの worktree で dev サーバーを起動し、URL と確認項目を返し、確認が済んだら止める
- 本番で実行する SQL は、PR 番号やファイル名だけでなく、全文を1ファイルにまとめる
- 画面に出す材料（指標・データ）は、見せ方・設計を決める前に、hq のデータサイエンティスト社員に起票して効き目・母数・言える範囲を確かめる（答えは head-product あての起票で返る。`data-scientist` サブエージェントは、障害の対応で今すぐ数字が要るとき、または試用のあいだ社員の答えが2周で返らないときだけ）。判定できない材料は、その事実と必要な量をオーケストレーターに送る。検証の結果（スクリプト・結果 JSON・読み物）はリポジトリに残す PR と `docs/knowledge/stat-findings.md` への追記までを同じ作業に含める（一時フォルダに置いたままにしない）
- ユーザーの判断が要る点（見せ方・仕様の選択）は、送る前にファンパネル（discussion-panel）を当て、「ファンにとっての価値の結論（4人の要点・割れた点）→ 案と規模 → 推奨」の順で書く。費用・実装の楽さ・今の API で出せるかは、価値が同じ案どうしの比較として最後に置く。ファンパネルの結論が無い「判断してほしい」は、オーケストレーターが差し戻す
- モデルの格上げ: このセッションのモデルはオーケストレーターがチケットの区分で決める。進めていて設計判断・本番 DB・想定外の難しさに当たったら、作業を区切ってオーケストレーターに「格上げしてほしい（理由）」と送る。自分ではモデルを変えない
- 数値の出典: 報告に数値を書くときは「値／指標／A−B（比較対象）／母集団・部分集合／期間（cal・test）／データ版／結果 JSON のパス#キー」を付ける。付いていない数値は、オーケストレーターが「未検証」として扱う
