## 1. 要件と決定（ユーザー承認: 2026-09-20）

## 3. 公開時刻の実測（U7）

「展示公開の何分前にファイルが現れるか」を、当日のファイルの HTTP `Last-Modified`（ファイルが置かれた時刻）で実測した。**当日のファイルの `Last-Modified` は、そのレースの公開時刻に当たる**（過去日のファイルは、毎晩 00:07〜00:12 JST頃に再生成されて時刻が変わるため、公開時刻としては使えない）。あわせて、DBの `exhibition_data.created_at`（boatrace.jp の展示を、こちらが最初に保存した時刻。WS2）と比べた。

|---|---|---|

| 13.0〜15.3分前 | 11 | 各会場の1R・6R（13.0〜15.3）、ポーリングした住之江8R・丸亀8R（ともに14.8） |

### 3.3 スロット（期限・窓）の決定

| 項目 | 値 | 根拠 |
|---|---|---|
| 期限（`offsets`） | **発走の8分前**（`-8`）の1本 | 公開は最小9.9分前。8分前なら、実測（n=21）の全てで公開済み（最小の余裕1.9分）。早く取りに行っても、公開前は403を返すだけで、リクエストが増えるだけ |
| 許容幅（`graceMin`） | **30分**（発走の22分後まで） | 3回目の取得（発走の約5分後）を含み、`expired` にならず打ち切りまで進める |
| 再試行 | 403（未公開）は、発走までの時間に応じて間隔を延ばし、**最大3回**（発走の約8分前・約3分前・約5分後）。その後は打ち切り（`skipped_not_target`。データ無し） | 403は「まだ無い」か「無い」（三国・津の12Rは、終了後も403のまま）。負荷を抑えるため、待たずに打ち切る |
| 他のエラー（HTTP 5xx・429/503・ネットワーク・解析不能） | 5分後に再試行（`retrySec`）、許容幅（30分）まで | 共通ラッパの既定 |

公開の検知遅延（公開から取得まで）は、設計上、**2〜21分**（公開が発走の10分前なら2分後、29分前なら21分後）。展示データを予測の入力に使うのは発走前の数十分で、日次の全データ収集（第1弾）としては十分と判断した。より早く（公開直後に）取りたい場合は、期限を早め、403の再試行を増やす（負荷とのトレードオフ。§5）。

## 4. 403の扱い（最重要の設計事項）

BOATCASTは「存在しない＝403のHTMLエラーページ」を返す。共有の `politeFetch`（`scripts/lib/scrapeJobs/politeFetch.js`）は 429/503 だけを失敗として数え、403は成功として扱い、ブレーカーの `recordSuccess` に渡す。そのため、

- (a)「未配置（正常）」と「アクセス拒否（異常）」を区別できない
- (b) ブレーカーの半開中（429/503で開いた後の、最初の1件）に403が来ると、ブレーカーを誤って閉じる

**共有の `politeFetch`・ブレーカーは変更しない**（別PRの領域）。ジョブ内で、次のとおり扱う（`scripts/lib/boatcast/boatcastClient.js`・`oritenJob.js`）。

| 論点 | 対策 |
|---|---|
| (i) 未配置とアクセス拒否の区別 | **各tickの先頭で、既知の存在ファイル（カナリア: `bc_mst_12`）を1回取る**。200かつ `YYYYMMDD` ならば正常。**カナリアが403・失敗・本文不正なら、その回のデータの取得を全て止め**（リクエストはカナリアの1件のみ）、スロットは `error` で再試行し（データ無しとして打ち切らない）、`last_report.alerts` に `canary_failed` を出す。カナリアが正常なときの403だけを「未公開または公開されないレース」として扱う |
| (b) 半開のブレーカー | 各tickの最初のリクエストが常にカナリア（必ず存在するファイル）になるため、半開の試行がデータの403（未配置）で誤って閉じることがない |
| (ii) 403の再試行の上限 | 1レースあたり最大3回（発走の約8分前・約3分前・約5分後）。間隔は5分・8分と延ばす。3回目以降は打ち切り（`skipped_not_target`）。打ち切りは、窓内取得率の分母に入らず、`expired` の通知にもならない |
| (iii) 常時403の会場 | 公開マップで対象外（`excluded`）にし、**予定表のスロットを作らず、取得しない**（江戸川）。会場の一部のレースだけが403になるのは通常起こりうる（津・三国の12R）が、**ある会場で当日の完了レースの半分以上・3件以上が打ち切りになったら、`no_data:{会場}` を通知する**（会場が非公開にした・マップが古い、の検知） |
| ホスト | ブレーカーのキーは `host:race.boatcast.jp`（boatrace.jp のブレーカーと独立）。BOATCASTの429・503が boatrace.jp の取得を止めることはない |

## 5. 取得先への負荷の見積り（ADR-0067の要件。逐次・2.2秒以上）

調査文書の「日次約150リクエスト」は、再試行を数えていない。再試行・カナリアを含めて見積り直した。

前提: 1日に開催する会場は約12〜13会場（江戸川を除く対象会場で約11〜13）で、対象レースは1日約130〜150（12R×約11〜12会場）。

| 項目 | 通常（推定） | 最悪（全レースが最大回数） |
|---|---|---|
| オリジナル展示: 1回目（発走8分前） | 約150 | 150 |
| 同: 公開が8分前より遅れたレースの再試行（2回目） | 約20（15%と仮定。実測では最小9.9分前で、遅れは少ない見込み） | 150 |
| 同: データ無しで打ち切るレースの3回目（発走の約5分後） | 約20（対象レースの約5%が公開されないと仮定。三国・津の12R等） | 150 |
| カナリア（tickごとに1回。スロットが有るtickのみ） | 約120（発走時刻が同じ分に集まるため、tick数は対象レースより少ない） | 約300（上限。全ての取得が別の分に散った場合） |
| モーター使用開始日（bc_mst） | 24（06:30に1回。一部失敗した日は08:00に再試行で最大48） | 48 |
| **合計** | **約330リクエスト/日** | **約800リクエスト/日（上限）** |

- リクエストは**逐次**で、間隔は**2.2秒以上**（調査時の2秒に余裕）。最悪でも約800×2.2秒＝約30分/日の間隔制御で済む。boatrace.jp の1日約12,000リクエストに対して小さい
- 429・503は `politeFetch` が指数バックオフ＋ジッターで最大2回再試行し、ブレーカー（`host:race.boatcast.jp`）が開いたら、そのホストの取得を止める。ブレーカーが開いている間は、スロットを取らずに終える
- 過去分のバックフィルは第1弾の対象外。実施する場合は、約44,700リクエスト（1日約2,000上限・夜間・複数夜に分割）。同じ `processOritenRace` を、手動CLIで呼ぶ（[plan.md §6](./plan.md)）

## 6. 保存と書き込みの見積り

| テーブル | 内容 | 1日の書き込み | 行サイズ・増加 |
|---|---|---|---|
| `race_original_exhibition`（レース単位） | 計測状態・項目名・内容のハッシュ・公開時刻（`source_last_modified`）・取得時刻 | 約150行（新規） | 約150バイト/行、約22KB/日 |
| `race_original_exhibition_values`（艇×項目の縦持ち） | `race_id`・`boat_number`・`kind`（項目名）・`value`（秒） | 約2,400行（18行×約135レース。新規） | 約70バイト/行（主キーの索引を含めて約100バイト）、約0.25MB/日、約90MB/年 |
| `venue_motor_start_dates` | `venue_code`・`start_date`（新しい組だけ追記） | 新しい日付が現れた日のみ（年に数回） | 数十行 |

- 変更の無い行は書かない（`upsertChangedRows`。再取得は内容のハッシュで読み飛ばす）。行は新規のみで、UPDATEはほぼ発生しない（dead tupleの増加は小さい）。WAL・Disk IO予算への影響は、`pit_reports` と同程度（1日数千行の追加のみ）
- 縦持ちの理由: 会場ごとに項目が異なる（3項目・2項目・半周ラップ）。項目名は位置ではなくラベルで解釈し、未知のラベルは取りこぼさず保存して `parse_anomaly` として通知する。データ洗い出しの案（[optimal-scraping-design.md](../scraping-vercel-consolidation/optimal-scraping-design.md)、固定4列の横持ち）より柔軟で、行数は約4倍になる（約90MB/年）

## 7. 完了の定義（.claude/rules/data-acquisition.md）

各データ項目のA・B・Cは、[tasks.md T4b-19](../scraping-vercel-consolidation/tasks.md) に3行ずつ書く。要点:

- **A（件数）**: 期待件数は **公開マップで対象の会場のレース数 × 艇数 × 項目数**（分母は事前凍結のマップと `races`・`race_entries` から算出し、BOATCASTの観測から作らない）。除外は、中止・順延（`cancellation_status='confirmed'`）、欠場艇（`race_entries.is_absent`）、計測不可（`measure_status=2`）、403の打ち切り（`scrape_slots.outcome='skipped_not_target'`）、対象外会場（江戸川）を、**件数付きで報告する**。取得開始日以降のみ（過去分のバックフィルは第1弾の対象外）
- **B（タイミング）**: 公開時刻（`source_last_modified`）が窓のどこに入るかの分布（公開の何分前にファイルが現れたか）と、公開から検知までの遅延（`created_at − source_last_modified`）を、取得時刻列から実測する。**窓内取得率（中心±3分）の代わりの基準は、tasks.mdに提案として書く（ユーザーの承認まで確定しない）**
- **C（継続監視）**: `scrape-monitor`（`registry.js` に載せれば自動）に加えて、**0件・カナリア失敗・parse_anomalyの増加を `last_report.alerts` に出す**（[plan.md §5](./plan.md)）
