# マイクロフト予想（Transformer・選手履歴系列）設計

ホームズ予想の最後の未実装タブ。`docs/proposal/holmes-model-methods-survey.md` §4 優先度D
として「データ蓄積待ちで据え置き」としていたものを、データ実測にもとづき着手した。

## 1. 据え置き判断の見直し

据え置きの根拠は「データ約7ヶ月・選手あたり履歴が浅い」だった。実測すると前提が変わっている。

| 実測項目 | 値 |
|---|---|
| 利用可能レース総数 | 143,137レース（2024-01-01〜2026-08-11、公式アーカイブのバックフィル込み） |
| 直近90日のアクティブ選手数 | 1,617名 |
| その選手あたり出走数 | 中央値 513走 / 下位25% 435走 / 下位10% 302走 |
| 系列長32での履歴充足 | 中央値32（満杯）、満杯率 54.5%、履歴ゼロ率 5.9% |

系列長32〜64のトークン列はほぼ全選手で満たせる。据え置き理由は解消した。

## 2. 狙い — 集計で失われる情報を取る

ワトソン（LambdaRank）の入力は `win_rate` や `recent_win_rate` のような集計済みスカラー。
集計した瞬間に落ちる情報を、系列のまま読むことで拾う。

1. **調子の波の形状** — 「勝率6.0で下降中」と「勝率6.0で上昇中」は同じ特徴量になる
2. **モーター慣れ** — 同じ節の中で日を追うごとに展示タイムが改善するパターン
3. **文脈つきの成績** — 「強い相手に外枠で僅差の敗け」と「弱い相手にインで惨敗」の区別
4. **当地・条件適性** — 特定会場に来ると毎回STが決まる、といった条件付き傾向

## 3. アーキテクチャ

```
[艇i の過去32走]                                        ×6艇（重み共有）
  各走 = 1トークン
     │
     ▼ ① フォームエンコーダ  scripts/ml/mycroft_model.py: FormEncoder
  Transformer Encoder 2層 / d=64 / 4ヘッド / pre-norm / dropout 0.2
  → attention pooling → フォーム埋め込み e_i（64次元）
     │                     ＋ pooling 重み = UI「マイクロフトの記憶」の根拠
     ▼ ② レース相互作用ブロック  Mycroft.inter_attn
  [e_i ⊕ 静的特徴量36項目の射影] に set-attention（6艇は集合＝順序不変）
  ── 「強い選手が誰に沈められるか」を捉える層
     ▼ ③ ヘッド
  艇ごとのスコア s_i → Plackett-Luce 損失（1〜3着の逐次尤度）
  ＋ 補助損失 0.3×（フォーム埋め込み単独での着順4クラス分類）
```

パラメータ数は意図的に小さく保つ（14万レースに対する過剰適合の回避）。
正則化は dropout 0.2 / weight decay 1e-2 / 勾配クリップ 1.0 / cal 損失での early stopping。

### トークンの中身（`mycroft_sequences.py`）

| 種別 | 特徴量 |
|---|---|
| カテゴリ埋め込み | 着順コード（1〜3着/着外/不明）、進入コース、会場、レースグレード |
| 連続値（絶対量） | 本番ST、展示タイムのレース内順位、展示STのレース内順位、モーター2連率、**相手強度**（他5艇の平均勝率）、展示欠損フラグ |
| 連続値（対象レースとの関係） | log1p(経過日数)、**同節フラグ**（同会場かつ7日以内＝同じモーターを使っている走） |
| 位置 | 新しさ順の位置埋め込み（0が直近走） |

## 4. リーク防止（最重要）

系列モデルは過去参照の実装を誤ると容易に未来情報が漏れる。以下を実装で保証し、
`python scripts/ml/mycroft_sequences.py` の self-test で毎回検証する。

- **同日レースを除外**: `race_id` の辞書順は会場コード優先で時刻順ではないため、
  同日レースを含めると同日の後続レース情報が混入しうる。トークンは対象より
  **厳密に過去の日付**のみ
- **選手の同一性**: `racer_id` 欠損行（backfill の47,644行）は欠損値 -1 に揃うため、
  素朴に実装すると「架空の同一選手」として互いの履歴を共有してしまう。
  該当行は**履歴なし**（空系列）とし、静的特徴量のみで推論させる
- **標準化統計は train のみ**から計算する（静的特徴量・トークン連続値とも）
- self-test の検証項目: 同日/未来トークンの不在、別選手トークンの不在、
  `racer_id` 不明行に履歴が付いていないこと、日付整数化のスパン一致

> 実装中に踏んだ罠: `pd.to_datetime(...).astype("int64") // 86400e9` は pandas の
> バージョンにより datetime64 の単位が ns/us/ms と揺れるため日数計算が壊れる
> （全レースが同一日付に潰れ、履歴の94%が消失した）。Timedelta の `.dt.days` を使う。

## 5. 評価プロトコル

ワトソンと**同一の time_split（70/15/15）・同一指標**で比較する。

| 指標 | 意味 |
|---|---|
| top1的中率 / 勝者logloss / AUC / NDCG@3 | 予測精度（ワトソン・ポアロと横並び比較） |
| **ΔR²** | Benter結合 − オッズ単独。市場への上乗せ情報があるか（シャーロック +0.060、ワトソン +0.059） |
| **アンサンブル増分** | ワトソンとの対数線形結合（重みは cal でフィット）が、ワトソン単独を test で上回るか |

**アンサンブル増分がこの設計の本質的な検定**である。系列情報が本当に新しい情報を
含むなら、単独精度がワトソンと同等でもアンサンブルは改善するはず。逆にここが
ゼロなら、系列は集計済みスカラーと同じ情報しか持っていないことになる。

### 出荷ゲート

- ①単独でワトソン同等以上、または ②アンサンブル増分が有意 — どちらかを満たせばβ版
- どちらも満たさない場合も「実測はこうだった」と表示してα版で出す
  （プロジェクトの正直運用。アドラー・ワトソンと同じ扱い）

## 5.5 実装中に踏んだ罠と、その診断（重要）

初版はゲートを大きく割り込み（top1 36.7% / アンサンブル増分 ±0.0000）、
4段階の修正で最終的に通した。**「情報を足したのに悪化する」ときは、
情報の価値ではなく実装・評価設計を疑う**という教訓が全て。

| 版 | 修正 | top1 | ΔR² | アンサンブル増分 |
|---|---|---|---|---|
| v1 | 初版 | 36.7% | +0.011 | +0.0000 |
| v2 | 静的カテゴリを埋め込み化 | 43.8% | +0.020 | −0.0002 |
| v3 | フォーム埋め込みに LayerNorm | 44.8% | +0.022 | +0.0000 |
| v4 | warmup / weight decay 分離 / 補助損失 0.3→0.1 | 45.8% | +0.023 | −0.0004 |
| **v5** | **cal 分割の品質是正** | **56.6%** | **+0.058** | **+0.0018** |

**① 静的カテゴリを連続値で入れていた（v2で修正）**
`boat_number` はワトソンの特徴量重要度で首位（2位の3.6倍）だが、標準化した
連続値を線形層に入れると単調な効果しか表現できない。LightGBM が
カテゴリ扱いする列（`F.CATEGORICAL_COLS`）は埋め込みで受ける。

**② フォーム埋め込みが未正規化だった（v3で修正）**
`norm_first=True` の TransformerEncoder は最終正規化が入らない。実測で
pooling 後の L2 ノルムが 2.24 と、LayerNorm 済みの静的埋め込み（7.64）と
桁が揃っていなかった。融合前に両分岐のスケールを揃える。

**③ アブレーションで初めて位置が判った**
`--ablation static-only` が top1 55.1% を出したのに完全版が 43.8% で、
「系列を足すと悪化する」ことが確定。どちらの分岐が原因かは、
片方を殺して測らないと分からない。`--ablation` は診断用に残してある。

**④ 真犯人: cal 分割がデータ品質の断層に重なっていた（v5で修正）**
`F.time_split` の cal 期間（2025-10-20〜2026-03-15）は、公式アーカイブの
バックフィルと Supabase 蓄積分の境目に当たり、品質が崩壊していた。

| 分割 | 展示あり | racer_id欠損 | 本番ST履歴 |
|---|---|---|---|
| train | 100% | 0% | 99.2% |
| **cal（旧）** | **31.4%** | **36.8%** | **48.3%** |
| test | 95.3% | 0% | 99.8% |

この cal で早期終了の判断と温度校正をしていたため、学習にも本番にも
似ていない領域に最適化していた（cal top1 51% に対し test 44.8% という
説明のつかない乖離が症状）。test 期間の先頭30%を cal として切り出し、
cal と test の品質を揃えた（`quality_matched_split`）ことで
cal top1 が 51%→56.7% に回復し、test も 45.8%→56.6% になった。

> **ワトソン・ポアロへの示唆**: 両者も同じ `F.time_split` を使っており、
> 早期終了と確率校正を同じ壊れた cal で行っている。GBDT は頑健なため
> 精度自体は出ているが、確率校正はズレている可能性が高い。
> 別タスクとして検証する価値がある。

## 6. 配信

Python モデルのためブラウザ内推論は不可。ワトソンで確立した経路をそのまま使う。

| 要素 | 内容 |
|---|---|
| 学習 | `scripts/ml/train_mycroft.py`（PyTorch）。初回はローカル学習→Storage アップロード |
| 推論 | `scripts/ml/predict_mycroft.py`。attention 上位の過去レースを根拠として出力 |
| 日次バッチ | `scripts/daily/generate-mycroft-predictions.js`（`generate-poirot.yml` に相乗り、1日3回） |
| DB | `mycroft_predictions`（migration 030）。`attention_evidence` に「重視した過去走」top3 |
| UI | `HolmesMycroft.jsx`。ランキング＋**「マイクロフトの記憶」**（どの過去レースを見たか） |
| 依存 | `torch`（CPU wheel）。ローカルは Python 3.12 の `.venv-torch`（3.14 は torch 未対応） |

週次学習の CI 化は、推論の安定稼働を確認してから第2段階として判断する
（Actions の2コアCPUでの学習時間を実測してから）。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| 過学習（14万レースはNNには小さめ） | 小型モデル・強い正則化・補助損失・cal早期終了 |
| 履歴の薄い艇（新人・racer_id不明） | 空系列を学習可能な既定埋め込み `empty_emb` で表現し、静的特徴量側に依存させる |
| 展示タイム欠損（Supabase期 57.5%） | 欠損フラグをトークンに含め、学習時から欠損を見せる（推論時と同分布） |
| 学習/推論の系列構築差異 | `mycroft_sequences.py` に集約し、標準化パラメータもチェックポイントに保存 |
| MPS/CPU の数値差 | `--device` で切替可能。保存物はデバイス非依存 |
