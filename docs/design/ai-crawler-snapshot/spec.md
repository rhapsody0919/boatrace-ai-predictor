# AIクローラー向け静的スナップショット配信 - 仕様書

**種別**: データ・分析機能寄り（画面変更なし。UIは既存のまま、配信経路のみ追加するインフラ機能）
**対応チケット**: なし（本会話内の集客戦略議論から起票）

## 背景

Search Consoleで報告された「CLS 0.25超（モバイル）」の調査・修正（[PR#467](https://github.com/rhapsody0919/boatrace-ai-predictor/pull/467)）を機に、集客戦略の議論に発展した。

boatAIはSSR・プリレンダリングの無い純粋なクライアントサイドSPA（`docs/reference/seo-architecture-constraints.md`）。GooglebotはJSレンダリングに対応しているため通常のSEOには支障が無いが、GPTBot・ClaudeBot・PerplexityBot等の**AIクローラーの多くはJSを実行しない**ため、初期HTML（空のシェル）しか読めず、ページの実コンテンツ（ブログ本文・分析ツールの説明等）がAI回答エンジンに引用されない状態にある。同じ問題はFacebook等のOGP/Twitterカード用ボットにも存在し、`docs/reference/seo-architecture-constraints.md`で「Vercel Edge Functionでのボット判定＋静的HTML返却、またはSSG化が必要」と課題認識だけが記録されていた（未実装）。

`robots.txt`はAIボットを明示的にブロックしておらず（`User-agent: * / Allow: /`）、クロール許可自体は問題ない。課題は純粋にレンダリングの可視性。

フルSSR/フレームワーク移行（Next.js化等）は`AppRouter.jsx`のルート数（27+）×4言語＋動的ページを考えると数週間規模の大規模リアーキテクチャで、既存の「SSR移行はPhase3まで見送り」判断（[[boa_growth_strategy_decision_2026_08]]）とも矛盾する。一方、現状GA4データ（`data/analysis/i18n-demand/report-2026-08-26.json`）ではAI経由のリファラルは0件で、投資対効果を裏付けるデータも無い。

そのため本機能は、フルSSRではなく**対象ページを限定した静的スナップショットを、非JS実行ボットにのみ返す**という、投資規模を一桁小さくした代替案として設計する。技術検証後、GA4で実際の効果を計測してから本格投資（SSR等）を検討する2段階アプローチの第1段階。

## 機能要件

### FR1（P0）: 対象ページのビルド時静的スナップショット生成
`npm run build`のパイプラインに、対象ページ（下記スコープ参照）をPlaywrightでレンダリングし、完成後のHTMLを静的ファイルとして保存するステップを追加する。

**受入基準**: `npm run build`実行後、対象ページ数分のスナップショットHTMLファイルが生成される。

### FR2（P0）: 対象ボットへのスナップショット配信
AIクローラー（GPTBot・ClaudeBot・PerplexityBot・Google-Extended等）およびSNSシェア用ボット（facebookexternalhit・Twitterbot等）がリクエストした場合、対応するスナップショットHTMLを返す。それ以外（通常ユーザー・Googlebot）には従来通りSPAのindex.htmlを返す。

**受入基準**: 対象ボットのUser-Agentを付与したリクエストで対象ページを取得すると、レスポンスHTMLに記事本文・タイトル・meta description等の実コンテンツが含まれる（JSレンダリング無しで確認できる）。それ以外のUser-Agentでは従来通りの挙動（SPAのindex.html）が変わらない。

### FR3（P1）: 技術検証手順の確立
`curl`等でボットUAを偽装し、スナップショットが正しく返ることを機械的に確認できる検証コマンド・スクリプトを用意する。

**受入基準**: リポジトリ内のスクリプト（またはドキュメント化されたcurlコマンド）で、デプロイ後に対象ページ全件を検証できる。

## スコープ

### やること
- 対象ページ: ブログ記事全件（日本語のみ）＋ `/winning-technique`（分析ツールの機能説明部分のみ）
- 対象ボット: AIクローラー（GPTBot/ClaudeBot/PerplexityBot/Google-Extended等）＋ SNSシェア用ボット（facebookexternalhit/Twitterbot等）
- スナップショットはビルド時に静的生成し、デプロイ成果物に含める
- 技術検証（curl等でのボットUA偽装確認）
- 効果測定（GA4のReferral/AI Assistantチャネルを1〜2週間定点観測、閾値は決めず定性的に「動きがあるか」を見る）

### やらないこと
- フルSSR/フレームワーク移行（Next.js化等）は対象外。本機能はその代替の限定的措置
- 英語・繁體中文・韓国語のスナップショット（v1は日本語のみ。効果を見てから多言語展開を検討）
- ホームページ（`/`）のスナップショット化（本日開催中のレース等、更新頻度が高いデータをビルド時静的生成すると古い情報を配信するリスクがあるため見送り）
- `/winning-technique`内の実レースデータに依存する分析タブ・結果部分のスナップショット化（機能説明部分のみ対象。データ鮮度の問題を回避）
- 会場ビジターガイド・レース詳細ページ等、上記以外のページのスナップショット化
- スナップショット配信のリアルタイム更新（オンデマンド生成・キャッシュ管理の仕組みは導入しない。次回ビルド・デプロイまで更新されない前提）

## 非機能要件

- 通常ユーザー・Googlebotへの挙動・パフォーマンスに影響を与えない（ボットUA判定でのみ分岐する経路であること）
- ビルド時間の増加がデプロイパイプラインに支障が出ない範囲に収まること（目安: 対象ページ十数件程度なので数十秒〜1、2分程度の増加を許容範囲とする）
- 生成したスナップショットに、実際に公開されているページと矛盾する内容（古いモデル名等）が含まれないこと。既存の「ブログ記事の公開前品質チェック」ルールの対象に、スナップショット生成物も含める

## 制約・前提

- 新規の重い依存関係追加は避ける。スナップショット生成にはPlaywrightを使う（`e2e/`で既にdevDependencyとして導入済み、追加インストール不要）
- ボット判定・配信の実装方式（Vercel Edge MiddlewareかServerless Functionか、`vercel.json`のrewriteとの整合等）はVercel Edge Runtimeのファイルシステムアクセス制約（`fs`が使えない）を踏まえて`/step2`で設計する
- 既存の`middleware.js`（SNSハブ管理画面のBasic認証、`matcher: ["/admin/sns-hub", ...]`）と共存させる必要がある。Vercelは1リポジトリにつき`middleware.js`を1つしか置けないため、matcherの拡張または統合が必要
- データ源: ブログ記事は`public/blog/*.md`、`/winning-technique`はReactコンポーネントの静的説明部分。いずれも既存ページをPlaywrightでレンダリングした結果をそのまま使う（新規のSupabaseクエリ・スクレイピングは不要）
- 「競艇」使用禁止等、既存の用語ルール（`.claude/rules/code-style.md`）に従う（スナップショットは既存ページの複製のため新規文言はほぼ発生しない想定）
- 法的制約: 該当なし（既存の公開コンテンツを別経路で配信するのみで、新たな情報開示・投票関連の論点は発生しない）

| `middleware.js`のmatcher統合方法 | SNSハブ管理画面のBasic認証と、ボット判定ロジックをどう共存させるか | `/step2`で決定。別セッションのSNSハブ作業との調整が必要な場合はその時点で確認 |

| 多言語展開の可否・時期 | 日本語版の効果を見てから判断 | 本機能リリース後、GA4計測結果を踏まえて再検討 |
