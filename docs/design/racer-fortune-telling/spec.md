# 選手占い機能（占術検証フェーズ） 仕様書

## 種別

**データ・分析機能**（画面変更なし。バッチスクリプト・分析ロジックのみ）

本機能は2段階で進める。本spec.mdは**Step1（占術による検証）のみ**を対象とする。検証結果を見てから、サイトUI化（選手ページへの組み込み等）を別チケットとして`/step1-screens`以降で改めて設計する。

- Step1（本チケット）: 生年月日データ取得 + 4占術のロジック実装 + 実績データとの相関検証 + レポート化
- Step2以降（別チケット、未着手）: 検証で有効と判断された占術のサイトUI実装 → 知り合いの占い師によるレビュー → SNS展開

対応Linearチケット: なし（新規起票は本spec確定後）

## 背景・目的

選手の生年月日を使った「その日の調子占い」を、単なるエンタメではなく実際のレース結果と突き合わせて統計的に検証してから採用する。龍神レーダーは「AIで40項目以上のデータを分析、的中率を実測公開」がブランドの核であり、占いを検証なしに出すとブランド毀損リスクがある。検証プロセス自体を、この信頼性と整合させる。

## 機能要件

### 1. 選手生年月日データの取得基盤（優先度: 高）

- `race_entries.racer_id`（全国共通登録番号、既存データで取得済み）を使い、boatrace.jp公式サイトの選手検索ページ（`racersearch/profile?toban={racer_id}`）から生年月日をスクレイピングする
- 取得結果を新規テーブル（仮称 `racer_profiles`、`racer_id`一意）に保存する。正確なカラム設計はStep2（システム設計）で決定
- 対象: 過去出走実績がある全選手（`race_entries`に登場する全racer_id）
- 除外: 生年月日が公式サイトに存在しない選手、取得失敗した選手、引退済み選手
- 受入基準: 対象選手について生年月日の取得を実行し、成功・失敗（除外）の内訳を件数で報告できる。具体的な目標成功率は未確定（下記「未確定事項」参照）

### 2. 4占術の計算ロジック実装（優先度: 高）

対象占術は以下の4種（ユーザー指定）:

| 占術 | 計算方式 |
|---|---|
| 西洋占星術 | 太陽星座ベースのトランジット計算（出生チャートとの重ね合わせではなく、太陽星座で代用） |
| 四柱推命 | 日柱までの三柱推命（時柱は出生時刻不明のため省略） |
| 九星気学 | 本命星 + 年盤 |
| 六星占術 | 運気リズム |

- 出生時刻は公式サイトに存在しないため、全占術とも「出生時刻不要な代用方式」で計算する（上記の通り）
- 各占術は、`(racer_id, 対象日)`を入力すると、その日の「調子スコア」を返す共通インターフェースを持つこと
- スコアの段階・数値表現の形式は実装時に決定してよい（例: 5段階、0-100スコア等）が、4占術間で比較検証できる形式にする
- 受入基準:
  - 同じ入力に対して常に同じ結果を返す（決定論的・再現性がある）
  - 各占術について、手計算または既存の占いツール（オンライン等）での検証サンプル数件と結果が一致する

### 3. 実績データとの相関検証（優先度: 高）

- 対象データ: 除外基準を満たさない全選手・全期間の `race_results`（着順）・`race_start_timings`（ST・フライング・出遅れ）
- **着順データの制約（2026-08-24実データ確認）**: `race_results`には1〜3着の艇番号（`rank1`/`rank2`/`rank3`）のみが記録されており、4〜6着の着順データは存在しない。そのため着順は連続値ではなく「複勝圏内（1〜3着）か否か」の二値として扱う
- 検証方法:
  - 着順: 各占術の「その日の調子スコア」を説明変数、「複勝圏内か否か」を目的変数としたロジスティック回帰、またはスコア区分ごとの複勝率の群間比較（カイ二乗検定等）で統計的に検証する
  - ST: 従来通り連続値（`start_timing`）として相関係数・p値で検証する
- 受入基準: 4占術それぞれについて、（着順の二値検証結果 + STとの相関）とサンプル数を含む検証結果を出力する。有効性の解釈（統計的に有意か）はClaudeが提案するが、「占術として採用するか」の最終判断はユーザーが行う

### 4. 検証結果レポート（優先度: 中）

- 4占術を横並びで比較できる形式でまとめ、`data/analysis/`配下に保存する
- 受入基準: ユーザーが1回読めば、どの占術が有意/有意でないかを判断できる形式になっている

## スコープ

### やること

- 生年月日データの取得（スクレイピング）とDB保存
- 4占術（西洋占星術・四柱推命・九星気学・六星占術）の計算ロジック実装
- 実績データ（着順・ST）との相関の統計的検証
- 検証結果レポートの作成

### やらないこと

- サイトUI実装（選手ページ・専用ページ等）— 別チケット（Step2以降）で扱う
- SNSコンテンツ化 — 占い師レビュー後の別スコープ
- 出生時刻の個別調査・取得（インタビュー記事等からの追加リサーチ）— 今回はスコープ外。将来必要になれば別途検討
- 占い師によるロジック監修 — Step1完了後の別ステップ
- リアルタイム計算・API化 — 今回はバッチ・分析スクリプトとして実行する。常時稼働のエンドポイントは作らない

## 非機能要件

なし（UI・SEO要件は本フェーズの対象外。バッチ・分析スクリプトのみのため）

補足: データ取得（スクレイピング）は既存のスクレイピングスクリプト（`scripts/maintenance/backfill-racer-ids.js`等）と同様のレート制限・User-Agent配慮を踏襲する。

## 制約・前提

- **データソース**: boatrace.jp公式サイト（`racer_id`の取得と同一サイトで、既存スクリプトでの利用実績あり）
- **既存コンポーネント再利用**: 該当なし（UI変更なし）
- **法的・倫理的配慮**: 実在選手の生年月日を用いて「占う」コンテンツを最終的に公開する際は、「娯楽目的であり実際の成績を保証しない」旨の注記を必須とする方針（本フェーズでは公開物自体は作らないため、方針の記録のみ。実装はStep2以降のUI/SNSチケットで行う）
- **用語ルール**: 「競艇」使用禁止（スクリプト・ドキュメント内も「ボートレース」表記、`.claude/rules/code-style.md`準拠）
- **DBスキーマの現状（2026-08-24実データ確認済み）**: `scripts/db/SCHEMA_DETAIL.md`は記載が古く、現行テーブルが未反映（要更新、未着手）。`racers`テーブルは存在せず選手マスタは無い。`race_entries`は`racer_id`(number)・`player_name`・`grade`・`age`・`win_rate`等を持つが生年月日・支部・出身地は無い。`race_start_timings`は`race_id`/`boat_number`/`start_timing`/`is_flying`/`is_late_start`。`race_results`は`rank1`〜`rank3`（1〜3着艇番号）のみで4〜6着データは無い（上記「3. 実績データとの相関検証」に反映済み）。Supabase MCPは`SUPABASE_ACCESS_TOKEN`失効中で使えないが、`scripts/lib/supabaseClient.js`（service role key）での直接クエリで代替確認できることを確認済み

| 生年月日取得の目標成功率 | 具体的な数値目標（例: 90%以上）は未設定 | 実際にスクレイピングを実行し実測値を見てから、Step3/Step4実装時に妥当性を判断 |
