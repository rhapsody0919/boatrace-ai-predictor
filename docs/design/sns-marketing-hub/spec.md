# SNSマーケティングハブ Phase 1: 承認・多言語化・投稿橋渡し基盤

**種別**: UI機能（管理画面新規追加）
**対応Linearチケット**: なし

## 背景・最終ゴール

boat-ai.jp（龍神レーダー）への集客・認知・SNSフォロワー/エンゲージメントの継続的な獲得を、「AIが投稿内容を考え動画を作りAIがレビューし、実際に投稿し（人間）、AIがエンゲージメントや集客状況を調査し、AIが競合アカウント等の動向も調査し、AIが戦略・投稿ネタづくりに活かす」というPDCAサイクルで高品質に回すことが目的。人間の介在は「本当に必要な判断」（内容承認、プラットフォーム側の投稿操作の一部）に絞り、かつ自分以外の人間（将来のアルバイト等）でも運用できる状態を目指す。

このspecは上記全体構想のうち**Phase 1（管理画面・承認フロー・多言語化・投稿橋渡しの基盤）**を対象とする。Phase 2（PDCAループ本体：戦略考案・競合調査・計測の自動反映）、Phase 3（YouTube新規展開・英語以外の多言語フル展開）は別specとする。

## 機能要件

| # | 要件 | 優先度 | 受入基準 |
|---|---|---|---|
| 1 | 下書き一覧・詳細表示 | 高 | 管理画面に生成済みの投稿下書き（動画・キャプション・意図/ペルソナ背景・対象プラットフォーム・言語・提案日時・リスク警告の有無）が一覧表示される。動画はページ内でネイティブ再生でき、別途ダウンロードや外部ツールを要しない |
| 2 | タップでの承認/一部修正/作り直し | 高 | 各下書きに対し「承認」「一部修正（定型理由＋自由記述）」「全部作り直し」の3アクションをワンタップで選べる |
| 3 | 修正指摘・作り直し要求の自動再生成 | 高 | 「一部修正」「全部作り直し」を選ぶと、対応するRoutineのAPIトリガーが修正内容付きで起動され、人間が再度チャットで指示し直す必要なく新しい下書きが生成される |
| 4 | 承認単位は1本ごと | 高 | 複数本をまとめて承認する一括承認ボタンは実装しない |
| 5 | リスク自動チェック結果の表示 | 高 | 既知のルール違反パターン（ギャンブル連想表現、廃止済みモデル名、「競艇」表記等の用語ルール違反）を機械的に検出し、該当する下書きに警告バッジ・該当箇所を表示する。警告があっても承認はブロックしない（第三者の判断に委ねる）。検出ルールは単一の機械可読ファイル（JSON等）で一元管理し、生成Routineのプロンプトと自動チェックの両方が同じファイルを参照する（プロンプト内の文章とチェックロジックが別々に更新されて食い違うことを防ぐため） |
| 6 | 承認後の英語版自動生成 | 高 | 日本語版が承認されると、人間の再確認なしに英語版（ナレーション・字幕・キャプション）が自動生成され、下書き一覧に追加される |
| 7 | 投稿実行への直接導線（PC） | 中 | 承認済みの下書きについて、管理画面に「動画ダウンロード」「キャプション＋ハッシュタグのコピー」ボタンと、各プラットフォームの投稿画面への直接リンクを表示する。Xはキャプション事前入力（`x.com/intent/post?text=...`）、TikTok/YouTubeは各アップロード画面への固定リンク。人間はリンク先を自分の（既にログイン済みの）ブラウザで開き、動画添付から即時投稿/予約投稿までを自分の判断で行う。Claude Codeの生きたセッション・Chrome in Claudeはいずれも不要 |
| 7b | 投稿実行への直接導線（iOS） | 中 | iOS Safariで管理画面を開いた場合、Web Share API（`navigator.share`）対応ブラウザでは共有ボタンを提供し、端末にインストール済みのTikTok/X/YouTubeアプリへ動画を直接渡せるようにする。API非対応時は通常のダウンロードリンクにフォールバックする。Android対応は現時点でスコープ外（まずiOSのみを想定） |
| 8 | 投稿後のステータス反映 | 中 | 投稿完了後、下書きのステータスを「投稿済み」に更新できる |
| 9 | TikTokエンゲージメント指標の手動入力 | 低 | TikTokの投稿について、再生数・いいね数等を管理画面から手動入力できる。保存形式は「指標名・値・取得日時・取得方法（手動/API）」という共通フォーマットとし、Phase 2で追加するYouTube/XのAPI自動取得指標とも同じ器で扱えるようにする |
| 10 | 承認待ち発生時のSlack通知（バッチ単位） | 中 | Routineの1回の生成実行（週次バッチ・当日ネタとも）ごとに、既存のSlack Webhook（`.github/workflows/slack-notify-pr.yml`と同じ`SLACK_WEBHOOK_URL`）経由で1通の通知が送信される（「今週分◯本が準備できました」等）。下書き1本ごとに個別通知は送らない（週次バッチで十数本が同時生成された際の通知過多を防ぐため） |
| 11 | Basic認証によるアクセス制御 | 高 | 管理画面全体にBasic認証がかかっており、認証情報を知らない第三者はアクセスできない。承認権限自体は第三者（将来のアルバイト等）にも付与できる想定 |
| 12 | 承認者のタップ選択記録 | 中 | 承認・修正指摘・作り直しの操作時に、承認者をタップで選択して記録する（自由入力は不可）。選択肢はSupabase上の簡易マスタで管理し、初期状態は「本人」のみ。将来アルバイト等を追加する際は選択肢を追加するだけでよい |
| 13 | 却下された下書きのアーカイブ | 中 | 「全部作り直し」により不採用となった旧バージョンの下書きは`archived`ステータスとし、ReviewTab/ReadyToPostTab/PostedTabの一覧には表示しない（ゴチャつき防止）。完全削除はしない（Phase 2の学習材料として保持するため、要件14参照） |
| 14 | 修正・作り直し履歴の追記保存 | 高 | 「一部修正」「全部作り直し」が行われた際、既存の下書きレコードを上書きせず、旧バージョンを保持したまま新バージョンを追加登録する（親子関係で紐付け）。旧バージョンは要件13により`archived`となり一覧からは隠れるが、データとしては残り続ける |
| 15 | 動画バイナリの定期軽量化 | 中 | 投稿済み（`posted`）の動画ファイルは投稿から30日、却下・アーカイブ済み（`archived`）の動画ファイルは7日を経過したら、Supabase Storage上のファイルを低圧縮・低画質の軽量版に置き換えるRoutineを新設する。**完全削除はしない**（デザイン・構成の視覚的な振り返り・改善検討にはメタデータだけでは代替できないため、2026-08-27の議論で方針転換）。軽量版は「見て振り返る」用途に十分な画質を保ちつつ元ファイルより大幅に小さいサイズとし、長期的に保持する。DB上のメタデータ（キャプション・意図/ペルソナ背景・リスクチェック結果等）・カバー画像/サムネは元から削除・圧縮の対象外で永続保持する |

## スコープ

### やる
- 上記機能要件1〜11
- Supabaseへの新規テーブル追加（下書き管理・承認履歴・リスクチェック結果・テンプレートバリアントレジストリ）
- Supabase Storageへの動画ファイル保存・署名付きURLでの配信
- 週次バッチ生成（月曜、定型枠）・当日ネタ生成（日次、当日開催レース依存の型）を行うClaude Code Routineの新規構築
- 動画バイナリの定期軽量化（完全削除はしない）を行うClaude Code Routineの新規構築（要件15）
- ブランド/既知ルール違反の自動チェックロジック
- X・TikTokの投稿実行は、管理画面が提供する直接リンク（PC: ダウンロード+プラットフォーム画面へのリンク、iOS: Web Share API経由の共有）を起点に、人間が自分のブラウザ・アプリで各プラットフォームのネイティブ投稿/予約機能（X: 予約投稿、TikTok: TikTok Studio予約）を使う運用への橋渡し

### やらない（今回スコープ外）
- 承認後・投稿前の「取り消し」操作（一度承認したら最終判断として扱う。今は不要と判断、必要になれば別途追加する）

### やらない（Phase 2以降）
- エンゲージメント指標のYouTube/X API自動取得
- 競合アカウント調査の自動化
- 戦略・改善案の自動立案・次サイクルへの反映（PDCAのCheck/Act本格実装）
- X・YouTubeの投稿実行自体のAPI自動化（Phase 1では人間+ネイティブ予約機能を使う。API化はPhase 1の運用が安定してから検討）
- 英語以外の多言語展開（中国語簡体/繁体・韓国語・スペイン語）
- YouTubeへの新規展開（チャンネル未開設）
- mulmocastの採用（調査の結果、不採用と結論済み。LICENSE不在によるライセンス不透明さ、TTS/翻訳コストの優位性の無さ、独自ワークフローエンジンへの依存増、字幕タイミング精度の低さが理由。既存Remotion基盤内でLLM翻訳・TTS APIを直接呼び出す方針とする）

## 非機能要件

- **コスト**: 新規の月額固定費追加を極力避ける。SupabaseはPro契約済みのため動画ストレージ追加コストはほぼ発生しない。Claude Code Routineは既存のClaude Code購読に含まれる
- **モバイル対応**: 管理画面はスマホ（まずiOS Safariを想定、Androidは現時点でスコープ外）の通常ブラウザからでも動画再生・承認操作・投稿導線（要件7b）が問題なくできること（リモートデスクトップ越しの視認性問題を解消することが導入目的の一つのため）
- **既存機能への非干渉**: 既存の`/admin/rules`等、他の管理画面ページの挙動・ルーティングに影響を与えない

## 制約・前提

- **投稿の最終実行操作（動画添付・投稿/予約ボタンのクリック）は常に人間が、管理画面からのリンクを起点に自分自身の（既にログイン済みの）ブラウザ・アプリ上で行う**。Claude Code Routine・Chrome in Claudeはこの工程に一切関与しない（Routineは承認待ちで一時停止できずChrome in Claudeへのアクセスも無いため代行不可、かつ人間が自分のブラウザ/アプリで操作する設計であればそもそも代行の必要自体がない）
- **承認自体もRoutineでは完結できない**。Routineは承認待ちで一時停止する機能がないため、承認は必ず管理画面という非同期の別チャネルで行う
- **運用データ（下書き・承認履歴・リスクチェック結果）はgit管理下に置かず、Supabaseのテーブル・Storageに保存する**。理由: boatAIには「全ての変更はPR経由で行う」という不変のルールがあり、Routineが生成物をgit（`claude/`prefixブランチ）にpushする形だとPRレビュー待ちが発生し自律ループが成立しないため。アプリのコード・ドキュメント変更は引き続きPR経由、日々の運用データはSupabase、と役割を分離する
- **既存コンポーネント再利用**: `src/pages/admin/AdminRules.jsx`のタブ構成パターンを参考にする（`.claude/rules/component-reuse.md`準拠）
- **用語ルール**: 「競艇」使用禁止等、`.claude/rules/code-style.md`準拠。リスク自動チェックの検出対象に含める
- **法的制約**: 追加の特別な制約はなし（自社プロモーションであり賭博勧誘ではない）。ただしTikTok/Xの各プラットフォームガイドライン（ギャンブル関連規制、`docs/operation/tiktok-posting-operations.md`のE節参照）に抵触する表現の検出をリスク自動チェックに含める
- **言語・プラットフォームを決め打ちのカラムにしない**: 下書きデータは「1下書き×1言語×1プラットフォーム＝1レコード」という可変長の構造にする（`language: 'ja' | 'en'`のような固定カラムにしない）。Phase 3で中国語・韓国語・スペイン語やYouTubeが増えた際も、テーブル構造の変更なしに対応できるようにするため（2026-08-27合意）
- **テンプレートバリアント（デザイン改善・A/Bテスト対応）**: 下書きレコードに「使用したコンポジション・デザインバリアント」を記録し、Supabaseに型ごとの現行バリアント一覧（有効/無効フラグ付き）を持つ軽量なレジストリを設ける。同じ型で複数バリアントを並行運用しPhase 2のエンゲージメント計測で比較できるようにするため（2026-08-27合意）。ただし**バリアントの追加・切り替え（レジストリの更新）はRoutineが判断できるが、Remotionコンポジション自体のビジュアル変更は引き続き人間のPRレビューを経る**。AIが自律的に見た目を変更して自動マージすることはない
- **既存ドキュメントとの関係**: `docs/operation/sns-marketing-strategy.md`・`x-operations-playbook.md`・`tiktok-posting-operations.md`・`sns-video-producer-prompt.md`・`sns-viral-copywriter-prompt.md`に蓄積された運用ノウハウ・禁止パターンは、Routineのプロンプト設計時に引き継ぐ
- **Routine環境でのRemotionレンダリングには2つの追加設定が必須**（2026-08-27、one-off検証で確認済み）:
  1. `ffmpeg`は環境にプリインストールされていないため、Routineの環境設定（セットアップスクリプト）で`apt-get install -y ffmpeg`相当の導入が必要
  2. Remotion標準の「自前でヘッドレスChromeをダウンロードする」動作は、クラウド環境のネットワーク許可リストで`remotion.media`がブロックされているため失敗する。環境にプリインストール済みのPlaywright用Chromiumヘッドレスシェル（検証時のパス: `/opt/pw-browsers/chromium_headless_shell-*/chrome-linux/headless_shell`）を`remotion.config.mjs`の`Config.setBrowserExecutable(...)`で明示的に指定することで解決する（`remotion.media`をネットワーク許可リストに追加する代替案もあるが、外部ダウンロードへの依存を避けられるプリインストール品の指定の方が望ましい）
  なお`sns-video-studio/remotion/`はこのspec検討中に発覚した通り一度もgit管理下になかったため、PR #407でソースコード（`src/`・`public/`・`audio-build/`・`package.json`）のみをコミット済み（`out/`・`node_modules/`は`.gitignore`で除外）
