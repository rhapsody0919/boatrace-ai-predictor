# 全レース関連データ取得・タイミング最適化 spec

種別: データ・分析機能（画面・UIは対象外、スクレイピング基盤・データ取得ロジックのみ）
対応チケット: なし（本specは複数の個別Linearチケットの親として機能する）
対応調査: [docs/proposal/scraping-full-coverage/data-inventory-2026-09-15.md](../../proposal/scraping-full-coverage/data-inventory-2026-09-15.md)（棚卸しマップ、本specの一次情報源）

## 背景・目的

「取得できる全てのレース関連データを取得したい。現状は取得できるデータが取れていないし、取得タイミングも最適化されていない」というユーザー方針のもと、中央ポータル（boatrace.jp）・24会場個別公式サイト・（比較対象としての）ボートレース日和を横断調査し、約20件のデータギャップと1件の実行基盤上の問題（GitHub Actionsのconcurrency構造、[BOA-313](https://linear.app/boat-ai/issue/BOA-313)で他セッションが対応中）を発見した。本specはこれらを統合し、データの見せ方（UI）は完全に対象外として、**取得範囲の網羅化と取得タイミングの最適化のみ**を扱う。

## スコープ判断（2026-09-15ユーザー確認済み）

- **対象範囲**: 中央ポータル由来・24会場個別サイト由来を**一括**でカバーする（分割しない）
- **アーキテクチャ方針**: [BOA-313](https://linear.app/boat-ai/issue/BOA-313)（GitHub Actions→Vercel Functions移行）のパターンを前提として拡張する。BOA-313自体のアーキテクチャ再設計・Phase 2/3（結果・オッズ）の実装遂行は他セッションの担当であり、本specはそこに新規データを乗せる設計のみを行う
- **優先順位**: ユーザー指示により、予測・信頼性への影響が大きいと判断した順に自動設定（下記FR参照）

## 機能要件

各要件は「タイミング分類」（[data-inventory-2026-09-15.md](../../proposal/scraping-full-coverage/data-inventory-2026-09-15.md)のT1〜T5）を明記する。

### FR-1: レース特記事項ページの取得（優先度: 高）

`race/information`（会場・日付単位）から「事故・内規違反・減点」「モーター・ボート変更」「欠場・帰郷」の3区分を取得する。対応チケット: [BOA-318](https://linear.app/boat-ai/issue/BOA-318) [BOA-319](https://linear.app/boat-ai/issue/BOA-319) [BOA-320](https://linear.app/boat-ai/issue/BOA-320)。タイミング分類: T2（当日随時更新）。

**受入基準**: 実際に通知がある日を1件以上見つけ、3区分それぞれのHTML構造・表記パターンを特定できている。3区分を共通の「特記事項」テーブルに保存し、会場・日付・区分・対象選手（分かる場合）を引ける。

### FR-2: 選手期別成績ページの取得（優先度: 高）

`data/racersearch/season?toban=`から能力指数・フライング回数・出遅れ回数（選手責任）・期別集計値を取得する。対応チケット: [BOA-321](https://linear.app/boat-ai/issue/BOA-321)。タイミング分類: T5（低頻度・半年更新）。

**受入基準**: 全選手（約1,600人）分を巡回できる。能力指数がDBに保存され、自社集計値（勝率・2連対率等）との差分検証が1件以上完了している。フライング回数から「F休み期間」を自社計算できるか（新規スクレイピング不要にできるか）の検証結果が記録されている。

### FR-3: 今節成績（節内の日別進捗）の取得（優先度: 高）

racelistページの「今節成績」相当を取得する。対応チケット: [BOA-291](https://linear.app/boat-ai/issue/BOA-291)（[BOA-220](https://linear.app/boat-ai/issue/BOA-220)の今節得点率とスコープ統合）。タイミング分類: **混合**（過去日分はT4、当日分はT2）。

**受入基準**: 過去日分と当日分を分離した設計になっている。当日分の更新はBOA-313のVercel Functionsパターンに乗せる（レガシーGitHub Actionsオーケストレーターに素朴追加しない）。[BOA-289](https://linear.app/boat-ai/issue/BOA-289)で実装済みの「前走成績」（直近1走）との重複範囲が整理されている。

### FR-4: オッズ全券種の取得（優先度: 中）

3連複（全通り）・2連単・2連複・拡連複を取得する。対応チケット: [BOA-314](https://linear.app/boat-ai/issue/BOA-314)。タイミング分類: T1（発走直前ウィンドウ）。

**受入基準**: `scrape-odds.js`の既存パーサー（`parseTrioAll`等）を再利用し、二重実装を避けている。BOA-313 Phase 3（オッズのVercel Functions移行）と同じ実行基盤に乗る設計になっている（Phase 3完了前に着手する場合は移行時の手戻りが最小になる設計）。

### FR-5: racer_profiles自動更新化（優先度: 中）

対応チケット: [BOA-322](https://linear.app/boat-ai/issue/BOA-322)。タイミング分類: T5。

**受入基準**: 手動実行不要になり、新規登録選手が一定期間内（要plan.mdで確定）に自動反映される。FR-2（選手期別成績）と同じ選手一覧巡回処理に統合できるか検討済み。

### FR-6: 会場個別公式サイト（24会場）のデータ取得基盤構築（優先度: 中）

進入コース別選手成績（[BOA-293](https://linear.app/boat-ai/issue/BOA-293)、最重要）・水面特性等（[BOA-294](https://linear.app/boat-ai/issue/BOA-294)）・潮汐（[BOA-295](https://linear.app/boat-ai/issue/BOA-295)）・会場レイアウト変更履歴（[BOA-296](https://linear.app/boat-ai/issue/BOA-296)）を取得する。タイミング分類: 主にT4〜T5、BOA-294の一部項目はT1〜T2の可能性あり要個別確認。

**受入基準**: 24会場のCMSベンダー分類（`/modules/`系共通CMS群とレガシー静的HTML/ASP群）が完了し、テンプレート共通化できる会場グループが特定されている。BOA-293（12会場で個別選手データ確認済み）から着手し、最低1会場で実データ取得が確認できている。**各会場サイトの利用規約（ToS）本文を実装着手前に確認する**（robots.txtは全24会場で確認済み・禁止なし、ToS本文は未確認のまま残っている既知の課題）。

### FR-7: 残存する個別ギャップの解消（優先度: 低）

[BOA-288](https://linear.app/boat-ai/issue/BOA-288)（racelistの静的体重）・[BOA-290](https://linear.app/boat-ai/issue/BOA-290)（展示スタート表のコース列）・[BOA-266](https://linear.app/boat-ai/issue/BOA-266)（前検タイム等）・[BOA-273](https://linear.app/boat-ai/issue/BOA-273)（選手コメントのAI言語化）・[BOA-292](https://linear.app/boat-ai/issue/BOA-292)（SG/G1限定ページ）。

**受入基準**: 各チケット単体の受入基準に従う。本specでは優先度付けのみ行い、個別の実装は各チケットで完結させる。

### FR-8: 取得タイミング実行基盤へのマッピング（優先度: 高、他FRの前提）

FR-1〜FR-7の各データ項目を、タイミング分類（T1〜T5）に応じてBOA-313のVercel Functions/cron-job.orgパターンか、既存の低頻度GitHub Actionsジョブかに振り分ける設計をplan.mdで確定する。

**受入基準**: 全FRの対象データがT1〜T5のいずれかに分類され、対応する実行基盤（Vercel Function／GitHub Actions定期実行／手動一次実行後は自動化）が明記されている。T1（発走直前ウィンドウ）に分類されるものは新規にレガシーGitHub Actionsオーケストレーターへ追加しない。

## スコープ外（やらないこと）

- **データの見せ方（UI・可視化）**: [BOA-305](https://linear.app/boat-ai/issue/BOA-305)配下のレース詳細ページタブ実装等は完全に別スコープ。本specはデータ取得・保存までを対象とする
- **MLモデルへの特徴量組み込み**: 能力指数等の新規データをAI予想モデルに組み込むかどうかの判断・実装は別途行う
- **期待値分析機能**: 的中率×オッズによる期待値算出は、モデル較正が前提になるため過去に却下済みの方針を維持し対象外とする
- **BOA-313自体のアーキテクチャ再設計・Phase 2/3の実装遂行**: 他セッションの担当。本specはBOA-313完了後（またはPhase進行と並行して）新規データを乗せる設計のみ行う
- **SG/G1限定ページ（BOA-292）の本格実装**: 対象イベントが少なく優先度が低いため、本specでは棚卸しに留め実装しない

## 非機能要件

- **サーバー負荷**: 新規スクレイピングは既存パターン（User-Agent明示 `BoatraceAIBot/1.0`、リクエスト間隔の考慮、対象レース・対象通知が無い場合はリクエスト0件）を踏襲する
- **データ精度の監視**: T1分類の新規データ（オッズ全券種等）は、BOA-313 Phase1で確立した欠落率監視の仕組み（閾値2%、`exhibition-gap-monitor.yml`と同様のパターン）を踏襲する
- **デグレ防止**: 既存の取得済みデータ（展示・結果・オッズ・出走表等）の取得成功率を悪化させない。新規追加は既存処理と独立した関数・ジョブとして実装し、失敗が既存処理をブロックしない設計にする（`continue-on-error`パターンの踏襲）
- モバイル表示・SEO等の非機能要件: 該当なし（UI無し）

## 制約・前提

- **実行アーキテクチャ**: BOA-313のVercel Functions/cron-job.orgパターンを前提とし、ゼロから再設計しない。既存の`run(schedule, date)`共通インターフェース（`scripts/daily/*.js`）を踏襲し、CLIエントリポイントとVercel Functionハンドラーを分離する設計を継続する
- **データソース**: 全て公式サイト（中央ポータル・24会場個別サイト）由来。ボートレース日和は比較・参考情報源であり、スクレイピング対象ではない
- **会場サイトの技術的制約**: 24会場は複数のCMSベンダーに分かれる（`/modules/`パス構成の共通CMS群と、レガシーな静的HTML/ASP構成群）。単一スクレイパーでは対応できず、CMSベンダー単位のテンプレート共通化の検討をplan.mdで行う
- **既存コンポーネント再利用**: `scripts/lib/oddsParser.js`（`parseTrifectaAll`/`parseTrioAll`）、`scripts/lib/raceSchedule.js`、`scripts/daily/scrape-*.js`の`run()`パターンを再利用する
- **用語ルール**: UIが無いため「競艇」表記禁止等のルールはN/A
- **法的制約**: 投票・年齢制限等はデータ取得基盤のため非該当。会場サイトのToS確認が唯一の法務観点の制約（未確定事項参照）
