# 全レース関連データ取得・タイミング最適化 plan

対応spec: [spec.md](./spec.md)

## 全体アーキテクチャ

```
                        タイミング分類
  T1(発走直前ウィンドウ)          T2(当日随時)         T4/T5(前日〜低頻度)
        │                          │                       │
        ▼                          ▼                       ▼
  Vercel Function              Vercel Function        GitHub Actions
  (BOA-313パターン踏襲)         (新規・軽量)             (既存 or 新規、低頻度)
  cron-job.org 1-2分間隔        cron-job.org 15-30分間隔  日次/週次/半年次
        │                          │                       │
        ▼                          ▼                       ▼
  FR-4(オッズ全券種)            FR-1(特記事項)          FR-2(期別成績)
  FR-3当日分(今節成績)                                  FR-5(profiles自動化)
                                                        FR-6(会場個別サイト)
                                                        FR-7(残存ギャップ)
```

原則（[BOA-313](https://linear.app/boat-ai/issue/BOA-313)を前提とした拡張）: T1に分類されるものは新規にレガシーGitHub Actionsオーケストレーター（`scrape-scheduled.js`）へ追加しない。T4/T5の低頻度データは、既存のconcurrency問題の影響を受けないため、新規にGitHub Actionsの定期ジョブを作ってよい（BOA-313の対象外）。詳細判断はADR-0056参照。

**各FRの具体的な頻度はADR-0058の原則（変化頻度・許容鮮度・可用性ウィンドウの有無から最小十分頻度を導く）に従って個別に決定する**。「T1だから高頻度」「T5だから低頻度」という粗い分類だけでなく、各FR節に具体的な頻度と根拠を記載する。

### 参考: 既存の実行済み・調査済みデータの頻度に関する観察（本spec外、他セッション管轄）

- **展示データ（BOA-313 Phase1）**: 現行はcron-job.org 2分間隔。ADR-0058の原則で見ると、展示データの可用性ウィンドウ（発走30〜10分前）に対し2分間隔は妥当な粒度だが、cron-job.orgは1分間隔まで無料で使えるため、欠落率の実測次第では1分間隔への短縮も検討の余地がある（BOA-313側で判断すべき事項として参考共有に留める）
- **結果取得（BOA-323関連）**: 結果データは単一のタイミングではなく、**払戻金（発走後約5分で確定）**と**スタート情報＝決まり手・ST（発走後20〜30分で確定）**という**2段階の可用性ウィンドウ**を持つことがBOA-323の調査で判明した。「結果が取得済みか」の判定を払戻金の有無だけで行うと、後から確定するスタート情報を待たずに確定扱いしてしまう（BOA-323の根本原因）。BOA-313 Phase2（結果のVercel Functions移行）の設計時は、この2段階構造を踏まえた再試行条件にする必要がある（他セッション管轄のため参考共有に留める）

## FR-1: レース特記事項ページ

### データ設計

新規テーブル `race_special_notes`:

| カラム | 型 | 説明 |
|---|---|---|
| id | bigint PK | - |
| venue_code | int | 会場コード |
| race_date | date | 対象日 |
| category | text | `accident`\|`equipment_change`\|`absence` |
| racer_id | int, nullable | 対象選手の登録番号（分かる場合） |
| boat_number | int, nullable | 艇番（分かる場合） |
| detail_text | text | 表示テキストそのまま（構造化しきれない情報の保険） |
| structured_data | jsonb, nullable | 種別ごとの構造化データ（例: absenceなら`{type: "途中帰郷"\|"即日帰郷"\|"即刻帰郷", replacement_racer_id}`） |
| scraped_at | timestamptz | - |

3区分（BOA-318/319/320）を1テーブルに統合する理由: 同一ページから1回のリクエストでまとめて取得できるため、取得ロジックを共有できる（ADR不要、自明な設計）。

### スクリプト構成

新規 `scripts/daily/scrape-race-information.js`（`run(schedule, date)`パターン踏襲）。会場・日付単位（レース番号非依存）のため、開催中の全会場を1日十数回巡回すれば十分。

### 実行タイミング（ADR-0058の原則を適用）

- **変化頻度**: 事故・違反・欠場は当日の開催時間中いつでも発生しうる
- **許容鮮度**: 特定のレースに影響する情報（欠場等）は、そのレースの締切前に反映されるのが望ましい。会場ごとのレース間隔は概ね20〜30分
- **可用性ウィンドウ**: 無し（一度掲載されれば当日中は消えない）
- **結論**: レース間隔（20〜30分）より短い間隔で確認すれば、次のレースが締切る前に反映できる可能性が高い。**30分間隔ではレース間隔と同程度〜やや長く、取りこぼす恐れがある**

**ファン視点の検証（後述「ファン視点での検証」参照）で、さらに10分間隔に短縮した**。帰郷等はファンコミュニティで速報性が求められる話題であり、次のレースまでに複数回確認機会を持てる余裕を持たせるため。

**タイムアウト設計（天才エンジニア視点レビュー、[ADR-0059](../../adr/0059-new-endpoint-timeout-security-monitoring-standards.md)参照）**: 開催中の全会場（最大24会場）を1回の呼び出しで巡回するため、素朴に実装するとcron-job.orgの30秒タイムアウトを超えるリスクがある。BOA-313 Phase1の展示データと同じ「即座に応答してバックグラウンド継続（`waitUntil`）」パターンを踏襲する。

新規 Vercel Function `api/cron/race-notices.js`、cron-job.org **10分間隔**（7:00-23:00 JST）。ADR-0056の原則に従い、レガシーオーケストレーターには追加しない。

### 実行タイミング（ADR-0058の原則を適用）

**訂正（2026-09-15ユーザー指摘）**: 「フライング回数・出遅れ回数は半年に1回しか変化しない」という当初の結論は、**公式の集計ページ（`season?toban=`）の更新頻度**と**フライング発生そのものの検知頻度**を混同していた。実際には`race_start_timings.is_flying`列（`scrape-results.js:80,94`で"F"表記を検出）により、**個々のフライング発生はレース結果取得のたびに即座に検知できる**（[BOA-323](https://linear.app/boat-ai/issue/BOA-323)が解消していれば）。以下のように2つの用途で頻度を分ける:

| 用途 | データ源 | 頻度 |
|---|---|---|
| **個々のフライング発生検知**（F休み期間の起点になる実イベント） | 既存の結果取得（`race_start_timings.is_flying`） | **T3、結果取得と同じ頻度**（レース後、既存の仕組みに乗る。追加のスクレイピングは不要） |
| **能力指数・公式集計フライング回数の突き合わせ**（自社カウントの検算用） | 公式期別成績ページ | **月次＋半年切り替わり直後2週間は週次**（この用途に限っては半年に1回しか変わらないため妥当） |

- **変化頻度**（能力指数・公式集計値に限定）: 集計期間（前期5/1-10/31・後期11/1-4/30）ごと、つまり半年に1回。生年月日・血液型等は実質不変。新規登録選手の追加は月に数件程度の低頻度
- **許容鮮度**: 能力指数等の検算用途は数週間〜1ヶ月古くても実害は薄い
- **可用性ウィンドウ**: 無し（常時閲覧可能）
- **結論**: 能力指数等の公式集計値の取得は月次で十分（週次は過剰）。**ただしフライング発生自体の検知は、この期別成績ページを待たず、既存の結果取得（T3）で即座に行う**設計にする

新規GitHub Actionsワークフロー（能力指数等の公式集計値取得のみ対象）、**月次実行**（例: 毎月1日）。5/1・11/1を含む月は、その月の第1〜2週のみ追加で週次実行する（cron式を月によって出し分けるか、常時月4回実行して差分を見るかは`/step4`で判断）。低頻度・静的データ（T5）でありBOA-313の対象外。個々のフライング発生検知は既存の結果取得の仕組みをそのまま使うため、本FRで新たなスケジュールは不要。

### 自社集計値との検算

期別成績ページの勝率・2連対率・3連対率・出走回数・優出回数・優勝回数を`racer_aggregated_stats`の対応値と突き合わせ、乖離があれば自社集計ロジックのバグの可能性として調査する（`.claude/rules/analysis.md`のデータ精度検証パターンを踏襲）。

### F休み期間の自社計算検証

`flying_count_period`と、既存の`race_results`/`race_start_timings`から取得できる各F発生日を組み合わせ、公式ルール（1回=30日、2回=90日、3回=180日、半年区切り）で休み期間を計算できるか検証する。可能であれば日和の「F休み期間」相当のスクレイピングは不要になる。検証タスクはtasks.mdで扱う。

**注意（[BOA-323](https://linear.app/boat-ai/issue/BOA-323)、2026-09-15発見、本spec対象外）**: `race_start_timings`はPR #612由来のリグレッションで2026-09-10以降ほぼ全レースで欠損している（決まり手も同様）。F発生日の検出もこのテーブルに依存するため、BOA-323が解消するまでは直近期間のF検出も同じ穴を引き継ぐ。本FRの検証タスク着手前にBOA-323の修正状況を確認すること。

## FR-3: 今節成績（節内の日別進捗）

### 技術判断（ADR-0053参照）

「racelistページを直接スクレイピングする」か「自社`race_results`等から導出計算する」かの選択がある。**ADR-0053で自社導出を採用**（理由はADR参照）。

### データ設計

新規ビュー/集計関数（テーブルではなくクエリ）: `getSeriesResultsByRacer(racerId, venueCode, meetStartDate)`（`supabaseDataService.js`に追加）。既存の`races`（`series_day`列、[BOA-226](https://linear.app/boat-ai/issue/BOA-226)実装後）・`race_results`・`race_entries`をJOINして、当該選手の当該節・当該日までの進入・着順・STを引く。

**注意（2026-09-15、BOA-226完了確認時に発覚）**: BOA-226は2026-09-12にスコープが転換し、`series_day`（節内の日数）自体は実装対象から外れた。代わりに`race_conditions.race_stage`（予選/準優勝戦/優勝戦等のラウンド種別、058マイグレーションで本番適用済み）が実装されている。race_stageは「優勝戦かどうか」の判定はできるが「節内の何日目か」という日数情報は持たないため、上記の`series_day`列を前提としたJOIN設計はそのままでは成立しない。FR-3着手前に、tasks.mdに記載した3つの選択肢（series_dayを別途実装する／race_dateの連続性から節を導出する／日数を使わない設計に変更する）のいずれを採るか決定すること。

「得点率」（節内の順位に応じた公式ポイント制）は自社計算が必要。公式ルール（1着=得点最大、着順が下がるごとに減点、優勝戦は加重等）を`docs/reference/`に一次情報源つきでまとめてから実装する（[BOA-220](https://linear.app/boat-ai/issue/BOA-220)と統合）。

**注意（[BOA-323](https://linear.app/boat-ai/issue/BOA-323)、2026-09-15発見、本spec対象外だが直接影響あり）**: ADR-0053で「自社`race_results`から導出する」と決めたが、PR #612由来のリグレッションで2026-09-10以降`winning_technique`・`race_start_timings`がほぼ全レースで欠損している（悪化継続中）。**BOA-323が解消するまでは、FR-3で導出する直近期間の今節成績（進入・着順は影響薄いが、STは大半欠損）が同じ穴を引き継ぐ**。FR-3の実装着手前にBOA-323の修正・バックフィル状況を確認すること。BOA-323自体は軸③（正確性・可用性のバグ）に分類され、[BOA-257](https://linear.app/boat-ai/issue/BOA-257)と同様に本specのスコープ外・独立した緊急対応が望ましい。

### 実行タイミング

過去日分: 導出クエリのため追加スクレイピング不要（T4相当、`races`/`race_results`が揃っていれば計算可能）。当日分: 当日のレース結果が確定するたびに反映されるため、`scrape-results.js`（結果取得、BOA-313 Phase 2でVercel Functions移行予定）の完了に連動する。**BOA-313 Phase 2の完了を待つのが望ましい**（結果取得自体の信頼性が今節成績の当日分の信頼性の上限になるため）。

## ファン視点での検証（2026-09-15、ユーザー指摘により実施）

ここまでの頻度設計は「情報源がどれくらいの頻度で変化するか」（ADR-0058）を軸にしていたが、それだけでは「熱狂的なファンが実際にどう使うか」という視点が漏れる。改めてその視点で全項目を見直した。

### 妥当と確認できたもの（変更なし）

- **FR-2 期別成績の月次＋半年ブースト**: 級別発表（ファンが最も盛り上がる瞬間）は集計終了直後（5月・11月頃）に行われるという公開ニュース例を確認した。5/1・11/1直後にブーストする設計はこの盛り上がりのタイミングと一致している（ただし発表の正確な日付は未検証、`docs/db-migration/061_racer_profiles_season_stats.sql`にコメントで注記済み）
- **FR-6 潮汐・水面特性・レイアウト変更履歴の低頻度**: ファンにとって「今すぐ知りたい」性質の情報ではなく、雑学的な文脈情報のため低頻度で問題ない
- **FR-3 今節成績の結果連動**: レース終了後すぐに反映されたい情報であり、既に結果取得のタイミングに連動する設計になっている

### 見直しが必要と判断したもの

1. **FR-1 特記事項（帰郷・事故・モーター変更）を15分→10分間隔に短縮**: 「お気に入り選手が突然帰郷した」はファンコミュニティで話題になりやすい速報性の高い情報。レース間隔（20〜30分）に対して15分では次のレースまでに1回しか確認機会が無いケースがあるため、10分に縮めて確実性を上げる
2. **FR-4 オンデマンド更新のクールダウンを見直し**: 当初「1分に1回まで」を想定していたが、締切直前の数分間はファンが最も頻繁にオッズを確認するタイミング（土壇場の投票判断）。この時間帯だけクールダウンを短く（例: 10〜15秒に1回まで）する設計に変更し、締切から離れた時間帯は現行想定（1分に1回程度）を維持する
3. **新規: SG/G1等グレードレースの優先度ティアを設ける**: SG/G1はファンの注目度・投票額が一般戦より格段に高い。全レース一律の頻度ではなく、**SG/G1開催中はオッズ・特記事項の時間窓の許容誤差（±3分）を±1分に狭める**等、優先度を上げる設計を追加検討する（実装コストは小さい想定、`race_conditions.race_grade`で既に判定可能なため）

### 本spec外だが強く推奨する事項（BOA-313、他セッション管轄）

**展示データ（展示タイム・展示ST）は、ファンにとって最もレース直前に確認したい情報**（買い目を最終判断する材料として最重視される）。現行のBOA-313 Phase1は2分間隔だが、cron-job.orgは1分間隔まで無料で使え、Vercel Pro移行によりCPU予算の制約も無いことが判明した。ファン体験の観点から、この項目こそ最優先で1分間隔への短縮を検討する価値があると考える（BOA-313側へコメントで共有済み）。

## 天才エンジニア視点での検証（2026-09-15、ユーザー指摘により実施、BOA-313の知見を踏まえる）

BOA-313の調査・実装から得られた技術的知見（タイムアウト設計、監視パターン、段階的検証手順）を踏まえ、本plan.mdの各FRを技術的に再点検した。詳細は[ADR-0059](../../adr/0059-new-endpoint-timeout-security-monitoring-standards.md)参照。

1. **FR-1のタイムアウト設計漏れ**: 全会場を1回で巡回するVercel Functionにも、BOA-313 Phase1と同じ「即時応答＋`waitUntil`バックグラウンド継続」パターンが必要だった（未設計のまま放置していた）
2. **FR-4オンデマンド更新のセキュリティモデル漏れ**: cron向け`CRON_SECRET`は公開エンドポイントには適用できない。IP単位のレート制限・パラメータ妥当性検証を別途設計する必要があった
3. **FR-6の監視を再発明しかけていた**: BOA-285（Done）で既に`driftHealth.js`（HTML構造変化検知の汎用ロジック）が実装済みと判明。ゼロから作らず再利用する設計に修正した
4. **オッズのデータ保存期間の方針が無かった**: 6窓×5券種×毎日約180レースでの蓄積量を見積もり、当面は上限を設けず監視のみ行う方針を明記した
5. **0分（締切）窓の失敗時フォールバックが未設計だった**: 直前の成功スナップショットを実質最終値として扱う設計を追記した
6. **新規パイプラインの検証手順が標準化されていなかった**: BOA-313が確立した「並走検証→自動監視での閾値確認→切替」の手順を、FR-1・FR-4・FR-6のT1〜T2寄りの項目にも適用する原則を明記した（ADR-0059）
