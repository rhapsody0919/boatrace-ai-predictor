## 目的

思考アシストは「条件→軸→展開→機力→買い目」の思考の型で、ファンが自分で組んだ買い目がオッズに見合うかを確かめる場所（BOA-430）。3連単だけだと、同じ読みを3連複・2連の券種で買う人が使えない。同じ候補のまま券種を替えて点数と合成オッズを比べられれば、「読みは同じでどの券種で買うか」を決める材料になる。

## オッズの取得状況

official-data-spec の確認（2026-10-27、コード・マイグレーション・本番 DB の読み取り・公式のページの照合）。

**結論: 4券種のオッズは全部 DB に入っている。この機能のために公式への取得を増やす必要は無い。** 増えるのは、思考アシストが `/api/odds/live` でその場の値を取りに行く設計にした場合だけ（下の「取得が増える場合」）。

| 券種 | 発売中（締切60・30・15・10・5・0分前の6窓） | 締切時オッズ | 公式のページ |
|---|---|---|---|
| 3連単（今使っている） | `race_odds.trifecta_all` 120通り（022） | `race_odds_final.trifecta_all` | odds3t |
| 3連複 | `race_odds.trio_all` 20通り・キーは昇順（065） | `trio_all`（108） | odds3f |
| 2連単 | `race_odds.exacta_all` 30通り（065） | `exacta_all` | odds2tf |
| 2連複 | `race_odds.quinella_all` 15通り（065） | `quinella_all` | odds2tf（2連単と同じページ） |
| 拡連複 | `race_odds.wide_all` `{"1-2":{"low","high"}}` 15通り（065） | `wide_all` | oddsk |

- 取るジョブ: 発売中は Vercel Cron `/api/cron/odds`（毎分、JST 7:00〜23:59、`scripts/daily/scrape-odds.js` の `fetchOddsDetailed`、窓は各±3分）。締切時オッズは `/api/cron/odds-final`（5分おき、締切の5分後から）。予備は GitHub Actions `scrape-scheduled.yml`
- 埋まり方（本番の読み取り、JST）: `race_odds`（source=vercel）は 10/24 168R・1,005行、10/25 144R・864行、10/26 138R・777行で、取れた行は5列とも埋まっていた。`race_odds_final` は 10/24〜26 で7列とも100%（10/26 が1日分そろっているかは未確認）
- 思考アシストは今 `getRaceOddsSnapshots`（4券種も返している）の最新の `trifectaAll` だけを使い、締切後も `race_odds_final` を読まない（`src/hooks/useThinkingAssistData.js` 52〜62行）。オッズ一覧タブ（`RaceOddsListTab.jsx`）は全券種を出している
- holmes（アドラー）の3連複・2連単は勝率からの確率（Plackett-Luce、`src/services/adlerModel.js`）でオッズを使わない。流用できるのは表記・組の並べ方だけ

### 拡連複の幅と払戻（2026-10-26 桐生1R で公式と DB を照合）

- 公式の oddsk は15組を「1.7-2.0」の下限-上限で出す。DB も同じ値（1-2 は 1.7/2.0、4-5 は 3.2/3.9）
- 拡連複は3着以内の2艇の組なので、払戻は3組（結果 3-2-1 で 2=3 ¥180・1=3 ¥300・1=2 ¥170。DB の `race_results.payout_wide_1..3` と一致）。確定の払戻は締切時オッズの幅の中に入った
- 単一の値の券種は、締切時オッズ×100 が確定の払戻と一致した（3連複 6.5→¥650、2連単 14.2→¥1,420、2連複 5.0→¥500）
- 列名の罠: 払戻の `race_results.payout_trio` が3連単、`payout_trifecta` が3連複（`scripts/lib/payoutCalculator.js` 冒頭）。オッズの jsonb（`trio_all`＝3連複）は英語名どおり

### 公表の時点

- 発売の開始: 当社の取得記録では、朝の会場の1〜3Rだけ締切60分前に未発売（`docs/design/scraping-load-budget/analysis/freshness-need.md`）。前売の制度は公式で未照合
- 更新の間隔: 5分の窓の間で3連単の表が同じだったのは 2,184件中 -15→-10 で28件、-10→-5 で2件、-5→0 で0件。5分より短い間隔で更新されている（何分おきかは未照合）
- 締切後は公式の表示が「締切時オッズ」に変わる。券種ごとに発売の開始・更新が違うかは未照合
- 締切後の買い目に `race_odds_final` を使うかは設計で決める（今の3連単も0分窓の値のまま）。単勝は0分窓から締切時オッズまで中央値28%動く（同 freshness-need.md）

### 取得が増える場合（費用・外部への負荷はオーナー判断）

- DB のスナップショットを読むだけなら、公式への取得は0件増える（5ページ×6窓は今も取っている。1日約4,730件＋締切時オッズ約780件、`docs/design/scraping-load-budget/spec.md`）
- 思考アシストが3連複・2連・拡連複のその場の値を `/api/odds/live` で取る設計にすると、odds3f・odds2tf・oddsk の3ページが増える。1ページあたり CDN 30秒に1回が上限で、締切60分前〜10分後の70分で理論上の最大は1レース×1ページ×1リージョンで約140件。実際は閲覧に左右され未計測。取得の予算（BOA-1145 の流れ、`docs/design/scraping-load-budget/spec.md` §4.2、ADR-0101 は提案）の上限は、ホスト全体 18,000件/日・ライブオッズ 3,000件/日（どちらも目安、根拠なし）。**このモックは DB のスナップショットを読む前提で、取得は増やさない**
- 関わる未決: 同 spec §6.1 の案 A5「3連複・2連・拡連複を -60/-15/-5 だけにする（−1,404件/日）」がオーナーに聞く項目にある。採ると、この機能の4券種のオッズが窓の間で最大約10分古くなる（今は約5分）

### 拡連複の合成オッズ

拡連複は3着以内の2艇の組なので、同じレースで最大3組が同時に払戻の対象になる。合成オッズ 1/Σ(1/オッズ) は「組んだ組のうちどれか1つだけが払戻の対象」の前提の式で、拡連複には当てはまらない（2組・3組が同時に対象になると、払戻は組ごとの和になる）。モックでは拡連複だけ合成オッズを出さず、「1組だけ払戻のときは合計の a〜b 倍」を出した。トリガミの印も組ごとの下限の払戻で付ける。

## ファンの結論（[fan-panel-mock-v1.md](fan-panel-mock-v1.md)）

1. 券種のタブ5つで1つずつ切り替え。既定は3連単。最後に選んだ券種は同じレースの中で覚える
2. 買い目のレンズの頭に「券種で比べる」小表（同じ候補での組・点数・合成オッズの5行）。行を押すとその券種へ
3. 候補の段は全券種で共有。連複は「1艇目・2艇目・3艇目（順不同）」、2連の券種は3段目を薄く残して使わない旨を1行
4. 近道「選んだ艇でボックス」と、押した直後の「元に戻す」
5. 表記は連単「-」、連複・拡連複「=」。フッターの頭に券種の名前
6. 拡連複のオッズは幅のまま、払戻・トリガミは下限で計算して注記。同じレースで最大3組が払戻の対象になる旨を1行
7. 人気はその券種のオッズの順。類似の列は統計の答えまで3連単だけ

割れた点: ボックスを主の入力にするか（20代男）、段を主にしてボックスは近道にするか（3人）。モックは3人の案。
