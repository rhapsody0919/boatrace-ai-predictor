# レース中止・順延検出の永続化 仕様書

## 種別
UI機能（画面・コンポーネントが関わる）。次工程は `/step1-screens race-cancellation-detection`。

## 対応Linearチケット
[BOA-254](https://linear.app/boat-ai/issue/BOA-254/レース中止順延の検出結果をdbに永続化する)

## 背景
[BOA-243](https://linear.app/boat-ai/issue/BOA-243/会場ページ-レース締切ステータスのライブ表示受付中まもなく締切締切済み)（会場ページの締切ライブステータス表示）の実装可否調査で発覚した、既存の未解決ギャップ。

`race_results`テーブルには`is_cancelled`/`is_no_race`カラムが存在する（`docs/db-migration/001_schema.sql`、デフォルト`FALSE`）が、リポジトリ全体を検索してもこれをtrueに書き込んでいる箇所がどこにも無い。集計クエリ側では`.eq('is_cancelled', false)`のようにフィルタ条件として読まれているのみで、実質常にFALSE固定の死んでいるカラムになっている。

この課題自体は`docs/proposal/DATA_FLOW_COMPARISON.md`で既知だったが、想定されていた対応方針は「レース結果ページで結果が取得できない場合のハンドリング」（発走後の後処理、優先度: 低）のみだった。BOA-243が必要とするのは**発走前（締切前）の検知**であり、既存の想定とは異なる新しい要件が加わっている。

さらに調査で、`race_results`は`rank1`/`rank2`/`rank3`が`NOT NULL`制約であることが判明した。着順が存在しない中止レースの行を`race_results`に作成できないため、発走前の暫定検知だけでなく、発走後の「本当に中止・不成立だった」という確定記録についても、`race_results`をそのまま使う想定は成立しない。

## 機能要件

### FR1: 発走前の暫定検知の永続化（優先度: 必須）
`scripts/daily/update-race-info.js`が既に持つ「選手情報が0人＝中止・未公開の可能性」の検出結果を、ログ出力ではなく`races`テーブルの新カラムに永続化する。同スクリプトは発走1時間前ウィンドウで5分毎に実行される（`scrape-scheduled.yml`）。
- 誤検出対策として、同一レースで3回連続（15分間）検出された場合にのみ「暫定中止」として確定する。1〜2回の検出はまだ記録しない（一時的なスクレイピング失敗との切り分け）
- 受入基準: あるレースで15分間にわたり3回連続で選手情報0人が検出された場合、`races`テーブルの該当カラムに暫定中止状態が記録される。2回以下の検出では状態が変化しない

### FR2: 発走後の確定検知の実装（優先度: 必須）
`scripts/daily/scrape-results.js`が結果を取得できないまま一定時間が経過したレースについて、`races`テーブルの同じカラム（FR1と共通）に「確定」状態を記録する。FR1で暫定中止済みのレースはそのまま確定に格上げしてよい。
- 受入基準: 発走時刻から一定時間経過しても結果が取得できないレースについて、当該カラムが確定状態になる
- 未確定: 「一定時間」の具体的な閾値は`/step2`で決定する

### FR3: データ取得層の拡張（優先度: 必須）
`getPredictions()`等の取得クエリが、FR1/FR2で記録した状態を返すようにする。
- 受入基準: `RaceCard.jsx`等の呼び出し元が、レースごとの中止状態（暫定/確定/なし）を取得できる

### FR4: RaceCard表示分岐（優先度: 必須）
`RaceCard.jsx`の既存の「結果反映待ち」表示に、「中止」表示への分岐を追加する。
- 確定状態のレースは「中止」バッジを表示する
- 暫定状態（まだ確定していない）のレースは、通常表示のまま変更しない（誤表示を避けるため、確定するまでは既存の「受付中」等の表示を維持する）
- `is_cancelled`（中止）と`is_no_race`（不成立）は区別せず、どちらも「中止」として統一表示する
- 誤って確定してしまった場合の手動取り消し機能は作らない
- 受入基準: 確定状態のレースカードに「中止」バッジが表示される。暫定状態・状態なしのレースカードは現行の表示と変わらない

## スコープ

### やること
- `races`テーブルへの新カラム追加（暫定・確定の両方を1つのカラム/状態で表現する。既存の`race_results.is_cancelled`/`is_no_race`カラムはNOT NULL制約の都合上使わない）
- `update-race-info.js`：暫定検知ロジックの実装（3回連続判定）
- `scrape-results.js`（または新規バッチ）：確定検知ロジックの実装
- `getPredictions()`等、取得クエリの拡張
- `RaceCard.jsx`：中止バッジの表示分岐
- 中止バッジの多言語対応（`/venue`は`TRANSLATED_PATHS`に含まれる翻訳対象パスのため、4言語分のi18nキー追加が必要）

### やらないこと
- BOA-243本体（会場ページの締切ライブステータス「受付中/まもなく締切/締切済み」表示）は別チケット。本チケット完了後に着手する
- 公式の中止発表ページ（boatrace.jp等）との突き合わせ（今回はヒューリスティック＋連続検知による確定のみ）
- 誤確定時の手動取り消しUI・管理画面機能
- `is_cancelled`と`is_no_race`をUI上で区別して表示すること
- 既存の`race_results.is_cancelled`/`is_no_race`カラムの削除・マイグレーション（触れずに残置する）

## 非機能要件
- 既存の`update-race-info.js`（5分毎実行）・`scrape-results.js`の実行時間・DB書き込み回数への影響は軽微であること（新規カラムへの追加更新1回程度）
- 誤検知率の定量目標は設定しない（3回連続検知という定性的対策のみ）
- 既存の会場ページ・レース詳細ページの動作に影響を与えないこと（既存の`RACE_STATUS`enum・`getRaceStatus()`は変更しない。本機能は独立した状態として扱う）
- `npm run build`エラーなし、`npm run test:e2e`（`RaceCard`は共通コンポーネントのため実行必須）が全件成功すること

## 制約・前提
- 既存コンポーネント`RaceCard.jsx`をそのまま拡張する（新規コンポーネント化しない、`.claude/rules/component-reuse.md`準拠）
- データ源: `races`テーブル（新カラム）、既存の`update-race-info.js`・`scrape-results.js`のスクレイピング結果
- 用語: 「競艇」使用禁止等の用語ルールを新規UI文言にも適用する。「中止」バッジの文言は「ボートレース」表記ルールに抵触しない
- 法的制約: 的中保証を連想させる表現は使わない（今回は状態表示のみのため該当リスクは低いが、文言レビュー時に確認する）
- BOA-243側で判明済みの制約（`RACE_STATUS`は`RaceCard.jsx`/`RaceDetailPage.jsx`/`PredictionSection.jsx`/`PredictionPanel.jsx`の4箇所から`===`比較で参照されており、既存enumの拡張は副作用リスクがある）を踏まえ、中止状態は既存enumとは別軸のフラグとして実装する

## 未確定事項
- **発走後「確定」までの待機時間**（発走から何分/何時間後に「結果が来ない」を確定とするか）: `/step2`（システム設計）で決定
- **`races`新カラムの正式なカラム名・型**（例: `cancellation_status`のようなenum文字列か、複数のbooleanか）: `/step2`で決定
- **確定検知ロジックの実装場所**（既存`scrape-results.js`への追加か、新規バッチスクリプトか）: `/step2`で決定
- **Linear上の優先度設定**: 未設定。ユーザーが別途判断
