## 2. 項目ごとの決着

### 2-1. G7（racelist の F数・L数・平均ST・体重）→ **実在した。日次は解決。過去分は既存チケット**

job-inventory.md の「`td.is-lineH2` の先頭列を使っていない」は、調査時点では正しかった。マイグレーション081が
`f_count` / `l_count` / `weight_kg` / `branch` / `hometown` / `is_absent` を追加し、`scripts/lib/raceListParser.js`
が先頭列を解析するようになっている（同ファイルの冒頭コメントがセルの並びを明記）。

#### 平均STは「無い」のではなく、別のテーブルにある（誤起票を1件防いだ）

**平均STは `race_entries` ではなく `racer_period_stats.avg_st`（マイグレーション083、fanファイル由来）に入っている。**
BOA-365 が警戒していた「別名の列を見落として誤って『無い』と判断する」の実例が、本監査中に実際に起きた。
取得側を担当している並行セッションは 2026-09-28 に `information_schema` を検索して「**平均STは列が存在しません**」と
結論したが、これは誤りだった。`information_schema.columns` を実測すると、`avg_st` は**4つのテーブルに実在する**。

| テーブル | 列 | 備考 |
|---|---|---|
| `racer_period_stats` | `avg_st`、`c1_avg_st`〜`c6_avg_st`、`c1_avg_start_rank`〜`c6_avg_start_rank` | 083。**24,165行・96.9%が非NULL**。コース別の平均STと平均スタート順位まで持っている |
| `racer_aggregated_stats` | `avg_st`、`avg_st_last_30` | 自社集計 |
| `st_course_baseline` | `avg_st` | 094（phase a のST考察のベースライン） |
| `venue_entry_course_stats` | `avg_st` | 064 |
| `races` | `first_boat_avg_st` | 009 |

**この1件で「G7の残件は平均STだけ」という結論が反転する。** 正しくは「G7に残っているのは過去分の充填だけで、
平均STは解決済み」。BOA-365 が明示していた注意（`docs/db-migration/` 全体を grep する。`racer_profiles` の
見落としで BOA-297 等を誤起票した実績がある）がそのまま再現した形なので、教訓として残す。

**検索の物差しを固定しておく**: 列の有無を確認するときは、対象テーブルを絞らずに
`information_schema.columns WHERE table_schema='public'` を全件見る。列名のパターンは1つに賭けず、
`ILIKE '%avg%st%'`・`ILIKE '%average%st%'`・`ILIKE '%_st'` のように複数の当て方を並べる。

- 残件: 2026-02-15〜2026-09-20 の約7ヶ月 → **[BOA-417](https://linear.app/boat-ai/issue/BOA-417)（既存）**
- 新規起票は不要

### 2-2. G8（スタート展示の進入順）→ **実在した。日次は解決。過去分は遡及不可**

マイグレーション082が `exhibition_data.exhibition_course`（スタート展示の表の行順＝コース順）を追加している。
同ファイルが「スタート展示の表は、行順がコース順（1行目=1コース）」と、前づけの予兆として使う意図まで書いている。

**過去分は遡及できない。** [backfill-plan.md](./backfill-plan.md) が「beforeinfoの気象（過去日は当日の最終観測を返す）」
を遡及不可として挙げているのと同じ理由で、beforeinfo の過去日は展示当時の状態を返さない。

- 全期間 8.3% は、**構造的にこれ以上上がらない**。完了の定義A の「過去分を遡って取得できないデータは、
  『取得開始日以降のみ』と明記してユーザーの承認を得る」に該当する
- 残件: **取得開始日（2026-09-21）以降のみ、というユーザー承認**。新規起票 → §3

### 2-3. G9（返還・不成立・失格理由）→ **実在した。日次は解決。過去分が未計画**

マイグレーション078が `race_results.race_status`（`normal` / `partial_refund` / `no_race`）・`refund_boats`（返還艇の枠番）・
`remark` を追加している。079が `race_payouts` を追加した。日次は 100%。

#### 副次的に見つけた実害: 画面が「書かれていない列」で中止を判定している

`is_cancelled` / `is_no_race` は、job-inventory.md D6/G9 が言うとおり**スクレイパーが書かない無効な列**のまま。
078のコメントは「読み手は `race_status` が `'no_race'` でない（IS DISTINCT FROM）で判定する」と新しい流儀を定めている。
**しかし画面側はこの流儀に移行していない。**

実測（2026-09-28）:

| 確認 | 結果 |
|---|---|
| `src/` が `race_results.race_status` を読んでいる箇所 | **0件**（`src/utils/raceStatus.js` の `RACE_STATUS` は画面上の進行状態を表す**別物**で、名前が衝突しているだけ） |
| `src/services/supabaseDataService.js` が `is_cancelled` / `is_no_race` を読む箇所 | **10箇所以上**。共通判定 `isUsableRaceResult()`（同 :28〜35）が `!result.is_cancelled && !result.is_no_race && result.rank1 !== null` |
| `race_status` が入っている 2,673行のうち `is_cancelled` が true | **0件** |
| 同 `is_no_race` が true | **0件** |
| 同 `race_status = 'no_race'`（不成立） | **8件** |
| 同 `race_status = 'partial_refund'`（返還あり） | **105件** |
| 不成立8件のうち `rank1 IS NOT NULL`（＝現在のフィルタを通過する） | **8件（全部）** |

つまり `isUsableRaceResult()` の中止・不成立の2条件は**常に真**で、除外がまったく効いていない。
**不成立の8レースが選手成績等の集計にそのまま混ざっている。** `race_status` の充足が過去分へ広がるほど、
混ざる件数も増える。

なお `partial_refund`（105件）は返還があっただけで着順自体は有効なので、除外対象ではない。
078が定めた `IS DISTINCT FROM 'no_race'` がそのまま正しい判定になる。

これは取得側（正しく取れている）と表示側（古い無効な列で判定している）の間に落ちた穴で、
[表示カバレッジ台帳](../../reference/display-coverage.md)が `race_payouts` を「要判断」に挙げたのと同じ根。
新規起票 → §3

- 全期間 5.8%。過去分の充填計画が**どこにも無い**（backfill-plan.md にも項目が無い）
- Kファイル・Bファイルは遡及可能（backfill-plan.md 結論1）なので、返還・不成立が K/B から復元できるかは
  調査すれば分かる。**未計画なので新規起票 → §3**

## 4. BOA-365 の残り — 「網羅」の物差しが未定義

本監査は job-inventory.md §7.2 が挙げた G7〜G11 を決着させたが、[orchestration.md](./orchestration.md) が
完了の定義A について「**全データセットでの網羅確認は未（BOA-365）**」と書いているのは、より広い問いを指している。
「取得すべきものが全部挙がっているか」であり、**これは G7〜G11 を潰しても答えられない。**

現状、次の非対称がある。

- **N番号（data-catalog.md）は、公式サイトの項目を人が列挙した結果**であって、列挙が網羅的である保証が無い
- `optimal-scraping-design.md` が「BOA-365の項目を N1〜N31 に沿って分割起票」と書いているが、
  **N番号ごとのLinearチケットは体系的には存在しない**（起票の計画として書かれたまま）
- 「公式サイトのどのページ群を全部見たとみなすか」という**物差しの定義が無い**

物差しを決めない限り、この項目は永久に「未」のまま残る。次のどれかを選ぶ必要がある。

| 案 | 内容 | コスト | 弱点 |
|---|---|---|---|
| A | ページ単位で宣言する。公式サイトのページ群を列挙し、各ページについて「このページの全項目は棚卸し済み」と人が宣言して data-catalog に記録する | 中 | 宣言の正しさは人に依存する |
| B | ページのHTML構造を機械監査する。取得対象ページの全テーブル・全セルを列挙し、パーサーが読んでいる箇所との差分を出す | 大 | 公式サイトへのアクセスが要る。構造変更で毎回壊れる |
| C | 網羅を諦め、代わりに「新しい項目に気づく仕組み」を置く。パース対象ページの構造変化を検知して通知する（ドリフト検知） | 小 | 既に存在する項目の見落としは埋まらない |

**この選択は事業判断に近い**（どこまで取るかのコストと、取り逃しのリスクの weighing）ため、本監査では
案を並べるに留める。決めてから BOA-365 を分割するのが筋。
