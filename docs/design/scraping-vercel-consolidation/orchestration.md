# データ取得基盤の一本化とデータ整備 オーケストレーション（体制の正本）

対応: [ADR-0066](../../adr/0066-scraping-execution-consolidation-to-vercel.md) / [完了の定義](../../../.claude/rules/data-acquisition.md) / Linear [BOA-353](https://linear.app/boat-ai/issue/BOA-353)（索引のみ。状態の正本は本ファイル）

## 目的と完了条件

全データ取得を、Vercel Functions + Vercel Cronの1基盤に集約し、全データセットが「完了の定義」のA（過去分を含む件数）・B（可変データの取得タイミング）・C（継続監視）を満たした状態にする。完了の判定は、コードのマージではなく、本番DBの実測で行う。

## 体制

- **親（オーケストレーター）**: 計画、依存関係の管理、ゲート判定、マージ承認の窓口。実装は子が担当する。状態の正本は本ファイル（git管理）とし、節目ごとに親が更新する。Linearは索引として使う
- **子**: バックグラウンドAgent（worktree隔離）または別セッション。1つの子には、1つのワークストリームまたは1つのデータセットを割り当てる
- **並列度**: 同時に動かす子は最大2〜3。マージは1件ずつ明示的な承認が必要なため、承認待ちが律速になる。承認依頼はまとめて提示し、順序を添える
- **子への共通ルール**: worktree隔離。完了報告に、完了の定義の実測証拠（クエリと結果）を添付する。devサーバーの停止は自ポートのみ（`pkill -f`禁止）。`preview_start`は使わずBashで自ポート起動しtabIdを明示する。他人のブランチにpushしない。マイグレーション番号は、着手時とPR作成前に`origin/master`の最大番号を確認する（重複はCIで機械検査する。WS6）
- **並行する他セッションとの境界**: 取得系に触れる作業には`.claude/rules/data-acquisition.md`が自動で適用される。追加の通知機構は設けない（worktreeとPRで足りる）

## 他セッションの調査結果の取り込み（BOA-313 再設計検討メモ、2026-09-19）

原文はLinearのBOA-313・342・343・344・349・350のコメント。以下は、体制の正本として必要な部分の要約。

- **予定表方式（検討中、未決定）**: 「レース×窓」の予定を表に持ち、毎分の起動で「期限が来て未完了」のものだけを実行し、成否・試行回数・エラーを記録する。期限は保存せず`races.start_time`から都度計算する（発走時刻の変更・中止・順延に追従）。取得タイミングの意味論を、「±3分の窓に起動が入れば実行」から「期限（発走のw分前）を過ぎた最初の起動で実行し、期限+3分まで、失敗時は毎分再試行」へ変える（ADR-0057の更新対象。0分のオッズが締切の3分前になる弱点も解消する）。結果は、発走5分後（払戻）・20分後（スタート情報）から90分後まで。状態は pending→running→done、期限内の失敗は pending に戻し、期限超過は expired（即時アラート）。対象は窓型（展示・オッズ・結果）。レース情報更新・買い目オッズ・特記事項・日次系は当面現状のまま。
- **既存決定との整合条件**: runningの有効期限（lease）は許容幅（3分）より短くする。同時実行数の上限は高め（会場数24程度）にするか、許容幅内の持ち越しで吸収する。既存の`run()`は残し、内側にレース×窓単位の入口を追加する（二重実装しない）。並走期間中の`race_odds`への二重書き込みは、出どころ（source）で区別する（ADR-0059 4）。
- **Vercelで個別予約する手段**: Cron Jobsは`vercel.json`に書く方式でデプロイ時に固定されるため、毎日変わる予定の登録には使えない。Queues（delaySeconds）は実験的機能。Workflow（sleep）は課金・上限・成熟度が未確認。いずれも採用は保留。したがって、毎分のVercel Cron + DB上の予定表の組み合わせが有力候補。
- **予測リフレッシュの依存（Phase 3の前提課題）**: 予測リフレッシュの対象（`updatedRaceIds`）は、`scrape-scheduled.js`で、レース情報更新とオッズの各窓から作られ、結果は除外されている。展示は、Vercel移行後は含まれない。`generate-predictions.js`は`exhibition_data`を読む。展示がVercelに移った現在、30/15/10分前の再計算は、実質的にオッズ取得のきっかけで動いている（コードの流れからの推定。実挙動の確認は未実施）。オッズをVercelへ移すと、このきっかけが消えるため、代替が必要。案1: Vercel側で展示・オッズの取得成功時に再計算を要求する。案2: GitHub Actionsで発走60分以内のレースを毎回再計算する。案3: 再計算を予定表の予定にして、展示・オッズの成功を条件に実行する。再計算は実測約8秒。未確認: 予測モデルをVercelで動かせるか。
- **前提となる修正**: BOA-350（展示欠落率モニターの1000行上限による誤報）はPR #707でマージ済み。BOA-349（過去日の進入コース再同期が毎回全件UPDATE）は、WS8(b)で修正中。結果取得をVercelへ移しても、この不具合は移行先に引き継がれるので、移行前に直す。
- **Phase 2（結果取得）着手のゲート**（BOA-313 Step 4）: 修正後のモニターで、土日を跨ぐ変動（9/19・9/20分は9/20・9/21朝に確定）を確認してから判断する。BOA-313 Step 4は、着手前にBOA-350・BOA-352・BOA-354を先に対応するとしている（BOA-354: Supabase障害で結果7レースが欠損し、中止・順延扱いになった件）。
- **窓別の評価から除外する時間帯**: 2026-09-16 18:04〜21:58 JST（Supabase障害、BOA-352）。この間、オーケストレーターは「スケジュール未登録」で早期終了した。

**(c)のスパイク結果（2026-09-19、読み取り専用の調査）: 条件付きで、Vercel Functionで予測の再計算を動かせる。**
- 根拠: `mainRefresh`（`scripts/daily/generate-predictions.js` 1373〜1573行）は、`fs`・`git`・`execSync`・ネイティブ依存を使わず、Supabaseの読み書きと純関数の計算だけで完結する。`api/cron/exhibition.js`が同じ形（`scripts/`のモジュールをimportして`waitUntil`で実行）で動いている。時間・メモリ・バンドルの上限に大きな余裕がある（直近6日の実データで、発走60分以内の最大は26レース）。予測の入力にオッズは含まれないため、現状のオッズ起点の再計算は、変化のない入力の再計算が大半。
- 比較（再計算回数は、現状が1レース1日約6.6回、180レースで約1,200回と見積もり。コードからの推定）: 案1（Vercelの展示取得成功後に再計算）は、実装が小さく、頻度が約3回/日（-55%）でDisk IOが改善し、ADR-0066と整合。案2（GitHub Actionsで毎回再計算）は、約12回/日（+80%）でDisk IOが悪化しうる。案3（予定表）は到達点として正しいが、予定表とWS4aの完成待ち。**推奨は案1**（案3への予行になる）。
