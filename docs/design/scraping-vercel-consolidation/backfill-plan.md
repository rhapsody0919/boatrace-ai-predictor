## 1. 前提と結論

### 1.1 ユーザーの決定（2026-09-19）

- 2025-12より前の履歴は補填しない。2025-12以降は、全てのデータセットでバックフィルする
- 遡って取得できないデータは「取得開始日以降のみ」と明記し、完了の定義Aに従いユーザーの承認を得る
- 公式サイトの大量アクセスは運営に支障を与える行為として禁止されている（ADR-0067。本書の作成時点で、ADR-0067を含む別PRは未マージのため、リンクは付けない）。リクエストは最小限・逐次・十分な間隔にする

### 1.2 対象規模（2026-09-19の実測）

対象期間は2025-12-03〜2026-09-19の291日、`races`は44,508レース。月別は、2025-12が4,536、2026-01が5,460、02が4,212、03が4,956、04が4,368、05が4,620、06が4,284、07が4,596、08が4,800、09が2,676（19日分）。

### 1.3 結論

1. **公式のダウンロードデータ（Kファイル=競走成績、Bファイル=番組表。`www1.mbrace.or.jp/od2/`）が、期間全体の主力の取得元になる。** 1日1ファイルに全会場分が入り、実測で2025-12-04・2026-03-15・2026-08-01の3日とも取得でき、DBの会場・レース数と一致した。全291日分でも、Kファイル・Bファイル各最大291件（合計最大582リクエスト）で、結果・スタート・展示タイム・確定気象（天候・風向・風速・波高）・節日数・ステージ・タイトル・着順・払戻・出走表の勝率類をまとめて取得できる
2. **結果の欠落（1,372レース）は、既存の取り込みコード（`scrape-results.js`の再利用）で、1,372リクエストで補える。** 過去日のraceresultページは当時の結果を返す（2026-03-15の欠落レースで確認）
3. **遡って取得できない、または値の意味が変わるもの**: オッズの時系列窓（60/30/15/10/5分前）、特記事項、会場サイトのモーター成績・進入コース別成績、選手の過去の期別成績、beforeinfoの気象（過去日は当日の最終観測を返す）。詳細は[§3.3](#33-遡及不可不完全なものと扱い案)
4. **リクエスト量が大きいのは、pcexpect（公式コンピュータ予想）約27,200、racelist（3連率の補完）約8,700、beforeinfo（展示の補完）約16,600〜43,000、raceresult（気温・水温）約14,200。** 合計は、必須に近いものだけで約7万リクエスト。日次の上限を2,500件とすると、約28日かかる（[§5](#5-実行計画)）
5. 本書の数値のうち、**コード・DBで確認できたものと、実際に公式ページで確認したものと、未確認のものを区別して記載する**（[§4](#4-実測した取得元の特性)、[§8](#8-未確認事項)）

## 4. 実測した取得元の特性

### 4.1 Kファイル・Bファイル（`www1.mbrace.or.jp/od2/{K,B}/YYYYMM/{k,b}YYMMDD.lzh`）

- 実測: Kファイル3日（2025-12-04・2026-03-15・2026-08-01）、Bファイル2日（2025-12-04・2026-08-01）とも取得でき、解凍後（Shift_JIS）に、パース可能だった。応答は約35KB（Kファイル）、約28〜31KB（Bファイル）
- 突合: 会場数・レース数が、DBと一致（2025-12-04は12会場144レース、2026-03-15は13会場156レース、2026-08-01は13会場156レースと、レース0件の中止会場1つ）。Kファイルの結果行を既存の正規表現（`K_RESULT_RE`）で解析した艇数は、861（144×6=864に対し3少ない）、936（156×6）、935（156×6に対し1少ない）。差分は、既存パーサーが欠場行を除外する仕様によるものと推定（欠場行の実在は個別には未確認）。Bファイルの解析（`backfill.py`の`B_ENTRY_RE`）は、864・936で、レース数×6と一致した。DBで結果が欠落していた2026-03-15下関11・12Rも、Kファイルに含まれていた
- Kファイルの内容: 会場・日ごとの見出し（節日数「第 N日」、最終日、大会名）、レースごとの見出し（ステージ名、天候・風向・風速・波高）、着順・艇・登番・モーター・ボート・展示タイム・進入コース・ST・レースタイム・決まり手、払戻（単勝・複勝・2連単・2連複・拡連複・3連単・3連複と人気）
- Bファイルの内容: レースごとの見出し（ステージ名、電話投票締切予定時刻）、艇ごとの登番・年齢・支部・体重・級別・全国/当地の勝率と2連率・モーター/ボートの番号と2連率・今節成績。3連率は無い
- Kファイルの気象は、レース時点の確定値。気温・水温は無い
- 既存の`kfileParser.js`は、進入コース・着順のみを抽出する。ST・気象・展示タイム・節日数・払戻の抽出は、`scripts/ml/backfill.py`（Python）の実装が参考になる（移植には、JS版とPython版の同期の注意が必要。`kfileParser.js`冒頭のコメント）
- 展開ツール: この環境の`bsdtar`でLZHを展開できた。既存コードは`@kirinsaninc/lhats`

### 4.2 過去日のbeforeinfoの気象は使えない

2025-12-04大村1Rのbeforeinfoの気象欄は「水面気象情報　22:44現在」（当日の最終観測）で、雨・気温7.0℃・風速1m・波高1cm。一方、同じレースのraceresultの気象欄は、曇り・気温10.0℃・風速1mで、Kファイルの1R見出し（曇り・北西1m・波1cm）と一致した。2026-03-15下関11Rでも、beforeinfoの気温9.0℃に対し、raceresultは8.0℃。したがって、**過去日のbeforeinfoから気象を取ると、別の時点の値が入る**。`backfill-race-conditions.js`はこの気象を書くため、過去分には使えない。一方、`scrapeAndUpsertRaces`は、過去分の補完では気象を書かない設計（`updateWeather`既定false）で、そのまま使える。

beforeinfoの過去日ページで一致を確認できた項目: 展示タイム（6艇全て、Kファイルと一致）。チルト・調整重量・当日体重（52.3kg等）も、値が表示されていた。

### 5.3 リクエスト間隔・日次上限・時間帯

- 公式サイトへの負荷は、逐次（同時接続1）、リクエスト間隔は2秒以上（今回の調査は1.5秒）。429・503は指数バックオフし、連続して発生したら中断する（[BOA-368](https://linear.app/boat-ai/issue/BOA-368)のサーキットブレーカーの要件と揃える）
- **日次の上限は2,500リクエスト**（現行の日次運用の約11,700〜13,500ページの2割弱）。この環境の実測の応答時間（中央値9.2秒）＋間隔で1リクエスト約10.7秒とすると、2,500件で約7.4時間。**夜間（JST 22:00〜06:00）に実行**し、レース開催時間帯の日次ジョブ（07:00〜23:55の5分間隔）と重ならないようにする。実際の実行環境で応答時間が短ければ、上限は見直す
- 所要日数の目安（日次上限2,500件）: Phase 2〜3 で約1.3日、Phase 4で約3.5日、Phase 5で約6.6日、Phase 6で約6.3日、Phase 7で約10.9日。合計は約28日。承認が得られれば、上限を引き上げて短縮できる
- Kファイル・Bファイルのダウンロード（582件）は、mbrace.or.jp。同様に逐次・2秒間隔で、1日に済ませる
- タイムアウトは、既存コードの15秒（`kfileParser.js`）ではなく、この環境の実測の最大が10.4秒のため、30秒以上にする

### 5.4 書き込みのバッチ・レジューム・Disk IO

- 1文の書き込みは200行以下、文の間に1秒以上の間隔。**1フェーズずつ、他のフェーズと同時に走らせない**
- 段階: (1)`--dry-run`で件数を確認 → (2)1レース（または1日）を本番実行し、書き込み内容とトリガー連鎖を確認 → (3)1か月 → (4)全期間
- NULLの列だけ補完する（既存値は上書きしない）。既存の`unchangedRows.js`（変更のない行を書かない。PR #716）を使い、行ごとの差分がある場合にのみ書く。行の挿入は、`ignoreDuplicates`のINSERT
- レジューム: 各スクリプトは、DBの欠落（NULL・行なし）から対象を都度導出する。途中で止めても、再実行すれば残りだけを処理する（`backfill-actual-course.js`・`backfill-rank456-from-kfile.js`の方式）。加えて、実行のたびに、対象・成功・失敗・スキップの件数を`data/analysis/backfill/{dataset}-{日付}.json`に記録する
- **Disk IO**: 各フェーズの前後で、Supabaseダッシュボードの Disk IO 消費を確認し、完了報告に含める（[完了の定義C](../../../.claude/rules/data-acquisition.md)）。中断の閾値（消費率の上限）は、確認事項として合意する。Supabaseの顧客向けメトリクスAPIが504で取得できなかったため（[orchestration.md](./orchestration.md)）、目視で確認する
- 特に注意: (a)`race_results`のINSERTのトリガー連鎖（Phase 2で、1レース先行実行して測る）、(b)`race_entries`のUPDATE（約52k行）、(c)`race_conditions`・`exhibition_data`のINSERTで、インデックスの更新がある
- 実行主体: 本番DBへの書き込みを伴うため、ユーザー自身の端末での実行を想定する（自動モードのエージェントセッションは、本番DBへの書き込みを拒否される実績がある）

### 5.5 完了の定義A: 各データセットの検証

期待件数の分母は、`races`から`cancellation_status='confirmed'`を除いたレース数（中止確定の件数も報告する）。充足率99%以上。実測クエリと結果を、完了報告に添付する。

| データセット | 検証クエリ（月別。`m = substr(race_id,1,7)`） | 期待される充足 |
|---|---|---|
| 結果 | `races`と`race_results`を`race_id`で結合し、分母＝`cancellation_status is distinct from 'confirmed'`、分子＝`rank1 is not null` | 99%以上 |
| スタート | 同、分子＝`race_start_timings`に行のあるレース（`count(distinct race_id)`）。**分母は、結果のあるレース**（欠場・失格を含めて、艇数は5〜6のことがある） | 99%以上 |
| 展示 | 同、分子＝`exhibition_data`で`exhibition_time`が非NULLの行を持つレース。展示ST・チルト・体重は、対象を承認された範囲に限る | 99%以上（会場によっては展示STが展示タイムより先に公開される。BOA-356の基準に合わせる） |
| レース条件 | 分子＝`race_conditions`の行、`weather`非NULL、`series_day`非NULL、`race_stage`非NULLを、列ごとに | 行・天候・節日数・ステージ99%以上。気温・水温は、承認された範囲 |
| グレード | 分子＝`races.race_grade`非NULL | 99%以上 |
| 出走表 | 分子＝`global_3rate`・`motor_2rate`・`boat_2rate`が非NULLの行（分母はレース数×6） | 99%以上 |
| 公式コンピュータ予想 | 分子＝`external_predictions`の行のあるレース | 99%以上（公式が予想を出さないレースがあれば、件数を報告） |
| 今節得点率 | 分母＝期待する節の数（SG・G1の会場日数から節を数え、pointrankで表のある節）。分子＝`racer_series_points`の節数 | 99%以上 |
| 能力指数 | 分子＝`racer_profiles.ability_index`非NULL、分母＝season表に値のある選手 | 99%以上 |
| 選手ニュース | 公式アーカイブの記事数に対する`racer_news`の件数 | 一致 |

`scripts/analysis/data-health-report.js`（`--end-date`）で再現できるように、Phase 0で月別・データセット別に拡張する。

### 5.6 完了の定義B（タイミング）は対象外

完了の定義Bは、レースの進行に応じて値が変わる、または取れる時間が限られるデータの、取得時刻と窓内取得率。過去分の取得タイミング（発走何分前に取れたか）は、遡って作れないため、**バックフィルの対象外**とする。バックフィルで入れた行は、窓内取得率の計測から除外する必要がある（[§7](#7-ユーザーへの確認事項推奨案つき)の確認事項6）。

### 5.7 進捗の記録

- 各フェーズの実行ログを`data/analysis/backfill/{dataset}-{日付}.json`に保存（対象期間・対象件数・成功・失敗・スキップ・リクエスト数・応答時間・書き込み行数）
- フェーズ単位で、[orchestration.md](./orchestration.md)のWS5の状態を更新する（親が更新。実行はユーザー承認と、フェーズ前後のDisk IO確認の後）
- 各フェーズの完了時に、完了の定義Aの実測クエリの結果を、PRのレビュー結果コメント、または完了報告に添付する
