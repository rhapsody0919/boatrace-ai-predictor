# Vercel切り替えの短縮方針（ドラフト。独立レビュー前）

> **状態: ドラフト。** ユーザーが、短縮した進め方と、切り替えの権限を承認した（2026-09-21）。ただし、「短縮の方法を調査・文書化し、天才エンジニアのレビューを終えてから実施する」ことも指示された。本書はレビューの対象で、**レビューを終えて承認されるまで、この方針での切り替えは実施しない**（結果取得のshadowは、現行の手順どおり継続する）。

対応: [plan.md §4.6・§4.7](./plan.md)（現行の並走方式）/ [verification-runbook.md](./verification-runbook.md) / [orchestration.md](./orchestration.md) / [ADR-0059](../../adr/0059-new-endpoint-timeout-security-monitoring-standards.md) 4（並走検証の手順）

## 1. 目的

データ取得のVercel一本化の期間を短縮する。現行の設計（plan.md §4.6）は、1ジョブごとに「shadow 3日 → live並走 3〜7日 → GitHub側停止 → 7日実測」を、1ジョブずつ進めるため、全ジョブの切り替えに数週間かかる（推定: 完了は11月中旬）。

## 2. 現行設計からの変更点

| 項目 | 現行（plan.md §4.6） | 短縮方針 |
|---|---|---|
| shadowの期間 | 3日（土日のいずれか1日を含む） | 原則1日（平日の全会場）。基準を満たしたら切り替える（§4の基準） |
| live並走（GitHub側と二重に書く） | 3〜7日 | **行わない。** live化とGitHub側の停止を、同じ切り替えの操作で行う |
| 切り替えの単位 | 1ジョブずつ（並走は同時に2つ以上にしない） | 独立したジョブは、shadowを並行して回す。live化は、原則1ジョブずつ、間隔を空ける |
| 完了の定義Bの実測 | 切り替え後の土日を含む直近7日（変更なし） | 変更なし。**切り替え後**に行う（早朝・閑散日だけは根拠にしない） |
| 切り替えの承認 | 各段階でユーザーの承認 | 基準（§4）を満たしたとき、親（Claude）が、対話中に切り替える（§7の範囲内） |

**変えないもの**: shadowの実施、数値基準、切り戻しの手順、完了の定義A・B・C、ADR-0067の取得先への負荷の配慮。

## 3. 短縮しても失わない安全性の根拠（主張。レビューで検証する）

1. **shadowが、live並走の情報の大半を代替する。** shadowは、Vercel上で、取得・解析まで実際に行い、予定表に`result_digest`・所要時間・試行回数・エラーを記録する。live並走で追加で分かるのは「Vercelの書き込み（upsert）が動くこと」だけで、これは、切り替え直後の数時間のliveで確認でき、1コマンドで切り戻せる。
2. **live並走の代価は大きい。** 二重の取得（オッズは1日約5,400〜5,900ページの追加）と、二重の書き込み（Disk IO）を、3〜7日続ける。shadowの期間でも二重取得は起きるので、短縮すれば、その分、負荷が減る。
3. **旧基盤の安全網としての価値が小さい。** 現行のGitHub Actions側は、オッズの窓内取得率が88.8〜92.5%（0分前は52.8%。直近7日、2026-09-20の実測）で、キュー詰まりによる取りこぼしがある。Vercelが、この基準を上回ることをshadowで確認できれば、旧基盤を残す利点は薄い。
4. **完了の定義Bの実測は、もともと切り替え後の数字。** 並走期間は、Bの根拠にならない（plan.md §4.6）。

## 4. ジョブ別の切り替え基準と手順

### 4.1 共通の基準（shadow→live。全て満たすこと）

| 基準 | 内容 |
|---|---|
| G1 一致率 | shadowのダイジェストが、既存基盤の書いた値と一致する率が99%以上。標本数が、そのジョブの1日の全スロットの70%以上（結果取得は約170スロット/日、オッズは約1,000スロット/日） |
| G2 未実行 | `expired`が0件（うち`attempts=0`の未実行が0件）。試行回数が、`retrySec`の設計内 |
| G3 所要時間 | 1回の呼び出しの所要時間のp95が、`maxDuration`の80%以内。ソフトデッドラインでの中断が0件 |
| G4 取得先 | 429・503・接続拒否が0件。サーキットブレーカーが、一度も開いていない |
| G5 遅延（窓型） | 各窓の完了時刻が、期限+許容幅の内側で、既存基盤の窓内取得率（§3の3）以上の見込み |
| G6 監視 | `scrape-monitor`が、shadow中に、該当ジョブの指標を計測し、誤報・未報がない。Slack通知が届く（SLACK_WEBHOOK_URLは登録済み） |
| G7 時間帯 | 切り替えは、最後のレースの許容幅が過ぎた後〜翌07:00前の、レースの無い時間帯（結果取得は00:20 JST以降）。**日中に切り替えない** |

### 4.2 手順（共通）

1. 切り替え前: 当日の`shadow`で`done`になったスロットのうち、期限+許容幅がまだ過ぎていないものを`pending`に戻す（runbook E）。レースの無い時間帯なら、通常は該当なし。
2. `scrape_job_state.mode`を`live`にする（DBの更新）。
3. **同じ操作で**、GitHub側のリポジトリ変数`SKIP_<JOB>_ON_GHA=true`を設定する。
4. 直後の最初の窓が`live`で完了することを確認する（翌朝の最初の窓）。`scrape-monitor`のSlack通知を、当日中、細かく確認する。
5. 切り戻しの条件（いずれか）: 窓内取得率が旧基盤の実績を下回る、`expired`が出る、エラー率が有意に上昇する、429・503が出る、クォータを超過する → §6のコマンドで即時に切り戻す。

### 4.3 ジョブ別

| ジョブ | 短縮方針での切り替え | 特記事項 |
|---|---|---|
| 結果取得（`result`・`result_catchup`） | shadow 1日（2026-09-20夜〜21で、22/22一致を確認済み。夜の全スロットが揃った時点で最終判断）→ 2026-09-22の00:20 JST以降に、live化とGitHub側の`SKIP_RESULTS_ON_GHA=true`を同時に | Kファイル同期（`kfile_sync`）は別ジョブ。`SKIP_KFILE_ON_GHA`は別の変数。LZH展開のVercel上の動作確認（`?probeDate=`）が先 |
| Kファイル同期 | `?probeDate=`で確認→shadow 1日→切り替え。結果取得と同日に行わず、間隔を空ける | 別ドメイン（mbrace.or.jp）。負荷は小さい |
| オッズ | shadow 1日（土日を含む日が望ましい。全会場・全窓の分布を見るため）→切り替え。**live並走は行わない** | 下記の§5の論点1・2を、レビューで確認する |
| 日次ジョブ（得点率・モーター成績・選手ニュース・進入コース別成績（停止方針）・選手プロフィール） | 1日1回の実行のため、shadowは1〜2回で足りる。独立しているので、shadowを他ジョブと並行して回す | 選手プロフィールは月次（次回10/2 03:00 JST）。手動実行（dry-run→少数→全件）で代替する |
| レース情報（A1）・展示（A2） | 直前情報の全項目化のPRのマージ後に、Vercel化のコードを作る。以後、同じ手順 | コード未着手 |
| `races-init`（A0）・pcexpect（A8） | 別の子がコードを作成中。shadow（05:00 JST起動、07:00のGitHub側の値と比較）→切り替え | 所要時間の実測（U12）が前提 |

## 5. リスクと、レビューで検証してほしい論点

1. **オッズは時系列で、取り直せない。** 取りこぼした窓は、永久に失われる。並走を省くと、Vercel単独の欠落が、そのまま損失になる。緩和策: shadowでの窓の完了時刻の実測、`expired`の即時通知、1コマンドの切り戻し。**これで十分か。オッズだけ、live並走（`source`で区別。ただし1〜2日に短縮）を残す方が、リスクに見合うか。**
2. **オッズのshadowの限界。** plan.md §4.6は、「`race_odds`は行が増える履歴表のため、shadowでの検証は、ダイジェスト（最新の行との一致）に限る」としている。時間で値が変わるので、GitHub側の行と、取得時刻が違うと、値の一致を比較できない。shadow 1日で、パース（全通り5列の解析）の正しさを、どこまで保証できるか。
3. **shadowの統計的な強さ。** 一致率99%・標本70%以上（G1）は、十分か。結果取得は約170スロット/日、オッズは約1,000スロット/日。週末（最大180レース）と平日で、分布が違うが、shadow 1日（平日）で足りるか。
4. **切り替えの時間帯のリスク。** 00:20 JST以降の切り替えは、直後の最初の窓（翌朝07:00過ぎ）まで、実際のliveの動作を確認できない。その間に問題があっても、気づけない。`scrape-monitor`の稼働窓（07:00〜23:50）と、死活の誤報防止（`livenessCheckable`）の設計が、切り替え直後の監視を、十分に支えるか。00:00〜00:59の`result`のcron窓に、監視の空白がある（子エージェントの報告）。
5. **二重取得の意味の変化。** shadow 1日でも、オッズは、GitHub側と二重に取得する。切り替え後は、GitHub側を止めるので、総負荷は減る（現行の約12.0〜13.4千/日 → 約8.0千/日の見込み）。ただし、切り替え直後の数日、両方が動く期間（shadow）の負荷は、ADR-0067の配慮として許容できるか。
6. **並行shadowの干渉。** 複数ジョブのshadowを並行して回すと、`boatrace.jp`へのホスト単位のブレーカー（`host:boatrace.jp`）を共有する。1つのジョブの失敗が、他のジョブのshadowの結果に影響するか。
7. **完了の定義Bの実測期間が、切り替え後に集中する。** 切り替えを短期間に集めると、7日の実測（土日を含む）が、ほぼ同じ期間に重なり、問題が出た場合の切り戻しが、複数ジョブに及ぶ。切り戻しが、ジョブ間で独立しているか。
8. **Vercelの使用量・費用。** オッズは毎分（JST 07:00〜23:59）の起動、結果取得も毎分。Vercel Functionsの起動回数・CPU時間・Fluid Computeの課金への影響が、未計測。
9. **親（Claude）が切り替える権限（§7）の範囲は、適切か。**
10. **この短縮方針が、完了の定義A・B・Cの満たし方を、実質的に弱めていないか。**

## 6. 切り戻し（1コマンド）

```bash
# 1. GitHub側を再開（次の実行から即時）
gh variable set SKIP_<JOB>_ON_GHA --body false -R rhapsody0919/boatrace-ai-predictor
# 2. Vercel側を止める（DBの更新。再デプロイ不要）
#    UPDATE scrape_job_state SET mode='off', updated_at=now() WHERE job='<ジョブ>';
```

切り戻し後も、Vercelが`live`で書いた行は、そのまま残る（上書き型で、GitHub側の行と同形）。オッズは`source='vercel'`の行が残る。

## 7. 親（Claude）の切り替えの権限（ユーザー承認、2026-09-21。レビュー後に有効）

**行ってよい**: §4.1の基準（G1〜G7）を全て満たしたときの、`scrape_job_state.mode`の更新と、`SKIP_<JOB>_ON_GHA`の変更（対話中のみ。ユーザーが不在の間の無人実行は、権限の判定でブロックされる可能性があるため、行わない）。切り替え後の観測と、基準を外れた場合の切り戻し。
**行わない**: 基準が満たされない切り替え、429・503・取得先の警告があった場合の継続（止めて報告）、DDLの適用、データの修正（Q6のような）、外部サービスの設定変更（cron-job.org、Vercelの環境変数のうち、承認済み以外）、ジョブの新規追加。
**必ず報告する**: 切り替えのたびに、根拠の数値（基準G1〜G7の実測）と、切り戻しの手順。
