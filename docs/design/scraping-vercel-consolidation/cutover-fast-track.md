## 1. 目的

データ取得のVercel一本化の期間を短縮する。現行の設計（plan.md §4.6）は、1ジョブごとに「shadow 3日 → live並走 3〜7日 → GitHub側停止 → 7日実測」を1ジョブずつ進めるため、完了は11月中旬の見込みだった。

## 2. 現行設計からの変更点（レビュー反映後）

| 項目 | 現行（plan.md §4.6） | 短縮方針 |
|---|---|---|
| 分類の軸 | 全ジョブ共通 | **取り直せるか**で分ける（§3）。取り直せるジョブは短縮、取り直せない（オッズ）は、live並走を1〜2日残す |
| shadow | 3日 | 復旧可能なジョブは、原則1日。**オッズはshadowを省き、live並走に置き換える**（shadowも同量を取得するため、取得負荷は増えない） |
| live並走 | 3〜7日 | 復旧可能なジョブ: 行わない。オッズ: 1〜2日（`source`で区別） |

## 3. 「取り直せるか」による分類（レビューの指摘#3・#4を反映）

| 区分 | ジョブ | 取りこぼしの影響 | 方針 |
|---|---|---|---|
| 復旧可能 | 結果取得・result_catchup、Kファイル同期（4日ルックバック）、日次ジョブ、pcexpect、（races-initはGitHubの07:00初期化が自己修復するため、損失は約2時間の遅れ） | 後から取り直せる（GitHub側が+90分以内の未完了レースを自己修復、次の実行で回復） | shadow 1日 → live化とGitHub側停止 |
| 取り直せない | **オッズ**（時系列。取りこぼした窓は永久に失われる） | 永久損失 | shadowを省き、live並走1〜2日 → 早朝にGitHub側を停止。**人間のgoを残す** |

**live並走が追加で分かること**（ドラフトの「書き込みだけ」は誤り）: (1)`source`別の窓内取得率の直接比較（runbook M-3のSQL）、(2)書き込みの経路（`race_odds`のupsert、再試行時の既存行の読み込み`coalesceRow`）、(3)結果取得の`trg_update_predictions`連鎖（結果の書き込みで`predictions`・`bet_recommendations`が全行再UPDATEされる。WS8）、(4)live限定の処理（onTick、catch-upの書き込み、`fixMissingHitFlags`）、(5)監視のlive限定の経路。

**オッズのshadowの限界**: ダイジェストは構造（キー集合）のみで値を見ず、パーサーはGitHub側と共有しているため、パース差はほぼ検出されない。shadowは`race_odds`へ書かず、再試行の既存行読み込みも通らない。

**オッズのlive並走の負荷**: shadowも同量の取得（1日約5,000ページ）を行うので、shadowをlive並走に**置き換える**なら、取得負荷は増えない。追加は書き込み（約2MB/日）と、画面のオッズ履歴に近接行が重複して出ることだけ。

### 4.2 手順（復旧可能なジョブ）

1. **切り替え前**: 当日の`shadow`で`done`になったスロットのうち、**期限+許容幅がまだ過ぎていないものだけ**を、`pending`に戻す。期限条件が無いと、日中に実行したとき、許容幅を過ぎたスロットが`run_mode=NULL`・`attempts>0`のまま`expired`になり、monitorが一斉に通知し、窓内取得率が崩れる:
   ```sql
   UPDATE scrape_slots s
      SET status='pending', done_at=NULL, outcome=NULL, run_mode=NULL, next_attempt_at=NULL,
          result_digest=NULL, rows_written=NULL
     FROM races r
    WHERE r.race_id = s.race_id AND s.job = '<ジョブ>' AND s.run_mode = 'shadow' AND s.status = 'done'
      AND s.race_date = (now() AT TIME ZONE 'Asia/Tokyo')::date
      AND ((r.race_date + r.start_time) AT TIME ZONE 'Asia/Tokyo')
          + make_interval(mins => s.offset_min + <graceMin>) >= now();
   ```
2. `scrape_job_state.mode`を`live`にする（DBの更新）。
3. 同じ操作で、GitHub側のリポジトリ変数`SKIP_<JOB>_ON_GHA=true`を設定する（§6のフェイルセーフにより、Vercelが不健全ならGitHub側が実行する）。
4. 最初の実書き込み（次の窓）が`live`で完了することを確認する。`scrape-monitor`のSlack通知と`check-*-shadow.js`（live用の出力）を、当日中、細かく確認する。結果取得は、`result_catchup`の初回のlive実行（00:30 JST）で、`fixMissingHitFlags`が本番Vercelで初めて動くので、観測する。
5. 切り戻しの条件（いずれか）: 窓内取得率が98%を下回る、`expired`が出る、エラー率が有意に上昇する、429・503が出る、クォータ超過 → §7のコマンドで即時に切り戻す。

## 6. GitHub側の停止のフェイルセーフ（自動フェイルオーバー。レビューの代替案C）

静的なSKIP変数だけだと、Vercelが不健全になったとき、人間が変数を戻すまで、取得が止まる（無人の夜間は、特に危険）。`scrape-scheduled.js`のスキップ判定を、次のようにする（別タスクで実装。**実装が終わるまで、GitHub側の停止は行わない**）:

- `SKIP_<JOB>_ON_GHA=true`のとき、GitHub側は、`scrape_job_state`を読み、**`mode='live'`かつ`last_success_at`が、そのジョブの想定間隔の数倍以内**なら、スキップする。
- それ以外（`mode`がlive以外、成功が古い、**DBの読み取りに失敗した場合を含む**）は、従来どおり実行する（フェイルセーフ）。
- 効果: 通常時は、二重取得なし。Vercelが止まったときは、GitHub側が自動で肩代わりする。人間の操作なしで、復旧する。

## 7. 切り戻し（1コマンド）

```bash
# 1. GitHub側を再開（次の実行から即時）
gh variable set SKIP_<JOB>_ON_GHA --body false -R rhapsody0919/boatrace-ai-predictor
# 2. Vercel側を止める（DBの更新。再デプロイ不要）
#    UPDATE scrape_job_state SET mode='off', updated_at=now() WHERE job='<ジョブ>';
```

切り戻し後も、Vercelが`live`で書いた行は、そのまま残る（上書き型でGitHub側と同形。オッズは`source='vercel'`の行が残る）。結果取得とオッズは、変数とmodeが別で、独立に戻せる。共通原因障害（Vercel本番の不具合）は、独立に戻せない（§6のフェイルセーフで対処）。
