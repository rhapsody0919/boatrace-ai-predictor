# ネタ駆動マルチチャネルコンテンツパイプライン

## 種別

UI機能（sns-hub管理画面拡張を含む）＋データ・分析機能（Routine・スクリプト）の複合。`/step1-screens`をスキップせず進める。

## 対応するLinearチケット

新規。ただし以下を吸収・統合する:

スコープ外として切り離し済み（本スペックの対象外、別チケットのまま）:
- [BOA-234](https://linear.app/boat-ai/issue/BOA-234) イベント性の活用
- [BOA-235](https://linear.app/boat-ai/issue/BOA-235) シェア機能・埋め込みウィジェット
- [BOA-236](https://linear.app/boat-ai/issue/BOA-236) コミュニティ・インフルエンサー連携

## 背景

`docs/design/content-ops-flow/`（フローA/B/C、PR #466）でトレーサビリティ・ブランド統一・陳腐化検知の基盤を整備した。その基盤の上に、実際のコンテンツ生成そのものを「ネタ（1つの題材）→チャネル別に最適化したOutput」という形で自動化し、集客拡大に直結させるのが本機能の目的。2026-09-01の壁打ちセッションで設計を固めた。

既存のsns-hub-content-generation Routine（X/TikTok当日ネタ動画生成、稼働中）と同じ思想を、ブログ・note・YouTube解説動画にも一般化する。

## 機能要件

### FR1: ネタ供給モジュール（拡張可能な共通インターフェース）

優先度: P0

ネタ供給源を、共通契約 `{id, 候補生成関数(使用履歴を考慮), 有効フラグ}` に従うモジュールとして実装する。当初4系統（新機能・会場特性・データ知見・成績）で設計し、2026-09-02にTikTokガイドライン対応（下記FR2参照）で常磐（evergreen）系3系統を追加した。

- **新機能**: 既存の`missingContentIndex`検知（`scripts/maintenance/content-ops-checks/check-missing-content-index.js`、実装済み）の結果を候補として使う。**2026-09-02拡張**: 新機能に限らず、既存機能（言語切替・レース間ナビゲーション・選手ニュース・会場ガイド等、成績・確率と無関係なUI機能）の使い方紹介も同モジュールのネタとして扱ってよい（`docs/proposal/tiktok-non-gambling-content-ideas.md`案4「使い方ライフハック型」を吸収）
- **会場特性**: 24会場をローテーション。同じ会場でも「アクセス」「水面特性」「決まり手傾向」「季節ごとの特徴」等、切り口を変えて再訪可能にする
- **データ知見**: 分析ツール15タブ（決まり手・モーター調子・ST・出目分布等）を型ライブラリとして使い、直近使用した型と重複しないようローテーションする
- **成績**: 当日レースが開催されていれば対象。開催が無い日は対象外（データが存在しないため、これは品質低下ではなく単純な非該当）
- **競技解説・技術トリビア**（2026-09-02新設）: 成績・確率に一切触れない競技解説（規格統一・ターンの物理・進入コースの決まり方等）。日々の実データに紐づかない常磐ネタのため、直近使用したネタと重複しないようローテーションする
- **海外向け入門**（2026-09-02新設）: 競技解説・技術トリビアの英語字幕版。対象言語は英語のみ（需要調査で確認済み、`i18n_technical_and_demand_audit_2026_08_16`参照）
- **サービス信頼性・スケール訴求**（2026-09-02新設）: 収集レース数・分析指標数等のインフラ規模を可視化。的中率等の精度指標は扱わない（TikTokポリシー対象になりうるため）

受入基準: 新規のネタ供給モジュールを追加する際、既存モジュールのコード・ロジックを変更せず追加できること（2026-09-02、実際に3系統を追加して検証済み）

### FR2: チャネル別展開マトリクス

優先度: P0

ネタ種別ごとに、展開するチャネル（ブログ／note／X／TikTok／YouTube）の組み合わせを明文化する。全ネタ×全5チャネルの機械的な総当たりはしない（例: 成績ネタに毎回YouTube解説動画は不要）。

**2026-09-02追加（TikTokガイドライン対応）**: TikTok広告ポリシーは「賭けの結果に影響する統計・インサイト」自体を規制対象にしており、表現の工夫では回避できないと判明した（`docs/operation/sns-video-producer-prompt.md`絶対厳守ルール12、BOA-237）。このため、TikTokへの展開可否は**ネタ種別（カテゴリ）単位ではなく、個別ネタごとの判定**に変更した。既存4系統（新機能・会場特性・データ知見・成績）は成績・確率・回収率等を扱うのが前提のためCHANNEL_MATRIX上ではTikTokを含めず、個別ネタが例外的に安全（例: 言語切替機能の紹介）と判定できた場合のみ`getChannelsForTopic(sourceId, {isGamblingRelevant: false})`でTikTokを追加する。新設3系統（競技解説・海外向け入門・サービス信頼性）は成績・確率を扱わない設計のため既定でTikTokを含める。詳細は`scripts/lib/contentChannels/channelMatrix.js`のコメント参照。

受入基準: すべてのネタ種別について、展開先チャネルの一覧が文書化されている

### FR3: ブログ/note共通ドラフトモデル

優先度: P0

同一ネタから派生するブログ・noteの下書きは、`sns_drafts`スキーマの`content_group_id`の考え方を踏襲し、同じ`content_group_id`で紐付けつつ`platform`別（`'blog'`/`'note'`）にレコードを分ける。

- note向け本文は既存の`convert_to_note_markdown.py`相当の変換を経る（ブログ本文と完全一致はさせない。フォーマットの違いと重複コンテンツによるSEO評価分散を避けるため）
- note下書きには画像、または新機能ネタの場合はYouTube動画リンクを必ず含める（文字だけの下書きを許可しない）

受入基準: ブログ下書きが承認された時、対応するnote下書きが同じ`content_group_id`から参照できる

### FR4: 品質自己レビューゲート

優先度: P0

品質は本機能の最重要要件（ユーザーより複数回明示的に強調済み）。単純な自己採点1回だけでは、生成した本人が自分を甘く評価する構造的リスクがあるため、以下の多層防御で担保する。

1. **生成と採点を別ロール・別視点で行う**: 生成パスの直後に、同じ内容を「初めて読む第三者」として批判的に検証する採点パスを独立したステップとして実行する（生成した文脈を引きずって甘くなることを防ぐ）。採点パスは`.claude/CLAUDE.md`の既存ブログ品質チェック6項目（数値・データ整合性／現行仕様との整合性／検索意図の網羅性／用語・表記ルール／多言語間の一貫性／構造要件）に対して行う
2. **数値は「読んで確認」ではなく実際に再計算する**: 記事内で引用する数値（回収率・的中率等）は、元データから再計算し一致を確認する。目視確認のみで済ませない
3. **実データが取得できない夜は、そのネタを見送る**: これは「良いネタが思いつかないから見送る」（ユーザーが明確に却下した設計）とは異なる。分析ツール由来のデータ知見ネタ・成績ネタで、Supabase接続失敗等により実データを検証できない場合は、ネタ自体は型ライブラリ・履歴管理により常に用意できる前提だが、**その回だけデータ欠如により生成を見送り、翌日以降に再試行する**。プレースホルダーや「実データ未確認」表記での公開はしない
4. Failがあれば人間に見せる前に自分で修正し、修正後に再度1の採点パスを通す（Passするまで人間には出さない）

受入基準: 採点パスでFailが残ったままの下書きが承認待ち一覧に表示されないこと。数値を含む下書きは、元データとの再計算突合ログが下書きに添付されていること

### FR4b: 公開済みコンテンツの定期抜き打ち監査

優先度: P1

自己レビューだけでは、採点基準自体の盲点（型化した評価軸をすり抜ける低品質パターン）に気づけない可能性がある。`session-start-check.js`に新規項目を追加し、直近公開されたブログ/note記事から1〜2件を定期的に人間へ提示し、スポットチェックを促す（tweet-drafts等と同じ「鮮度優先で提示」パターン）。ここで質の低下傾向が見つかった場合、FR4の採点基準そのものを見直す入力にする。

受入基準: `session-start-check.js`実行結果に、直近公開コンテンツからの抜き打ち監査対象が含まれること

### FR5: 却下フィードバック

優先度: P1

却下操作は自由記述ではなく、事前定義済みの選択肢（reason codes）から選ぶ形にする（sns_draftsの`revision_reason_codes`と同じパターン）。却下理由はRoutineが次回生成時に参照できる形で記録する。

受入基準: 管理画面の却下操作が、選択肢のタップのみで完結する

### FR6: sns-hub管理画面拡張（BOA-233統合）

優先度: P0

`src/pages/admin/SnsHubAdmin.jsx`を拡張し、以下5タブ構成にする: **TikTok／X／YouTube／Note／Blog**

- Note/Blogタブ: 下書き一覧、本文・タグのコピペボタン、承認/却下（却下は選択式理由、FR5）
- **Blogタブの承認操作**: 承認ボタン押下でGitHub API経由の該当PRを自動マージする（新規のサーバーサイドアクション、認証された管理画面からのみ実行可能にする）
- **Noteタブの承認操作**: 承認後、実際のnoteへの入力・公開は人間が手動で行う（ブラウザ自動化はしない、コピペ止まり）

受入基準: 各タブで下書きの一覧・プレビュー・承認/却下操作が完結する

### FR7: X/TikTok/YouTube当日ネタレーン（既存拡張、別レーン）

優先度: P0（YouTube追加分）／変更なし（X/TikTok既存分）

- X/TikTokの`generate-daily`/`generate-evergreen`は既存のまま変更しない
- YouTubeを新たに`platforms`配列の対象に追加する（`sns_drafts.platform='youtube'`は既存スキーマのコメントで想定済みのためマイグレーション不要）
- YouTube専用: サムネイル画像を自動生成する（Remotionでbrand-kit.md準拠の静止画を生成、1280x720）
- **YouTube承認時**: YouTube Data API v3経由で動画・サムネ・タイトル・説明文・タグを自動アップロードする
- X/TikTokは既存通り、承認後の実際の投稿は人間が手動で行う（Xは自動投稿が技術的に不可と確定済み、TikTokは未検証のため今回は変更しない）

受入基準: YouTube承認ボタン押下で、実際にYouTubeへ動画が公開されること（要API認可設定後）

### FR8: 調査→反映ループの一般化

優先度: P1

既存の`scripts/lib/snsStrategyInsights.js`（insightsストア）の`platform`スコープに`'blog'`/`'note'`を追加する。`/growth-pdca`等の調査結果もこのストアに書き込めるようにし、週次昇格ロジック（`promote-strategy-insights.js`）はそのまま流用する。

受入基準: `getActiveInsights({platform: 'blog', ...})`で、ブログ向けに登録されたinsightが取得できる

## スコープ（やらないこと）

- リテンション・オンボーディング改善（別軸、今回は明示的に対象外とする判断済み）
- 被リンク構築・有料広告（未着手、今回のスコープ外）
- イベント活用（BOA-234）・シェア機能強化（BOA-235）・インフルエンサー連携（BOA-236）——別チケットのまま、本スペックでは触らない
- X/TikTokの投稿自動化（既存の制約通り、人間手動のまま変更しない）
- noteの公開自体のブラウザ自動化（コピペまでで止める、公開ボタンのクリックは自動化しない）
- 各チャネルの数値KPI目標設定（既存の集客PDCAスキル側の役割）

## 非機能要件

- **品質**: FR4の6項目チェック通過が公開の必須条件。数値のSEO/エンゲージメント目標は本スペックの対象外
- **頻度**: 系統合計で1晩1本を初期運用の上限とする（品質が安定したと判断されるまで）。上限見直しのタイミングは未確定
- **セキュリティ**: Blog承認→PRマージ、YouTube承認→API投稿は、いずれも認証された管理画面からのみ実行可能な形にする（第三者が外部から叩けないこと）

## 制約・前提

- Routineサンドボックスは外部サイト（X/TikTok等）を自律的に閲覧できない（確定済み制約、`docs/design/sns-hub-phase2-pdca-loop/spec.md`参照）。競合・エンゲージメント調査は対話セッション側（`/growth-pdca`等）で行う既存パターンを維持する
- Routineサンドボックスは`npm run dev`によるlocalhost接続は可能（2026-09-01の技術検証で確認済み）。ただし`VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`を実行環境に設定しないと実データが表示されない（この2つは公開用の値のため、Routineのセットアップ手順内に直接書き込んでよい）
- YouTube API連携には、Google CloudプロジェクトでのYouTube Data API v3有効化＋対象チャンネルでのOAuth認可（ユーザー自身による一度きりの手動操作）が必要
- 「競艇」表記禁止等、`.claude/rules/code-style.md`の既存ルールに従う
- 既存資産を再利用する: `content-index.json`、`missingContentIndex`検知、`brand-kit.md`、`snsVideoShared.jsx`、`sns_drafts`系スキーマ、`convert_to_note_markdown.py`、既存ブログ品質チェック6項目
