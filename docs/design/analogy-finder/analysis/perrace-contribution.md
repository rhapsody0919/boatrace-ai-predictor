同じ設定で、直前情報8列（展示タイムとその差・順位、天候、風、波）あり／なしの2つのモデルを学習した。学習 2025-06-01〜11-02（23,403R）、温度合わせ 2025-11-03〜12-02（3,825R）、test 2026-04〜09（28,185R）。train.py の設定、木 250本、seed 0 の1回。**縮小版**（学習期間が本番より短い。ありモデルの test の対数損失 1.1999 は、Phase M の F5 の 1.1911 より弱い）。

- **1着の対数損失**: あり 1.19993、なし 1.21135。**差（なし − あり）＝ +0.0114 [+0.0090, +0.0139]**（日単位のクラスタ・ブートストラップ、#paired_without_minus_with）。展示がそろったレース 26,781R に限ると +0.0118 [+0.0093, +0.0144]（#paired_live_complete_races）
  - 目安: MD-3 のオッズの上積み（−0.0026〜−0.0038）の約3〜4倍
  - 1位の的中率は 57.1% と 56.7%（#logloss）
- **寄与度**（中心化、#centered_share_mean）:

| モデル | 会場×枠 | 基礎成績 | ST・直前 | 機力 | 環境 | 属性 |
|---|---|---|---|---|---|---|
| ありモデル | .356 | .343 | **.147** | .074 | .021 | .059 |

## 3. 展示の後に締切まで間に合うか（本番 DB の読み取り、2026-09-26〜10-01、912R、サブエージェントの実測）
- 展示タイムが DB に入った時刻は `scrape_slots.done_at`（job=exhibition、offset=-33、outcome=ok）。`exhibition_data.created_at` は、2026-09-29 から体重だけを取るスロット（-60）が先に行を作るので使えない
- **DB に入ってから締切（`races.start_time`、締切予定時刻）まで: 中央値 16.4分、10%点・5%点 12.4分、最小 8.4分。締切後は 0/912**。朝・昼・ナイターで差はほとんど無い（ミッドナイトの中央値は 13.6分）
- 公式サイトの公開から DB までの遅れは、0〜約2分（120秒おきの取り直し）＋処理 約10秒
- 計算＋配信に60秒かかると、締切までに出せるのは100%、締切10分前までは96.6%
- 期間の外では、締切7分前より後に公開されたレースが 0.3〜1.9% ある（`docs/design/scraping-vercel-consolidation/verification-runbook.md:1305`）。これは間に合わない
- ADR-0080 の「展示から締切まで中央値20分」は `created_at` を使った値の可能性が高い。「展示の後では間に合わない」は、GitHub Actions の定時実行に頼る経路の話で、計算そのものの話ではなかった
- **既存の仕組み**: 展示の取得（`api/cron/exhibition.js` → `preRaceHandlers.js` の `runSlotsWithRefresh`）は、展示を書いたレースだけを同じ起動の中で再計算する（`scripts/lib/predictionRefresh.js`、環境変数 `REFRESH_ON_VERCEL`）。既存の予想（standard 等）は、展示が DB に入ってから数秒以内に書き直されている

## 4. どこで計算するか
- 計算量（本番の3本＝木 830本に換算）: 1レース（6艇）の推論＋SHAP は Python で CPU 約57ms、JS で約0.11秒。168R で Python 約9.5秒、JS 約20秒（いずれも load average が非常に高い状態での CPU 時間）
- モデルの大きさ（3本の推定）: テキスト 約2.9MB（gzip 1.25MB）、JSON ダンプ 約10.2MB

| 実行場所 | 判定 | 理由 |
|---|---|---|
| Vercel の Node 関数で TreeSHAP を JS に移植 | **可** | 117行の試作（`treeshap.mjs`）が Python の pred_contrib と誤差 4.4e-16 で一致（1,008艇、カテゴリ変数と欠損を含む）。関数の上限（250MB・300秒・2GB）に余裕で収まる。展示の取得の直後のフックに足せる |
| Vercel の Python 関数 | 条件付き | 依存の合計 約187MB（上限 500MB）。lightgbm が使う libgomp が実行環境にあるかは、デプロイしないと分からない。前例なし |
| Vercel の Edge 関数 | 不可 | コードの上限（gzip 後 1〜2MB）にモデルが収まらない |
| Supabase Edge Function | 条件付き | CPU 時間の上限が1リクエスト2秒。1レースずつなら収まる。前例なし |
| 常時起動のワーカー | 無い | 既存のインフラに無い。GitHub Actions の定時実行は遅れが常態で使えない |

- JS 移植の約束: 学習ジョブが、版ごとに Python の pred_contrib を N 行書き出し、JS の結果と一致すること（最大差 < 1e-9、SHAP の合計＝生スコア）を CI で検査する
- 前提: 直前情報以外の36列は出走表の時点で作って保存しておく（選手の過去30走の ST・成績は Python の features.py でしか作れないため、日次の Python ジョブが要る。Vercel Cron → workflow_dispatch）。展示の後は8列だけ差し替える
