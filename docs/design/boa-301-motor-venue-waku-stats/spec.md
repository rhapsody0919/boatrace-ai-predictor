# モーター単体の会場内比較・枠番別成績・選手×モーター×枠成績 spec

対応チケット: [BOA-301](https://linear.app/boat-ai/issue/BOA-301)

## 種別

UI機能（画面・コンポーネントが関わる）

## 背景

[BOA-268](https://linear.app/boat-ai/issue/BOA-268)（選手の会場別・コース別成績、Done）と同様の解像度をモーター側にも求める要望から起票。調査の結果、選手ページの`RacerMotorStatusCard.jsx`・分析ツール「モーター調子」タブ（BOA-265/283）にはモーター単体の通算成績・過去10走比較は存在するが、**枠番別の切り口が一切無い**ことが判明した。

`docs/design/boa-301-motor-venue-waku-stats/`策定時点（2026-09-15）で、以下2件の外部依存調査を別途バックグラウンドAgentで実施中:
- BOA-257（進入コース精度、ヘッドレスブラウザ+Vercel Proでの再現可能性）
- モーター交換日の扱いに関する既存機能（BOA-264/265/283/221）の監査

両方の結果が出るまで、枠番別集計の精度保証方式は未確定（下記「未確定事項」参照）。

## 前提となる重要な事実（設計を左右するため明記）

- **モーターは会場に固定**（`venue_code`, `motor_number`の組で一意）。同一物理モーターが複数会場を跨ぐことは無いため、「会場別」という軸は成立しない。成立するのは「同一会場内での他モーターとの比較」のみ
- **データソースが軸ごとに異なる**:
  - 軸1（会場内ランキング・通算成績）: `venue_motor_stats`（BOA-264、会場公式サイトから毎日スクレイピング済み）で完結。新規データ取得不要
  - 軸2（枠番別成績）・軸3（選手×モーター×枠）: `venue_motor_stats`に枠番の列が無く、公式サイトにも相当ページが無いため、自社`race_entries`×`race_results`から新規に集計する必要がある

## 機能要件

| # | 要件 | 優先度 | 受入基準 |
|---|---|---|---|
| FR-1 | 会場内モーターランキング表示（このモーターは今、会場内で何位か・勝率/2連率/3連率/事故率） | 必須 | `venue_motor_stats`の最新値から、同一`venue_code`内の全モーターを指標順に並べた順位を算出し表示できる |
| FR-2 | 枠番別成績表示（このモーターが1〜6号艇の各枠で使われた時の1着率/2連率/3連率） | 必須 | `race_entries`（`motor_number`, `boat_number`）×`race_results`から枠番ごとに集計し、n数（出走数）を併記した状態で表示できる |
| FR-3 | 枠番別・展示タイム推移表示 | 必須 | `exhibition_data`を枠番別に集計し、直近の推移（スパークライン等）を表示できる |
| FR-4 | 選手×モーター×枠の成績表示 | 必須 | 特定選手が特定モーターを特定枠で使用した際の成績（出走数・1着率等）をn数付きで表示できる。ユーザー合意によりBOA-268のような優先度落ちは行わず、今回スコープに含める |

## スコープ

**やること**
- レース詳細ページ「モータ情報」タブ（PR #661実装済み）に、今日そのレースで割り当てられているモーター・艇番を起点にした凝縮ビュー（FR-1のランキングバッジ＋FR-2/3の「今日の艇番」の枠での実績＋FR-4のドリルダウン）を追加する
- 分析ツール「モーター調子」タブ（`/winning-technique?tab=motor`）に、会場・モーターを選択して6コース全部のグリッド比較・選手別利用履歴を見られるフル版を追加する
- 上記2箇所は表示コンポーネントを共通化し、埋め込み先によって表示範囲（凝縮/フル）を切り替える設計にする（BOA-265/283と同じ「1つのロジック・コンポーネントを2箇所で使い分ける」パターンを踏襲）

**やらないこと**
- 新規の専用ページ作成
- 会場を跨いだ同一モーターの比較（技術的に成立しないため）
- モーター交換日の記録・追跡機能そのものの実装（これは前提調査の結果を踏まえ、必要なら別チケットとして切り出す）
- BOA-257（進入コース精度）自体の解消（前提調査のみ、解消は別チケット）

## 非機能要件

なし（新規ページを作らず既存画面の拡張のため、追加のパフォーマンス・SEO要件は無い）

## 制約・前提

- 表示コンポーネントは既存の`MotorConditionChart.jsx`（`src/components/analysis/`）を拡張する方針とし、新規に別コンポーネントを一から作らない（`.claude/rules/component-reuse.md`準拠）
- 軸1のデータソースは`venue_motor_stats`（会場公式サイト由来）を正とし、自社`race_results`からの再計算は行わない（既存ADR/plan.mdの規約に準拠、会場ごとの値の方が正確という既存合意による）
- 軸2〜4の自社集計は、[BOA-303](https://linear.app/boat-ai/issue/BOA-303)の規約（会場横断のような大規模集計は日次バッチで事前集計）の対象になるかを実装時に判断する。今回のスコープは「1会場・1モーター」単位の集計であり、BOA-303が問題視する「全会場横断ランキングの都度ライブ集計」とは規模が異なるため、原則ライブ集計で問題ないと想定するが、実装時のパフォーマンス次第では事前集計に切り替える
- 軸4（選手×モーター×枠）はサンプル数が最小になりやすい。既存の基本情報タブ（BOA-306）で確立した「n数併記、n<6は小標本として視覚的に区別する」パターンを踏襲する（合否判定・非表示化はしない、[[feedback_ui_visualization_over_statistical_rigor]]の方針）
- 用語ルール: 「競艇」使用禁止、他は`.claude/rules/code-style.md`準拠

## 未確定事項

| 項目 | 内容 | いつ・誰が決めるか |
|---|---|---|
| 枠番別集計の精度保証 | BOA-257（進入コース精度）の再調査結果次第で、「艇番」をそのまま「枠番」とみなしてよいか、実進入コースへの補正が必要かが変わる | BOA-257再調査Agentの完了後、ユーザーと確認 |
| モーター交換をまたぐ集計の扱い | モーター交換日を考慮せずに集計すると、異なる物理モーターの成績を混在させるリスクがある。交換日データが取得できない場合の代替策（例: 直近N走のみに窓を絞る等）が必要か | モーター交換監査Agentの完了後、ユーザーと確認 |
| 軸2〜4の集計をライブ計算にするか事前バッチ集計にするか | 実装時のクエリ負荷次第（上記「制約・前提」参照） | `/step2`（設計）フェーズで実装者が判断、性能上問題があれば`/step3`で事前集計に変更 |
