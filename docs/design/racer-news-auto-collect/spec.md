# racer-news-auto-collect 仕様書

## 種別
データ・分析機能（画面変更なし。表示は既存 `/racer/:racerId` の `RacerNewsList` コンポーネントをそのまま使う）

対応チケット: なし

## 背景
[[racer-news-feature]]（`racer_news`テーブル、[ADR-0022](../../adr/0022-racer-news-approval-flow.md)で人手承認制と決定済み）の延長。手動承認が手間である一方、defamation/誤情報リスクへの配慮自体は引き続き必要なため、以下の条件を**すべて満たす場合に限り**人手承認を自動チェックに置き換える例外を設ける。

- 情報源が単一の高信頼性ソース（公式サイト／自社DB）に限定されている
- 内容が事実（数値・順位・級別等）であり要約・解釈の余地が無い
- 自社DBとの整合性チェックで裏付けが取れる

対象外の情報（選手の日常的な近況・人間味のあるエピソード等）は、信頼できる自動取得元が存在しないため、引き続き既存の手動リサーチ→承認フロー（ADR-0022）で扱う。

## 機能要件

### FR1: 自社DB由来のグレードレース優勝ニュース自動生成（優先度: 高）
`race_results.rank1`が示す艇番の選手について、そのレースの`races.race_grade`がSG/G1/G2/G3のいずれかであれば、当日のレース結果確定後に`racer_news`へ自動生成する。

受入基準:
- 当日終了した全レースのうち`race_grade IN ('SG','G1','G2','G3')`を対象に走査し、該当racer_idの1着実績を検出できる
- 同一レース（race_id単位）について重複生成しない
- `title`/`summary`は定型テンプレートで生成する（記事文言の直接転載はしない。具体的な文面は`/step2`で確定）
- `source_url`は当該レースの結果ページを指す
- `racer_profiles`に該当racer_idが存在しない場合は生成せず、FR3の要確認リストに記録する

### FR2: 公式ニュースアーカイブ（レーサーデータカテゴリ）からの級別発表取り込み（優先度: 中）
`boatrace.jp/owpc/pc/site/news/`の「レーサーデータ」カテゴリのみを対象に新着記事を検出し、記事本文から選手名・支部・成績数値を抽出する。

受入基準:
- 記事記載の氏名＋支部が`racer_profiles`と一意に一致する場合のみ処理対象とする（一致しない・複数該当する場合はFR3の要確認リストへ）
- 自社DB（`race_entries`等の直近成績）と記事記載の数値が整合していることを確認できた場合のみ`racer_news`へ自動投入する。整合しない場合は投入せずFR3の要確認リストへ
- 既に処理済みの記事は再処理しない（記事IDベースの処理済み管理）
- `summary`は定型テンプレートで生成する（記事文言の要約・転載はしない）
- 「レーサーデータ」カテゴリ以外の記事は対象外（イベント・キャンペーン等）

### FR3: 要確認リストの記録とセッション開始時の提示（優先度: 高）
FR1/FR2で自動投入をブロックされた候補を記録し、次回セッション開始時に確認を求める。

受入基準:
- ブロックされた候補は`data/analysis/racer-news-pending-review/`配下にJSON記録する
- 未確認の候補が1件でもあれば、次回セッションの最初の応答でClaudeが自発的に提示し、投入可否を確認する（既存のTikTok/Xツイート下書きの session-start check と同じパターン。`.claude/CLAUDE.md`へのルール追記が必要）

### FR5: 会場公式サイトの選手コメント取り込み（優先度: 中、少数会場で試験導入）
開催中の会場公式サイトが掲載する「全選手コメント」（意気込み等の短文）を取り込む。選手自身の発言のため、FR1/FR2の「定型テンプレートのみ・要約転載しない」原則の**例外**として、原文ママ引用する。

受入基準:
- 検証対象会場（最初は1〜数会場。具体的な会場選定は`/step2`で行う）で、開催期間中に「選手コメント」ページからコメント本文と選手名を抽出できる
- 開催期間外（プレースホルダー表示のみ）の場合は何も生成せずスキップする
- 抽出した選手名は、その会場・その節に出走している選手（`race_entries`等、自社DBの当該開催スケジュールから判定）と突合して一意に特定する。**支部ではなく「今節その会場に出走している選手か」がマッチングの手がかりになる**（選手の所属支部と出走会場は別概念のため）
- 一意に特定できない場合（同姓同名等）は投入せずFR3の要確認リストへ
- `summary`は原文ママ引用し、出典（会場公式サイトURL）を明記する
- 会場ごとにHTML構造が異なるため、対応会場ごとに専用パーサーを用意する（共通化は困難と判断済み。既存の`beforeinfo`/`raceresult`のページ間HTML差異と同種の課題）
- 対応会場は段階的に拡大する前提とし、未対応会場は単に取り込み対象外（エラーにはしない）

### FR4: 定期実行（GitHub Actions）（優先度: 高）
既存の日次集計ワークフロー（`calculate-accuracy.yml`等）と同様のパターンで、全レース終了後に新規GitHub Actionsワークフローとして自動実行する。セッション開始時に人が手動実行する運用にはしない。

受入基準:
- `workflow_dispatch`でも手動実行できる
- 失敗時も他の日次ジョブ（予測生成・的中率集計等）に影響を与えない（`continue-on-error`等の既存パターンを踏襲）

## スコープ

### やる
- 自社DB（`race_results`/`race_entries`）由来のグレードレース優勝ニュースの自動生成・自動投入
- `boatrace.jp`公式ニュースアーカイブの「レーサーデータ」カテゴリのみを対象にした級別発表の取り込み（DB整合性チェック付き自動投入）
- 少数会場から試験導入する、会場公式サイトの選手コメント（原文ママ引用）の取り込み
- 整合性・一意性が取れない候補の要確認リスト化とセッション開始時提示
- GitHub Actions cronによる定期実行

### やらない
- 「レーサーデータ」カテゴリ以外の記事（イベント・キャンペーン等）の取り込み
- 選手の日常的な近況・インタビュー的なニュースのうち、会場公式サイトの選手コメント以外の自動収集（他に信頼できる自動取得元が存在しないため、引き続き手動）
- FR1/FR2（記事要約系）における要約・言い換えによる転載（定型テンプレートのみ。FR5の選手コメントは原文ママ引用のため対象外）
- 管理画面の新設（ADR-0022の決定を継承）
- 初期導入時点での24会場一括対応（段階的に拡大する）

## 非機能要件
- 生成される文言は既存の表記ルール（「競艇」使用禁止等、`.claude/rules/code-style.md`）に従う
- 自動投入は既存の手動承認フロー（ADR-0022）と共存する。Claudeが手動でリサーチして提示する経路も引き続き有効
- スクレイピング失敗・パース失敗時は、他の日次ジョブに影響を与えない

## 制約・前提
- データ源: 自社Supabase（`races`/`race_entries`/`race_results`/`racer_profiles`）＋`boatrace.jp`公式サイト（スクレイピング）
- 既存`racer_news`テーブルに`status`カラムは無い（ADR-0022の前提を維持。自動投入されたものは「承認済み」と同等に扱う）
- 処理済み記事の状態管理には新規の永続化先が必要（新規テーブル or JSONファイル、`/step2`で確定）
- 支部を含む氏名一致では同姓同名の別支部選手と誤認しないよう注意する
- `race_grade`の値は実データで確認済み: `ippan`/`G3`/`G2`/`G1`/`SG`の5種類（実データ件数: ippan 855, G1 101, G3 29, G2 13, SG 2 ※サンプル取得時点）
