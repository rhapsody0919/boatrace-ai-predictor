## 1. 現状の実装を読んで判明した訂正（3件）

洗い出しの前に、既存コードのコメントに記録された前提が現在は成り立たないことが3つ分かった。いずれも設計の出発点が変わる。

### 1.1 「ST考察・逃げシミュレーションは自社DBに存在しない」は誤り

`src/components/race/RaceWakuInfoTab.jsx` の冒頭コメント（BOA-307、2026-09-16）:

> 調査結果（チケット項目3、対象外）: 「逃げシミュレーション」「ST考察（安定率/抜出率/出遅率）」に相当する集計・カラムは自社DBに存在しない（grep調査済み、2026-09-16）。無理にダミーで埋めず対象外とする

**事前集計カラムが無いのは事実だが、算出できないのは誤り**。`race_start_timings.start_timing` / `is_flying` と `race_results.actual_course_1〜6` から算出できることを2026-09-23に本番DBで確認した（[spec.md FR-1・FR-6](./spec.md)）。grepで「それらしいカラム名」を探す調査だったため、生データからの導出可能性が検討されていなかった。**実装時にこのコメントを更新する**。

### 1.2 コース別成績が「艇番＝コース前提」で集計されている

同じコメント:

> コース別成績: getRaceRacerStatsが返すracerStats … の courseRaceCounts（racer_aggregated_stats由来、全国合算・全期間、**艇番＝コース前提**。実際の進入コース変化はBOA-257の制約により区別できない）

**BOA-257はDoneで、`race_results.actual_course_N` の充足率は99.7〜99.9%**（直近1年で取れないレースは1,628 / 45,125＝3.6%）。実進入コース基準に直せる。

ただし現状の `courseRaceCounts` は `racer_aggregated_stats`（事前集計、全期間）由来で、実進入コース基準に変えるとデータソースそのものを差し替えることになる。**FR-1の期間別×コース別グリッドは実進入コース基準（`actual_course_N`）で新規に作り、既存のコース別バーとは出所を分ける**。両方を並べると同じ「コース別成績」が違う値で2つ出るため、[§8の論点1](#8-モックで確認したい論点)として扱う。

### 1.3 基本情報タブの期間別フィルタは既に存在する

`RaceBasicInfoTab.jsx`（BOA-306）は既に以下を持つ。spec.md FR-2 の「期間別グリッドがレース詳細に無い」は不正確で、正しくは「**チップで1つずつ切り替える形式のため一望できない**」。

| 軸 | 現在の選択肢 |
|---|---|
| 指標（METRICS） | 勝率 / 2連対率 / 3連対率 / 平均ST |
| グレード（GRADES） | 全体 / 一般戦 / SG・G1 |

n併記・小標本フラグ（`rbit-n.is-small-sample`、`--color-warning-text`）・バーの網掛け（`rbit-bar-fill.is-small-sample`）も実装済み。**FR-2は「新規に作る」のではなく「既存のチップ切替をグリッドに再編する」**のが正しい。

既存のチップ切替（[§1.3](#13-基本情報タブの期間別フィルタは既に存在する)）を、**行＝期間・条件 × 列＝艇番**のグリッドに再編する。FR-0の共通コンポーネントの2例目。

```
        │  ①   │  ②   │  ③   │  ④   │  ⑤   │  ⑥   │
────────┼──────┼──────┼──────┼──────┼──────┼──────┤
一般戦   │ 2.36 │ 2.65 │ 3.00 │ 3.32 │ 4.06 │ 3.26 │
SG/G1    │  —   │  —   │  —   │  —   │  —   │  —   │
初日     │ 2.88 │ 2.38 │ 3.67 │ 3.17 │ 4.00 │ 3.27 │ ←FR-4dで新規に可能
最終日   │ 1.00 │ 2.00 │ 2.00 │ 3.60 │ 3.33 │ 3.19 │ ←FR-4dで新規に可能
波5cm超  │ 2.40 │ 2.71 │ 3.10 │ 3.28 │ 4.11 │ 3.30 │ ←新規（気象から算出可）
```

日和の条件区分と、龍神レーダーで出せるかの対応。**この表が実装範囲を決める**。

| 日和の区分 | 龍神レーダー | 根拠 |
|---|---|---|
| 今期 / 直近3ヶ月 / 直近1ヶ月 | **実装済み**（`PERIODS`） | `RaceBasicInfoTab.jsx` |
| 一般戦 / SG・G1 | **実装済み**（`GRADES`） | 同上 |
| 当地 / 全国 | **実装済み**（`scope`） | 同上 |
| 初日 / 最終日 | **FR-4dで新たに可能** | `race_series.start_date` / `end_date`（2019-04-01〜2026-10-05、6,312節、730日窓を完全にカバー）。現在は `race_conditions.series_day` / `is_final_day` が実データ全nullのため削除済み。**anon SELECT権限が無いのでGRANTが前提** |
| 波5cm超 | **新たに可能** | `race_conditions` の波高（充足95.5〜96.3%）。既に匿名から読める |
| ナイター | **不可** | 開催時間帯が未取得（data-catalog: index/raceindex由来、判定「望ましい」）。`race_series.kind` は ippan/g1/g3/lady/rookie/venus/masters/g2/sg のシリーズ種別のみで、時間帯は含まない（実測） |
| F持 | **条件区分としては不可／当日の表示項目としては可能**（下記） | `race_entries.f_count` / `l_count` は**列も値も存在する**（マイグレーション081）。data-catalog N13の「取得なし」は古い記述。ただし充足率が低い |

**F持についての実測（2026-09-23）**: data-catalog N13は「取得なし」と書いているが、`race_entries.f_count` / `l_count` は実在し値も入っている（同時に `weight_kg`・`branch` も同じ）。**ただし充足率は条件区分に使えるレベルではない**。

| 期間 | f_count の充足率 |
|---|---|
| 直近1年 | **約4.5%**（11,250 / 約250,000行） |
| 2026-09（月別で最良） | 19.0% |
| 2026-08 / 07 / 06 / 05 / 04 | 2.7% / 6.8% / 8.2% / 5.6% / 1.4% |
| 2026-03以前 | 0% |
| **2026-09-21 / 22 / 23（日別）** | **61.5% / 99.4% / 87.2%** |
| 2026-09-16〜20（日別） | すべて0% |

つまり**2026-09-21から安定して入り始めた**（2026-04〜08の値は特定日のバックフィル分と見られる）。したがって:

- **「F持」を過去成績の条件区分（行）として使うのは不可** — 選手ごとに「F持ちで走った過去レース」を集める必要があり、過去の充足率4.5%では母数がほぼ残らない
- **F数・L数を当日の出走表の表示項目として出すのは可能** — 判定に必要なのは「今走る選手の現在のF数」だけで、2026-09-21以降はほぼ揃っている。FR-2のグリッドの行ではなく、**基本情報タブの選手行に「F1」等のバッジ**として出すのが適切（日和も選手情報の一部として持っている）
- 同じ理由で `weight_kg`（選手の登録体重）・`branch`（出走時点の支部）も当日分は表示可能（data-catalog N14）

- 出せない区分（ナイター）と、条件区分としては使えない区分（F持）は**行ごと出さない**。「—」の行を並べない
- **data-catalog N13・N14の記述（「取得なし」）は現状と合っていない**。取得基盤側（BOA-353配下）で更新してもらう必要がある（本specの範囲外）
- FR-4c（`racer_period_stats` の期別成績・能力指数）は「**前期**」の行として足す。前期の平均STは racelist の平均STと一致することが実測で確認済み（data-catalog N13）

## 5. デザイントークンで表現できる部分／新規CSSが必要な部分

### 5.1 トークンで足りるもの

- 色・余白・角丸・フォントサイズはすべて `src/styles/design-tokens.css` の意味トークン（`--text-primary` / `--text-secondary` / `--surface-card` / `--surface-page` / `--border-hairline` / `--spacing-*` / `--radius-*` / `--font-size-*`）
- 差の符号の色分けは `--color-success-text` / `--color-error-text`（どちらもダークモードで自動反転する。Layer 1の生パレット値は使わない）
- 小標本の表現は既存の `is-small-sample`（網掛け＋`--color-warning-text`）をそのまま流用
- 艇番チップは `BOAT_COLORS`（`src/utils/colors.js`）。1号艇（白）・2号艇（黒）は輪郭を付けて背景に沈まないようにする（ピットレポートで確立した扱い）

### 5.2 新規CSSが必要なもの

| 要素 | 内容 |
|---|---|
| クロス集計グリッド | `display: grid` ＋ 行ラベル列の `position: sticky; left: 0`。グリッド内だけの `overflow-x: auto`（ページ全体を横スクロールさせない） |
| 直近10走の帯 | 10本（モバイルは5本×2段）のフレックス。着順の濃淡 |
| 逃げシミュレーションの横棒 | 既存の `rwit-bar-track` / `rwit-bar-fill`（枠別情報タブのバー）を流用できる見込み。流用できない場合のみ新規 |
| ST考察の3行レイアウト | 「値」「コース平均」「差」の3列。モバイルでは2行に折り返す |

### 5.3 日和の「赤・黄セル背景」をどう扱うか

日和は上位2艇をセル背景（濃い赤＝1位、黄＝2位）で強調している。**そのまま持ち込まない**。

理由: `DataRaceTable.css` に「最良値セルの強調はブランドアクセント（金）を使う唯一の箇所」というコメント付きで `drt-best`（金14%背景＋40%インセット枠）が定義されている。赤・黄を新たに導入するとブランドカラー体系（`docs/reference/brand-kit.md`）から外れ、かつ既存の「金＝最良値」という意味づけと競合する。

**方針**: 金の強度で2段階にする。1位＝`color-mix(... 14%)`（既存の `drt-best` と同じ）、2位＝`color-mix(... 7%)`。3位以下は無装飾。実際に2段階が判別できるかは[§8の論点2](#8-モックで確認したい論点)でモックで確認する。

## 8. モックで確認したい論点（ユーザー判断）

1. ~~コース別成績を2つ出すか~~ → **2026-09-23に(b)で決定**。既存のコース別成績バーを**実進入コース基準（`actual_course_N`）に作り直して期間別グリッドに統合する**。ドリルダウン（タップで直近10走）はグリッドのセルタップに移す。同じ指標が2つの値で並ぶのは phase a の目的（可視化で分かりやすくする）に反するため。`racer_aggregated_stats` 由来の `courseRaceCounts` はこのタブでは使わなくなる（他の利用箇所への影響は `/step2` で確認する）
2. **強調の2段階が判別できるか** — 金14%（1位）と金7%（2位）の差がライト・ダーク両方で見分けられるか。無理なら1位のみ強調に留める
3. **日和の「ST分布値一覧」「ST履歴（詳細）」を入れるか** — 画面にボタンがあり、STのヒストグラムと全走の履歴が見られるらしい。`race_start_timings` から作れるが、情報量が増える。phase aに入れるか次段階か
4. **直近10走にモーター2連対率を入れるか** — 日和は入れている。帯1本に4要素（コース・着順・ST・モーター）は詰め込みすぎに見える
5. **逃げシミュレーションを会場別で出すか、全国で出すか** — 会場別のほうが有用だが、会場×1年で母数が400前後（全国は23,056）。母数が小さい会場での閾値とフォールバックの方針
6. **会場ページでBOA-222のランキングバッジと1カードに統合するか** — 「今日この会場はどういう日か」を1つのカードにまとめるか、ランキングとサマリーを分けるか
7. **基本情報タブのグリッド化で、既存のチップ切替を残すか** — グリッドにすると指標（勝率／2連対率／3連対率）の切替チップは残るが、期間・グレード・当地のチップは行に吸収される。プリセット（当地×一般戦 等）の扱いをどうするか
