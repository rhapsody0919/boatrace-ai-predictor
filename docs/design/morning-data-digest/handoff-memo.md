# 「本日のデータ一覧」ページ・SNS展開 引き継ぎメモ

新セッション（新worktree）向け。このファイルを読んでから着手する。ここに書かれた内容は2026-09-23時点の実測に基づく。日付が経つほど古くなるため、着手前に該当箇所を再実測すること（この一日だけでも複数のdata-catalog.md記載が「記載時点では未対応」→「数日で解決済み」に変わった実績があるため、記載を鵜呑みにせず実測する）。

## 1. 目的

競合（ボートレース日和）が毎朝X（旧Twitter）でこの投稿をしている。

```
【本日のデータ一覧(9/23】

本日は若松のG1ヤングダービーが2日目
また下記の場が優勝戦です
・江戸川
・住之江
・宮島

朝一に下記の情報チェック🔽
https://kyoteibiyori.com/blog/202609230001

・逃げ70%/逃し50%以上レース
・捲率25%以上
・中間整備情報
・昨日Fと帰郷、途中追加選手
```

リンク先ページ（実際に開いて確認済み。URL: https://kyoteibiyori.com/blog/202609230001）の内容は6セクション:

1. 昨日のフライングと出遅れ選手（選手名・場・レース・枠・ST）
2. 昨日の帰郷選手（選手名・場）
3. 本日の途中追加選手（無ければ「本日追加選手はいません」）
4. 本日の中間整備（無ければ「本日の中間整備はありません」）
5. 逃げ70%以上/逃し50%以上 期間直近1年/6ヶ月共通レース（選手名・場・レース・締切）
6. まくり率25%以上のレース（選手名・場・レース・枠・捲率・締切）

**目的は「同じものを作る」ではなく、龍神レーダーとして昇華・改善させたページを作り、X/YouTube/blog/noteへ毎朝展開すること。** 「6項目そのまま」を最終形と思い込まない。§5に方向性を書いた。

Xの投稿API連携は無い（用意していない）ため、**sns-hub管理画面から手動投稿する運用**になる。

## 2. フェーズ分割（ユーザー承認済み）

「昨日の帰郷選手」「本日の途中追加選手」「本日の中間整備」の3セクションは、公式サイトの`race/information`ページ（`race_special_notes`テーブル）に依存するが、このテーブルは稼働開始から0件のまま（[BOA-353](https://linear.app/boat-ai/issue/BOA-353)関連、data-catalog.md N28）。原因調査中で、[PR #796](https://github.com/rhapsody0919/boatrace-ai-predictor/pull/796)（2026-09-23マージ）で「通知検出時に生HTMLを保管するフック」を仕込み、実例が本番で捕捉されるのを待っている段階（数日〜1週間の見込み、能動的な作業ではなく観測待ち）。

**この観測待ちのために新機能全体を止めない。**

- **Phase 1（今すぐ着手可）**: 逃げ70%以上/逃し50%以上レース、まくり率25%以上のレース、昨日のフライング選手（出遅れは除く、理由は§3参照）
- **Phase 2（N28の実例が取れてから）**: 帰郷選手、途中追加選手、中間整備情報

## 4. 着手前に必ず確認する既存コンポーネント（車輪の再発明を避ける）

検索した結果、関連しそうな既存資産が既にある。**新規実装の前に必ず中身を読むこと。**

- **`scripts/daily/todays-volatility-digest.js`** ＋ **`src/components/race/TodaysVolatilityHighlights.jsx`**: 「本日のレースをハイライトし、Web表示とSNS投稿ダイジェストで同じデータソースを共有する」という、今回作りたいものと**ほぼ同じ構造の先行実装**。ヘッダーコメントに「Web/SNS間で表示内容が食い違うことはない」という設計意図が明記されている。**このペアを設計の出発点にする**
- `src/components/analysis/NigeOutcomeChart.jsx`: 逃げ成功時の複勝分布（winning_technique='逃げ'で絞り込み）。集計クエリの書き方の参考になる
- `src/components/race/AttackDefenseTable.jsx`・`AttackDefenseAnalysis.jsx`・`TurnPatternList.jsx`: 決まり手・攻守分析の既存タブ。「まくり率」「逃げ率」に類する指標が既にどこかで計算されていないか確認する
- `src/components/race/VenueTendencyPanel.jsx`: 会場傾向パネル

## 5. 「昇華・改善」の方向性（ユーザー指示）

競合ページはテキスト+素朴な表のみ。差別化ポイントの案（新セッションで深掘りし、モック提示時にユーザーと合意する）:

- **可視化**: 表の羅列で終わらせず、グラフ・チャート化する（進行中の別セッション「UI/UX刷新 phase a（可視化強化）」と方向性が重なる。**§6の重複注意を必ず読むこと**）
- **文脈・説明の付加**: 「なぜこの指標が重要か」「今日はどのレースに注目すべきか」という、数値の並びだけでは伝わらない解釈・優先順位付けを加える。プロジェクトの基本方針（「予想の的中率では戦わず、分析ツールとして戦う」、`docs/design/analogy-finder/spec.md`参照）と合致させる
- **ブランド統一**: `docs/reference/brand-kit.md`のギャラリーを確認し、既存の採用実例と矛盾しないデザインにする
- 「6項目そのまま」に縛られず、龍神レーダー独自の項目を足す／競合の項目でも自社データで裏付けが弱いものは無理に真似ない、という判断も可

## 5.5 実装着手前の独立レビューが必須になった（2026-09-23〜、project-wide rule）

`.claude/rules/sdd-workflow.md`に新しいルールが追加されている。**`/step3`でtasks.mdを書き終えた後、`/step4`の実装に入る前に、Agent toolで独立エージェントのレビューを必ず挟む**（省略不可）。追加のきっかけは、まさに「UI/UX刷新 phase a」（`analysis-visualization-upgrade`）セッションで実際に起きた手戻り: `/step1-spec`〜`/step3`まで通した設計に対し独立レビューで33件の指摘、うち「集計窓『730日／直近1年』が実データでは295日しかない」「Fの符号正規化の効果を逆に記述」「事前集計のキー設計がグレードの交絡を無視」という、**仕様の前提そのものが誤っていた**指摘が含まれていた。

**今回のPhase 1（逃げ70%以上/逃し50%以上、まくり率25%以上）は「直近1年/6ヶ月」という期間窓を扱う点で、この失敗例と同じ罠に落ちやすい。** レビュー依頼では、最低限「集計窓（1年・6ヶ月）が実データの分布に対して本当に成立するか（対象選手の出走数が母数として十分か、期間の定義が複数箇所で食い違っていないか）」を明示的に確認させること。詳細な依頼の作法は`sdd-workflow.md`§「実装着手前に天才エンジニアの独立レビューを必ず挟む」を参照。

## 6. 他セッションとの重複に関する注意（重要）

`ListAgents`で確認したところ、**「UI/UX刷新 phase a（可視化強化）」セッションが既に進行中（busy状態）**。これは以前合意した「既存の分析タブをkyoteibiyori踏襲+可視化で昇華させる」という広いテーマのセッションで、今回の「本日のデータ一覧」ページと**視覚化強化という方向性が重なる**。

- 新セッション開始時に、まず`ListAgents`で「UI/UX刷新 phase a」セッションの状態を確認する
- 可能なら`SendMessage`でそのセッションに「今、可視化強化でどのコンポーネント・タブに手を入れているか」を尋ね、重複するコンポーネント作成（特にチャート系）を避ける
- 場合によっては、今回のタスクを独立セッションにせず「UI/UX刷新 phase a」セッションのサブタスクとして統合したほうが良い可能性がある。ユーザーに一言確認してから統合するかどうかを決めてよい

## 7. SNS展開の接続先（ゼロから作らない）

無人投稿基盤は無く、手動投稿前提（X APIは未整備）。既存のsns-hubパイプラインに新しい「ネタ種別」として乗せる設計にする。

- `docs/design/sns-topic-gate/`（plan.md・spec.md・screens.md）: ネタ→チャネル別下書き生成→sns-hub管理画面での承認・投稿、という既存アーキテクチャ
- `docs/operation/sns-pipeline-{blog,note,x,tiktok,youtube}.md`: チャネルごとの生成プロンプト・ルール
- `.claude/rules/content-ops.md`・`.claude/rules/sns-content-generation.md`: 横断ルール（`fitHeadline()`、主要ビジュアル要素の中央寄せ等）
- 投稿の最終送信は、このプロジェクトでは常に個別の明示的承認が必要（バッチ化の対象外）

## 8. 進め方

1. 新しいworktree・新しいブランチを`master`から作る（このオーケストレーションセッションとは独立させる）
2. §6の重複確認を先に行う
3. `/step1-spec`から着手（UI機能として分類。既存のSDDフローに従う）。§3のデータreadinessと§4の既存コンポーネントを読み込んだ上で質問に答える
4. spec確定後、`/step1-screens`でモックを作り、**実装前にユーザーの承認を得る**（プロジェクトCLAUDE.mdの「大規模な新機能はモック承認後に実装」ルール）
5. SNS展開は§7のsns-topic-gateへの新規ネタ種別登録として設計する
