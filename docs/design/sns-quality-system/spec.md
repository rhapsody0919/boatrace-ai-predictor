## 1. 実行タスク

### T1: BGMの末尾切れ（実測23.4%）

| | 実測（`sns-hub-media` の mp4 **184本**を全数計測） |
|---|---|
| 発生 | **43本（23.4%）** |
| 内訳 | x-ja 15/70・tiktok-ja 12/50・youtube-ja 11/39・tiktok-en 2/12・x-en 1/11・x-ja-v2 2/2 |
| 無音長 | 0.451〜7.299秒 |
| 原因 | **43本すべて `silence_start` が 13.09575 の一点**＝「動画尺 − BGM尺13.056秒」 |
| 動画尺 | 9.728〜30.059秒（20.1秒が65本と最多） |
| BGM資産 | `soundtrack-hitcheck.wav` 13.056秒 / `soundtrack.wav` 11.000秒 / `soundtrack-young.wav` 13.000秒 |
| `loop` | `staticFile("soundtrack…")` 26箇所中2箇所のみ（`VenueRankingCM.jsx:1396`・`ToolTallyCM.jsx:462`。いずれも意図的な差ではない） |

**対処（3点セット。1点では止まらない）**

1. **BGM資産を長くする。** `ffmpeg -i a.wav -i a.wav -filter_complex acrossfade=d=1.0:c1=tri:c2=tri` を2回 → **37.17秒・6.56MB**（前例 `note-bgm-calm-corporate-relax.wav` 50秒・8.8MB の範囲内）。
   単純連結や `loop` では、資産の先頭0.3秒が -16.6dB・末尾0.36秒が -18.7dB（本体 -9.5dB）のため**13.06秒地点に約9dBの谷**ができ、`silencedetect -50dB` では検出できない。`acrossfade` なら継ぎ目の mean が -11.0dB（本体との差1.5dB）に収まる。
   **これが唯一のソース非依存の対処。** レンダリングは `VenueRankingCM_batch0831.jsx`・`root-adhoc-0831.jsx` 等の**非コミットの自己完結ファイル**から行われており（`renderEnv` に明記）、コミット済みコードを直しても次のコピー元に届かない。実際、08-30/31 にアドホックで `loop` を入れた後も **9/3〜9/15 に22本の無音動画が posted まで到達**している
2. コミット済み24箇所に `loop` を付ける。副作用は実測で否定（`loop` を記録した下書きの動画は末尾無音0件、`volume` と独立）。`<Bgm>` 共通化は、共通モジュールを import しているのが5ファイルだけで工数が同じ、かつアドホックコピーに波及しないため採らない

### T2: 末尾無音の検知と阻止（2段）

**判定式**（184本で検出43件・偽陽性0件・取りこぼし0件を確認）:
- `ffmpeg -af silencedetect=noise=-50dB:d=0.4`
- 最後の `silence_end` が `duration - 0.05` 以上、または `silence_start` 以降に `silence_end` が出ない
- 冒頭のフェードイン4本（`silence_start 0` / `silence_end 2.545`）はこの条件で正しく除外される

**2段にする理由**: nightly だけでは posted を止められない（実測で22本が到達済み）。

| 段 | 場所 | 役割 |
|---|---|---|
| 検知 | `.github/workflows/content-ops-nightly-check.yml` | 前日分の新規 mp4 を測り、結果を**DBの列に書く** |
| 阻止 | `api/admin/sns-hub/drafts/[id]/approve.js` | 判定列が fail の下書きは 409 を返す |

**結果の保存先はファイルにしない。** 同じ nightly の `check-revision-escalation.js` は dedup 用 JSON を `.gitignore:55` 配下に書き、ワークフローが何もコミットしないため毎晩リセットされ、**同一タイトルのLinear issueを14件積み上げている**（BOA-374/375/377/378/384/385/387/388/392/393/415/416/446/447、うち8件はDuplicate処理済み）。同じ形を繰り返さない。

**ffmpeg は runner で使える。** 前例: `.github/workflows/post-x-animation.yml:35-36` が `sudo apt-get install -y ffmpeg` している。

**要対応**: 対象範囲（新規のみ／全件）、再通知の抑制、`scripts/maintenance/verify-registry.json` への登録。

### T3: `title` 列の位置づけ（**格下げ**。質への寄与は0と明記する）

v5 はこれを「不満16件中1件に対応」としたが**誤り**。

- `title` 列は **2026-09-02 追加**で、COMMENT は `'blog/note下書きのタイトル'`。x/tiktok 用に導入されたものではない
- insight（2026-09-01）が求めたのは**画面上のタイトル**。実際にフレームを抜くと、09-07 trivia は「B2級のスタートは、A1級より1.3倍遅い」を最上部に大きく表示、09-06 live-prediction-hook も見出しを表示しており、**部分的に守られている**
- 苦情の対象だった 09-01 tiktok venue-ranking には**既に「1号艇勝率ランキング」という見出しがあった**。不満は「無い」ではなく「具体性・目立ち方」

**よって T3 は「ユーザー体験の質」には 0/16 しか寄与しない。** 残すなら位置づけは「blog/note と同じメタデータを動画チャネルにも埋める」であって、品質ゲートではない。

CHECK 制約で強制する場合の既知の障害: **既存違反行が179件**（pending_review 36 / approved 9 / posted 60 / archived 74）。`NOT VALID` を付けても PostgreSQL は既存行の UPDATE 時に評価するため、`updateDraft()` 経由の承認・アーカイブ・mark-posted が **45件で400を返して壊れる**。回避策は(a)バックフィルしてVALIDで張る (b)`created_at < '<適用日リテラル>'` を OR に入れる (c)BEFORE INSERT トリガ、の3択。式は `platform NOT IN ('x','tiktok') OR btrim(coalesce(title,'')) <> ''`。

## 3. ネタ選定に今は着手しない理由

| 案 | 実データで崩れた点 |
|---|---|
| `topic_text` 類似度で既出を落とす | 承認済み82件中、最近傍 cosine 0.5超が58件。campaign連載（41件）は最近傍 cosine の中央値0.918、さらに**同型テンプレの別会場**（「『○○』会場の1コース勝率…」）でも 0.531〜0.859 |
| クールダウンの横展開 | `recordUsage()` は呼び出し元ゼロ。ただし `trivia` の実データは15グループで軸が分散しており、**反復という実害は観測されていない**（優先度が低いという意味であり、作動させれば効くという意味ではない） |
| 「古いデータ」の機械判定 | 当の3件は作成日当日のレースを指している。**データが古いのではなく、ユーザーが何を「古い」と呼んだかが不明**。1問確認すれば済む |
| 却下コードの保存をマイグレーションで足す | `TOPIC_REJECTION_REASONS` の7ラベルは一意なので逆写像で今日から集計できる。真のボトルネックは**却下が7件・うち6件が同一理由**という母数 |
| 却下フィードバックを生成側へ戻す経路の新設 | `sns_strategy_insights` に `source=revision-feedback` が2件 active で経路はある。ただし **`referenced_insight_ids` が入った12件はすべて own-metrics の insight を指しており、revision-feedback 2件を参照した下書きは0件**。`getActiveInsights()` のコードからの呼び出し元も0件で、**読み戻しが実行された証跡は無い** |

## 4. 前提（体制の外側）

- 生成Routineが2026-09-15から意図的に無効（週次上限を開発へ。`claude-account-migration.md:47,184`）
- TikTokのシャドウバン未解消（発覚2026-08-29）。tiktok posted 10件は全期間内で対照群が無い

## 5. これで質は担保されるか — されない

T1〜T3 が直すのは:

- **T1/T2**: 末尾無音。**修正依頼16件のうち音に言及したものは0件。** セルフレビューが見つけた欠陥で、ユーザーが体験した不満とは別系統。ただし無音動画が22本 posted まで到達している客観的事実がある
- **T3**: メタデータ整備。ユーザー体験への寄与 **0/16**

**合計: ユーザーが実際に訴えた不満 16件のうち、0件。**

質の本体（ネタ選定 56%）に届かせるには、Routine の再開と、active insight が実際に読み戻されているかの計測が先。どちらも §4 の前提が解けるまで着手できない。

### ユーザーに委ねる判断

**Routine が停止中の今、T1〜T3 を出す意味があるか。**

- **出す**: 無音動画22本が実際に公開されており、Routine 再開時に同じことが起きる。T1-1（資産差し替え）は1時間程度で、再開を待つ理由が無い
- **待つ**: ユーザーが訴えた不満には0件しか効かない。前提が解けてから、ネタ選定を含めて設計し直す方が無駄がない

## 6. やらないこと

- 一般化を立てること（5回中4回、実データで崩れた）
- 人が読むチェック項目を増やすこと
- 検出力を実証せずにゲートを導入すること
- 判定結果をファイルに保存すること（nightly は状態を持てない）
- 「タイトルが画面に目立つように出ているか」を T3 に混ぜること（OCRが要る別問題）
