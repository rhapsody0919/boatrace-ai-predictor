# 更新のお知らせ（site-updates）spec

- 種別: UI機能
- 元の依頼: オーナー 2026-11-23「アプリ側で機能を追加したり改善した場合に、ユーザーに何をいつどんな更新をしたのかをいい感じに見せられるようにしたい。背景としてはユーザーにこのサイトは逐次更新されていて将来的にも面白い機能が増えていくというのを感じさせたい」
- Linear: なし（窓口の依頼で直接）
- ファンパネル: [fan-panel.md](fan-panel.md)。モック: [mock/](mock/)（承認後に置く）

## 目的

ファンに「このサイトは途切れずに育っている」と感じさせ、再訪の理由を1つ増やす。PV を戻すのが最優先の時期なので、新しい機能へ人を送る入口（トップの帯→その画面）も兼ねる。

## オーナーが決めたこと（2026-11-23、AskUserQuestion）

| 点 | 決定 |
|---|---|
| 置き場 | 専用ページ `/updates`＋ja のトップの1行の帯＋メニューの項目と NEW |
| 書き手 | 機械がマージした PR から候補を出し、窓口が選んでファンの言葉に書く。オーナーは見ない（データだけの PR は段階0。ただし文に pr-lane の H9 の語（的中率・回収率など）が入ると重い道になり人の判断が要る） |
| 予定 | 「今つくっている物」を時期なし・3件まで。載せる物はオーナーが決める |

## 機能要件

| # | 要件 | 優先 | 受入基準 |
|---|---|---|---|
| R1 | `/updates` に更新を新しい順・月ごとに並べる | 必須 | 月の見出し（例「2026年11月」）の下に、日付の新しい順。同じ日は並びがデータの順 |
| R2 | 1件は「日付・札・見出し・1〜2文・見てみる」 | 必須 | 札は「新機能」「改善」の2種。`path` があれば「見てみる →」がその画面へ（`localizePath` を通さない。ja 専用）。`blogId` があれば「使い方の記事 →」が `/blog/{id}` へ |
| R3 | 細かい直しは月ごとに畳む | 必須 | 種別 `minor` は月の末に「ほか細かい改善 N件」の `<details>` 1つ。開くと「日付 見出し」の行だけ。N はその月の minor の件数 |
| R4 | 「今つくっている物」 | 必須 | 0〜3件。0件なら枠ごと出さない。時期を書かない。4件以上は verify が赤 |
| R5 | ja のトップの帯 | 必須 | ja のトップ（`/`）だけ。直近14日（JST の暦日で、今日を含め14日）の `feature`・`improvement` のうち最新1件。帯を押すと `/updates` へ。×で閉じるとその件の id を端末に覚え、次に新しい件が載るまで出ない。14日を過ぎたら出ない |
| R6 | メニューの項目と NEW | 必須 | ja のときだけ「更新のお知らせ」。直近7日に `feature`・`improvement` があれば項目に NEW、☰ に赤い点。既読は覚えない（ブログの7日の NEW と同じ決まり） |
| R7 | 候補を出す機械 | 必須 | `node scripts/maintenance/site-updates-candidates.js [--since YYYY-MM-DD]` が、origin/master のマージのうち画面に触れた物（`src/pages`・`src/components`・`src/hooks`・`src/locales/ja`）を Markdown の一覧で出す。既にデータの `prs` にある PR、題がリファクタ・試験・CI・SNS・管理画面・機能フラグの裏の物は外す。既定の起点はデータの最新の日付。読むだけで、何も書かない |
| R8 | データの検査 | 必須 | `verify-site-updates.js`（tier ci）: id の重複なし・日付が `YYYY-MM-DD`・種別が3種のどれか・見出し40字以内・本文90字以内・`path` が `/` で始まる・`blogId` が実在・禁止語なし・`making` が3件以内・並びが日付の新しい順。今日より先の日付は verify では見ない（tier ci は今の時刻に依存しない）。代わりに画面・帯・NEW は今日までの件だけを出す |
| R9 | 断り | 必須 | ページの末尾に「投票は日本国内に住む20歳以上だけ」の断り（新しい案内のページ、AGENTS.md） |
| R10 | 初めの中身 | 必須 | 2026-10-01 以降に出たファンに見える変更を、窓口が候補から選んで入れる（目安 10〜15件、根拠なし）。300行の線のため、10月下旬以降の10件を最初の PR に、10月上旬の残りを次のデータだけの PR に分ける |

## スコープ

やる: 上の R1〜R10。

やらない:
- 4言語の版（他言語のトップに帯を出さない、`TRANSLATED_PATHS` に足さない）
- 項目ごとの個別ページ、RSS、プッシュ通知、X への自動の投稿（SNS は別の担当）
- 各画面の中の NEW の印（オーナーの決定で外した）
- 既読の記録（帯の×だけ端末に覚える）
- 定期の自動実行（GitHub Actions で候補を起票する等）。`.github/workflows/` は作り手が変えられない。窓口が手で回し、回す頻度は運用の文書に書く
- /about・/how-to-use・ブログの変更

## 非機能要件

- 375〜1920px で崩れない（`npm run test:layout` の5幅）。ライト・ダークの両方で読める（意味トークンだけ）
- トップの帯で CLS を出さない: 帯はデータ（同梱の JS）と時計だけで決まり、通信を待たない。最初の描画で出る
- SEO: `/updates` は ja を index し sitemap に足す。title「更新のお知らせ｜龍神レーダー」、description は最新の月の件数を含む固定の文
- 計測: 帯の表示・押下・×、ページの「見てみる」押下を GA4 のイベントで送る（名前と引数は plan で measurement-planner と決める）

## 制約・前提

- データは `src/data/siteUpdates.js`（定数の層。何も上を読まない）。計算は `src/pure/siteUpdates.js`（月ごとの束ね・帯の1件・7日の NEW）。データ層・Supabase は使わない（DB の変更なし）
- 端末の保存は `boatai-user:site-updates-dismissed`（キャッシュの全削除 `boatai:*` で消えない名前空間、`src/config/featureFlags.js` の注釈と同じ）。読み書きは try/catch で、失敗したら帯を出す側に倒す
- 日付は「本番に出た日（JST）」。本番は1日3回の定時（ADR-0106）なので、窓口はその変更が本番に出た後にデータを足す。データの PR 自身も次の定時で出るので、帯が出るのは最大約12時間遅れる（許す）
- 並行で別のセッションが `/winning-technique` と `/racer/` の画面を直している。その2画面のファイルは触らない
- 共通の既存: ブログの NEW の判定 `isWithinDays`（`src/pages/Blog.jsx`）。同じ決まりの純関数が `src/pure` か `src/utils` にあれば使う（plan で `docs/reference/shared-logic-index.md` を引く）

## 既定値で決定した事項（後から覆せる）

| 項目 | 既定値 | 根拠 |
|---|---|---|
| 載せる粒度 | ファンが画面で分かる変化だけ。リファクタ・試験・CI・SEO・記事・内部の文書は載せない | spec-ambiguity-detector の既定値。10月以降に画面に触れた PR は約300本で大半が内部（git log） |
| 帯の期間 14日・NEW の期間 7日 | 14日は目安（根拠なし）。NEW の7日はブログに合わせた。3件まではオーナーの決定。定数1か所に置き、公開後の実データで見直す | ブログの `isWithinDays(post.date, 7)` |
| 「ほか細かい改善 N件」の N | データに書いた minor の件数（数え直さない。配列の長さ） | 集計の値ではなく載せた行の数 |
| 日付の意味 | 本番に出た日（JST の日単位） | ADR-0106 |
| 過去分 | 2026-10-01 以降 | 10月以降はファンに見える変更が続いている（git log）。それより前は掘らない |
| ブログとの関係 | 記事がある件だけリンク。お知らせは短い告知に徹する | ファンパネル |
| 文の書き方 | 「○○できるようになりました」の言い方。開発の言葉・票の番号を出さない | ファンパネル（30代女） |

## モックの承認（2026-11-23、オーナー）

- モック v2 を「このまま承認」。各件に画面の絵は付けない。例文の文体を見本にする（[mock/APPROVED.md](mock/APPROVED.md)）
- 今つくっている物の初めの中身: 「データ分析ツールを見やすく」「選手ページの見直し」。できたら一覧へ移し、見送ったら黙って外す（時期を書かないので「見送り」とは書かない）
