# スクレイピング基盤のサーバーレス移行 調査記録

種別: 調査記録（採用・実装済み。設計は[docs/design/scraping-serverless-migration/spec.md](../../design/scraping-serverless-migration/spec.md)参照）
対応Linearチケット: [BOA-313](https://linear.app/boat-ai/issue/BOA-313)（2026-09-15、実装・並走検証が進んだ後に遡って起票）
関連: [DATA_ACQUISITION_STRATEGY.md](../DATA_ACQUISITION_STRATEGY.md)、[docs/issues/DATA_SCRAPING_GAPS.md](../../issues/DATA_SCRAPING_GAPS.md)、`docs/operation/external-cron-setup.md`

## 背景・問題

ユーザーから「レース前に展示情報を開いてもデータが無い」「レース後に開いても結果が無い」という信頼性への懸念が提起された。調査の結果、根本原因はスクリプトのロジックではなく**GitHub Actionsをリアルタイム処理に使っていること自体の構造的なミスマッチ**と判明した（詳細は下記「発見した根本原因」）。恒久的な解決策として、時間に厳しい処理をVercel Serverless Functionsへ移行する方向で検討を進める。

**重要な方針**: 本番運用中のシステムであり、デグレを絶対に起こさない。移行は段階的に行い、各段階で実データ検証を行う。

---

## 発見した根本原因（2026-09-14調査、実データ・実ログで確認済み）

### 症状
直近3日間で、結果確定済みレースのうち展示データが欠落している割合: 2026-09-12=0.6%、2026-09-13=6.7%、2026-09-14=8.1%。2026-09-13は福岡会場で7レース連続（13時台〜16時台、3時間超）欠落。

### 原因の連鎖（GitHub Actions run履歴・ジョブステップのタイムスタンプで実証済み）

1. `scrape-scheduled.js`オーケストレーターは、レース情報更新・オッズ・展示・結果・予測買い目オッズの5処理を1回の実行で順に処理する設計
2. cron-job.orgから5分間隔で`workflow_dispatch`が発火する（**トリガー自体は健全、5分間隔でほぼ途切れなく発火し続けていることを確認済み**）
3. しかし**オーケストレーター本体の実行だけで4〜10分かかる**ことがある（実測: 06:00:44発火分は547秒、06:05:17発火分は629秒）
4. `concurrency: { group: scrape-scheduled, cancel-in-progress: false }`のため、前の実行が終わるまで次のトリガーはキュー待ちになる
5. キュー待ち中にさらに新しいトリガーが来ると、GitHub Actionsの仕様で**古い方の待機中ジョブは自動的にキャンセルされる**（最新1件のみ保持）
6. キャンセルされた回に割り当てられていた展示データ取得の窓（発走30/15/10分前）がまるごと失われる

さらに、ジョブ開始前の**キュー待ち時間そのもの**も大きい（06:05:17トリガー→06:09:53ジョブ開始＝4分36秒待ち）。ジョブ開始後も、checkout（30秒、`fetch-depth: 0`による全履歴取得）+ npm install（8秒）+ morning-init（18秒）で約1分の固定コストがある。

**結論**: 個々のスクリプトロジック（BOA-57で実装済みの発走時刻ベースの窓判定）は正しく機能している。問題は「複数の処理を1つの直列実行にまとめ、GitHub Actionsのconcurrency機構に頼っている」というオーケストレーション層にある。

## Vercel側の制約調査（2026-09-14、Vercel MCP + 公式ドキュメントで確認）

### 現在のプラン
Vercel MCP（`list_teams`）で確認: **本プロジェクトはHobby（無料）プラン**。

### Cron Jobs（Vercel純正機能）

| | Hobby | Pro |
|---|---|---|
| 実行頻度 | **1日1回まで**（`*/5 * * * *`のような高頻度cron式はデプロイ時にエラーになる） | 1分間隔まで可能 |
| 実行時刻の精度 | ±59分（例: `0 1 * * *`は1:00〜1:59の間のどこかで実行） | 分単位で正確 |
| 登録可能ジョブ数 | 100件/プロジェクト | 100件/プロジェクト |

**→ Vercel純正のCron Jobs機能はHobbyでは使えない**（1日1回・精度±59分では展示データのユースケースに全く合わない）。したがって、外部トリガー（cron-job.org等）から素のAPIエンドポイントを直接叩く方式が必須になる（Vercel純正Cronの制限は「Vercelの`crons`設定」にのみ適用され、外部から直接HTTPリクエストを送ること自体は制限されない）。

### Function実行時間（Fluid Compute有効時、デフォルトで有効）

| | Hobby | Pro |
|---|---|---|
| デフォルト/最大 | 300秒（5分） | 300秒（デフォルト）/800秒（最大）、拡張ベータで最大1800秒 |

現在のオーケストレーター全体（4〜10分）をVercel Function 1本に移植するのはHobbyの300秒上限に対してリスクが高い。**処理を種類ごと（オッズ/展示/結果等）に分割し、それぞれ短時間で終わる別々の関数にする**設計が必須になる（実測ログでは展示データ単体の処理は8レースで約55秒、オッズ単体は12レースで約90秒だった＝分割すれば十分300秒以内に収まる）。

### 使用量上限（Hobby、月間）

| リソース | Hobby上限 |
|---|---|
| Invocations（呼び出し回数） | 100万回 |
| Active CPU（実行中のCPU時間、I/O待ち時間は含まない） | **4 CPU時間** |
| Provisioned Memory | 360 GB時間 |

**要注意**: Invocations（100万回/月）は、1分間隔×複数関数で1日1,440回×関数数×30日程度なら余裕で収まる。しかし**Active CPU（4時間/月）は精査が必要**。スクレイピング処理はネットワークI/O待ちが大半（Active CPU課金対象外）だが、cheerioでのHTML解析等の実CPU時間が仮に1回200msかかるとすると、4関数×1日約900回（レースがある9-23時のみ稼働と仮定）×30日×200ms ≈ 6時間/月となり、**4時間の無料枠を超える可能性がある**。これは見積もりであり、実測が必要（下記「次のアクション」参照）。超過した場合の挙動（実行がブロックされるのか、従量課金が発生するのか）も要確認——Hobbyプランはクレジットカード未登録が前提のため、ブロックされる可能性が高い。もしそうなると、GitHub Actionsの問題を「別の枯渇問題」に置き換えるだけになりかねない。

### 参考: Proプランへのアップグレード（$20/月〜）を検討する価値

Proプランなら: Cron Jobsが1分間隔・分単位精度で使える（cron-job.org依存を解消できる可能性）、Active CPUは従量課金（ハード上限による停止が無い）、関数実行時間の上限も800秒に拡大。月20ドル程度の投資で、上記のHobby特有の不確実性・リスクをまるごと除去できる。**これは技術判断というより費用対効果の事業判断であり、ユーザー側で決めてほしい部分**。

### 追記（2026-09-15）: Proプラン移行確定、cron-job.org依存解消の再調査

ユーザー確認により**本プロジェクトは既にProプランへ移行済み**（Vercel MCP `list_teams`で`"plan": "pro"`を独立に再確認）。上記のHobby前提の懸念（Active CPU 4時間/月の枯渇リスク等）はそもそも解消している。この前提変更を受け、「cron-job.org依存を純正Cronで解消できるか」を公式ドキュメントで再調査した。

**結論: 技術的には解消可能**（Proでは1分間隔・分単位精度、[Cron Jobs Usage & Pricing](https://vercel.com/docs/cron-jobs/usage-and-pricing)）。ただし新たに以下の論点が判明しており、単純な優劣比較ではない。

* **タイムゾーンは常にUTC固定**（[Cron Jobs](https://vercel.com/docs/cron-jobs)）。現行の「7:00-23:00 JST」はUTCでは日をまたぐ範囲（前日22:00〜当日14:00 UTC）になり、cron式は`0-14,22-23`のような時間帯分割表記が必要になる
* **cron-job.orgの30秒タイムアウト制約が無くなる**。純正Cronが直接呼ぶ場合、cronのタイムアウトはFunction自体のmaxDurationと同一（[Troubleshooting Vercel Cron Jobs](https://vercel.com/kb/guide/troubleshooting-vercel-cron-jobs)）。`api/cron/exhibition.js`の即応答+`waitUntil()`設計（案B）はこの30秒制約への対応が動機の一つだったため、純正Cronに切り替えるなら同期処理へ単純化する余地がある（必須ではない）
* **純正Cronにも保証は無い**（[Managing Cron Jobs](https://vercel.com/docs/cron-jobs/manage-cron-jobs)で明記）: 失敗時の自動リトライは無し、配信はbest-effort（まれに未配信・まれに重複配信がありうると明記）、重複実行防止の仕組みも無し（自前ロックが前提。ただし現行実装は`upsert(onConflict: race_id,boat_number)`で既に冪等なので追加対応は不要）。cron-job.orgより明確に劣るわけではないが、**「純正に変えれば信頼性が上がる」とは言えない**
* cron-job.org側の実行履歴という「並走検証期間中の二重監視経路」（上記「追加の利点」参照）を失う

**判断（2026-09-15、ユーザー確認）**: 現在Step 2（並走検証）が進行中のため、ここでトリガー機構自体を変えると「欠落率の変化がStep 2の効果か純正Cron切替の効果か」の切り分けが難しくなる。**BOA-313 Step 3（GitHub Actions側の展示データ処理無効化）完了まで、cron-job.orgのまま現状維持**とし、その後の設計変更として改めて評価する。

## cron-job.org側の制約調査

**2026-09-14、cron-job.org公式サイト（トップページ・FAQ）を直接確認して裏取り済み**。既存の`docs/operation/external-cron-setup.md`（「無料枠: 最大4ジョブ、最小間隔1分」）は**古い/不正確な記載だった**ため訂正する。

| 項目 | 公式サイトの記載 |
|---|---|
| 登録ジョブ数 | 「アカウントごとのジョブ数に制限を設けていない」と明記（ただしフェアユース前提） |
| 最小実行間隔 | 1時間に60回まで＝**1分間隔まで可能** |
| タイムアウト | **30秒**（呼び出し先が30秒以内に応答しないとタイムアウト扱い） |
| 実行時刻の精度 | 「正確性の保証はできないが、遅延は最小限に抑える」という記載のみ（数値的なSLAは無い） |
| 料金 | **完全無料**（サービス全体が無料、有料プランという概念自体が無い） |
| 失敗時の通知 | ジョブ失敗時・復旧時に通知を受け取る機能あり。SSL証明書期限切れの事前通知もあり |
| 実行履歴の閲覧 | 応答内容・タイミング詳細を含む実行履歴を閲覧可能 |
| API | REST APIでジョブ管理が可能（ドキュメントあり） |

**訂正点**: 旧ドキュメントの「最大4ジョブ」は誤りだった可能性が高い（現行の公式記載は無制限）。ジョブタイムアウト30秒は前回調査時点のWeb検索結果と一致し、確度が高い。

**この調査で分かった追加の利点**: cron-job.org自体が実行履歴（応答時間・成否）を保持しているため、**移行後の監視に、GitHub Actionsのrun履歴を見る方法（今回の調査で使った手法）に加えて、cron-job.org側の実行履歴・失敗通知も併用できる**。二重の監視経路を持てることは移行の安全性を高める材料になる。

**設計上の制約（変更なし）**: タイムアウト30秒のため、**cron-job.orgとの通信（Vercel Functionへのリクエスト〜レスポンス）は30秒以内に完結させる設計にする必要がある**。Vercel Function自体はFluid Compute下で最大300秒動けるが、それとは別に「cron-job.orgへの応答」を30秒以内に返す設計（例: 応答を即座に返し重い処理は非同期継続、または1回の処理対象を小さく保ち30秒以内に確実に終わらせる）が要る。

## 推奨アーキテクチャ（暫定、未確定）

```
現状:
  cron-job.org（5分間隔）
    → GitHub Actions workflow_dispatch
      → チェックアウト+npm install（〜1分固定コスト）
      → オーケストレーター（レース情報+オッズ+展示+結果+予測買い目、1本の直列実行、4〜10分）
      → concurrency直列化により詰まる → キャンセル発生

提案:
  cron-job.org（種類ごとに複数ジョブ、頻度は種類に応じて調整）
    → Vercel Serverless Function（種類ごとに分離、例: /api/cron/exhibition, /api/cron/odds, /api/cron/results）
      → 起動コストほぼゼロ（チェックアウト・npm install不要、デプロイ済みコードを呼ぶだけ）
      → 各関数は30秒以内に完結する粒度に保つ
      → 同時実行の直列化に依存しない（各関数呼び出しは独立、既存のexistingIds方式で冪等性は保たれる）

GitHub Actionsに残すもの:
  ML学習、日次集計、選手プロフィール等、分単位の即時性が不要なバッチ処理
```

## 安全な移行のための方針（デグレ防止）

1. **並走期間を設ける**: 新しいVercel Function版を、既存のGitHub Actions版と同時に動かし、両方が同じSupabaseテーブルに書き込む（upsertなので競合しても致命的ではないが、書き込みタイミングのログを両方残して比較する）
2. **ロジックの共通化**: `scripts/daily/scrape-exhibition-data.js`等の既存スクリプトが持つスクレイピング・パース関数はそのまま流用し、呼び出し口（GitHub Actions用のCLIエントリポイント vs Vercel Functionのhandler）だけを分離する。ロジックの二重実装は避ける
3. **データ精度の独立検証**（`.claude/rules/analysis.md`準拠）: 移行後、一定期間の欠落率を移行前と比較し、悪化していないことを確認してから完全切り替えする
4. **段階的ロールアウト**: 展示データ（最もユーザー影響が大きい）から着手し、安定を確認してからオッズ・結果に展開する
5. **切り戻し可能性**: 新方式が問題を起こした場合、GitHub Actions側のワークフローを即座に再有効化できるよう、cron-job.org側のジョブを無効化するだけで切り戻せる構成にする（コードの削除はしない）

## Active CPU実測結果（2026-09-14）

Vercelにデプロイせず、ローカルで実際のスクレイピング＋パース処理を`process.cpuUsage()`で計測した（ネットワークI/O待ち時間を除いた、純粋な実行中CPU時間のみを抽出——Vercelの「Active CPU」課金の定義と一致する近似）。実際に開催中のレース（浜名湖、複数レース）で計測。

| 処理 | 実測CPU時間/レース |
|---|---|
| 展示データ（HTML取得+cheerioパース） | 約30〜60ms（初回はモジュール初期化コストで105ms、以降は30〜40msに収束） |
| オッズ（2ページ取得+パース） | 約27〜69ms |

**月間Active CPU使用量の試算**（1日約180レース、展示は平均1.5回試行/レース、オッズは平均3窓/レースと仮定）:

```
展示: 180レース × 1.5試行 × 50ms ≈ 13.5秒/日
オッズ: 180レース × 3窓 × 50ms ≈ 27秒/日
合計 ≈ 40.5秒/日 × 30日 ≈ 1,215秒/月 ≈ 0.34 CPU時間/月
```

**結論**: Hobbyプランの上限（4 CPU時間/月）に対して、実際のパース処理そのものは**1割にも満たない**。当初懸念していた「Active CPU枯渇によるブロック」リスクは、この試算では大きな問題にならなそうだと分かった。ただし以下は未計測のまま残る:
- 1分間隔で常時トリガーした場合の「対象レース無し」チェック自体のオーバーヘッド（Supabaseクエリの往復含む、恐らく数msだが未実測）
- Vercel上での実測（ローカル計測はコンテナ起動・ネットワークスタックの違いを含まないため、あくまで近似）

これらを踏まえても、桁が1桁以上変わるようなことは考えにくく、**Active CPUはHobby継続の障害にはならなそう**という暫定結論。本番相当のテスト関数をデプロイした際に実測値で最終確認する。

## 将来のインフラ選択（Vercel+Supabase vs AWS等への移行）について（2026-09-14、ユーザーからの追加相談）

「ユーザーが増えたらAWS等への移行が必要か、その場合どの規模で判断すべきか」という質問への回答。

### 結論: 移行の判断基準は「ユーザー数」ではなく「具体的にぶつかった制約」にすべき

Supabase・Vercelのようなマネージドサービスは、想像以上に高いスケールまで単体で耐えられるよう設計されている。実際の料金体系を確認したところ:

- **Supabase**: 無料枠は月間アクティブユーザー5万人・DB 500MBだが、Proプラン（$25/月）で10万MAU・DB 8GB・同時リアルタイム接続500まで拡張。さらに専用コンピュートのアドオンは16XL（256GB RAM・64コア、$3,730/月）まで用意されており、**Postgresを使い続けたまま相当な規模までスケールできる**設計
- **Vercel**: Enterprise帯まで含めれば、大企業の本番サービスも普通に稼働している実績がある基盤

つまり「ユーザー数が◯万人を超えたらAWSへ」という単純な閾値は存在せず、**移行が正当化されるのは以下のような「PaaSでは解決できない具体的な制約」にぶつかった時**:

1. **コストの逆転**: 従量課金の請求額が、自前でインフラを構築・運用するコスト（人件費込み）を明確に上回った時。これは一般に月商・アクセス規模が相当大きくなってから（多くの事例で月額請求が数十万円〜百万円規模になってから）起きる話で、個人〜小規模チーム運営のサービスが自然に到達する規模ではない
2. **PaaSの技術的な天井に当たった時**: 例えば「Vercel Functionの実行時間上限（Enterpriseでも30分が事実上の上限）では終わらないバッチ処理が必要になった」「Supabaseの接続数上限がプーリングを駆使しても足りない」等、具体的な機能不足
3. **コンプライアンス・データ主権要件**: 特定のデータセンター立地・監査要件が必須になった場合（Supabase/VercelもSOC2等は提供しているが、業界によってはより厳格な要件がある）
4. **運用体制の問題**: 自前でAWSを運用するには、セキュリティパッチ・スケーリングポリシー・監視・オンコール等の運用負荷が増える。小規模チームではこのコストがPaaS利用料より高くつくことが多い

### 龍神レーダーへの当てはめ

現状は「スクレイピング・分析中心のサイトで、ユーザーからの書き込みは少ない（閲覧中心）」という特性上、DBの書き込み負荷・接続数のプレッシャーは典型的なSaaSアプリよりむしろ低い可能性が高い。**「Hobby→Proへの引き上げで完全に足りるところまで粘り、具体的な壁にぶつかってから初めてAWS等への移行を検討する」というユーザーの方針は妥当**だと考える。今回のスクレイピング基盤移行についても、AWS Lambda等への移行ではなく、まずVercel Functionsで解決を図る現在の方向性はこの原則と整合している。

**次に見るべき指標**（「ユーザー数」の代わりに）: Supabaseダッシュボードの「Database Size」「Concurrent Connections」「Egress」使用率、Vercelダッシュボードの「Active CPU」「Function Invocations」使用率。これらが継続的にProプランの上限に近づいてきたら、その時点で初めて「次のプラン（Team/Enterprise）で足りるか、それともアーキテクチャごと変えるべきか」を検討すればよい。
