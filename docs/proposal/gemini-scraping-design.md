# **ボートレースデータ分析基盤における最適なスクレイピング設計とアーキテクチャ構築に関する包括的研究**

## **1\. 序論：ボートレースアナリティクスの現状と技術的要請**

近年のスポーツアナリティクスおよび予測モデリングの分野において、公営競技、特にボートレース（競艇）は極めて高度なデータサイエンスの対象として注目を集めている。全国24カ所に存在するレース場において、年間約5万レースという膨大な試行回数が提供されており、選手の級別や勝率、モーターやボートの性能、枠番ごとのコース特性、さらには風向、風速、波高、水温といった気象条件など、勝敗を決定づける多種多様な変数が複雑に絡み合っているためである。精緻な機械学習モデル（AI予測エンジン）を構築するためには、収集した生データから最低でも160以上の特徴量を生成するための網羅的なデータパイプラインが不可欠となっている1。

しかしながら、ボートレースの公式プラットフォームである「BOAT RACE オフィシャルウェブサイト（boatrace.jp）」や、各レース場が独自に運営する公式ウェブサイトからは、システム開発者向けに構造化されたデータを提供する公式API（Application Programming Interface）が用意されていない。過去のレース結果を一括で取得するための有志によるオープンAPI（GitHub上で公開されているJSON形式のエンドポイントなど）は一部存在するものの2、刻一刻と変動する直前情報やリアルタイムなオッズデータ、各レース場が独自に計測している詳細な展示タイムなどを網羅するには至っていない。したがって、実用的なデータ分析プラットフォームを構築するためには、公式ウェブサイト群に対する高度かつ体系的なスクレイピング・アーキテクチャの設計が実質的に唯一の解決策となる。

本研究では、ボートレースにおいて取得可能なあらゆるデータ群を体系的に整理し、利用規約や著作権法等の法的コンプライアンスを遵守しながら対象サーバーへの負荷を最小化しつつ、システムの安定性とデータの網羅性を両立する最適なスクレイピング設計について論じる。具体的には「どのような情報を取得できるか（取得対象）」「何をどのように設計すべきか（技術的アプローチ）」「どのタイミングでスクレイピングを実行すべきか（スケジューリング）」「どれくらいの期間のデータを収集・保持すべきか（データライフサイクル管理）」という中核的な問いに対し、実務的かつ技術的な解を提供する。

## **2\. 取得可能なデータ体系と情報源の構造的分析**

ボートレースの予測モデル構築に必要となるデータは、大きく分けて全国共通の標準データと、各レース場が独自に計測・提供する付加価値データの2層構造となっている。これらを統合することで初めて、多角的な解析が可能となる。

### **2.1. オフィシャルウェブサイトが提供する標準データ**

「BOAT RACE オフィシャルウェブサイト」は、過去のレース成績から当日のリアルタイム情報までを提供する最も基盤となるデータソースである。スクレイピングの対象となる主なページ（エンドポイント）は以下の4種類に大別され、これらは全国24のレース場に割り振られた1〜24の「場コード（jcd）」、8桁の「開催日（hd: YYYYMMDD）」、そして1〜12の「レース番号（rno）」という3つの複合パラメータによって一意のURLとして構成されている2。

| データ種別 | URLパラメータ構造 | 取得可能な主要情報と分析上の意義 |
| :---- | :---- | :---- |
| **出走表 (racelist)** | ?jcd={場コード}\&hd={YYYYMMDD}\&rno={レース番号} | 各レースの出場選手（1〜6号艇）、級別（A1〜B2）、全国勝率、当地勝率、モーター番号、ボート番号、過去の成績履歴。事前予測の最も根拠となる静的データである。 |
| **直前情報 (beforeinfo)** | ?jcd={場コード}\&hd={YYYYMMDD}\&rno={レース番号} | レース開始直前（締切約15分前）に公開される、展示タイム、チルト角度、部品交換状況、天候、風速・風向、水温、波高。当日の環境要因を示す動的データ。 |
| **時系列オッズ (odds)** | odds3t 等の各種識別子 | 3連単、3連複、2連単など各種舟券の倍率。時系列での変動を追うことで、インサイダー的な大口投票（スマートマネー）の動きを検知する時系列特徴量となる。 |
| **レース結果 (resultlist)** | ?jcd={場コード}\&hd={YYYYMMDD}\&rno={レース番号} | 着順（1着〜6着）、決まり手（逃げ、差し、捲り等）、レースタイム、払戻金。予測モデルの正解ラベル（ターゲット変数）として必須の情報。 |

### **2.2. 各レース場独自サイトのデータ（オリジナル展示タイム）**

公式ウェブサイトの標準データに加えて、現代のボートレース分析において極めて重要視され、かつ収集の難易度が高いのが「オリジナル展示タイム（通称：オリ展）」である。これは、公式が発表する直線150mの従来の「展示タイム」に加えて、レース前の展示航走における各セクションのタイムを各レース場が独自に計測・公表しているものである5。

オリジナル展示タイムは主に「一周タイム」「まわり足タイム」「直線タイム」の3種類から構成されており、それぞれがモーターの機力や選手の操縦技術を反映している5。一周タイムはモーターと選手の総合的なスピードを示し、まわり足タイムはターンの鋭さや操作性を反映するため、インコースの逃げや差しを決める上で極めて重要視される5。一方、直線タイムはスリット通過後やバックストレッチでのモーターの伸び足を示す。良いモーターは伸びに特徴が出やすく、上位機は出足と伸びが両立しているバランス型に仕上がる傾向があるため、特にアウトコース（3〜6コース）からの捲り展開を予測する上で、直線タイムの優劣は決定的な特徴量となる5。

特筆すべきは、全国24場のうち、オリジナル展示タイムを計測・公表しているのは23場にとどまるという事実である。江戸川競艇場（場コード03）のみ、日本で唯一河川の流水をコースとして利用しており、水面が荒れやすく水位の変化も激しいため、物理的な計測器の確実な設置と運用が困難であるという理由から、この独自タイムの計測を行っていない6。したがって、江戸川に関しては通常の展示タイムとスタートタイミング（ST）のみに依存する分析モデルへの切り替えが必要となる8。

これらのオリジナル展示タイムは、各レース場が管理する個別の独自ドメイン（例：boatrace-karatsu.jp など）から取得する必要がある9。公式サイトのような統一されたURL構造やHTMLフォーマットが存在しないため、データプラットフォーム側では23種類の異なるサイト構造に対応するためのスクレイピング・パーサー（解析ロジック）を個別に設計し、継続的に保守する体制が求められる10。

## **3\. スクレイピング手法の最適設計（何を・どのように）**

必要なデータ群が定義された後、次に取り組むべきは、それらを「どのように」システムへ取り込むかという手法の設計である。過去の履歴データのバルク取得と、日々進行するレースの差分・リアルタイム取得とでは、採用すべきアプローチが根本的に異なる。

### **3.1. 過去データの一括収集における課題とアプローチ**

過去のレース結果や出走表を一括で取得する場合、オフィシャルウェブサイトの「データを調べる」セクションから、LZH形式で圧縮されたテキストファイル（番組表および競走成績）をダウンロードする方法が公式より提供されている12。この方法は、サーバーへのHTTPリクエスト回数を劇的に減らせるため、アクセス負荷対策の観点からは極めて優れている。また、かなり古い年代のデータから最新のものまで網羅されている点も魅力である13。

しかし、このテキストファイルを解析してリレーショナル・データベースに格納するプロセスには、データエンジニアリング上の深刻な障害が存在する。フォーマットの仕様が旧態依然としており、明確な区切り文字（カンマやタブ等）が存在せず、全角と半角の空白文字が規則性なく混在しているのである12。さらに、選手氏名が5文字以上の場合に文字列が強制的に切り取られる仕様や、モーター番号・ボート番号が3桁になった際、直前列の数値（例えば勝率）との間にある空白スペースが消失して文字列が結合してしまう（例：勝率「20.50」でボート番号「111」の際、「20.50111」となる）という致命的な仕様バグが内包されている12。加えて、レースが中止や延期になった場合、テキストファイル内の列数自体がずれ込み、固定長や正規表現を用いた単純なパース処理を容易に破綻させる12。

もう一つの決定的な欠点は、オッズ情報に関する仕様である。公式のテキストデータおよび一部のWeb画面上の「オッズ情報・結果」では、配当が999.9倍（万舟券を超える超大穴）以上になった場合、表示上限の仕様により「9999」と丸められるか、情報が欠損する仕様となっている13。ボートレースの歴史上、最高払戻額は7618.4倍に達した事例が存在しており、999.9倍以上のデータが欠損・クリッピングされることは、機械学習モデルにおける期待値計算やリスク評価において無視できない誤差を生む要因となる14。

これらの課題を克服するための最適な設計は、テキストファイルの直接利用を避け、Python等のプログラミング言語を用いた動的なスクレイピングとオープンソースツールの活用を組み合わせることである。

### **3.2. オープンソースライブラリの活用と実装設計**

ゼロからすべてのHTMLパーサーを実装・保守するコストは膨大であるため、GitHub等で公開されているOSS（オープンソースソフトウェア）の活用が推奨される。例えば、Pythonベースのライブラリである pyjpboatrace は、公式サイトのスクレイピングからデータ構造化までのプロセスを高度に抽象化している16。

このライブラリは requests と BeautifulSoup4 をベースに構築されており、特定日付・特定場の12レース分の情報を一括取得する get\_12races、単勝・複勝等のオッズを取得する get\_odds\_win\_placeshow、直前情報を取得する get\_just\_before\_info、そしてレース結果を取得する get\_race\_result といったメソッドを提供している16。戻り値が整形された辞書（Dict）形式で得られるため、後段のデータベース格納やPandasのDataFrameへの変換が極めて容易である16。また、metaboatrace/scrapers のような専用のリポジトリも存在し、スクレイピング業務の標準化に寄与している17。

### **3.3. ボット対策とネットワークアーキテクチャ**

データ収集を自動化する上で考慮すべきリスクが、対象サイト側によるスクレイピング遮断（WAF: Web Application Firewall や Cloudflare 等の導入）である。標準的なHTTPライブラリ（requests 等）は、ユーザーエージェントの偽装を行っても、TLSフィンガープリント等の高度なボット検知システムによってブロックされる可能性がある。

この事態を想定した堅牢な設計として、ネットワークリクエストの失敗を検知した際に、自動的にブラウザ操作自動化ツールである Selenium（バージョン4.6以上）や、より高度な回避能力を持つ Playwright などのヘッドレスブラウザへ処理をフォールバックさせるアーキテクチャが求められる16。pyjpboatrace においても、内部でChrome、Firefox、Edge等のドライバを生成し、動的レンダリングを伴うページ取得に対応する機構が備わっている16。ただし、ヘッドレスブラウザの起動はメモリとCPUリソースを大量に消費するため、あくまでHTTPリクエストが失敗した場合の例外処理として組み込むことが、システムの効率性を保つ上で重要である。

## **4\. スクレイピングのスケジューリング戦略（どのタイミングで）**

対象システムの負荷を最小化しつつ、予測モデルに必要なデータを適切なタイミングで欠損なく収集するためには、「過去・基本データのバッチ処理」と「当日・直前データのリアルタイムポーリング処理」を明確に分離した高度なジョブスケジューリングが必要となる。データ収集のライフサイクルは、イベント駆動型のステートマシンとして設計されるべきである。

### **4.1. データ収集のフェーズとタイムライン**

1つのボートレース開催日は、出走表の公開に始まり、各種情報の解禁、投票の締切、レースの実施、そして結果の確定という状態（ステート）を順次遷移する。スクレイピングバッチはこのタイムラインに厳密に同期して起動しなければならない。

&nbsp;

| 収集フェーズ | 想定実行タイミング | 取得対象データ | スケジューリングの意図とシステム要件 |
| :---- | :---- | :---- | :---- |
| **事前基本情報取得 (バッチ処理)** | 前日 22:00 〜 当日 8:00 | 出走表 (racelist) | 当日開催される全レースの選手情報、モーター情報を事前にキャッシュする。公式サイトへのアクセスが減少する深夜から早朝のトラフィック閑散期に実行し、サーバー負荷を分散させる。 |
| **直前情報ポーリング** | 締切予定時刻の 15分前 〜 | 直前情報、展示タイム、気象条件 | レース開始直前の状況を捉える。締切寸前に発表が遅延することもあるため、公開されるまで一定間隔での監視が必要となる。 |
| **オリジナル展示タイム取得** | 締切予定時刻の 12分前 〜 | 23場独自ドメインの展示データ | 「12分前」は最速でデータが公開される目安である。水面状況による周回短縮等で計測不能となるケースや、締切寸前の公開となるケースが存在するため、欠損時のリトライ制御が必須11。 |
| **時系列オッズ収集** | 締切 30分前、15分前、5分前 | 3連単等の各種オッズ | オッズは締切直前まで変動を続ける。特に締切5分前以降の大口投票は予測において重要。ただし過剰なアクセスを避けるため、間隔を空けた定点観測とする14。 |
| **結果確定処理** | レース終了後 10〜15分 | 競走成績、払戻金 | 結果の確定およびデータベース上の正解ラベル更新。特払い、返還、同着などの特殊事象が発生した場合、処理ロジックの分岐が必要となる。 |

### **4.2. 直前情報収集におけるリトライ制御（エクスポネンシャル・バックオフ）**

直前情報とオリジナル展示タイムは、機械学習モデルの推論をレース直前に実行するためのトリガーとなる最も重要なデータ群である。しかし、これらのデータは常に予定時刻通りに公開されるわけではない。特にオリジナル展示タイムは、競艇場側のアナウンスが締切寸前までもつれ込むことや、機器トラブル・水面状況の悪化により最終的に「計測不能」としてデータが欠損したままレースが開始されることもある11。

したがって、単純なCronジョブによる単発のHTTPリクエストではデータの取りこぼしが発生する。最適な設計としては、「締切15分前に初回リクエストを送信し、データが未公開（あるいはHTMLの特定要素が空）であれば、1分後に再試行する。その後はサーバーへの負担を考慮して、再試行間隔を徐々に伸ばす（エクスポネンシャル・バックオフアルゴリズムの適用）」といった堅牢なジョブキュー（Celery等）の設計が求められる。また、レースの発売締切時刻を過ぎてもデータが取得できない場合は、例外をキャッチして「欠損値」としてデータベースに記録し、推論パイプラインを止めることなくフォールバック動作へ移行する設計が必要である。

## **5\. データ保持期間とデータベース設計（どれくらいの期間で・保管構造）**

分析プラットフォームを構築する際、どの程度の期間にわたってデータを遡及して収集・保持すべきか、そしてそれをどのような構造で格納すべきかの設計（データモデリング）は、システムのパフォーマンスと予測精度に直結する。

### **5.1. データの収集期間と保持戦略**

ボートレースの予測において「どれくらいの期間（何年分）のデータを収集すべきか」という問いに対する最適な解は、機械学習モデルの性質とボートレース特有の「サイクル」に依存する。

ボートレースでは、各レース場ごとに1年に1回、モーターとボートが新品に交換される明確なサイクルが存在する。また、数年に一度の頻度でプロペラ制度の変更（持ちペラ制の廃止等）やモーターの出力低減措置などの大幅なルール改正が行われることがある。そのため、あまりに古い過去データ（例えば15年以上前のデータ）を学習モデルに投入すると、現在の環境要因との間に「コンセプトドリフト（入力データの分布やターゲットとの関係性が時間とともに変化する現象）」が生じ、かえって予測精度を低下させる原因となる。

実務的な最適解としては、過去5〜7年分のデータをバルクで収集してベースラインモデルの学習データとし、以降は日々のスクレイピングで得られる最新データを追加・保持し続けるローリング・アップデート方式を採用することである。データ容量の観点からは、全国24場・年間約5万レース分の出走表、成績、直前情報を網羅的に取得したとしても、リレーショナル・データベースに格納した場合のサイズは年間200MBから300MB程度に収まる21。つまり、10年分のデータを蓄積しても数GB規模であり、最新のRDBMS（PostgreSQLやMySQL等）であればストレージやインデックス検索のパフォーマンス面でボトルネックになることはほぼない。そのため、取得したデータは原則としてパージ（削除）することなく、永続的に保持する設計で問題ない。

### **5.2. リレーショナル・データベースのスキーマ設計**

収集したデータを効率的に管理するためのデータベース設計において、各テーブルの主キー（Primary Key）となるのは、普遍的に「日付（YYYYMMDD）」「開催場コード（1〜24）」「レースナンバー（1〜12）」の3つの複合キーである22。この基底テーブルに対して、選手ごとの詳細成績、直前情報、時系列オッズを外部キー（Foreign Key）で紐づける第三正規形までの正規化が推奨される。

データベース設計を最も複雑にする要因は、不測の事態に伴う例外処理（エッジケース）のモデリングである。ボートレース特有の以下の事象を正確に表現できるよう、スキーマは柔軟性を持たせる必要がある。

> 1. **欠場と返還の処理:** フライング（F）や出遅れ（L）、周回誤認、転覆などによる欠場が発生した場合、関係する艇を含む舟券はすべて「返還（不成立）」の対象となる。この際、返還されていない組み合わせの中で、はずれの組み合わせが存在し、かつ必要艇数がゴールしている場合にのみレースが成立する13。データベース上では、単なる着順の整数型カラムだけでなく、「着順異常フラグ（F, L, 転, 落等）」を保持するカラムを用意しなければならない。  
> 2. **特払い:** 万が一、的中者が一人もいなかった場合、法規定に基づき100円の投票につき70円が払い戻される「特払い」が発生する13。これを通常の払戻金と同列に扱うと期待値計算に異常値が混入するため、区別フラグが必要である。  
> 3. **同着によるオッズ再計算:** 競艇において稀に発生する同着（デッドヒート）の際、配当の払戻金は複雑な計算式（（全的中組合せに対する票数＋不的中票数×(1-控除率)）÷的中となる組合せの数）を用いて再算出される23。払戻金テーブルは、通常3連単であれば1行（1レコード）で済むところ、同着時には複数行が動的に挿入されることを前提とした1対多のテーブル設計とする必要がある。

## **6\. 法的制約・利用規約と倫理的スクレイピングの実践**

データを網羅的に収集する技術的アプローチが確立されたとしても、それを実行する上でのコンプライアンス（法令・利用規約の遵守）は、システムの持続可能性において最も重要な要件である。

### **6.1. 利用規約に基づく禁止事項の解釈**

ボートレースの公式サイト群や、関連する分析プラットフォーム（boatracedata.com, tenjiscope.com, 各レース場AIサイト等）の利用規約を分析すると、スクレイピングに関連して概ね以下のような行為が明確に禁止されている24。

&nbsp;

| 規約上の禁止事項の類型 | 該当する具体的な行為とシステムへの影響 |
| :---- | :---- |
| **システムへの過度な負荷・業務妨害** | 「自動化された大量アクセス・自動スクレイピング等」「不正アクセス、大量の情報送受信」24。無配慮な並列リクエストによって相手方のサーバーリソースを枯渇させる行為。 |
| **知的財産権・著作権の侵害** | 「当サイトのコンテンツを無断で複製・転用・販売する行為」「著作権表示等を削除または変更する行為」24。文章、写真、加工データ等をそのまま自サイトで再配布する行為。 |
| **情報の改竄・不適切利用** | 「評価情報を的中を保証するかのように表示して第三者へ提供・販売する行為」「リバースエンジニアリングによる解析」26。 |
| **公序良俗・法令違反** | 犯罪行為に結びつく行為や、プライバシー権を侵害する行為26。 |

特に注意すべきは、robots.txt において公式ページへのクローラーのアクセス自体が技術的に特別禁止（Disallow）されていなくとも32、利用規約上は「過度な負荷をかける自動スクレイピング」が禁止されているという法的二重構造である。善意で貴重なデータを公開している個人サイトやデータベースサイトも多数存在するが、これらに対する無配慮なスクレイピングも厳禁とされており、ボートレースデータ界隈における共通の倫理規範となっている13。

### **6.2. サーバー負荷低減（偽計業務妨害罪への対策）**

日本の刑法において、Webスクレイピング行為自体を直接的に禁止する法律はない。しかし、設計の不備や過剰な並列処理によって対象サーバーに過度な負荷を与え、正常なサービスの提供を困難にさせた場合、刑法第233条の「偽計業務妨害罪」や同第234条の「電子計算機損壊等業務妨害罪」に抵触する重大なリスクがある33。

過去の判例・事例として極めて有名な「岡崎市立図書館事件（2010年）」では、蔵書検索システムに対してWebスクレイピングを行っていた開発者が偽計業務妨害の容疑で逮捕された。この事件では、実際には「1秒間に1アクセス程度」の頻度であったにもかかわらず、図書館側のシステムが旧式であったためにデータベースの処理が滞り、閲覧障害が発生したことが逮捕の理由とされた（最終的には悪意が認められず起訴猶予処分）33。

この事例から導き出されるアーキテクチャ上の教訓は、「1秒に1回なら安全である」といった固定的な基準は存在しないということである。相手方のサーバーの脆弱性やトラフィックのピークを総合的に判断する必要がある。したがって、最適なスクレイピング設計においては、リクエスト間にランダムな遅延（スリープ）を意図的に挿入すること、マルチスレッドや非同期処理（asyncio等）を用いた過度な並列アクセスを避けること、そしてエラー応答（HTTP 503 Service Unavailable 等）を検知した場合は直ちにアクセスを停止するサーキットブレーカーの仕組みを実装することが法務要件として必須となる。

### **6.3. 著作権法における情報解析の免責（第30条の4）**

収集したデータの取り扱いに関しても、著作権法との整合性が求められる。Web上にある出走表やオッズ等のコンテンツは、創作性が低くとも編集著作物等として何らかの著作権が発生している可能性がある33。

しかしながら、平成30年の著作権法改正により整備された「第30条の4（情報解析のための複製等）」および「第47条の7」の規定により、コンピュータ等を用いて情報の抽出・比較・分類等の「情報解析（機械学習を含む）」を行うことを目的とする場合には、必要と認められる限度において記録媒体に著作物を複製・翻案することが適法とされている33。

すなわち、スクレイピングで収集したボートレースのデータを、自らのWebサイトで「そのまま出走表やオッズとして公開・再配布・販売」すれば著作権法違反および利用規約違反となるが、収集したデータをデータベース内で加工し、機械学習アルゴリズムを用いて「各艇の勝率予測スコア」という新たな価値（特徴量・推論結果）に変換して出力する「情報解析エンジン・AI予測の作成」の用途であれば、適法な利用として認められる公算が高い33。

## **7\. 特徴量エンジニアリングと機械学習パイプラインへの統合**

最後に、最適に設計されたスクレイピング基盤から得られたデータを、どのように分析・予測モデルへ昇華させるかについて述べる。データ収集は手段であり、目的は高精度な予測の実現である。

先進的な競艇AI予測サービスでは、収集した生データから160を超える予測に有効な特徴量（変数）を生成している1。例えば、オリジナル展示タイムを単なる秒数の絶対値として扱うのではなく、以下のような高度な特徴量エンジニアリング（変数加工）を施す。

* **Zスコア正規化:** 各レース場、あるいは当該レースにおける平均タイムからの偏差（Zスコア）を算出し、レース内での「相対的な実力差」やモーターの相対的な良さを定量化する1。  
* **タイムの相関分析:** 「1周タイム（総合力）」と「直線タイム（伸び足）」、「まわり足タイム（出足・操作性）」の差分を分析する。出足や乗り心地に寄せたセッティングは競り合いに強いが、伸び足に寄せたセッティングはスタートを決めれば一撃の破壊力（捲り）がある反面、威力が半減するリスクも伴う7。これらの脚質の傾向をカテゴリ変数化し、アップセット（波乱）検出用の指標を作成する1。

さらに最新のトレンドとして、単にデータを推論APIに流し込むだけでなく、AI自身が生成物を評価し、予測の品質が不十分（確信度が低いなど）と判断した場合には、過去の類似レースのデータを自律的に再検索・評価・修正を行う「Agentic AI（自律エージェント型AI）パイプライン」を構築するアプローチも実用化され始めている34。こうした高度なパイプラインも、欠損がなく、エッジケース（返還や同着等）がクレンジングされた堅牢なデータベース基盤があって初めて成立する。

## **8\. 結論：全体最適化されたデータ基盤アーキテクチャ**

本研究を通じ、公式APIが存在しないボートレース領域におけるデータ分析プラットフォーム構築のための最適なスクレイピング設計は、以下の要件を統合した分散・イベント駆動型アーキテクチャに帰着することが明らかとなった。

> 1. **ハイブリッドな収集先の統合:**  
>    出走表、オッズ、直前情報、結果等の標準データはオフィシャルウェブサイトから取得し、予測モデルの精度を左右する「オリジナル展示タイム」は江戸川を除く全国23のレース場独自ドメインから個別にスクレイピングする二段構えのパーサーを設計・保守する。  
> 2. **イベント駆動型のスケジューリングとフェーズ分割:**  
>    深夜帯のバッチ処理による事前情報の一括取得と、レース進行（締切15分前〜5分前）に同期したリアルタイム・ポーリングを分離する。直前データの公開遅延や欠損に備え、エクスポネンシャル・バックオフを伴うリトライロジックを実装する。  
> 3. **データモデリングとエッジケースへの耐性:**  
>    フォーマット崩れの多い公式のLZH圧縮テキストファイルへの依存を避け、動的なHTML/JSONパースを行うOSS（pyjpboatrace等）を活用する。データベースは「日付・場・レース番号」を複合主キーとし、特払い、返還、同着といったボートレース特有の複雑な例外事象を状態として保持できる柔軟なリレーショナル設計とする。データは年間数百MBと軽量であるため、5年以上の長期間ローリング保持し、機械学習モデルの経年劣化（コンセプトドリフト）を防ぐ。  
> 4. **厳格なコンプライアンス設計:**  
>    偽計業務妨害罪への抵触や利用規約違反を回避するため、リクエスト間隔の十分な確保、トラフィックピークの回避、エラー時の即時停止機構（サーキットブレーカー）を実装する。取得データは著作権法上の「情報解析」の枠組み内で特徴量として加工し、AIの推論スコア生成にのみ活用する。

以上の要件を満たして構築されたスクレイピング基盤は、法的な安全性と倫理性を確保しながらも、機械学習ポテンシャルを最大化するための極めて高解像度なデータセットを安定して供給し続けることが可能となる。これが、現代のデータドリブンなボートレース分析におけるアーキテクチャ設計の最適解である。
