# ボートレース日和 出走表ページ 全タブの項目一覧（網羅確認の基準）

対応: [BOA-365](https://linear.app/boat-ai/issue/BOA-365)（網羅確認）/ [BOA-305](https://linear.app/boat-ai/issue/BOA-305)（レース詳細のUI/UX）

## この文書の役割

**プロジェクトのゴール「日和が提供している情報は全て取れるようにする」に対する、網羅の基準（物差し）。**
2026-09-28にユーザーが定義した。

> 日和が提供している情報は全て取れるようにしたい。出走表ページの各タブを見て
> 全て提供（出さないものは出さないと判断）できていたらOK。

各項目が次のどちらかになっていれば網羅を満たす。**達成条件は「未判断のまま残っている項目が0件」。**

| 状態 | 意味 |
|---|---|
| ✅ 提供済み | 龍神レーダーで同等の情報を出している |
| ⛔ 出さない | 出さないと**明示的に判断済み**（理由が要る） |
| ❓ 未判断 | まだどちらでもない。**これが0件になるまで網羅は未達** |

**本文書は日和側の「事実」（どんな項目があるか）を確定させることを主目的にする。**
龍神レーダー側の状態列は、タブ単位で埋めていく（一度に全部やると300項目超になり、
1セッション・1PRでは終わらないため）。

### 数え方

- 6艇分の列は1項目として数える（列軸なので）
- 同じ指標が期間別に行で分かれていれば、**期間ごとに別項目**として数える
  （自社が同じ切り口を持てているかの棚卸しに使うため）
- 別ページへのリンク・凡例・注記・UI機能はカウント外。ただし「ST履歴」「決り手履歴」のように
  艇ごとに列として並ぶ詳細リンクは、その位置に1項目分の枠を占めるためカウントに含める

### 全タブ共通のフレーム（項目とは別）

- 日程切替（初日〜最終日、日付併記）／レース切替（1R〜12R）

## 11. 未判断項目をどう判断するか（2026-09-28ユーザー決定）

**「未判断」を「提供する／出さない」に振り分ける手順は、8人パネルの議論を挟む。**

```
① 日和側の項目一覧を確定する（本文書）
        ↓

        ↓
④ 出すと決まったものだけ起票する（出さないものは理由を本文書に記録）
```

③は `.claude/skills/discussion-panel/` の8人（天才マーケター／エンジニア／経営者／デザイナー
＋20代・30代男女のボートレースファン）。`.claude/rules/review-fix-cycle.md` の

（同じモデルのロールプレイなので偏りを共有している。同ルール §「8人パネルは仮説を出す用途」）。
検証はモック承認とリリース後の実データで行う。

### 議論は項目単位ではなくグループ単位で行う

**360項目を1件ずつ議論するのは現実的でない。** 実際に一覧を作って分かったのは、
日和の項目の大半が「同じ指標の条件バリエーション」だということ。**1つの判断で数十項目が同時に決まる。**

議論の単位はこの形にする（グループの切り方は突き合わせの結果で変わりうる）。

| グループの例 | 含まれる項目数の目安 | 議論の問い |
|---|---|---|

## 12. 期間軸 — 実現可能性と結論（2026-09-28）

### 12-1. 「出さない」に付ける理由の型（必須）

セカンドレビューの最大の指摘は「**台帳に『出さない（理由）』と書いた項目は、理由が誤っていても
再検討のトリガーが無い**」だった。実際に本節の初版で、①と②を混同して3件を誤って「出さない」に
分類していた。以後、すべての「出さない」に**理由の型**と**再検討の契機**を付ける。

| 型 | 意味 | 再検討の契機 |
|---|---|---|
| ① | データがどこにも存在しない | 取得が実装されたら |
| ② | **存在するが表示経路が無い**（権限・本体テーブル未昇格・事前集計なし） | **優先度の判断次第。いつでも** |
| ③ | 情報量が増えない | 前提（DBの期間等）が変わったら |
| ④ | 母数が足りない | 母数が増えたら |
| ⑤ | ポリシー判断 | 方針が変わったら |

**①と②を混ぜないこと。** ①は「できない」、②は「やっていない」で、意味がまったく違う。

### 12-3. 母数の実測

1選手あたりの走数（中央値、2026-09-28）。

| 窓 | 走数 | 節に換算 |
|---|---|---|

選手×会場 22,430組のうち小標本（`SMALL_SAMPLE_THRESHOLD`=6）を割る割合は、当地×全期間 4.1% /
当地×直近3ヶ月 60.5%。

**ただしこの60.5%を「当地×期間を作らない」根拠に据えるのは的を外している**（セカンドレビューの指摘）。
理由は3つ。

1. **日和にそのセルは無い。** 日和の「当地」は期間と**並列の1行**で、当地を窓と掛けているのは
   「直近10走比較表（総合/当地）」＝**走数ベース**だけ。網羅の穴を1つも埋めない
2. **走数ベースの当地は龍神レーダーにも既にある**（`courseGridStats.js` の
   `getCourseRecentRuns(records, {rowKey:"local", course})`、`RaceWakuInfoTab.jsx:257-264` が描画）
3. **nは節単位でクラスタしている。** 当地の走は1回の参戦で約6走まとまるので、独立な観測単位は
   走ではなく節。中央値10走＝**約1.5節**＝「1回行っただけ」。同じモーター・同じ週・同じ水面の
   相関が強い。**「当地×全期間はn<6が4.1%だから安全」という読みも危うい**（[BOA-437](https://linear.app/boat-ai/issue/BOA-437) が
   「閾値6は1着率に緩すぎる。当地0.0% n=8 に⚠が付かない」と同型の指摘をしている）

さらに未解決の疑い: 母数を `race_entries` にすると**中止レース・欠場艇が分母に入る**
（`is_cancelled`/`is_no_race` が全行false＝判別できない＝[BOA-477](https://linear.app/boat-ai/issue/BOA-477)）。
n を過大にし、**n<6 の割合を過小に見せる方向にバイアス**する。4.1% は甘く出ている可能性がある。

### 12-4. ファン4人の議論（③のステップ）

ユーザー指示により、**ボートレースファン4人だけ**で議論した（経営者は外し、他の役割は当てていない）。

**一致した点**

1. **13の期間軸を並べることに、4人とも価値を認めなかった。** 熟練者ですら「期間より
   『どう負けるか』」と言い、初心者は「多いと閉じる」と言った
2. **「2つ並べて比べる」ことには全員が価値を認めた。** 「直近1ヶ月と全期間を比べたい」
   「当地と全国の差」。**単独の数字ではなく差に意味がある**
3. **母数が少ないことを隠さないでほしい。** 「当地は1回行っただけだった」「データが少ないなら
   正直に書いてほしい」
4. **予想外に強かったのが用語の説明の要求**（2人）。新しい指標を増やすより、既にある指標の

**割れた点**: 「地力」を見る軸が要るか。ただし「既定1軸＋比較用に1軸」までは支持がある。

②母数の明示 ③用語の説明。

### 12-5. 結論

**13軸を追わず、4つの問いに束ねて「既定1軸＋差」で見せる。**

| 問い | 軸 | 状態 |
|---|---|---|
| **いま調子がいいか** | 直近1ヶ月（既定）／直近3ヶ月 | 提供済み |
| **地力はあるか** | 全期間（**状態で「今期（公式）」と出し分ける**） | 提供済み。ラベルの出し分けが要実装 |
| **この会場で走れるか** | 当地（**カレンダー期間とは掛けない**。走数ベースの直近10走は提供済み） | 提供済み |
| **今日の条件に合うか** | 波5cm上／グレード／初日・最終日 | **すべて出荷済み**。波は会場交絡（BOA-438） |

**「掛け合わせない」の対象は当地×カレンダー期間に限る。** 当地×条件（波・グレード）は別判断
として残す（そうしないとBOA-438が結論の枠内で解けない）。

**差の基準を決める必要がある。** 先例の `RaceStConsiderationCard` は「**同コース・同級別の集団
平均**との差」で、事前集計テーブル（`st_course_baseline`、+1クエリ）が要る。一方この結論が想定する
のは「**本人の別期間**との差」でクライアント計算のみ（+0クエリ）。**ファンにとって意味が全く違う**
（前者＝格、後者＝調子）。モックの段階でどちらかを明示する。

**期間軸の追加はクエリを増やさない。** `getRacerScopedRaceStats` が1選手の全走（730日）を
まとめて持ち、期間・条件の絞り込みは純関数（`filterRecords`）。spec の「+3本以内」は事前集計
テーブル側の予算で、期間軸はそれを消費しない。**後戻りは安い。** ただし直近1年・6ヶ月を
後から足す場合だけは事前集計テーブル＋日次バッチ＋RLS/GRANT＋Disk IO見積り＝Phase相当になる。

### 13-2. ファン4人が一致した点

   「開いたことがない」「出走表にあれば使う」。**データが無いのではなく、レースを見ている画面から
   届いていない。** 関連して、分析ツール17タブのうち**11タブがレース詳細に埋め込まれておらず
   遷移が必要**
2. **「超展開データ」という名前で押していなかった**（2人）。「何のことか分からなかった」
3. **期間2種（6ヶ月/1年）は誰も要求しなかった。** 熟練者が明確に「1つでいい」と言い、他3人は
   言及すらしなかった。**日和の16項目は、うちでは8項目で足りる**
4. **「逃げ逃し出目確率」も誰も要求しなかった。** 「そこまで細かく買わない」。spec が
   「やらないこと」にした判断はファン視点でも支持される
5. **用語が再度壁になった**（2人）。「捲差され」が読めない。§12と同じ結論が別の項目でもう一度出た

### 13-3. 割れた点と、その決着

**「された側」だけで足りるか、「した側」も要るか。** 熟練者は「された側」（1号艇が負ける形）、
推し軸のファンは「した側」（推しが勝つ形）を求めた。

**割れたままにしない。** 推し軸のファン自身が指摘したとおり、**1号艇の「差された」は2号艇の
「差した」と同じ事象**。日和が「した/された」を対で持っているのはこの両面性のため。
**片方だけ出す設計に意味はなく、対で出すのが正解。**

### 13-4. 優先順位（実装が必要なものより「届け方」が上に来た）

| 優先 | 内容 | 状態 |
|---|---|---|
| **1** | された側/した側のデータを**レース詳細に出す** | データは選手ごとに実装済み。**置き場所だけの問題**。ただし BOA-168/169（PR #184）で**意図的に分析ツールへ外出しした**経緯があり、戻すなら当時の判断を覆す |
| **2** | 「超展開データ」の**名前を変える** | 2人が「何のことか分からず押していない」 |
| **3** | 用語を日本語で言い直す | `termHints.js` が既にあるがカバー未確認 |
| **4** | した側と された側 を**対で出す** | 現状「差され」「捲差され」中心。対になっているか未確認 |
| **5** | 期間2種 | **要求されなかった。出さない（型⑤: 設計判断）** |
| **6** | 逃げ逃し出目確率・逃がし3着率 | **要求されなかった。spec の判断を維持（型⑤）** |

### 13-5. 2回の議論で3回出た結論

§12（期間軸）と本節（された側）の2回で、同じことが3回出た。

- **項目を増やすことは求められていない**（期間13軸も、された側16項目も、誰も全部は求めなかった）
- **用語が壁になっている**（§12で2人、本節で2人）
- **母数と届け方が価値を決める**（§12「データが少ないなら正直に書いて」、本節「遷移が必要なら
  無いのと同じ」）

**日和の360項目に対して、ファンが求めているのは項目の追加ではなく、既にあるものの整理と
言い換えだった。** これは「日和は情報量は最大級だが数値の羅列で判断基準が不明瞭」という
当初の課題認識（`data-coverage-comparison-2026-09-14.md` 冒頭）と正確に一致する。

## 14. 再調査するときの技術メモ

次に同じ棚卸しをするとき（日和の機能追加への追随）に必要な手順。

- `?slider=N` は有効だが、**ページ読み込み直後は slider=0 の内容が表示され、スライダーが
  N の位置までアニメーションで移動する**。navigate 後に **5〜6秒待ってから**本文を取らないと、
  基本情報タブの中身を取ってしまう
- タブ見出しは href を持たないJS制御要素（`id="modalMenu0"`〜`modalMenu9"`）。
  クリックより **URL直指定＋待機**のほうが確実
- 過去日のレースでも、オッズ検索・オッズ一覧とも**締切時点の値が残っている**。
  当日開催レースで開き直す必要はない
- 要ログインで確認できないのは **MyData タブ本体**と**舟券メモ**の2つだけ
