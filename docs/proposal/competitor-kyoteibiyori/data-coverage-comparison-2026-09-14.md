# 公式サイト×ボートレース日和×龍神レーダー データ三者比較（2026-09-14）

## 目的・背景

龍神レーダーのUI方針は「公式・日和のUIに寄せる（ユーザーが使い慣れているため）」を基本としつつ、それだと分かりにくい箇所は龍神レーダーならではの可視化で昇華する、という方針（2026-09-14ユーザー合意）。日和は情報量は最大級だが、数値の羅列で判断基準が不明瞭になりやすく、ボートレースの面白さが伝わりにくいという課題認識がある。

本ドキュメントは以下3方向の比較を行う:

1. 公式サイト（boatrace.jp＋全24会場サイト）にあるデータで、日和に無いもの
2. 公式サイトに無いデータで、日和にあるもの
3. 龍神レーダーに無いデータで、日和にあるもの。加えて、それらを日和がどうUI表示しているか・見やすいか・龍神レーダーで昇華する余地があるか

材料: [DATA_SCRAPING_GAPS.md](../../issues/DATA_SCRAPING_GAPS.md)（公式サイト横断調査、2026-09-14実施）、[docs/proposal/competitor-kyoteibiyori/](.)配下の既存12ファイル＋[competitor-analysis-kyoteibiyori.md](./competitor-analysis-kyoteibiyori.md)（日和の機能分析、過去セッション実施分を集約）、日和の実ページを本セッションで直接確認したスクリーンショット。

## 1. 公式サイトにあるが、日和に載っていないデータ

日和の163項目カタログ（本調査で集約）を確認した限り、以下は掲載が見当たらなかった:

| データ | 出典（公式） | 備考 |
|---|---|---|
| **潮汐表（潮位・満干潮時刻）** | 鳴門・若松・大村・丸亀・徳山の会場公式サイト | 日和のカタログに潮汐関連項目は1件も無い。海水面会場特有のデータで、日和も含めた業界全体で手薄な領域の可能性がある（[BOA-295](https://linear.app/boat-ai/issue/BOA-295)で既に着手検討中） |
| **会場の物理レイアウト変更履歴**（例: 唐津2025年12月のピット位置変更） | 唐津会場公式サイト「水面特性」 | 日和のカタログにも同種の記載なし。会場側の一次情報でしか分からない可能性が高い（[BOA-296](https://linear.app/boat-ai/issue/BOA-296)） |
| **備考欄（事故・失格等のフリーテキスト）** | boatrace.jp raceresultページ | 日和は「事故率」という集計済み数値（項目21）は持つが、個別レースの事故内容のフリーテキストをそのまま見せる機能は確認できなかった |
| **ラウンド種別ラベル**（予選/準優勝戦/優勝戦、`.title16_titleDetail__add2020`） | boatrace.jp | 日和は「一般戦/SG・G1/女子戦」というグレード軸の切替はあるが、同じグレード内の「予選か優勝戦か」という軸を独立して持つ項目はカタログ上見当たらない |

**総括**: 公式（特に会場個別サイト）は「その会場固有の物理環境・運営情報」（潮汐、レイアウト変更）に強く、日和はそこを追い切れていない可能性がある。事故情報・ラウンド種別は、公式側もつい最近（本セッション）判明した穴であり、日和が持たないのは自然な結果とも言える。

**訂正（2026-09-14、claude-in-chromeで実機確認）**: 当初「選手ごとの枠→実進入コース遷移確率マトリクス」は日和に無いのではと保留していたが、**実際には存在した**。選手詳細ページ（例: `https://kyoteibiyori.com/racer/racer_no/5284`）の「前づけデータ」セクションに、まさに戸田・びわこ等の会場公式サイトと同じ形式（枠番×1〜6コースの遷移率マトリクス、例: 「3枠→3コース90.3%／4コース6.5%／6コース3.2%」）が存在する。ただし集計の切り口が異なる: 会場公式サイト版は「その会場」に絞った集計、日和版は「その選手が出走した全24場」を合算した集計（さらに「場別成績」タブで場ごとの実進入コース内訳も個別に確認できる）。断定を避けて保留にした判断は正しかったが、結果としては日和側も同種のデータを持っていた。

## 2. 公式サイトに無いが、日和にあるデータ

日和のカタログの中で、いかなる公式サイト（中央・会場個別）にも存在しない、日和独自の**加工・派生指標**:

| データ | カテゴリ | 内容 |
|---|---|---|
| 新概念データ「走りのクセ数値」 | 決まり手 | 決まり手率を独自ロジックで総合数値化（BOATBoy考案と明記） |
| 超展開データ（1マーク攻防データ） | 決まり手 | 1マークでの攻め方・抵抗回数・絞り込み回数を数値化。当日分は無料、全日分は有料 |
| モーター貢献ポイント | モーター | モーター使用時の連対率から選手自身の実力（使用前勝率）を差し引いた指標。「モーターの実力」を選手の実力から分離する発想 |
| 展示STと本番STのズレ評価（SS〜C 5段階） | 直前情報 | **訂正（2026-09-14）**: 「日和独自」と記載していたが、龍神レーダーも[BOA-153](https://linear.app/boat-ai/issue/BOA-153)（展示STと本番STのズレ分析）で既にDone。この項目は公式にも日和にも龍神レーダーにも存在する三者共通の分析軸 |
| ガチガチ/穴/まくり/前づけ/チルト跳アラート | アラート | 生データ（逃げ率・展示タイム差・チルト角度等）は公式にもあるが、閾値を設けて「レースを検出する」というアラート層は日和独自 |
| 勝率上昇/下降選手一覧 | 選手 | 直近1ヶ月vs前3ヶ月という比較設計自体が日和独自 |
| 固い場/荒れている場/イン逃げ率/万舟率ランキング | 場情報 | 当日結果を会場横断でランキング化する見せ方が独自 |
| 期待値分析 | その他 | 的中率×オッズの期待値算出（龍神レーダーは的中率のモデル較正が前提になるため過去に却下済み、[[feedback_volatility_model_tuning_avoid]]） |
| 番組マンの癖解析データ | 決まり手 | 番組編成者（レース割り当てを決める人）の傾向という、データというより「人」に着目した独自切り口 |

**総括**: 公式サイトは基本的に「生データ・一次情報」の置き場で、日和の強みは生データそのものではなく**生データへの独自の加工・要約・アラート化**にある。これは龍神レーダーが「分析ツールとして戦う」上でも同じ土俵——公式データをどう加工するかの勝負であり、生データの網羅性だけでは差別化にならないことを裏付ける。

## 3. 龍神レーダーに無いが、日和にあるデータ＋UI批評

### 3-1. データ面のギャップ（確認できた範囲）

龍神レーダーは現在15タブ（`/winning-technique`）＋選手ページ等で日和の基本項目（勝率・2連率・3連率・当地成績・モーター成績・決まり手傾向・出目分布・回収率分析・調子ランキング等）の多くを既にカバーしている。その上で、日和にあり龍神レーダーに確認できない項目:

| データ | 状態 |
|---|---|
| 選手の身長・血液型・生年月日 | **新規ギャップ**。体重は[BOA-288](https://linear.app/boat-ai/issue/BOA-288)、支部・出身地は`DATA_SCRAPING_GAPS.md`で既知だが、身長・血液型・生年月日は本比較で初めて言語化した。出典が公式か日和独自の選手名鑑かは未確認 |
| フライング休み・前期/今期未消化フライング数 | 既知・保留中。VUP分析スキルの過去調査で「選手のF回数・休み中判定のマスターデータが無く新規スクレイピングが必要」と判明済み（[[vup_feature_analysis_skill]]） |
| モーター過去3節比較表・貢献ポイント | **訂正: 大部分は対応済み**。「貢献ポイント」相当は[BOA-265](https://linear.app/boat-ai/issue/BOA-265)の機力指数（使用時2連対率−選手自身のベースライン勝率の残差、日和の単純な「連対率−使用前勝率」より統計的に厳密）で実装済み（Done）。「過去3節比較表」相当の使用履歴・期間別ドリルダウンは[BOA-283](https://linear.app/boat-ai/issue/BOA-283)で実装済み（Done、過去10走比較・直近1ヶ月/90日トグル）。ただし以下は未対応のまま残る: ①日和は「節」という離散単位で3列横並び表示するが、龍神レーダーは日数ベース（90日/1ヶ月）の連続トレンドグラフで代替しており厳密に「直近3節ぴったり」を切り出す表示は無い（意図的にグラフ化を選んだ結果であり、[[feedback_ui_visualization_over_statistical_rigor]]の方針とも整合するため優先度は低い）、②モーター使用時の決まり手比率（逃げ/差し/捲り等）の表示は未対応、③モーターの優出・優勝回数の表示は未対応 |
| 天候×水質フィルタでのコース勝率絞り込み、番組解析、平均値データ | 未着手。既存の集計基盤（`race_conditions`等）で作成可能な可能性が高い分析ビュー。既存チケットとの重複は確認できず |
| アラート機能全般（ガチガチ/穴/まくり/前づけ/チルト跳） | **既存チケットあり**: [BOA-224](https://linear.app/boat-ai/issue/BOA-224)（レース検索・アラート機能、Backlog）で起票済み。関連: [BOA-274](https://linear.app/boat-ai/issue/BOA-274)（全国×当地・機力×枠適性・ST×展示の「不一致」検出、Backlog、アラートと近い切り口）、[BOA-170](https://linear.app/boat-ai/issue/BOA-170)（選手別前づけ傾向分析、BOA-257の調査で一度保留になったが、BOA-290/293の新データ源で再検討可能とコメント済み） |
| SG履歴・優勝履歴の年度別検索 | 未着手。既存チケットとの重複は確認できず |
| 固い場/荒れている場/イン逃げ率/万舟率ランキング | **既に実装済み**（`src/components/analysis/VenueRankingChart.jsx`）。Angle2で「日和独自」として記載したが、龍神レーダーも既に同等機能を持つため訂正 |
| 今節得点率・今節得点率早見表 | 既存チケットあり: [BOA-220](https://linear.app/boat-ai/issue/BOA-220)（今節得点率表示、Backlog） |

身長・血液型・生年月日以外は概ね既存ドキュメント（本ファイル群やVUPメモリ）で捕捉済みのため、新規チケットは身長・血液型・生年月日のみ起票する（下記）。

### 3-2. UI批評（実ページを直接確認）

日和の実際の画面を確認した結果、ユーザーの課題認識（数値の羅列・判断基準不明・面白さが伝わらない）を裏付ける具体例が複数見つかった。

**① 出走表「基本情報」タブ**: ST順位・展示順位・勝率を「直近3ヶ月/1ヶ月/当地/初日/最終日/ナイター/F持」等7〜8種類の期間軸×6艇で並べた巨大な数値グリッド。セルは赤・黄色等で強調されるが、どの色が「良い」でどの色が「注目すべき」かの凡例がその場に無い。数値を読み解くには利用者側の予備知識が前提になっている。

**② 出走表「枠別情報」タブ**: 1着率・3連対率を「今期/直近6ヶ月/3ヶ月/1ヶ月/当地/一般戦/SG-G1」の軸でさらに積み上げる。サンプル数`n`は各セルに`(11)`のような小さい灰色の括弧書きで併記されており、**掲載はしているが視覚的に埋もれている**（n=1のセルとn=42のセルが同じ太字の数字サイズで並ぶ）。龍神レーダー側で既に確立している「小標本フラグを目立たせる」「n<30で⚠️を出す」という設計原則（BOA-271 アナロジー・ファインダーのモック検討で確立）は、この点で明確に優位性を主張できる。

**③ 「着順分析グラフ」モーダル**: 選手のコース別成績を1着時/2着時/3着時/着外の4区分×3つの円グラフ＋決まり手棒グラフ、計16個の小さいチャートで表示。可視化そのものは評価できるが、**n=1〜2件のセグメントでも100%の円グラフを描画しており**、実質1回しか無い事象があたかも安定した傾向であるかのように見える。1画面に16個のチャートが並ぶため、どれが重要な情報かの優先順位付けが利用者に委ねられている。

**④ 出目分析ツール**: 条件検索フォーム→ソート可能な出目ランキング表（艇番を公式ゼッケン色のバッジで表示）という設計は、日和の中では比較的よくできている部類。ただし全体件数（例: 44,234件）は表の上に1回だけ表示され、条件を絞り込んだ後の各行の実サンプル数は表示されない。狭い条件（特定会場×特定コース×特定決まり手）まで絞ると母数が数十件規模になりうるが、UIはそれを警告しない。

**⑤ 全ページ共通**: Adobe Creative Cloud等の広告バナーが頻繁にコンテンツ表と重なって配置され、データを読んでいる最中に表の下部が隠れる。情報の多さに加えて広告の視覚的ノイズが「面白さが伝わらない」体験に寄与している可能性がある。

### 3-3. 龍神レーダーで昇華する余地

**最重要（2026-09-14ユーザー指摘）: 日和の本質的な課題は「情報量が多すぎて視認性が悪く、直感的にわからない」こと。解決策は数値の羅列を適宜グラフ化することそのものであり、小標本(n)の扱いのような統計的厳密性は本題ではない。** 以下、この優先順位で整理する。

1. **数値グリッドのグラフ化を最優先で検討する**: 日和の「基本情報」「枠別情報」タブは、ST順位・展示順位・勝率・3連対率を7〜8種類の期間軸×6艇で並べた巨大な数値グリッドになっており、これがそのまま「情報量は多いが何を見ればいいか分からない」の主因になっている。龍神レーダーでは、この種の多軸データを素の数字で並べず、艇ごとの棒グラフ・レーダーチャート・スパークライン等に置き換えることを既存タブ・新規タブ問わず標準の設計方針にする（BOA-271のレーダーチャート・ソナー画面はこの方針の実例）
2. **情報の階層化**: 「着順分析グラフ」のように16個の小さいチャートを一度に見せるのではなく、まず1つの「見出し」（例: 差しが得意な選手／逃げられると弱い等の一言サマリー）を先に出し、詳細は「くわしく見る」で展開する。これも視認性向上の一環として位置づける
3. **凡例の常設**: 色分けされた数値セルやグラフには、常に「この色・この形は何を意味するか」を示す凡例を画面内に固定表示する
4. **広告と分析体験の分離**: 龍神レーダーは広告モデルへの依存度次第だが、少なくとも分析中のコンテンツ領域には広告を重ねて表示しない設計を明確なルールにする

（参考・優先度低）n数の視認性やn=1の円グラフ表示のような統計的厳密性の論点は、BOA-271のモックで既に確立したパターン（小標本フラグ等）があるため必要に応じて流用すればよいが、日和との差別化における主軸としては扱わない。

- **重複が見つかりCanceledにしたもの**: [BOA-297](https://linear.app/boat-ai/issue/BOA-297)（身長・血液型・生年月日）は、`racer_profiles`テーブル（`scripts/maintenance/scrape-racer-profiles.js`、boatrace.jp「レーサー検索」由来）に全項目が既に存在すると判明。DATA_SCRAPING_GAPS.mdの「支部・出身地❌」という記載自体も誤りで、同テーブルに支部・出身地も含めて既に存在した（自動実行ジョブが無く手動実行頼みという運用面の課題は残る）。[BOA-288](https://linear.app/boat-ai/issue/BOA-288)（体重）も同テーブルの`weight_kg`で大半代替可能と判明し優先度を下げた
