# TikTok向け新規コンテンツ軸（賭け結果に無関係な企画）

マルチチャネルコンテンツパイプライン（`feature/content-ops-flow-redesign`ブランチ、`docs/design/content-multi-channel-pipeline/`）の企画メモ。案1〜3は2026-09-02にパイプラインへ統合済み（下記「現状の運用方針」参照）。

## 背景: なぜ新しい企画軸が必要か

2026-09-01、TikTok運用で以下が判明した（詳細: `docs/operation/tiktok-posting-operations.md` D節（このブランチでの節。他ブランチではF節）、`docs/operation/sns-video-producer-prompt.md` 絶対厳守ルール12）。

- 「本命」「対決」等の煽り表現を避けた「純粋なデータ紹介」の会場攻略型動画（複勝率ランキング）も、TikTokガイドライン違反と判定され削除された。異議申し立ても却下
- TikTok広告ポリシーは「賭けの結果に影響を与える・改善するために設計されたインサイト・統計・賭け戦略を提供するコンテンツ」をギャンブル情報として広く規制対象にしている。**表現面の対策では回避できない**
- 結果、会場攻略型・データ一覧型・答え合わせ型・予想数値フック型・回収率型・出目分布型など、既存フォーマットの大半が新規制作停止になった

一方でマルチチャネルパイプラインの `channelMatrix.js` は `venue-characteristic`（会場特性）トピックモジュールをTikTokチャネルに接続しており、コメントで「既存の会場攻略型ローテーションに乗る」ことを前提にしている。この前提はルール12で崩れている（この矛盾自体はBOA-237で起票済み）。

このドキュメントは、その代わりにTikTokで使える新しい企画軸を提案するもの。

## 承認済みの企画案

### 1. 競技解説・技術トリビア型（物理・規格ネタ）

ボートレースの競技性そのものを解説する型。勝率・回収率等の成績データには一切触れない。

- ネタ例: 全艇同一規格（モーター・ボートは抽選で貸与、重量統一）、ターン時にかかる遠心力、進入コースが決まる仕組み（スタート展示・くじ）、プロペラ調整の話
- 訴求: 「なぜこのスポーツは面白いか」を伝える教育コンテンツ。勝敗と無関係な競技解説で興味を引く
- リスク評価: 低。成績・確率・統計を扱わないため賭け結果と無関係と説明しやすい

### 2. 海外向け「Kyotei/Boat Racing入門」（英語字幕）

日本特有のこの競技を海外視聴者に紹介する型。1と同じ「競技解説」の海外版だが、狙う市場が異なるため別軸として扱う。

- 既存のi18n調査（[[i18n_technical_and_demand_audit_2026_08_16]]）で「英語圏は『AI予想』より『観戦教育コンテンツ』需要が中心」と判明済み。この知見と直結する
- リスク評価: 低。1と同様、成績・確率を扱わない前提を維持すれば安全

### 3. サービスの信頼性・スケール訴求型

「AIが読んでいるデータの量」を可視化し、信頼性・ブランド訴求を行う型。的中率のような結果指標は使わない。

- ネタ例: 毎日自動収集しているレース数・選手データ件数、分析している指標の数（40項目以上）、開発の裏側
- 訴求: サービスの本気度・透明性を見せてブランド信頼を作る
- 注意点: 「的中率◯%」のような精度指標は今回のルール12の対象になりうるため使わない。純粋にインフラ・データ量の話に留める
- リスク評価: 低〜中。数値の選び方次第でグレーになりうるため、公開前に「賭けの判断材料になりうるか」を毎回チェックする

### 4. 使い方ライフハック型（機能紹介の強化版）

既存の「一覧アピール型」を、単なる機能紹介から「知らないと損する使い方」の切り口に強化する型。

- 対象は明確に賭け結果と無関係な機能に絞る（例: 言語切替、レース間ナビゲーション、選手ニュース機能、会場ガイド）
- 対象外にすべき機能: AI予想・展開予測・出目分布・回収率分析等、成績・確率に関わる分析ツールタブ
- リスク評価: 低。対象機能を正しく選別すれば安全

### 5. 観戦体験型（要検討）

レース実況の臨場感を見せる型。ユーザーとの会話で `> E` として言及されたが、具体的な承認内容は未確定のため要再確認。

- ネタ例: スタート・ターンの映像美、水しぶき等、スポーツとしての興奮を結果情報ゼロで見せる
- 技術的な制約: 現行のマルチチャネルパイプラインはRemotionベースのデータ可視化（統計をグラフィック化する仕組み）が中心で、実際のレース映像素材を使う制作フローは無い。素材調達・権利関係の確認が別途必要
- リスク評価: 低（結果情報を含めなければ）だが、技術的な実現性が他の案と異なるため優先度は低めに扱ってよい。**2026-09-02時点でも未統合**（下記参照）

## 既存のネタ供給タクソノミーとの不整合（統合前の分析）

マルチチャネルパイプラインの4モジュール（`new-feature` / `venue-characteristic` / `data-insight` / `daily-result`）は「日々の実データに紐づくネタ」を前提にした設計。対して上記の案は性質が異なる。

| 案 | 性質 | 既存モジュールへの適合 |
|---|---|---|
| 1. 競技解説 | 評価軸固定の教育シリーズ、日次データに紐づかない | 不適合だった。新しいモジュール種別として統合済み（`competition-trivia`） |
| 2. 海外向け入門 | 同上 | 不適合だった。新しいモジュール種別として統合済み（`overseas-intro`） |
| 3. データ規模訴求 | 単発〜低頻度の恒久ブランドコンテンツ | 不適合だった。新しいモジュール種別として統合済み（`service-trust`） |
| 4. 使い方ライフハック | 既存機能の切り口違い | 部分適合。`new-feature`モジュールの対象を「機能（新規/既存問わず）」に拡張して吸収済み |
| 5. 観戦体験 | 素材（映像）ドリブン、データドリブンではない | 不適合のまま。別の制作フローが必要で未統合 |

## 現状の運用方針（2026-09-02更新）

案1〜4をマルチチャネルパイプラインに統合した（`docs/design/content-multi-channel-pipeline/spec.md` FR1・FR2、`scripts/lib/contentChannels/channelMatrix.js`）。

- TikTokへの展開可否は、ネタ種別（カテゴリ）単位ではなく**個別ネタごとの判定**に変更した。既存4系統（新機能・会場特性・データ知見・成績）は成績・確率・回収率等を扱うのが前提のため`CHANNEL_MATRIX`上ではTikTokを含めず、個別ネタが例外的に安全と判定できた場合のみ`getChannelsForTopic(sourceId, {isGamblingRelevant: false})`でTikTokを追加する
- 新設3系統（`competition-trivia`・`overseas-intro`・`service-trust`）は成績・確率を扱わない設計のため既定でTikTokを含める
- **未実装（次のステップ）**: 新設3系統の候補生成ロジック・Remotionコンポジションテンプレートは今回設計のみで、実際のコンテンツ制作フローはまだ無い（`docs/design/content-multi-channel-pipeline/tasks.md`タスク41）
- 案5「観戦体験型」は引き続き未統合。実レース映像素材の調達・権利関係の確認が別途必要なため、着手する場合は別途スコープを切る
