# データ取得戦略 - サーバー負荷と利用価値のバランス

## 前提条件

### ボートレース公式サイトの特性
- 1日最大24会場×12レース = **288レース**
- レース間隔: 約30分
- 各レースページへのアクセスが個別に必要

### データ公開タイミング
| データ種別 | 公開タイミング | 更新頻度 |
|-----------|---------------|----------|
| 出走表（選手情報） | 前日〜当日朝 | 変更なし |
| 天候情報 | レース前に随時更新 | 数時間ごと |
| 展示タイム・ST | レース約30分前（展示航走後） | 1回のみ |
| オッズ | 発売開始〜締切まで変動 | 数分ごと |
| 結果 | レース終了後（約5分） | 1回のみ |

---

## 現状の取得フロー

```
[毎時0分] GitHub Actions
    │
    ├─ scrape-to-json.js (出走表・天候)
    │   └─ 約300リクエスト/回
    │
    ├─ generate-predictions.js (AI予想生成)
    │   └─ Supabase書き込みのみ
    │
    └─ scrape-results.js (結果取得)
        └─ 約300リクエスト/回（完了済みはスキップ）
```

**1日あたり推定リクエスト数**: 約600〜1,000リクエスト

### 3. オッズ

**2026-09-14追記: このセクションは古い（2026-03-10時点の記載）。BOA-49（2026-04-08）で下記の通り実装済み・稼働中。**

| 取得タイミング | 利用価値 | サーバー負荷 | 実現可能性 |
|---------------|---------|-------------|-----------|
| 締切直前 | 最高（期待値計算） | 非常に高 | ~~❌ 非推奨~~ → ✅ **実装済み**（下記参照、負荷を抑える設計で解決） |
| 結果取得時（確定オッズ） | 高（回収率計算） | 低 | ✅ 推奨（従来通り） |
| 取得しない | - | - | ~~現状~~ → 現状は取得している |

**実装済み**（`scripts/daily/scrape-odds.js`、BOA-49）: 発走60/30/15/10/5分前（各±3分のウィンドウ）に、単勝・複勝オッズ（`oddstf`ページ）と3連単人気上位オッズ（`odds3t`ページ）を取得し、`race_odds`テーブルに`captured_at`込みで時系列保存する（1レースにつき複数スナップショットが残る設計）。

「締切直前は負荷が非常に高い」という当時の懸念は、**全レースを毎回ポーリングするのではなく、発走が近いレースだけをイベント駆動的に狙い撃ちする設計**で解決した:
- 外部cron-job.org（プライマリ）またはGitHub Actions（バックアップ、10分間隔）から5分毎にオーケストレーター（`scrape-scheduled.js`）を起動
- 対象ウィンドウに該当するレースが1件も無ければ、その回は**リクエスト0件で即終了**（Egressゼロ）
- 該当レースがある場合のみ、そのレース分だけ`oddstf`/`odds3t`の2ページを取得（1秒の待機を挟む）
- User-Agentは`BoatraceAIBot/1.0 (+https://github.com/rhapsody0919/boatrace-ai-predictor)`で素性を明示（偽装しない）

結果、1日あたりの実質リクエスト数は「全288レース×高頻度ポーリング」ではなく「発走が近づいたレースの分だけ、5つの時点で2ページずつ」に抑えられている。ブロックされるリスクを避けるための待機・User-Agent明示は既存の展示データ取得（15分間隔ワークフロー）と同じ設計思想を踏襲している。

#### 競合（ボートレース日和）のオッズ取得設計との比較（2026-09-14実証）

日和のオッズ設計が「全レース常時ポーリング」なのか「イベント駆動型」なのかを、日和の出走表ページが実際に発行するAJAXリクエスト（`request_odds_shousai.php`、ページ読み込み時に元々発生するものと同一）を2回呼び出し、レスポンスの構造から検証した（追加の負荷はかけていない、通常のページ利用で発生する範囲のリクエスト）。

レスポンス中の`jikan_odds_list`（時間別オッズ一覧）に含まれる`shimekiri`（締切までの残り分数）フィールドの値は、実際には次の5種類のみだった:

```
shimekiri: [0, 5, 10, 20, 30]  （各120件＝3連単120通り分のスナップショット）
```

**結論**: 日和も、発走（締切）の30/20/10/5/0分前という**5つの離散的なタイミングでしかオッズを取得しておらず、全レースの常時ポーリングはしていない**。龍神レーダーの60/30/15/10/5分前ウィンドウ方式（粒度は異なるが同じ発想）と本質的に同じ「イベント駆動型・複数スナップショット方式」であることが確認できた。むしろ龍神レーダーの方が発走60分前という早い時点から1点持っており、より早期のオッズ変動を追える設計になっている。

この事実により、「発走直前だけ狙い撃ちして取得する」という現行設計は、独自の妥協案ではなく、この種のデータを扱う上での業界標準的なアプローチだと裏付けられた。

## リアルタイム取得が必要な場合の代替案

### 案1: 公式API（存在する場合）
- ボートレース公式がAPIを提供していれば、スクレイピングより効率的
- 現時点で公式APIの存在は未確認

### 案2: 外部データプロバイダー
- ボートレースデータを提供するサードパーティサービス
- 例: 競艇データベース系サービス
- コストがかかるが、サーバー負荷なし

### 案3: ユーザー起点の取得
- ユーザーがレースページを閲覧した際にデータを取得
- フロントエンドからのリクエストは公式サイトへの直接アクセス
- サーバー側でのスクレイピング不要

## 補足: ユーザーにとっての「利用価値の高い期間」

| ユースケース | 必要なデータ | 取得タイミング |
|-------------|-------------|---------------|
| レース前の予想閲覧 | 出走表、AI予想、天候 | 当日朝で十分 |
| 賭け直前の判断 | 展示タイム、ST、オッズ | レース30分前が理想 |
| 結果確認 | 着順、配当 | レース後 |
| 過去分析・モデル改善 | 全データ | レース後で十分 |

**現実的な判断**:
- 賭け直前のリアルタイムデータは**負荷が高すぎる**
- 過去分析用データは**結果取得時に併せて取得**が効率的
- ユーザーへの価値提供は**AI予想の精度向上**（過去データ分析による）が現実的
