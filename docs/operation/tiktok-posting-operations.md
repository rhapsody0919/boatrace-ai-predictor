# 龍神レーダー TikTok投稿運用フロー（2026-08-24確定）

`sns-video-producer-prompt.md`（動画制作・型選定ロジック）とは別に、「作った後どう投稿・追跡するか」のTikTok版を扱う。Xの`sns-posting-operations.md`と役割は同じだが、プラットフォームごとに分岐させる方針（`sns-marketing-strategy.md`参照）に沿って別ファイルにしている。

## 前提となる制約（Xと共通）

- **投稿は毎回ユーザーの明示的な承認が必要**（Claude側の安全ルール。一度の許可を根拠に以降無許可で投稿し続けることはできない）
- **動画ファイルの添付は自動化不可**（2026-08-24確認済み）。TikTok Studioのアップロード画面（`tiktok.com/tiktokstudio/upload`）のファイル入力に対し、Chrome拡張の`file_upload`ツールでプロジェクト内のmp4ファイルを渡そうとしたが、Xの時と同じ理由（「セッションに明示的に共有された添付ファイルのみ」という制約）で失敗した。毎回ユーザーに手動添付を依頼する前提で設計する。同じ検証を毎回繰り返さない
- **プロフィール写真の自動設定も不可**（2026-08-24確認済み、同じ制約）。ロゴ画像はユーザーに手動アップロードを依頼する

- サイズと長さ: 最大30GB、動画の長さ最大60分（本パイロットの15〜20秒設計は問題なく収まる）
- ファイル形式: `.mp4`推奨（他の一般的な形式もサポート）
- 動画の解像度: 1080p・1440p・4K推奨（Remotionの1080x1920出力で対応）
- 縦横比: 横向きは16:9、縦向きは9:16推奨（既存コンポジションは1080x1920＝9:16で設計済み）

## A. コンテンツ制作（毎日投稿の確認フロー）

`.claude/CLAUDE.md`の「セッション開始時のTikTok投稿確認」・`sns-video-producer-prompt.md`の「TikTok投稿頻度・型選定ロジック」に従う。

## B. 投稿準備（Claude側で毎回実施）

1. TikTok Studio（`tiktok.com/tiktokstudio/upload`）のアップロード画面を開く
2. 「動画ファイルを`{パス}`から選んで添付してください」とユーザーに明確なパスを伝える（フォルダを探させない）
3. 添付完了の報告を受けたら、キャプション・ハッシュタグを入力する（作法は`sns-viral-copywriter-prompt.md`のTikTok向けセクションを参照、未整備なら次回整備する）
4. 投稿前の最終状態をスクリーンショットで確認し、ユーザーに一言「この内容で投稿していいか」を確認してから投稿ボタンをクリックする

## C. 投稿後のトラッキング

1. `data/analysis/tiktok-posts/history.json`の該当エントリを`status: "posted"`に更新し、`postedAt`を記録する
2. 24時間後を目安に、いいね数・保存数・再生数を確認できれば`metrics`に追記する（TikTok版の定点観測の仕組みはまだ未整備、`/x-growth-report`相当が必要）

## D. ギャンブル関連ガイドライン違反による方針転換（2026-09-01発覚、2026-09-02当ブランチに反映）

対決煽り型の削除・異議申し立て却下に続き、「本命」「対決」等の煽り表現を一切使わない「純粋なデータ紹介」の会場攻略型動画（複勝率の会場別ランキング）も追加でガイドライン違反判定を受け削除された。TikTok広告ポリシーに「賭けの結果に影響を与える・改善するために設計されたインサイト・統計・賭け戦略を提供するコンテンツ」がギャンブル情報として明記されており、**表現面の対策では回避できない**と判明した。詳細な調査経緯・型ごとの継続可否は`sns-video-producer-prompt.md`絶対厳守ルール13（このブランチでの番号。他ブランチでは12として先に文書化されている）を参照。

2026-09-02、代替のTikTok向けコンテンツ軸（`docs/proposal/tiktok-non-gambling-content-ideas.md`）をマルチチャネルパイプラインに統合し、TikTokへの展開可否をネタ種別単位ではなく個別ネタ単位で判定する方式に変更した（`scripts/lib/contentChannels/channelMatrix.js`、BOA-237）。

## E. 1日の投稿本数上限（2026-08-26追加）

1日の投稿本数は**6本を上限**とする。`data/analysis/tiktok-posts/history.json`の当日エントリが既に6件あれば、追加投稿は提案せず翌日に回す（`.claude/CLAUDE.md`「セッション開始時のTikTok投稿確認」参照）。`docs/reference/tiktok-algorithm-and-growth-notes.md`の調査によると、業界分析が指摘するスパム判定の閾値は「1日10本以上の過剰投稿」であり、この6本上限はまだ余裕がある水準（項目11参照）。

## F. シャドウバン発生時の回復プロトコル（2026-09-05追加、`tiktok-algorithm-and-growth-notes.md`項目11を反映）

複数の業界分析が一致する段階的な回復期間の目安（TikTok公式は「シャドウバン」概念自体を公式には認めていない点に留意、確度中）:

| 違反の重さ | 回復期間の目安 |
|---|---|
| 軽微な初回違反 | 24〜48時間 |
| スパム的行動フラグ（過剰投稿・大量フォロー等） | 3〜7日 |
| コミュニティガイドライン違反 | 7〜14日 |
| 深刻・繰り返し違反 | 2週間以上 |

**兆候検知時の対処手順**:
1. 連続投稿で再生数が複数本0になる等の兆候が出たら、新規投稿を即座に停止する（`.claude/CLAUDE.md`フローC-3で既に運用中）
2. 問題となった可能性のあるコンテンツを削除・非公開化する
3. 上表を目安に投稿を休止する（違反の重さが不明な場合は「スパム的行動フラグ」相当の3〜7日を初期値とする）
4. 休止期間終了後、ガイドラインを再確認した上で、安全な高リテンション動画（過去の実績が良かった型）から復帰する
5. 復帰後も再生数の推移を確認し、再び0が連続する場合は休止期間を1段階重い区分に引き上げる

2026-08-29発覚のシャドウバンは、本プロトコル整備前のため上記手順を経ずに「ユーザー判断待ち」のまま保留されていた。今後同様の事象が発生した場合は本プロトコルに従う。
