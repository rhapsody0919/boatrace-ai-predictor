# バグ原因の定点観測

## 何のための手順か

2026-09-25に、fixコミット147件を全件分類して「バグが量産される原因」を特定した。その結果を受けて入れた対策が実際に効いたかを、**同じ基準で測り直す**ための手順。

基準を残しておかないと、次回の分類が別の基準になって比較できなくなる。文献上も、主観評価は当てにならないことが実証されている（[METR RCT](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) で、実測19%遅くなっているのに開発者本人は20%速くなったと評価した）。「良くなった気がする」は証拠にならない。

## 計測の区間

| | 起点 | 終点 |
|---|---|---|
| 第1期（ベースライン） | 2026-08-15 | 2026-09-25 |
| 第2期 | **2026-09-26**（コミット `464761ef`、PR #861 のマージ） | **2026-10-24〜11-07** |

第2期は4〜6週間取る。2週間だとfixが約13件しか出ず、原因別に割ると1カテゴリ3〜4件で、効果の有無を判断できないため。

| 期間 | 推定fix件数 | うち最多カテゴリ |
|---|---:|---:|
| 2週間 | 約13 | 3〜4 |
| 4週間 | 約26 | 7 |
| 6週間 | 約40 | 10〜11 |

## 第1期の実測（比較対象）

fixコミット169件のうち、レビュー・フィードバック由来を除いた**147件**が「実装完了後に実行時・本番で発覚したもの」。

| 原因 | 件数 | 比率 |
|---|---:|---:|
| R4 仕様・要件の取り違え | 39 | 26.5% |
| R7 単純な実装ミス | 36 | 24.5% |
| R3 既存実装を知らず再実装・規約逸脱 | 26 | 17.7% |
| R5 実行環境差異 | 16 | 10.9% |
| R1 外部データの想定外パターン | 13 | 8.8% |
| R2 失敗の握りつぶし・誤った成功判定 | 9 | 6.1% |
| R6 並行セッション・worktree起因 | 8 | 5.4% |

同期間のマージPR数は**125**、全コミット中のfix率は19.5%。

なお `bug-cause-report.js` で同じ期間を集めると**146件**になり、手作業の147件と1件ずれる。集計時点の履歴の違いによるもので、比率には響かない。マージPR数は当時の報告で130としていたが、**このスクリプトの数え方に揃えて125とする**。第2期も同じ数え方をするので、分母の算出方法を合わせる方を優先した。

### 分類の定義

| 記号 | 定義 |
|---|---|
| R1 | 外部データ・外部サイトの想定外パターン（中止レース、欠場、未公開オッズ等、現実世界のエッジケース） |
| R2 | 失敗の握りつぶし・誤った成功判定（エラーを「データなし」に化かす、0件書き込みを成功扱い等） |
| R3 | 既存コード・既存ヘルパーの存在を知らずに再実装した（重複実装・規約逸脱） |
| R4 | 仕様・要件の取り違え（意味の取り違え、指標の定義ミス、UIの意図と違う） |
| R5 | 実行環境差異（ローカルでは通るがVercel/CI/Routineでは通らない） |
| R6 | 並行セッション・worktree起因（ブランチ混線、古いコード参照、番号衝突） |
| R7 | 単純な実装ミス（typo、条件式ミス、スケール不一致など、注意で防げるもの） |

混在するコミットは**主因1つに丸める**（第1期もそうした）。

## 指標

生の件数は開発量に比例するので比較できない。**正規化する。**

```
原因別fix率 = その原因のfixコミット数 ÷ 同期間のマージPR数
```

第1期のベースライン: 仕様取り違え 39 ÷ 125 = **0.312 件/PR**、単純ミス 36 ÷ 125 = **0.288 件/PR**。全体では 147 ÷ 125 = **1.176 件/PR**。

## 手順

### 1. 対象を集める

```bash
node scripts/maintenance/bug-cause-report.js --since=2026-09-26 --until=2026-10-24
```

fixコミットの一覧（ハッシュ・件名・変更ファイル）と、同期間のマージPR数を出す。

### 2. 分類する

出力された各コミットを `git show` で読み、上のR1〜R7に割り当てる。**件名だけで判断しない**（第1期も全件 diff を読んだ）。

除外するもの: 件名または本文に「セルフレビュー」「レビュー指摘」「フィードバック」「実機」を含むもの。これらはマージ前に捕捉されており、「実装完了後に発覚した」に当たらない。

### 3. 比較する

原因別fix率を第1期と並べる。**傾きで見る**。DORA 2026 は AI導入のROIがJ-curve（初期はマイナス）を描くと報告しているため、導入直後の悪化だけで判断しない。

## 第2期に入っている対策

| 対策 | 狙う原因 | 入った日 |
|---|---|---|
| 曖昧性検出エージェント（`spec-ambiguity-detector`、PR #860） | R4 | 2026-09-26 |
| セッション長の自動判断（PR #861） | 全般（指示遵守率の劣化） | 2026-09-26 |

**この2つは同時に入れた。** どちらが効いたかは分離できない。4〜6週間待って厳密に切り分けるより、対策を早く効かせる方を選んだ（2026-09-26にユーザーが判断）。

第2期の直前（2026-09-25）に入った対策も効果が混ざる。マージのローカルゲート（ADR-0075）、中止判定の集約（BOA-418）、4言語ロケール整合検査、本番DB検証の夜間実行、worktree棚卸し、共通ロジックの索引、`.worktreeinclude`、常時読み込みルールの削減、E2Eのskip可視化。

**この混在は避けられなかった。** 同一モデルでも harness を変えるだけで SWE-bench Verified の結果が 28%→49% に変わる（[arXiv 2608.26218](https://arxiv.org/abs/2608.26218)）ので、本来は1つずつ入れて測るべきだった。第3期以降はそうする。

## 効果が否定されている施策（再提案しない）

測り直す前に、文献で否定済みのものを再び入れないこと。

| 施策 | 実証結果 | 出典 |
|---|---|---|
| CLAUDE.md のサイズ・順序・分割の調整 | 4変数とも有意差なし（BF10で帰無仮説を積極支持） | [arXiv 2605.10039](https://arxiv.org/abs/2605.10039) |
| context file の追加 | 成功率は上がらず、コスト+20%超。リポジトリ概要は役に立たない | [arXiv 2602.11988](https://arxiv.org/abs/2602.11988) |
| embedding索引によるコード検索 | issue→編集箇所の特定で nDCG@10 が 71.7→20.3 に崩壊。効くのは構造ベース | [arXiv 2606.11864](https://arxiv.org/html/2606.11864) |
| 外部フィードバック無しの自己レビュー | 改善せず、悪化しうる | [arXiv 2310.01798](https://arxiv.org/abs/2310.01798) |
| reasoning を強めて曖昧性に気づかせる | ほぼ改善しない（Reasoning Paradox） | [arXiv 2607.00711](https://arxiv.org/html/2607.00711) |
| 品質ガイダンスで劣化を止める | 初期値は最大1/3改善するが劣化率は不変 | [arXiv 2603.24755](https://arxiv.org/abs/2603.24755) |
| ファイル分割でfixを減らす | fix率と行数の相関 r=0.19。サイズ起因の9件中8件は分割しても同じファイルに入る距離だった（このリポジトリの実測） | 2026-09-25の分類 |
