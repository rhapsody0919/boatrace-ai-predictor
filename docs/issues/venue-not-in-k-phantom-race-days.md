# race_results欠損のうちvenue_not_in_k分類（408件）の原因調査（BOA-407）

調査日: 2026-09-24。読み取り専用調査（本番DBへの書き込みは無し）。対象は[BOA-403](https://github.com/rhapsody0919/boatrace-ai-predictor/pull/807)（PR #807）で発覚した`race_results`欠損のうち、`venue_not_in_k`（該当日のK-fileにその会場のブロックが無い）に分類される分。もう一方の`race_not_in_k_venue`（K-fileにはその会場があるがレース番号が超過＝中止・打ち切りの疑い、269件）は別チケット（BOA-406、cancellation-status-investigation）の範囲であり本書では扱わない。

## 1. 結論

- **`race_id`の日付ズレではない**。408件（34会場日×12レース）はいずれも、**過去の実在する開催日の出走表（`race_entries`）がそのまま複製され、その会場の開催がとっくに終わった別の日付の下に誤って保存された「幻の開催日」**である。日付を書き換えて正しい`race_id`に直す対象（BOA-325のような修正）ではなく、**行そのものを削除すべき**データである。
- **BOA-325・BOA-402とは別原因**。BOA-407のチケット説明はBOA-325・BOA-402と「同一原因の疑い」としていたが、確認の結果いずれとも異なる：
  - BOA-325は自社データ最古日（2025-12-03）の120レースで、`race_id`に埋め込まれた日付と`race_date`列が**同じレース内で**食い違っていた問題（実際に開催されたレースのIDの誤り）。今回の408件は`race_id`と`race_date`は一致しており、その代わり**開催そのものが実在しない**。
  - BOA-402は「本日のデータ一覧」ページ機能のチケットで、日付ズレとは無関係（チケット説明への記載は誤り）。
- **34会場日のうち33件（396レース）**は、自社DB内に残る**過去の実在日の`race_entries`と完全一致**（同一レース番号に対し6艇全ての`racer_id`が一致、12レース×6艇=72値が全て一致）することを確認した。**残り1件（2025-12-03の津、12レース）**は自社データの最古日のため比較対象が自社DBに無いが、公式K-fileで2025-12-02に同一会場・同一レース番号のレースが存在することを確認した（BOA-407チケット記載の実例と同一、BOA-325の120件と同じ日）。408件全てについて、「その日その会場のレースは実在しない」という結論の根拠（自社DB内の完全一致、またはK-fileでの実開催日確認）が揃った。
- 発生日は2025-12-03〜2026-03-31の間で**7日のみ**（2025-12-03・2026-01-09・2026-01-11・2026-02-03・2026-03-06・2026-03-08・2026-03-09）。1日あたり1〜9会場、1会場=12レース単位でまとまって発生しており、レース単位のランダムな欠損ではない。
- 複製元は直前の1日とは限らない（1〜4日前）。さらに、**複製先が翌日以降に再度複製される「複製の連鎖」**を確認した（例: 2026-03-05[実データ]→03-06[複製]→03-08[03-06をさらに複製]、03-08→03-09[さらに複製]）。連鎖は次の実データ取得（例: 該当会場の03-10）で自然に途切れている。

各会場日について、`race_entries`の艇番1〜6の`racer_id`を、レース番号ごとに、直近14日以内で最初にその会場のデータが存在する過去日と突き合わせた（完全一致するまで、データが無い日は読み飛ばしてさらに過去へ遡る）。

```js
// race_id.slice(11,13) が会場コード、race_id.slice(14,16) がレース番号
// 対象日の各レース番号のracer_idが、過去Nの日の同一レース番号のracer_idと
// 12レース全て一致するかを確認（境界=6艇×12レース=72値の完全一致）
```

### 3.1 複製の連鎖

2026-03-06→03-08→03-09と、複製先がさらに複製されるケースを確認した。例: 丸亀(15)は03-05（実データ）→03-06（03-05の複製、本調査の対象）→03-08（03-06をさらに複製、本調査の対象）という2段階の連鎖。浜名湖(06)・蒲郡(07)等は03-08→03-09で1段階の連鎖。

いずれのケースも、連鎖はその後の実データ取得で途切れている（例: 平和島(04)は03-10に03-05・03-08とは異なる新しい乗艇表が確認でき、複製ではなく実データに復帰している）。1回限りのサーバー側の不具合ではなく、**「その会場は今日レースが無い」と正しく判定できなかった日に、直前に保持していた出走表をそのまま今日の分として書き込んでしまう、という挙動が、条件が揃うたびに繰り返し起きている**ことを示す。

### 3.2 races.created_atのばらつき

比較のため、対象34会場日の`races.created_at`（JST換算）を確認したところ、07時台〜17時台まで分散しており、特定の時刻帯（例: 深夜0〜4時台）に集中していなかった。[`docs/issues/races-opening-day-missing.md`](./races-opening-day-missing.md)が特定した「日付未ロールオーバーの`race/index`を深夜に取得してしまう」バグ（`getTodayVenues()`、PR #625で対応済み）とは**発生タイミングの特徴が異なる**。両者は「その会場の開催状況を当日基準で正しく判定できていない」という点で似ているが、同一のコードパスと断定はできない。

## 4. 自社DB内で複製元を確認できない唯一のケース

### 4.1 2025-12-03 津(09) — 自社データ最古日

自社DBには2025-12-02のデータが一切存在しない（`races`テーブルの最古日は2025-12-03）ため、自社DB内での複製元特定はできない。ただし、K-fileでは2025-12-02に津(09)の同一レース番号（R1〜R12）が存在することを確認済み（BOA-407チケット記載の実例と一致）。

これはBOA-325（自社データ初日120レースの`race_id`日付ズレ）と**同じ120レースの一部**である。BOA-325は「`race_id`の日付部分(2025-12-02)を`race_date`列(2025-12-03)に合わせて訂正する」対応をPR #664/666で実施済みだが、この対応は**`race_date`列側が正しいという前提**に立っていた。今回の調査結果（津のレースは実際には2025-12-02に開催されていた）は、その前提が疑わしいことを示唆する。ただし、以下の理由で本チケットの対象からは切り離す：

- BOA-325の120レース中、`race_results`が存在するレース（津以外の会場）は結果が確定済みで、"2025-12-03に開催された"という前提のまま予測・的中率集計等に既に使われている。今さら日付を差し戻すと、この期間の集計全体に波及する
- 津の12レースだけを他と異なる扱い（削除）にすると、BOA-325で「1日分・120レース」として扱った単位を割ることになり、影響範囲の切り分けが複雑になる
- BOA-325は既にDoneでクローズ済みのチケットであり、その前提の再検証（本当に`race_date`側が正しかったか）は本チケットのスコープ外の別問題

**津(09)の12レースは、本チケットの削除対象に含めず、現状維持のうえ、BOA-325の前提再検証は別チケットで扱うことを提案する**（§6参照）。

## 6. 修正方針の提案

### 6.1 削除対象（推奨）

**33会場日・396レース**（§3の一覧全て）を削除する。いずれも自社DB内で過去の実在日と12レース×6艇=72値が完全一致することを確認済みであり、「その日その会場に開催は無かった」と断定できる。

```sql
-- 例（実際の削除は、対象race_idリストを都度§2.3の突き合わせロジックで
-- 再抽出してから実行する。本番DBは並行稼働の他ジョブで日々変動するため、
-- ハードコードしたリストをそのまま使わない）
DELETE FROM races WHERE race_id IN (
  '2026-01-09-02-01', '2026-01-09-02-02', ..., -- 33会場日×12レース分
  ...
);
```

推奨する実行手順:

1. 実行直前に、本書§2.3の突き合わせロジック（`classifyMissingResult`が`venue_not_in_k`を返し、かつ直近14日以内に12レース全一致する過去日が自社DB内に存在する）を**スクリプト化**し、対象行を都度再抽出する（ハードコードされたrace_idリストを直接使わない）
2. `--dry-run`で対象件数・会場日一覧を出力し、本書の想定件数（396レース、33会場日）と一致することを確認する
3. ユーザー承認後、`DELETE FROM races WHERE race_id IN (...)`を実行（CASCADE任せでよい。子テーブルの個別UPDATE退避は不要）
4. 削除後、`backfill-kb-recent-results.js plan`を再実行し、`venue_not_in_k`が33会場日分（396件）減り、津(12件)のみが引き続き`venue_not_in_k`として残っていることを確認する

### 6.2 削除しない・別扱いとするもの

- **津(09) 2025-12-03分12レース**（§4.1）: BOA-325の120レースの一部であり、`race_date`側の前提再検証が必要なため、本チケットでは現状維持し、BOA-325の前提再検証を別チケットで扱うことを提案する

### 6.3 再発防止・追加調査の提案（本チケットでは未実施）

- **調査範囲の限定**: 本調査は`docs/design/scraping-vercel-consolidation/data-catalog.md` N32の対象期間（2025-12-03〜2026-03-31）に限定した。同じ「会場日単位の複製」パターンが2026-04-01以降にも存在するかは未確認（`race_results`が存在する会場日は本チケットの抽出方法では見つからないため、別途K-fileとの突き合わせが必要）
- **現行パイプラインでの再現性は未確認**: 対象期間（Dec2025-Mar2026）は`scraping-vercel-consolidation`（2026-09以降）による刷新前のコードで発生している。当時の該当コード（会場ごとの出走表取得処理）は既に置き換わっている可能性が高く、本調査では現行コードでの再現性を確認していない。`docs/issues/races-opening-day-missing.md`の再発防止策（`hd=`明示指定、月間スケジュール由来の充足チェック）が本事象（開催終了後の会場が翌日以降も出走表を複製し続ける）もカバーするかは要確認
- 上記2点は、本チケットの範囲（過去データの原因調査・修正方針）を超えるため、別チケットでの追跡を推奨する
