# イン崩れ指数（volatility_level）閾値の妥当性分析

**問題 ID**: BOA-115  
**調査期間**: 2026-05-07 ～ 2026-05-08（7日間）  
**分析対象**: 全24会場のスコア分布と閾値設定

---

## 概要

スコア計算が **30-70 の範囲に意図的に制限** されているのに対し、複数会場の閾値が **55-75 の高い値** に設定されており、スコアの上限では達成不可能な設定になっています。これにより、一部会場で **100% 「本命有利」(low) 分類** という異常状態が発生しています。

### 現象
- **多摩川 (05)**: 全レース 100% 'low' 分類（72/72）
- **住之江 (12)**: 全レース 100% 'low' 分類（72/72）

---

## 問題の根本原因

### 1. スコア計算の設計（scripts/daily/generate-predictions.js:170）

```javascript
// キャリブレーション: 分析で観測した30〜70%レンジに線形変換
const finalScore = Math.min(100, Math.max(0, Math.round(30 + composite * 40)));
```

- **スコア範囲**: 30 ～ 70（固定）
- **設計根拠**: 過去分析で観測された実績値レンジ
- **制約**: `composite` が [0, 1] の範囲になるため、スコアは必ず 30-70 に収まる

### 2. 閾値計算の設計（scripts/daily/generate-predictions.js:185-191）

```javascript
function getVolatilityLevel(score, venueCode) {
    const highThr = VENUE_VOLATILITY_THRESHOLD[venueCode] ?? VENUE_VOLATILITY_THRESHOLD_DEFAULT;
    const lowThr  = Math.max(30, highThr - 15);
    if (score < lowThr)  return 'low';
    if (score < highThr) return 'medium';
    return 'high';
}
```

- **high 閾値**: VENUE_VOLATILITY_THRESHOLD から取得（45-75）
- **low 上限**: `Math.max(30, highThr - 15)`
- **問題**: `highThr - 15` がスコア最大値 70 を下回る会場が複数存在

### 3. 会場別閾値の実績ベース設定（scripts/lib/venueParameters.js:19-44）

実績ベースで設定された high 閾値（定義引用）：

```
多摩川 (05):  75  // スコア上限70では到達不可 🔴
住之江 (12): 70  // スコア最大51では到達不可 🔴
宮島 (17):   65  // スコア最大51では「本命有利」のみ 🟡
```

## 詳細な問題分析

### 🔴 重大: 多摩川 (05)

| 項目 | 値 |
|------|-----|
| 観測スコア範囲 | 42-57 |
| 平均スコア | 48.36 |
| スコア幅 | 15pt |
| high 閾値 | **75** |
| low 上限（lowThr） | **60** |
| 結果（7日間） | **100% 'low'** (72/72) |

**診断**:
- `highThr = 75` はスコア最大値 70 を上回る → **達成不可能**
- `lowThr = max(30, 75-15) = 60` は観測スコア最大値 57 を上回る
- すべてのスコアが 60 未満 → **すべてが 'low' 分類**

---

### 🔴 重大: 住之江 (12)

| 項目 | 値 |
|------|-----|

| 平均スコア | 45.47 |
| スコア幅 | 9pt |
| high 閾値 | 70 |
| low 上限（lowThr） | 55 |
| 結果（7日間） | **100% 'low'** (72/72) |

**診断**:
- スコア範囲 42-51 がすべて `lowThr = 55` を下回る
- 「medium」「high」のスコアが物理的に存在しない

## 問題の種類と影響

### 問題 A: スコア上限の達成不可（多摩川）

| 症状 | 原因 | 影響 |
|------|------|------|
| high 閾値 75 の達成不可 | スコア最大 70 < 75 | 「崩れやすい」ラベルが発生しない |
| low 上限 60 は観測最大値を上回る | スコア最大 57 < 60 | すべてが 'low' 分類 |

### 問題 B: スコア分布が狭すぎる（住之江、宮島）

| 症状 | 原因 | 影響 |
|------|------|------|
| スコア幅が9pt以下 | スコア計算の結果的な限定性 | 閾値調整の余地なし |
| 「本命有利」のみが表示される | low 上限が観測最大値を上回る | 差分化できない |

### 問題 C: 閾値の過度な保守性

| 会場 | 理由（コメント） | 実績 | 改善提案 |
|------|----------|------|---------|
| 多摩川 | (実績ベース) | 100% low | 閾値 60 へ下げる |
| 住之江 | (実績ベース) | 100% low | 閾値 55 へ下げる |
| 宮島 | (実績ベース) | 91.7% low | 閾値 50 へ下げる |

## 改善提案

### 案 1: 全会場で統一スコア範囲を使用（推奨 ⭐）

**方針**: スコア計算を **0-100 に拡張** し、現在の閾値設定を維持

**変更対象**: `scripts/daily/generate-predictions.js:170`

```javascript
// 現在
const finalScore = Math.min(100, Math.max(0, Math.round(30 + composite * 40)));

// 改善後
const finalScore = Math.min(100, Math.max(0, Math.round(composite * 100)));
```

**メリット**:
- ✅ スコア本来の範囲（0-100）を活用
- ✅ 閾値設定を一切変更しない（既存設定の安全性を保証）
- ✅ 実装が最小限（1行変更）
- ✅ 新しいスコア分布下での 'low'/'medium'/'high' の最適性を再検証後、段階的に採用可能

**デメリット**:
- ❌ スコア分布が大きく変わる → 過去データとの比較困難
- ❌ 既存の閾値が「新スコア」での最適性を保証しない（再検証必須）

**実施手順**:
1. スコア計算を変更
2. 今後7日分のデータで新スコア分布を観測
3. 新分布下での 'low'/'medium'/'high' 比率を確認
4. 必要に応じて閾値を微調整

---

### 案 2: 各会場の閾値を低く調整（代替案）

**方針**: スコア計算は 30-70 のまま、会場別閾値を **観測スコア分布に合わせて下げる**

**変更対象**: `scripts/lib/venueParameters.js:19-44`

**調整案**:

```javascript
export const VENUE_VOLATILITY_THRESHOLD = {
  // 現在 → 改善後
  "05": 60,  // 多摩川: 75 → 60（観測最大57に合わせ）
  "12": 55,  // 住之江: 70 → 55（観測最大51に合わせ）
  "17": 50,  // 宮島: 65 → 50（スコア分布9ptに対応）
  "02": 50,  // 戸田: 55 → 50（スコア分布9ptに対応）
  // 他は現状維持
};
```

**メリット**:
- ✅ スコア計算は変更しない（過去データとの互換性保証）
- ✅ 短期で対応可能
- ✅ 段階的に検証しながら調整可能

**デメリット**:
- ❌ 閾値が低くなりすぎる可能性（例: 60 → 50 へ下げたことで「本命有利」が増加し過ぎる）
- ❌ 根本的なスコア設計の矛盾を残す（30-70 制限のままでは、今後も同じ問題が繰り返される）

---

## 推奨方針

**案 1（スコア 0-100 拡張）を採用し、段階的に進める**

**理由**:
1. スコア計算の根本的な矛盾を解消
2. 0-100 は業界標準スコア範囲
3. 実装が最小限（1行変更）
4. 既存閾値の「実績ベース」設定を活かしながら、新スコア分布での最適性を再検証できる

**段階計画**:

### Phase 1（今週）: スコア計算を変更

```javascript
// scripts/daily/generate-predictions.js:170
const finalScore = Math.min(100, Math.max(0, Math.round(composite * 100)));
```

### Phase 2（1週間観測）: 新分布を確認

実行コマンド:
```bash

```

必要に応じて VENUE_VOLATILITY_THRESHOLD を微調整。調整基準:
- **目標 low 比率**: 30-40% 程度（現在 70-100%）
- **目標 medium 比率**: 50-60% 程度（現在 0-30%）
- **目標 high 比率**: 5-10% 程度（現在 0-5%）

## FAQ

**Q1: 30-70 に制限した理由は何か？**

A: コメント「分析で観測した30〜70%レンジに線形変換」より、過去分析で観測された実績値レンジへの正規化と思われます。ただし、会場別の閾値（45-75）はその後に実績ベースで追加されたため、スコア範囲と閾値の間に矛盾が生まれました。

**Q2: 案 2（閾値下げ）ではだめか？**

A: 短期対応としてはあり。しかし、根本的にはスコア 30-70 制限が不要な制約となっており、いずれ 0-100 への拡張が必要になります。その時点で再度調整することになるため、今から 0-100 へ移行する方が総合的には効率的です。

**Q3: スコア計算を変更したら、過去データとの比較ができなくなるのではないか？**

A: その通りです。ただし、現在の 30-70 スコアは業界標準ではなく、かつ多くの会場で実用的でない分類になっています（100% low など）。1週間データが新スコア分布に移行すれば、その後の相対比較は可能です。必要に応じて過去データの再計算も検討してください。
