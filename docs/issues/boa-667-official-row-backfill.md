# BOA-667 公式の行の順（official_row）の過去分を埋める手順

`race_start_timings.official_row`（公式の結果ページの着順表の上からの行の順、マイグレーション119）は、結果の取得で 2026-10-03 から入っている。それより前の行はほぼ NULL のまま（2026-10-04 の実測で 283,920行中 281,724行）。画面は値が無いと艇番順に並べるため、着順の無い艇の並びが公式と違って見える。

過去分は2段階で埋める。本番の実行はユーザーが行う。

| 段階 | 対象 | やり方 | 公式への取得 |
|---|---|---|---|
| A | DB の着・着欄から導けるレース（45,129レース・270,774行） | SQL（月ごとに11回） | なし |
| B | 導けないレース（約1,825レース） | 結果ページを取り直す CLI | あり（JST 0〜6時） |

**A を先、B を後に実行する。** B の CLI は「official_row が NULL の行」を対象にするので、A の前に実行すると全レース（約4.7万）を取りに行く。CLI は対象が3,000レースを超えると止まる。

## 導出の規則と根拠（A）

- 完走した艇（`finish_rank` あり）を着の昇順に並べる。同着は艇番の昇順。その後に、完走しなかった艇を艇番の昇順に並べる
- 対象は、完走しなかった艇の記号（F・欠・転 など）が1種類以下のレースだけ。公式の着順表は記号の種類ごとに並ぶ（例: ＿→F、転→欠）が、種類の間の順はまだ全部を確かめられていない。そのため、2種類以上のレースは B に回す
- 着欄が NULL の艇（失格 S0〜S2 で、K から記号が決まらなかった艇）がいるレースも B に回す
- 既に official_row がある艇が1艇でもいるレースは対象外（取得時に書かれた値を上書きしない）
- **照合**: 2026-10-04 時点で本番に official_row がある368レースのうち、規則の対象になるのは363レース・2,178行。値を消してから A の SQL で埋め直すと、本番の値と全件一致した（PGlite で照合）。一致した中には、同着19レースと、同じ記号の非完走が2艇以上の39レースを含む

## 手順 A（SQL、月ごとに11回）

ファイル: [`boa-667-official-row-backfill.sql`](./boa-667-official-row-backfill.sql)。月ごとに「dry-run の SELECT」と「本体（BEGIN〜COMMIT）」が並んでいる。

1. **開始時刻を控える**（戻すときに使う）: `SELECT now();`
2. **事前確認**（読み取りのみ）:
   ```sql
   SELECT tgname FROM pg_trigger WHERE tgrelid = 'public.race_start_timings'::regclass AND NOT tgisinternal;
   ```
   → 0行（あれば実行せず連絡する）
3. 月ごとに、dry-run の SELECT を実行する。`races` と `rows` が上の表の A の列と合えば、その月の本体を実行する（「UPDATE <rows>」）
4. 月の間は数分あける（約2.5〜3万行ずつの UPDATE。Disk IO のため）。開催中に実行してもよい（公式への取得は無い）
5. **事後確認**（全月の後）:
   ```sql
   SELECT substr(race_id,1,7) AS m,
          count(*) FILTER (WHERE official_row IS NULL) AS null_rows,
          count(DISTINCT race_id) FILTER (WHERE official_row IS NULL) AS null_races
   FROM race_start_timings
   WHERE race_id >= '2025-12-01' AND race_id < '2026-10-03'
   GROUP BY 1 ORDER BY 1;
   ```
   → `null_races` は、上の表の B の列とほぼ同じになる（計約1,825）
6. もう一度 dry-run の SELECT を実行すると、どの月も 0件になる

## 手順 B（結果ページの取り直し、JST 0〜6時）

A の後に、ユーザーの端末で実行する。CLI は `scripts/maintenance/backfill-disqualified-finish-marks.js`（BOA-582 の失格の着欄と同じ1回の取得で、行の順も書く）。

1. **計画**（DB は読むだけ。公式へ1レース1リクエスト、3秒以上の間隔、429・503 で即中止）:
   ```bash
   node --env-file=.env.local scripts/maintenance/backfill-disqualified-finish-marks.js --out=boa667-plan.json
   ```
   - 既定の期間は 2025-12-01〜2026-10-02
   - JST 6時以降は実行を拒否する。中止したら、翌日の0時以降に同じコマンドを実行すると、残りだけを取る（対象は都度 DB から導く）
   - 約1,825レースで、1.6〜2.5時間かかる
   - 出力の「書く行 着欄 N・行の順 M（--confirm=N+M）」と「異常」の件数を控える。異常（着順表に無い艇、記号が失格と合わない艇）は書かれない
2. **書き込み**（取得はしない。1行ずつ update し、NULL の列だけを書く）:
   ```bash
   node --env-file=.env.local scripts/maintenance/backfill-disqualified-finish-marks.js --apply --plan=boa667-plan.json --confirm=<N+M>
   ```
   → 「書いた行 <N+M に近い>・書かなかった行 <少数>」。書かなかった行は、計画の後に値が入った行、または行が無い艇
3. **事後確認**: 手順 A の5の SELECT を実行する → `null_races` がほぼ0になる。残りは計画の「異常」の件数と一致する

## 戻し方

A・B の書き込みは、どちらも official_row（と B の着欄）を NULL から値にするだけで、既存の値を上書きしない。戻すときは、手順 A の1で控えた開始時刻以降に書いた行を NULL に戻す（A・B の両方が戻る）。

```sql
BEGIN;
UPDATE race_start_timings
SET official_row = NULL
WHERE race_id >= '2025-12-01' AND race_id < '2026-10-03'
  AND official_row IS NOT NULL
  AND updated_at >= '<手順Aの1で控えた時刻>';
COMMIT;
```

B で書いた着欄（finish_mark）も戻す場合は、同じ条件で `finish_mark = NULL` にする。ただし、対象は `official_finish_code ~ '^S'` の行に限る（それ以外の着欄は項目7で書いた値）。

注意: 開始時刻以降に、別の処理（結果の修正の取り直し等）で書かれた行も戻る。戻した後は、手順 A から実行し直せば同じ値になる。
