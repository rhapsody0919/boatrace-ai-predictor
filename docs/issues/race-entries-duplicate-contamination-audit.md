# 出走表（race_entries）の複製汚染 — 全期間監査と日次自動検知（BOA-422・BOA-423）

## 1. 結論

- BOA-414（PR #823）が「新規発見・3会場日」として起票した race_entries の複製汚染は、**全期間（2025-12-02〜2026-09-25）で22会場日・219レース**に及ぶ。既知の3会場日は、その一部にすぎない
- 最大のかたまりは**2026-01-09の9会場（108レース）**で、既知のどのチケットにも入っていなかった。前日2026-01-08の出走表が、9会場の全12レースにわたってそのまま書かれている
- 汚染された日は `race_results` が正常に入っているため、**欠損ベースの抽出（BOA-403・BOA-406・BOA-407 が使った方法）では原理的に発見できない**
- 日次の自動検知を、DBだけで完結する形で `data_health` に追加した（`entries.duplicates`、マイグレーション100）。この検知は、下の公式K/Bファイルとの突き合わせで確定した22会場日を、**取りこぼし0・誤検知0**で拾う

## 2. 調査方法

2つの独立した方法で突き合わせ、両者が一致することを確かめた。

| 方法 | 根拠 | 長所 | 短所 |
|---|---|---|---|
| (A) 公式K/Bファイルとの突き合わせ | 一次情報（Bファイル＝番組表の「艇番→登録番号」） | 汚染の**確定**ができる | K/Bアーカイブが要る（Vercel上では動かせない） |
| (B) DB内の自己参照（同一会場・同一レース番号で、直近21日以内の別日と完全一致） | DBのみ | 日次で自動実行できる | 一致が正常な場合（順延・偶然）を除外する必要がある |

(A) は `scripts/maintenance/audit-race-entries-vs-kb.js`（本PRで追加。読み取りのみ）。
(B) は `data_health_entries_duplicates`（マイグレーション100）。

### 3.1 汚染はレース単位で、必ず先頭から連続する

部分的にしか汚染されていない会場日（蒲郡 04-11 の4レース等）を調べると、汚染されたレースは**必ず R1 から連続**していた（例: 大村 04-11 は R1〜R5、常滑 04-25 は R1〜R9）。

朝の取得が始まった時点ではまだ前日の内容が返り、途中から当日の内容に切り替わった、という経過と整合する。`update-race-info.js` は取得した出走表が「その `race_id` にふさわしいか」を検証しないため（BOA-414 §4.3）、切り替わる前に取れた分がそのまま書かれる。

### 3.2 2026-04-09 が繰り返し複製元になっている

2026-04-11・04-24・04-25 の複製元は**すべて 2026-04-09**（04-24 は15日前）。BOA-414 が唐津について「散発的に3回」と書いた現象は、会場をまたいで起きていた。同じ日のデータが2週間以上あとの取得で再び現れており、取得側のキャッシュが疑わしいが、当時のHTTP応答は再現できないため特定はできていない。

### 3.3 結果（race_results）は正常

汚染された22会場日はいずれも `race_results` が12/12そろっており、着順は実際のレースのものが入っている。したがって、**的中率の集計・レース分析・選手成績は、この219レースについて「実際とは違う選手同士の対戦」として扱われている**。復旧（BOA-422）は `race_entries` 側の差し替えになる。

## 4. 日次自動検知（方法B、BOA-423）

Vercel上の `data_health`（完了の定義C）は、DBの関数しか呼べず、K/Bアーカイブを読めない。そこで、DBだけで同じ汚染を拾う判定を設計した。

**判定**: 同一会場・同一レース番号で、直近21日以内の別の日と「艇番→登録番号」が完全一致するレースが、**同じ会場×日に2つ以上**あれば、その会場×日を汚染の疑いとする。

**除外（いずれも、正常なのに一致するケース）**:

| 除外 | 理由 |
|---|---|
| 確定中止（`cancellation_status = 'confirmed'`）のレースを、複製元・複製先の両方から外す | 順延は、前日の出走表がそのまま翌日の同じ節で使われるため、正常に完全一致する（BOA-414 カテゴリB） |
| 結果（`race_results`）の無いレースを、複製元・複製先の両方から外す | 未確定の順延スタブ（BOA-421 の古い7件）が、確定中止として印されないまま残っているため |
| 1レースだけの一致は数えない | 同じ節の別の日に、同じ6人が同じ枠で再び組まれることが実際にある。**2026-01-22 常滑 R6 が実例**で、公式Bファイルでも両日の一致が正しい。汚染は必ず複数レースにまたがる（最小でも4レース） |

**実測（2025-12-02〜2026-09-25）**: この判定が拾う会場×日は、方法Aが確定した22会場日と**完全に一致**した（取りこぼし0・誤検知0）。3つの除外をすべて外すと59会場日が挙がり、うち37件は順延・偶然の一致（誤検知）になる。

**実装**:

- SQLの正本: `scripts/lib/dataHealth/functions.js` の `data_health_entries_duplicates`
- 登録: `scripts/lib/dataHealth/checks.js` の `entries.duplicates`（閾値100%・`severity: alert`・`lagDays: 1`）
- DDL: `docs/db-migration/100_data_health_entries_duplicates.sql`（**本番未適用**。適用はユーザー承認後）
- 通知: 既存の `scrape-monitor` 経由でSlackへ（`data_health` の `alerts`）。`data_health` のモードが `live` になって初めて通知が出る（2026-09-25時点は `shadow`）
