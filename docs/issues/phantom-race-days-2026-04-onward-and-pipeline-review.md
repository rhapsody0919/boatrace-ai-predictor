# 「幻の開催日」パターンの範囲拡大確認と現行パイプラインでの再現性調査（BOA-414）

調査日: 2026-09-25。読み取り専用調査（本番DBへの書き込みは無し）。K/Bアーカイブへの新規アクセスは、既存アーカイブに無かった2026-09-21〜23の3日分（K/B計6リクエスト、夜間窓外のため`--window=any`で明示許可）のみ行った。BOA-407（[`venue-not-in-k-phantom-race-days.md`](./venue-not-in-k-phantom-race-days.md)、PR #818）の残課題（同doc §6.3）を引き継ぐ。

## 1. 結論

- **(1) 2026-04-01以降にも同じ「幻の開催日」パターンが見つかった。ただし1回・4会場日のみ（2026-04-11、戸田・常滑・三国・児島）**。BOA-407の対象期間（〜2026-03-31）の直後、スクレイピングオーケストレーター実装（PR #49、2026-04-11デプロイ）の当日に発生しており、それ以降2026-09-25まで（K-fileで確認できる範囲）**同型の再発は無い**。
- **加えて、BOA-407とは別方向の関連バグを2件（3会場日）新たに発見した**: 開催が実在した日（K-fileにも本番`race_results`にも実データがある）にもかかわらず、`race_entries`（出走表の艇番⇔選手の対応）だけが**別の日（最大15日前）のデータとそっくり同じ値で保存されていた**（びわこ2026-04-11、唐津2026-04-11・04-24）。これはBOA-407が定義した「幻の開催日」（開催そのものが存在しない）とは異なり、**実開催日のrace_entriesが汚染される**、より影響が大きい派生パターンである。本チケットの範囲（BOA-407と同一方向の事象の確認）を超えるため、詳細はBOA-407スコープ外の新規発見として別途フォローアップを提案する（§6）。
- **(2) 現行パイプラインでの再現性**: BOA-407の対象期間に動いていた当時のコード（`scripts/scrape-to-json.js`のJan2026版、`getTodayVenues()`が`hd=`無しで`race/index`を取得）は、[`races-opening-day-missing.md`](./races-opening-day-missing.md)が特定した「日付ロールオーバー未検知」バグと**同じ関数**を使っていた。2026-04-11の再発は、このバグが2026-09-12（PR #625、`hd=`明示指定）まで温存されていたことと整合する。**現行コード（2026-09-21時点）は`hd=`指定に加え、会場を丸ごと失敗にする新しいガード（発走時刻が1件も取れなければ書かない）を持ち、BOA-407と同型の「開催終了後の会場に出走表を複製する」経路は塞がれている**と判断する。ただし、上記で新たに見つけた「実開催日のrace_entriesが別日のデータで汚染される」経路（§4.3）は、現行コードでも構造的に防げていない（未検証・未確認のリスクとして残る）。
- **(3) [`races-opening-day-missing.md`](./races-opening-day-missing.md)の再発防止策は、本事象を狙って作られたものではなく、直接カバーしない**。ただし副産物として、そのうち1項目（`hd=`明示指定）が本事象の主因も断っている（§5）。

## 2. 調査方法

### 2.1 「範囲拡大確認」（やること1）: DB内の自己参照突き合わせ + K-fileでの裏取り

BOA-407の抽出方法（`race_results`欠損 → K-fileで`venue_not_in_k`と分類 → 過去14日以内の自社DBと72値一致）は、`race_results`が欠損している会場日からしか始められないため、2026-04-01以降（`race_results`がほぼ欠損なく埋まっている）には使えない（チケット記載のとおり）。

そこで、`race_results`の有無に依存しない別の抽出方法を使った。`races`と`race_entries`から、会場×日ごとに「レース番号×艇番→racer_id」の72値グリッド（12レース×6艇）を作り、**同一会場内で、過去14日以内の別の日と72値が完全一致する組**を、`races`テーブル全件（2025-12-03〜2026-09-25、46,536レース、range_entries 279,216行）に対してSQLで自己結合した。**サンプリングはしていない。データ量が全期間で本番Supabaseの読み取り専用SQL1回で完結する規模だったため、2026-04-01〜2026-09-25の全期間を対象にした**。

```sql
WITH fp AS (
  SELECT r.venue_code, r.race_date,
         array_agg(e.racer_id ORDER BY r.race_number, e.boat_number) AS grid,
         count(*) AS n
  FROM races r JOIN race_entries e ON e.race_id = r.race_id
  WHERE r.race_date >= '2026-04-01'
  GROUP BY r.venue_code, r.race_date
  HAVING count(*) = 72   -- 12レース×6艇が揃っている会場日のみ
)
SELECT a.venue_code, a.race_date AS day, b.race_date AS matched_day,
       (a.race_date - b.race_date) AS days_diff
FROM fp a
JOIN fp b ON a.venue_code = b.venue_code
  AND b.race_date < a.race_date
  AND a.race_date - b.race_date <= 14
WHERE a.grid = b.grid
ORDER BY a.race_date, a.venue_code;
```

境界チェックとして、`fp`の集計開始日を2026-03-18（14日分のバッファ）まで広げ、`day`側だけ2026-04-01〜04-14に絞った再実行も行い、結果が変わらないことを確認した（3月末のデータを起点に4月頭で発覚するケースの見落としが無いことの確認）。

この方法は「12レース×6艇=72値の完全一致は偶然では起こらない」という前提（[`venue-not-in-k-phantom-race-days.md`](./venue-not-in-k-phantom-race-days.md) §3と同じ）に立つ。ヒットした全件について、K-fileと突き合わせて「本当に複製か」「複製の方向（どちらが本物でどちらが偽物か）」を個別に確認した。K-fileアーカイブ（`data/kb-archive/parsed/`、[`venue-not-in-k-phantom-race-days.md`](./venue-not-in-k-phantom-race-days.md)と同じ中間形式）は2026-09-20までパース済みのものが既存だったため、9月分のヒット（2026-09-21〜23）だけ新規にK/Bをダウンロード・パースした（新規の公式サイトアクセス6件、逐次3秒以上間隔、403/429/503は0回）。

## 4. 現行パイプラインでの再現性確認

### 4.1 BOA-407期間（2025-12-03〜2026-03-31）に動いていたコード

`morning-init.js`（GitHub Actions、5分毎起動・1日1回のみ実処理）が`scripts/scrape-to-json.js`をexecSyncで呼び出し、その中の`getTodayVenues()`が**`hd=`無しで`https://www.boatrace.jp/owpc/pc/race/index`を取得**して当日開催会場を決めていた。これは[`races-opening-day-missing.md`](./races-opening-day-missing.md) §3が特定した「日付ロールオーバー未検知」バグと**全く同じ関数・同じ欠陥**である。同docは主に「開催会場の**取りこぼし**（当日開催なのに前日の一覧が返る）」を扱っているが、逆方向——**前日まで開催していた会場が、ロールオーバー未完了のため『まだ今日も開催中』の一覧に残ってしまう**——も理論上あり得る同根の欠陥である。

さらに当時の`getRacelist(date, placeCd, raceNo)`は、`racers.length > 0`であれば（実際に艇番×選手のテーブルが1件でも取れれば）その内容をそのまま採用し、**「その内容が本当に指定した`hd=`の日のものか」を検証していない**。公式サイトの`racelist`ページが、存在しない`hd=`（開催が無い日）に対して、直前の実開催日のキャッシュ・直近データを誤って返す挙動があった場合（本調査では過去のHTTPレスポンスを再現できないため未確認・推測）、この2つの欠陥が組み合わさって「終了済み会場が一覧に残る→その会場の`hd=`指定racelistが直前の実データを返す→そのまま複製として保存される」という、BOA-407・本調査カテゴリAで観測された挙動を説明できる。

### 4.2 2026-04-11以降の変化と、カテゴリAが以後発生していない理由

2026-04-11の再発は、[`スクレイピングオーケストレーター実装（PR #49、BOA-39）`](https://github.com/rhapsody0919/boatrace-ai-predictor/pull/49)が**同日にデプロイ**されたことと時期が一致する。ただしPR #49は日中のリアルタイム更新系（`update-race-info.js`・`scrape-odds.js`等）の統合が主目的で、`scrape-to-json.js`の`getTodayVenues()`・`getRacelist()`自体は変更していない。**したがって2026-04-11時点でも、根本の欠陥（`hd=`無し・出走表の妥当性検証なし）はまだ残っていた**とみられる。

その後の変化点は2つ:

1. **2026-09-12（PR #625）**: `getTodayVenues(date)`が`hd=`を明示指定するようになった。コードコメントに「`hd=`は日付ごとに正しく異なる開催会場一覧を返すことを実地検証済み」とあり、これが事実なら、**開催が終わった会場は、その日の`hd=`指定一覧に含まれなくなる**——カテゴリAの起点（終了済み会場の誤選定）を断つ。現行の`api/cron/races-init.js`（`scripts/lib/racesInit/job.js`）は、この`getTodayVenues`・`scrapeVenue`を`scripts/scrape-to-json.js`から**そのままimportして使っている**ため、この修正の恩恵を継承している。
2. **2026-09-21（PR #762、WS4b T4b-07-1〜3）**: `scrapeVenue()`に「発走時刻が1件も取れない場合、会場全体を失敗として扱う」という新しいオール・オア・ナッシングのガードが入った。仮に`hd=`の会場選定を何らかの理由（手動の`?venues=`指定・将来のバグ）ですり抜けても、開催が無い日は発走時刻が取れないはずなので、このガードが第二の防波堤になる。

以上から、**カテゴリAと同型の「開催終了後の会場に出走表を複製する」経路は、現行コード（2026-09-21時点）では二重に塞がれていると判断する**（`hd=`による正しい会場選定＋発走時刻ゼロ件でのオール・オア・ナッシング失敗）。ただし、これは公式サイトの応答が「開催の無い`hd=`には正常にエラー・空ページを返す」という前提に依存しており、この前提自体を本調査では実地検証していない（過去日への再現テストが不可能なため）。

### 4.3 カテゴリC（実開催日の汚染）は、現行コードでも未解決

カテゴリCの本質は「会場選定は正しかった（実際に開催があった）のに、**個別のレースのracelistページが、たまたま別の日の内容を返した**」という失敗モードであり、上記の2つの対策はどちらも効かない:

- `hd=`による会場選定の正しさ（対策1）は無関係（会場自体は正しく選ばれている）
- 発走時刻ゼロ件のガード（対策2）も無関係（実際に発走時刻はある。取れているのは「間違った日の出走表」であって「出走表が取れないこと」ではない）

現行の`scripts/daily/update-race-info.js`の`runForRaces`・`fetchRaceInfoDetailed`、および`scripts/lib/racesInit/job.js`経由の初回取得のいずれも、**取得した出走表の中身が「その`race_id`にふさわしいものか」を裏付ける仕組みを持たない**（例: 前回取得時と全く同じ72値になっていないか、選手の年齢・出走間隔などから明らかに矛盾がないか、といった妥当性チェックは無い）。`detail.status === "ok"`（艇番×選手が1件でも取れた）であれば、その内容をそのまま`race_entries`に書き込む点は、BOA-407当時のコードと構造的に同じである。

**したがって、カテゴリCと同型の障害（実開催日のrace_entriesが別日のデータで汚染される）は、現行コードでも理論上再現しうる**。ただし、2026-04-11以降（K-fileで確認できた2026-09-23まで）に同型の事例は見つかっておらず、頻度は低い（唐津の3件のみ、いずれも2026-04中）。

## 5. `races-opening-day-missing.md`の再発防止策のカバレッジ

[`races-opening-day-missing.md`](./races-opening-day-missing.md) §6.4の5項目は、いずれも「会場の**取りこぼし**（開催があるのに`races`に1行も無い）」を検知・防止するために作られたものであり、本事象（幻の開催日＝**逆方向**、開催が無いのに行ができる）を狙って設計されたものではない。

| # | 対策 | 本事象（幻の開催日）へのカバー |
|---|---|---|
| 1. `getTodayVenues(date)`への`hd=`明示指定 | **副次的にカバーする**。開催終了会場を`hd=`指定の一覧から正しく除外できるなら、カテゴリAの起点を断つ（§4.2）。ただし取りこぼし対策として作られたもので、幻の開催日を検知する目的の実装ではない |
| 2. 9時前の`ensureAllVenuesScraped`（開催会場とracesの差分再取得） | **無関係**。取りこぼした会場を追加する処理であり、誤って追加された幻の会場日を除去する処理ではない。誤って害を及ぼす向きの相互作用も無い（`hd=`指定の一覧に基づくため、存在しない会場を追加することは無い） |
| 3. Vercel移行後の`races-init`が`hd=`・会場差分チェックを継承 | 1と同じ理由で**副次的にカバー** |
| 4. 月間スケジュール由来の初日充足チェック（未実装） | **無関係**（充足＝存在するはずの日が無いことの検知であり、存在しないはずの日があることの検知ではない） |
| 5. 完了の定義C（08:00に当日racesが0件を検知） | **無関係**（同上、方向が逆） |

**結論**: 5項目のうち直接的に「幻の開催日を検知する」ものは無い。1件（`hd=`明示指定）が結果的にカテゴリAの主因を塞いでいるに過ぎず、**「開催が無いのに`races`に行ができていないか」を積極的に検知する仕組み（ディテクティブコントロール）は存在しない**。取りこぼし側には（未実装だが）月間スケジュール突き合わせという検知の仕組みが設計されているのに対し、幻の開催日側には同等の検知手段が無いという非対称性がある。
