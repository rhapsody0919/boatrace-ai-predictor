# ADR 0087: 思考アシストの類似レースの割合は、龍神ソナーと同じ「今日に近い順の上位400件」で数える

## ステータス
提案中（ユーザーの判断待ち。spec D-34 の「層の全件」を置き換える）

## 背景
思考アシストは、類似レースの割合を5か所で出す。
- 「このレースは堅い？荒れる？」（1号艇の1着・万舟）
- 買い目レンズの万舟
- よく出た3連単
- 組ごとの件数
- 展開レンズの決まり手

spec D-34 で「類似レースの件数は層の全件」に決まった。ただしこの推奨は、層が63件の例のレース（徳山10R・準優勝戦）だけを見て出したもので、数え方の価値は比べていなかった。

ユーザーの指示（2026-10-07）は「ファンにとって何が価値が高いかから決める。要るなら API の修正・新規開発もする」。そこで実装の都合を伏せて、ファン4人（discussion-panel、設計に関わっていないサブエージェント）に価値から議論させた。

### 材料にした実データ（本番 API、2026-10-07 のレース）
層（条件がそろう全レース）の大きさはレースで大きく違う。36レース中31レースで2,000件を超え、最大は58,326件だった。800件以下は準優勝戦・優勝戦の2レースだけだった。

数え方を変えると、値は数ポイント動く。

| レース（層の件数） | 今日に近い順 上位100 | 上位400 | 上位800 | 新しい順2,000件 |
|---|---|---|---|---|
| 1号艇A1・勝率トップ1号艇（58,326） | 1号艇の1着 75.0%・万舟 15.0% | 82.0%・11.5% | 82.5%・12.0% | 76.0%・12.7%（直近3か月） |
| 1号艇B1・勝率トップ2号艇（9,902） | 33.0%・10.0% | 41.8%・12.5% | 42.2%・16.8% | 39.4%・15.2%（2025/5〜） |
| 1号艇A2・勝率トップ4号艇（5,674） | 52.0%・13.0% | 51.8%・14.0% | 53.1%・14.9% | 50.3%・15.8%（2023/11〜） |

## 価値の結論（ファンパネル。ロールプレイの仮説）
- 5か所すべてで、龍神ソナーと同じ「今日に近い順の上位400件」に統一する。理由は次の3つ
  - 同じ呼び名「類似レース」なのに、龍神ソナーと値が違うと、どちらを信じればいいか分からない（20代女）
  - 締切前に見る数字は1種類でよい（30代女）
  - 会場・モーター・ST まで近いレースの方が、堅い？荒れる？・決まり手の判断に効く
- 層の全件数は割合には使わない。説明の中で母集団の大きさとして書く（「条件が合う58,326件から今日に近い順に400件」）。件数が多いことの安心感（30代男）には、これで応える
- よく出た3連単は、400件だと3位以下が薄くなる（30代男）。上位3組に件数を添えて見せる（「1-2-3　41件」）。30代男も、件数が出るなら許容した
- 新しい順（最近の傾向）は採らない。期間がレースごとに3か月〜3年とばらつき、「最近」の意味が一定しない
- 層が400件以下（準優勝戦・優勝戦など）のときは全件を使い、「条件が合う全件」と書く

パネルの限界: 層が大きいレースの「層の全件」の割合は材料に無かった（今の API で取れないため）。ただし結論の理由は、ソナーとの一致・1種類の数字・近さで、層の全件の値の大小には依らない。

## 決定（推奨）
- similar API の `neighbors` の先頭 min(400, `n_layer`) 件を `aggregateNeighbors` で数える
- 万舟は `payout_3tan >= 10000` を数える小さな関数を `analogyAggregate.js` に足す
- 画面の書き方:
  - 層が大きいとき: 「今日に近い類似レース400件」
  - 層が400件以下のとき: 「類似レース{n}件（条件が合う全件）」
  - 用語の「?」: 「条件が合う{n_layer}件から今日に近い順に400件。龍神ソナーの類似レースと同じ」
- 龍神ソナーのスライダー（件数を変える操作）は思考アシストに置かない。ソナーで選んだ件数との連動もしない（ソナーの件数はページの中だけの状態で、保存していない）。件数は既定の400件で固定する
- API・バッチ・DB の変更は要らない

## 却下した選択肢
- **(A) 層の全件（v16 の朝のバッチで層の集計を出す）**
  - 実装は小さい。`v16_morning.py` には、比べる相手の層を全件で数える `outcome_counts` が既にある。今日の層 `lm` にも呼び、万舟（`payout_3tan`）と3連単の件数を足して `similar-racecard` に書けばよい。similar API は出走表の段のファイルをそのまま返すので、API の変更は要らない。1レースあたりの計算は配列の集計で数ミリ秒で、朝のバッチ（約10分、目標20分）への影響は小さい。Storage は1レースあたり数KB増える
  - それでも採らない理由は価値の側にある。同じ呼び名で龍神ソナー（上位400件）と値が違い、ファンが迷う
  - もし採るなら、変えるのは BOA-271 の実装レーン（「BOA-271 v16 の実装（/step4）を始める」）が持つ `v16_morning.py` になる。段取りは次のとおり
    1. そのレーンにオーケストレーター経由で依頼する
    2. ADR 0085 の出力形式に追記する
    3. 朝のバッチの出力が変わった後で、思考アシストが読む
- **(B) 新しい順の2,000件（layer API）**: 期間がレースごとにばらつき、「最近」の意味が一定しない
- **(D) 層の全件と上位400件を並べる**: 数字が2種類になり、締切前に読めない

## 影響
- 用語の「?」の「龍神ソナーの類似レースと同じ」（D-20）が、そのまま成り立つ
- 例のレース（層63件）は D-34 のときと同じ値（63件、1号艇の1着 34件、万舟 11件）
- spec D-34 の「類似レースの件数は層の全件」は、採用されたらこの ADR の内容に書き直す
