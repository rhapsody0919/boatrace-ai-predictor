# ADR 0025: 選手ニュース自動収集の処理済み判定は新規テーブルを作らない

## ステータス
採用

## 背景
[[racer-news-auto-collect]]は毎日GitHub Actionsで実行されるため、同じレース・同じ記事・同じ選手コメントを二重に処理しない冪等性が必要になる。一般的には「処理済みID」を記録する専用テーブルやファイルを新設するが、このプロジェクトは複数セッションが同一リポジトリを並行編集しており（`.claude/CLAUDE.md`のGit安全策参照）、CIが頻繁に書き込むファイルを増やすほどコンフリクトリスクが上がる。

## 決定
新規の状態管理テーブル・ファイルは作らず、**既存のデータで冪等性を判定する**。
- 公開済みかどうかは`racer_news.source_url`の一意性チェックで判定する（各ソースのURLをFR単位で一意になるよう設計する。plan.md 1.2参照）
- 保留中かどうかは既存踏襲予定の`data/analysis/racer-news-pending-review/pending.json`（FR3で元々必要なファイル）に同一`sourceUrl`のpending項目が無いかで判定する

つまり「新規に増える永続化先」は元々FR3で必要だった`pending.json`1つだけであり、処理済み管理専用の状態は増やさない。

## 却下した選択肢
- **専用テーブル（例: `racer_news_processed_sources`）を新設**: 素直な設計だが、このためだけに新しいテーブル・RLSポリシー・マイグレーションが増える。YAGNI（`racer_news.source_url`で同じ目的を達成できる）
- **専用JSONファイル（例: `data/state/racer-news-seen.json`）で処理済みIDを記録**: CIが毎日書き込むファイルが1つ増える。`pending.json`と役割が重複し（「見た」と「保留中」の2つの状態ファイルを整合させる必要が出る）、複雑さが増すだけで得るものがない

## 影響
- 各ソースの`source_url`を設計する際、必ず「そのソースの中で一意になる値」にする責務が発生する（FR5はページURLが複数選手・複数節で使い回されるため、`#racerId-YYYYMMDD`のようなフラグメント付与が必須。plan.md 1.2参照）
- 将来的に「一度pendingでrejectされた候補を二度と再提示しない」等の要件が増えた場合、`pending.json`の`status`のみでは表現しきれない可能性がある。その際は本ADRを見直す
