# ADR 0101: 公式への取得の上限と止め方

## ステータス

提案（2026-10-26）。項目のうちオーナーに聞くもの（オッズの窓・体重の先出し・展示の取りに行く時刻）は、答えを受けてこの ADR に追記する。設計の正本は [docs/design/scraping-load-budget/spec.md](../design/scraping-load-budget/spec.md)。

関係する ADR: [ADR-0066](./0066-scraping-execution-consolidation-to-vercel.md)（取得の実行基盤を Vercel に一本化）、[ADR-0067](./0067-official-site-content-redisplay-policy.md)（公式サイトの再表示の方針と、取得負荷の抑制）、[ADR-0057](./0057-odds-capture-frequency-and-full-grid-scope.md)（オッズの6窓・全券種）、[ADR-0058](./0058-data-refresh-frequency-optimization-principle.md)（取得頻度の4つの問い）。

## 背景

- 2026-10-26 15:50 JST から、公式の直前情報（`www.boatrace.jp/owpc/pc/race/beforeinfo`）が当社の取得だけ HTTP 403 になった（BOA-1145）。直前情報は1日1,874回で、1つのページとして最も多く取っていた。ブレーカーは 429/503 だけを数え、403 の間も叩き続けた
- boatrace.jp への取得は合計約8,400件/日（10/19〜25 の実測）、うちオッズが約65%。ADR-0067 が求める「リクエスト間隔、並列度の上限、429/503 でのバックオフとサーキットブレーカー」のうち、boatrace.jp のリクエスト間隔は実装されていなかった。全体で何件取っているかを持つ仕組みも無かった
- GitHub Actions の予備（`scrape-scheduled`）と cron-job.org の展示の旧経路は、ブレーカーの無い素の fetch だった。画面のライブオッズ（`/api/odds/live`）に全体の上限が無かった。月次の選手の取得が Vercel と GitHub Actions で二重だった
- 応急の対応は #1945（朝の初期化が直前情報を取らない）・#1946（403 でパス単位のブレーカー、展示の回数を約60%減）。本 ADR はその後の恒久の決まり
- オーナーの決定（2026-10-26）: BOATRACE振興会には連絡しない。名乗り（User-Agent）・IP を変えて回り込むことはしない

## 決定

1. **相手（ホスト×パス）ごとに1日の予算を持ち、取得の数を数える**。予算の表は registry に置く（値は spec.md §4.2）。80%で知らせ、100%でその日は取らない。取り直せないデータ（オッズ・展示）も例外にしない（値が違えば PR で値を直す）。予算のうち根拠の無いものは「目安（根拠なし）」と書く
2. **1分の上限は、毎分起動するジョブの1起動の上限の和で抑える**。politeFetch はホストごとに要求の開始を200ms以上あけ、同時を6までにする。BOATCAST は今の2.2秒の間隔のまま
3. **403（boatrace.jp）は全パスで、パス単位に1回で開く**。同時に2パス以上が開いたらホスト全体を開く。開く時間は30分から倍にして6時間を上限とし、回数を DB に残す。429・503・500・502・504・タイムアウトの連続はホストを開き、Retry-After を尊重する（spec.md §5）。BOATCAST の 403 は今のまま（カナリアで判定）
4. **非常停止**: `scrape_job_state` の `host:<ホスト>` の行の mode を off にすると、そのホストへのすべての取得（Vercel・ライブ・GitHub Actions）が止まる
5. **守りを通らない取得の経路を持たない**。GitHub Actions の予備は、Vercel が起動していないときだけ、同じ politeFetch・ブレーカー・予算を通して肩代わりする（展示は肩代わりしない）。cron-job.org の展示の旧経路は消す。mode=off は「取らない」の意味にそろえる
6. **監視**: まず scrape_slots から相手ごとの回数を毎日出し、次に politeFetch が数えた表（`fetch_counts`）で、ライブ・日次・GitHub Actions を含めて数える。403 は即時に知らせる
7. **取得の頻度の変更は、ADR-0058 の4つの問いに加えて「公式の公開の時刻の実測」と「画面の閲覧の時刻（GA4）」で決める**。見せる時刻が遅くなる変更（窓を落とす・先出しをやめる等）はオーナーに聞く。遅れが0の変更（結果の最初の取得を締切+5分→+10分 等）は聞かずに進める
8. **止められたとき、値が無いことを「未発表」と見せない**。ブレーカーが開いているページの欄は「公式から取得できていません」と公式へのリンクを出し、展示前の予想はそう明記し、展示後の SNS は出さない（spec.md §9）
9. User-Agent は `BoatraceAIBot/1.0 (+https://github.com/rhapsody0919/boatrace-ai-predictor)` の1つにそろえる（中身は変えない）。robots.txt を1日1回読み、当社が取るパスが Disallow に入ったら、そのパスを止めて知らせる

## 却下した選択肢

- **ジョブごとの上限だけのまま**: 全体の数を誰も持たず、今回の 1,874回/日を止めなかった
- **すべての取得を1つの窓口で予約する（要求ごとに DB で枠を取る）**: 1分の上限を厳密に守れるが、要求ごとに DB の往復が入る。1分の実測の最大（43ページ、下限）が目安の60より下なので、今は要らない。実測で超え始めたら見直す
- **名乗り・IP を変える、別の場所から取る**: オーナーの決定で採らない。回り込みは拒否の意図に反する
- **取り直せないデータは予算を超えても取る**: 止めない例外があると、今回と同じく誰も止めない
- **GitHub Actions の予備をすぐ消す**: Vercel が止まったときの予備が無くなる。守りを通す形で30日残し、肩代わりが無ければ消す

## 影響

- ADR-0067 の「取得負荷の抑制」は、本 ADR の数字と仕組みで持つ。取得量を増やす変更は、spec に負荷の見積りを書くのに加えて、予算の表を更新する（予算を超える変更は表の変更の PR が要る）
- ADR-0066 の「監視を1系統に統一する」に、取得の回数を足す
- オッズの窓を落とす場合は ADR-0057 の変更になる（オーナーの答えの後に追記）
- 実装は spec.md §12 の順に PR を分ける。マイグレーション（`fetch_counts`、開いた回数）は system-architect を通す

## 見直しの契機

- 予算の80%・100%の通知が月に3回以上出たとき（値が実態に合っていない）
- 公式から 403 以外の形（通知・要請）で連絡を受けたとき（ADR-0067 の見直しの契機と同じ）
- 1分の実数（`fetch_counts`）が目安の60を超えたとき
