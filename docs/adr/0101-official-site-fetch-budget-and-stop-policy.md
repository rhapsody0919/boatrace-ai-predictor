# ADR 0101: 公式への取得の上限と止め方

## ステータス

提案（2026-10-26）。項目のうちオーナーに聞くもの（オッズの窓・体重の先出し・展示の取りに行く時刻）は、答えを受けてこの ADR に追記する。設計の正本は [docs/design/scraping-load-budget/spec.md](../design/scraping-load-budget/spec.md)、審査の指摘と対応は [review.md](../design/scraping-load-budget/review.md)。

関係する ADR: [ADR-0066](./0066-scraping-execution-consolidation-to-vercel.md)（取得の実行基盤を Vercel に一本化）、[ADR-0067](./0067-official-site-content-redisplay-policy.md)（公式サイトの再表示の方針と、取得負荷の抑制）、[ADR-0057](./0057-odds-capture-frequency-and-full-grid-scope.md)（オッズの6窓・全券種）、[ADR-0058](./0058-data-refresh-frequency-optimization-principle.md)（取得頻度の4つの問い）、[ADR-0069](./0069-query-error-propagation.md)（クエリの取得エラーを黙って既定値にしない。同じ考え方を予算の読み取りに使う）。

## 背景

- 2026-10-26 15:50 JST から、公式の直前情報（`www.boatrace.jp/owpc/pc/race/beforeinfo`）が当社の取得だけ HTTP 403 になった（BOA-1145）。直前情報は1日1,874回で、1つのページとして最も多く取っていた。ブレーカーは 429/503 だけを数え、403 の間も叩き続けた
- boatrace.jp への取得は合計約8,400件/日（10/19〜25 の実測）、うちオッズが約65%。ADR-0067 が求める「リクエスト間隔、並列度の上限、429/503 でのバックオフとサーキットブレーカー」のうち、boatrace.jp のリクエスト間隔は実装されていなかった。全体で何件取っているかを持つ仕組みも無かった
- 守りを通らない経路があった: GitHub Actions の予備（`scrape-scheduled`・`morning-init` の安全装置）は、403・接続の失敗の連続や mode≠live で、別の IP から素の fetch で肩代わりする。cron-job.org の展示の旧経路も素の fetch。画面のライブオッズ（`/api/odds/live`）に全体の上限が無い。月次の選手の取得が Vercel と GitHub Actions で二重
- 応急の対応は #1945（朝の初期化が直前情報を取らない）・#1946（403 でパス単位のブレーカー、展示の回数を約60%減）。どちらも 10/26 にマージ済み。本 ADR はその後の恒久の決まり
- オーナーの決定（2026-10-26）: BOATRACE振興会には連絡しない。名乗り（User-Agent）・IP を変えて回り込むことはしない

## 決定

1. **守りを通らない取得の経路を持たない**。GitHub Actions の肩代わりは「mode=live かつ Vercel が起動していない（tick_stale）かつ非常停止・ブレーカーが閉じている」ときだけにし、連続失敗の理由が 403・接続の失敗なら肩代わりしない。朝の初期化の安全装置も同じ条件。肩代わりの取得も同じ politeFetch・ブレーカー・予算を通す。cron-job.org の展示の旧経路は消し、mode=off は「どこからも取らない」の意味にそろえる。別の網から取り直すことは回り込みに当たる
2. **相手（ホスト×パス）ごとに1日の予算を持ち、取得の数を数える**。予算は「1レースあたりの枠×その日のレース数（中止を除く）×1.3＋固定分」で、多い日にも足りるようにする。ホスト全体には暴走の検知のための絶対の上限を別に置く。画面のライブオッズはホスト全体と別に数え、ライブが上限に達しても定時の取得は止めない。値は spec.md §4.2。根拠の無いものは「目安（根拠なし）」と書く
3. **予算は段階で効かせる**。最初の2週間は知らせるだけにし、数えた実数で値を直してから止める。止めるときは80%で知らせ、90%で優先の低い取得（オッズの早い窓・pcexpect・ピットレポート・夜の日次）を止め、100%でそのパスを止める。取り直せないデータも例外にしない（予算をレース数に比例させることで、止まるのは異常のときだけにする）。予算の読み取りに失敗したら取らない（ADR-0069）
4. **1分の上限（目安60）は数えて見る**。ジョブの1起動の上限の和やプロセスごとの間隔では、起動をまたいで守れない。1起動の上限はページ数で持ち、毎分のジョブの起動をずらす。実数が60を超え始めたら、要求ごとに枠を取る作りを検討する。BOATCAST は今の2.2秒の間隔のまま
5. **403（boatrace.jp）はパス単位に1回で開き、全パスへ順に広げる**（数えた2週間で 403 が0だったパスから）。パスが開いたら軽いページ（`race/index`）を1件試し、403 ならホスト全体を開く。開く段階は30分から倍にして6時間を上限とし、段階を DB に残し、24時間 403 が無ければ1段下げる。自動で閉じた後24時間は、そのパスのジョブの1起動の上限を半分にする。429 は Retry-After を尊重してホストを開く（追記 2026-10-27、#1983 の system-architect の審査）: 429/503 で開く期間は段階で 5分→10分→20分→60分。段階は 403 と同じ列（breaker_level）を使う（止める側に倒れるので共用を採る）。24時間で1段下げるのも、閉じた後24時間の絞りも 429 に効く。開いている間に届いた 429・403 では段階を上げない（上げるのは閉じている状態か半開から開くときだけ）。Retry-After が10秒を超えるときは再試行せず、その時間（上限60分）開き、段階は上げない。利用者の要求（/api/odds/live）の 429 は段階を上げない（Retry-After>10秒ならその時間開く）。5xx・タイムアウトは先に数え、開くかは実数で決める。403 の応答のヘッダの一部を記録に残す。BOATCAST の 403 は今のまま（カナリアで判定）
6. **非常停止**: `scrape_job_state` に専用の列を足し、`host:<ホスト>` の行で立てると、そのホストへのすべての取得（Vercel・ライブ・GitHub Actions）が止まる。mode の列は使い回さない（既定が 'off' で、ブレーカーが作る行がその値になるため）。読み取りに失敗したときはプロセスの中の直前の値のまま（一度立ったと読めば止まったまま）で、プロセスの最初の読み取りが失敗したときだけ止めない側に倒す（決定3の予算と逆向き。共通ラッパは readState の失敗で取得の前に終わるので当たるのは一時の1回と `/api/odds/live` だけで、ライブを DB の障害に巻き込まない。2026-10-26 system-architect の審査、マイグレーション178）。立っている間は scrape-monitor が知らせ続ける。下ろすときは `breaker_open_until` を今にして半開から戻す（spec.md §9.3 の4）
7. **監視**: まず scrape_slots から相手ごとの回数を毎日出し、次に politeFetch が数えた表で、ライブ・日次・GitHub Actions・再試行・応答の種類を含めて数える。403 は即時に知らせる
8. **取得の頻度の変更は、ADR-0058 の4つの問いに加えて「公式の公開の時刻の実測」と「画面の閲覧の時刻（GA4）」で決める**。見せる時刻が遅くなる変更（窓を落とす・先出しをやめる等）はオーナーに聞く。遅れが0の変更（結果の最初の取得を締切+5分→+10分 等）は聞かずに進める。拒否されているパスへの取得を増やす変更は、そのパスが続けて取れるようになってから入れる
9. **止められたとき、値が無いことを「未発表」と見せない**。止めの状態（ブレーカー・予算・非常停止・mode=off・最終成功が古い）を画面向けの公開の要約で出し、その欄は「公式から取得できていません」と公式へのリンクを出す。展示前の予想はそう明記し、予想の行に印を残して成績の集計で分ける。展示後の SNS・/today の自動投稿は出さない（spec.md §9）
10. User-Agent は `BoatraceAIBot/1.0 (+https://github.com/rhapsody0919/boatrace-ai-predictor)` の1つにそろえる（旧アカウントの表記を正しい連絡先にそろえるだけで、名乗りを変える回り込みではない）。robots.txt を1日1回読み、当社が取るパスが Disallow に入ったら、そのパスを止めて知らせる

## 却下した選択肢

- **ジョブごとの上限だけのまま**: 全体の数を誰も持たず、今回の 1,874回/日を止めなかった
- **固定の1日の上限**: レース数は1日144〜240と幅があり、多い日の夕方（12R・優勝戦）に止まる
- **すべての取得を1つの窓口で予約する（要求ごとに DB で枠を取る）**: 1分の上限を厳密に守れるが、要求ごとに DB の往復が入る。1分の実測の最大（43ページ、下限）が目安の60より下なので、今は要らない
- **名乗り・IP を変える、別の場所から取る**: オーナーの決定で採らない。GitHub Actions からの肩代わりも、拒否の後に別の網から取るなら同じ
- **取り直せないデータは予算を超えても取る**: 止めない例外があると、今回と同じく誰も止めない
- **非常停止に mode の列を使い回す**: ブレーカーが作る行の mode が既定の 'off' になり、一度開いたホストが永久に止まる
- **GitHub Actions の予備をすぐ消す**: Vercel が止まったときの予備が無くなる。条件を絞って守りを通し、30日肩代わりが無ければ消す

## 影響

- ADR-0067 の「取得負荷の抑制」は、本 ADR の数字と仕組みで持つ。取得量を増やす変更は、spec に負荷の見積りを書くのに加えて、予算の表を更新する
- ADR-0066 の「監視を1系統に統一する」に、取得の回数を足す
- オッズの窓を落とす場合は ADR-0057 の変更になり、`.claude/rules/data-acquisition.md` の -60 の再試行の基準と窓内取得率の監視も直す（オーナーの答えの後に追記）
- 実装は spec.md §12 の順に PR を分ける。マイグレーション（非常停止と段階の列、`fetch_counts`）は system-architect を通す
- ADR の番号: 開いている PR #1694・#1696 も 0101 を使っている。後からマージする方が `npm run verify:adr-numbers` で付け直す

## 見直しの契機

- 予算の80%・100%の通知が月に3回以上出たとき（値が実態に合っていない）
- 公式から 403 以外の形（通知・要請）で連絡を受けたとき（ADR-0067 の見直しの契機と同じ）
- 1分の実数が目安の60を超えたとき
- ホスト全体が止められたとき（spec.md §9.3 の5で代わりの取り先を起票する）
