# ADR 0058: 全データ項目の取得頻度・タイミング最適化の原則

## ステータス
採用

## 背景

ADR-0057（オッズ）の検討過程で、既存の取得頻度設計（[BOA-313](https://linear.app/boat-ai/issue/BOA-313)のExhibition Phase1、既存`scrape-odds.js`のウィンドウ等）や、`plan.md`初版のFR-1/FR-2/FR-6の頻度設定（「30分間隔」「週次」「日次〜週次」等）が、いずれも根拠のある計算ではなく感覚的な数値だったと判明した。ユーザー指摘（2026-09-15）「オッズだけでなく全てのデータに関して、どの頻度でいつ取得するかを最適化したい」を受け、全データ項目に共通する頻度決定の原則を定め、各FRに機械的に適用する。

## 決定

各データ項目の取得頻度は、以下4つの問いに答えることで決定する（感覚値で決めない）:

1. **変化頻度**: 情報源そのものが、実際にどれくらいの頻度で変化するか（例: 能力指数は半年に1回、オッズは締切に近いほど連続的に変化、展示データは一度確定したら変わらない）
2. **許容される鮮度**: 自社の利用目的にとって、どれだけ古いデータまで許容できるか（例: 選手プロフィールは数日〜数週間古くても実害が薄いが、直前情報は数分の遅れが命取りになりうる）
3. **可用性ウィンドウの有無**: 情報源に「この時間しか正しい値が取れない」という制約があるか（例: 展示データは発走前の一定時間しか表示されない＝ウィンドウを逃すと二度と正確な値が取れない。レース特記事項のような日中随時掲載型のページにはこの制約が無い）
4. **上記を踏まえた最小十分頻度**: 1〜3から導かれる、可用性ウィンドウを逃さず・鮮度要件を満たす範囲で**最も緩い**頻度を採用する（過剰な頻度はサーバー負荷・スクレイピング対象への配慮の観点で避ける）

この原則を各FRに適用した結果は`plan.md`の各FR節・FR-8まとめ表に反映する。

## 却下した選択肢

**「取得できるだけ高頻度で取得する」方針**: 鮮度は最大化されるが、可用性ウィンドウが無いデータ（選手プロフィール等、半年に1回しか変化しない）まで高頻度でポーリングするのはサーバー負荷・スクレイピング対象への配慮の観点で不適切。却下。

**「既存の実装パターンをそのまま流用する」方針**（本spec着手前の実態）: 実装コストは最小だが、ADR-0057で判明した通り、既存パターン自体が必ずしも最適化された頻度ではない（オッズの全通り捕捉が1窓のみだった等）。新規データ項目に対して無検証で既存パターンを踏襲すると、同じ非最適さを複製することになる。却下。

## 影響

- `plan.md`の各FRについて、上記4問いに基づく頻度の再検討を行い、結果を反映する（詳細は`plan.md`参照）。主な変更点:
  - FR-1（レース特記事項）: 30分間隔→15分間隔に見直し（可用性ウィンドウは無いが、レース間隔（約20〜30分）内に収まる頻度が望ましいため）
  - FR-2/FR-5（期別成績・プロフィール自動化）: 週次→**月次＋半年切り替わり（5/1・11/1）直後1週間はブースト**に見直し（データが実際に変化するのは半年に1回のみで、週次は過剰）
  - FR-6（会場個別サイト）: 項目ごとに変化頻度が大きく異なることが判明したため、「日次〜週次」という一括りをやめ、項目別に頻度を分ける（BOA-293は日次、BOA-294は項目により日次/年次混在、BOA-295潮汐は年1回のバルク取得＋自社計算転用も検討、BOA-296は低頻度の随時チェック）
- 既存BOA-313（展示データ、Phase1で2分間隔採用済み）・BOA-323（結果取得の「払戻金は早いがスタート情報は遅い」という二段階の可用性ウィンドウ）についても、本原則に照らした観察を記録するが、実装・変更自体は他セッション管轄のため本spec外（`plan.md`に参考情報として記載するに留める）
- 今後新たなデータ項目を追加する際も、本ADRの4問いを機械的に適用する運用とする
