# ADR 0022: 選手ニュース候補提示→承認フローの実装形態

## ステータス
採用

## 背景
spec.md（[[racer-news-feature]]要件2）は「Claudeが候補提示→ユーザーが承認したものだけ掲載」というフローを要求するが、実装形態（管理画面 vs スクリプト+チャット承認）は未確定のまま`/step2`に持ち越されていた（[screens.md](../design/racer-news-feature/screens.md)「3. 選手ニュース候補提示→承認フロー」参照）。

このプロジェクトには既に類似の「人手承認が必須の一括掲載フロー」が複数運用されている: note.com下書き（`note-articles/{slug}.md`をユーザーがエディタに貼り付け）、Xツイート下書き（`note-articles/tweet-drafts.md`にチェックボックス形式で管理、チャットで確認→ブラウザ操作→ユーザーがPostボタンを押す）、TikTok動画投稿（`data/analysis/tiktok-posts/history.json`で履歴管理、動画完成後にチャットで承認を得る）。いずれも管理画面を持たず、チャット上での確認とファイル/スクリプトの組み合わせで完結している。

## 決定
**案B（スクリプト+チャット承認）を採用する。** 管理画面は作らない。

- Claudeがニュース候補をリサーチし、チャット上で提示する（見出し・要約・出典URL）
- ユーザーが承認したら、Claudeが`scripts/maintenance/add-racer-news.js`（後述plan.md参照）を実行し、`racer_news`テーブルに直接INSERTする
- 下書き段階のデータはDBに保存しない（承認前のものはチャット履歴上にのみ存在する）。既存のXツイート下書き（`tweet-drafts.md`）のようなファイルでの下書き管理は、選手ニュースの掲載頻度が低い（都度手動リサーチ）ことを踏まえ今回は導入しない。承認後に直接INSERTする一発勝負のフローとする

## 却下した選択肢
- **案A: 管理画面（`src/pages/admin/`配下）**: 既存の`AdminRules.jsx`という直接再利用できる実装パターンがあり技術的には低コストだが、(1) このプロジェクトの他の人手承認フロー（note/X/TikTok）が全てチャット+スクリプト運用で統一されており、選手ニュースだけ管理画面を持つと運用パターンが割れる (2) 掲載頻度が低い（都度Claudeが手動リサーチする性質上、大量処理を捌く必要がない）機能に専用UIを作る費用対効果が薄い、という理由で見送る

## 影響
- ニュースの「下書き→承認待ち」という中間状態がDB上に存在しない。掲載しないと決めた候補はチャット上で棄却されるだけで、削除操作等が発生しない（シンプル）
- 将来的にニュース掲載頻度が大きく増えた場合、チャット+スクリプト運用が回らなくなる可能性がある。その際は本ADRを見直し案Aへの移行を検討する
- `racer_news`テーブルには「承認済みのもの」だけが入る前提のため、`status`カラム等は設けない（YAGNI）
