# ADR 0073: レイアウト検証だけを複数の画面幅で回す（全テストの多軸化はしない）

## ステータス

採用（2026-09-25）

## 背景

E2E（`e2e/smoke.spec.js`）は87テストあるが、**すべてPlaywrightの既定ビューポート（1280×720）でだけ走っていた**。

### 実測（2026-09-25）

| 項目 | 値 |
|---|---|
| E2Eのテスト数 | 87 |
| `setViewportSize` / `devices[]` / config の `viewport` の使用 | **0件** |
| ダークテーマの検証 | 23ページ×2テーマ＋Holmes5タブ×2テーマ（`localStorage` の `ryujin-radar-theme` を切り替え。axe-coreのcolor-contrastのみ） |
| モバイル幅の検証 | **0件** |
| 1280pxより広い幅の検証 | **0件** |

このプロジェクトは「モバイルファーストのPWA」を掲げ、`.claude/CLAUDE.md` にモバイル余白の表まで持っているが、**主戦場であるモバイル幅を一度も自動検証していなかった**。ダークテーマは（コントラストに限れば）既に網羅されており、欠けていたのは幅の軸だった。

### 実際に放置されていた崩れ

トップページのブログ一覧（`.blog-preview-grid`）は `repeat(auto-fill, minmax(280px, 1fr))` を使っており、`auto-fill` はアイテムが足りなくても列の枠を作る。カードは `VenueGridPage.jsx` が `.slice(0, 3)` で常に3枚に固定しているため、広い画面ほど空の枠が増えた。

| 画面幅 | 生成された列数 | カード数 | 右側の空白 |
|---|---|---|---|
| 1280px | 3 | 3 | なし |
| 1440px | 4 | 3 | **334px** |
| 1920px | 5 | 3 | **726px**（グリッド幅の約4割） |

中央寄せの見出し・リード文・CTAボタンに対してカードだけが左に寄り、ユーザーから「横幅がずれている」と指摘された。既定の1280pxでだけ検証していたため、**問題が出ない唯一の幅でテストしていた**ことになる。

`repeat(auto-fill, ...)` はリポジトリ内に13箇所あり、同じ崩れが起きうる。

## 決定

1. **`playwright.config.js` に projects を定義し、レイアウト検証だけを複数の幅で回す。**
   - `smoke`: 既存の全テスト。ビューポートは既定のまま（`testIgnore: /layout\.spec\.js/`）
   - `layout-mobile`: 375×812（`isMobile` / `hasTouch` 付き）
   - `layout-desktop`: 1440×900
   - `layout-wide`: 1920×1080
2. **`e2e/layout.spec.js` を新設し、機械的に判定できる崩れだけを検証する。**
   - 横スクロールの発生（`scrollWidth > clientWidth`。はみ出している要素も報告する）
   - グリッドの空トラック（幅を持つ列の数 > 実アイテム数）
3. **既存の `smoke.spec.js` のビューポートは変えない。** レスポンシブ分岐の前提が変わって既存87テストが揺れるのを避ける。

### 全テストを多軸化しなかった理由

87テストを3軸で回すとE2Eが9分から30分近くに伸びる。得られるのは主に「モバイルでも同じ要素が見えるか」で、レイアウト崩れの検知は専用テストのほうが直接的かつ具体的に失敗理由を出せる。費用対効果が見合わない。

機能そのもののモバイル検証（タップ操作、モバイル専用UI）が必要になったら、その導線に絞って追加する。

### 「見た目が美しいか」を判定しない理由

自動判定できるのは「壊れている」ことであって「美しい」ことではない。閾値で美しさを測ろうとすると誤検知が増えて無視されるようになる。人が見て気づける崩れのうち、機械的に判定できるものだけを対象にする。

## 結果

- 修正前の `layout.spec.js` は**4件失敗した**（`/` と `/venues` × 1440px・1920px）。検知できることを確認してから `.blog-preview-grid` を直した。
- 修正は `repeat(auto-fit, minmax(280px, 360px))` ＋ `justify-content: center` ＋ `max-width`。`auto-fit` は空トラックを0pxに潰す。`1fr` のままだと1920pxでカード1枚が570px超に間延びするため上限を360pxに固定した。
- カードを中央に寄せると、今度は小見出し「注目記事」「新着記事」が左端に取り残されたため、小見出しとグリッドで `--blog-preview-row-width` を共有して左端を揃えた。修正後は全幅で `subheadingLeft === gridLeft === firstCardLeft`。
- 修正後は72テスト全通過（3軸 × 12ページ × 2種類）。

### 検知ロジックの注意点

`repeat(auto-fit, ...)` が潰したトラックは、`getComputedStyle().gridTemplateColumns` に **`0px` として残る**（1920pxでは `360px 360px 360px 0px`）。これを列として数えると、正しく中央寄せされたグリッドを誤検知する。実装では幅が0のトラックを除外している。

## 検討したが採らなかった案

- **`auto-fill` を全13箇所で機械的に `auto-fit` に置換する**: 左寄せが意図的な箇所もあるため、テストで検知された箇所だけを直す。今回検知されたのは `.blog-preview-grid` のみだった。
- **タップ領域（44px以上）の検証を入れる**: 既存UIで大量に引っかかる可能性が高く、最初から無視される検査になりかねない。必要になった時点で別途入れる（YAGNI）。
