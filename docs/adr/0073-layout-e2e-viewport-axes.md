# ADR 0073: レイアウト検証だけを複数の画面幅で回す（全テストの多軸化はしない）

## ステータス

採用（2026-09-25）

## 背景

E2Eは**すべてPlaywrightの既定ビューポート（1280×720）でだけ走っていた**。

### 実測（2026-09-25）

| 項目 | 値 |
|---|---|
| E2E全体 | 934件（`smoke.spec.js` 142件 ＋ `venue-guide-data.spec.js` 792件） |
| そのうちブラウザで画面を開くもの | 142件（残り792件は `venueGuides*.js` の座標・データ検証でビューポートと無関係） |
| `setViewportSize` / `devices[]` / config の `viewport` の使用 | **0件** |
| ダークテーマの検証 | 22ページ×2テーマ＋Holmes5タブ×2テーマ（`localStorage` の `ryujin-radar-theme` を切り替え。axe-coreのcolor-contrastのみ） |
| モバイル幅の検証 | **0件** |
| 1280pxより広い幅の検証 | **0件** |

このプロジェクトは「モバイルファーストのPWA」を掲げ、`.claude/CLAUDE.md` にモバイル余白の表まで持っているが、**主戦場であるモバイル幅を一度も自動検証していなかった**。ダークテーマは（コントラストに限れば）既に網羅されており、欠けていたのは幅の軸だった。

### 実際に放置されていた崩れ

トップページのブログ一覧（`.blog-preview-grid`）は `repeat(auto-fill, minmax(280px, 1fr))` を使っており、`auto-fill` はアイテムが足りなくても列の枠を作る。カードは `VenueGridPage.jsx` が `.slice(0, 3)` で常に3枚に固定しているため、広い画面ほど空の枠が増えた。

| 画面幅 | 生成された列数 | カード数 | 右側の空白 |
|---|---|---|---|
| 1280px | 3 | 3 | なし |
| 1440px | 4 | 3 | **334px** |
| 1920px | 5 | 3 | **726px**（グリッド幅の約4割） |

中央寄せの見出し・リード文・CTAボタンに対してカードだけが左に寄り、ユーザーから「横幅がずれている」と指摘された。既定の1280pxでだけ検証していたため、**問題が出ない唯一の幅でテストしていた**ことになる。

`repeat(auto-fill, ...)` はリポジトリ内に13箇所あり、同じ崩れが起きうる。

## 決定

1. **`playwright.config.js` に projects を定義し、レイアウト検証だけを複数の幅で回す。**
   - `smoke`: 既存の全テスト。ビューポートは既定のまま（`testIgnore: /layout\.spec\.js/`）
   - `layout-mobile`: 375×812（`isMobile` / `hasTouch` 付き）
   - `layout-tablet`: 768×1024
   - `layout-laptop`: 1024×768
   - `layout-desktop`: 1440×900
   - `layout-wide`: 1920×1080
2. **`e2e/layout.spec.js` を新設し、機械的に判定できる崩れだけを検証する。**
   - 横スクロールの発生（`scrollWidth > clientWidth`。はみ出している要素も報告する）
   - グリッドの**空トラック**（幅を持つ列の数 > 実アイテム数）
   - グリッドの**使い残し**（箱の幅 −（トラック合計 + gap合計））
3. **既存の `smoke.spec.js` のビューポートは変えない。** レスポンシブ分岐の前提が変わって既存テストが揺れるのを避ける。

### 幅の選び方

768 / 1024 は `App.css` のメディアクエリの境界。**最初は 375 / 1440 / 1920 の3軸だけにしたが、これは誤りだった**（下記「実装中に踏んだ失敗」参照）。ブレークポイントの境界と、レイアウトが切り替わる帯の中を通す必要がある。

### 全テストを多軸化しなかった理由

E2E全934件のうち792件は `venue-guide-data.spec.js` のデータ検証で、ブラウザを開かないため多軸化しても意味がない。対象になるのは `smoke.spec.js` の142件だけ。それを3軸以上に広げても、得られるのは主に「モバイルでも同じ要素が見えるか」で、レイアウト崩れの検知は専用テストのほうが直接的かつ具体的に失敗理由を出せる。

実測では、レイアウト検証5軸（120件）の追加によるCIの増加は**約1分**（PR #838 のジョブ10分54秒 対 master系PR 9分40秒〜10分16秒）。

機能そのもののモバイル検証（タップ操作、モバイル専用UI）が必要になったら、その導線に絞って追加する。

### 「見た目が美しいか」を判定しない理由

自動判定できるのは「壊れている」ことであって「美しい」ことではない。閾値で美しさを測ろうとすると誤検知が増えて無視されるようになる。ここで見る3つはいずれも「箱の幅に対して中身が足りていない」という構造的な事実で、閾値のチューニングなしに判定できる。

## 実装中に踏んだ失敗（重要）

**軸の選び方と、検知ロジックの狭さで、自分が入れた回帰を自分で通した。**

最初の修正は `repeat(auto-fit, minmax(280px, 360px))` だった。カードの間延びを防ぐためトラックの上限を固定pxにしたが、これにより**列数の刻みが384px単位になり**、3列に必要な1128pxに届かない帯（約769〜1255px）で列が落ちた。

| 画面幅 | 修正前(master) | 固定px版（誤った修正） |
|---|---|---|
| 800px | 2列 / 332px / 右0px | 1列 / 360px / **右328px** |
| 1024px | 3列 / 288px / 右0px | 2列 / 360px / **右168px** |
| 1152px | 3列 / 325px / 右0px | 2列 / 360px / **右280px** |

**直したはずの不具合と同種の崩れを、別の幅で作っていた。**しかも:

- 選んだ3軸（375 / 1440 / 1920）がこの帯を完全に飛び越していたため、テストが通った
- 検知ロジックが「列数 > アイテム数」しか見ておらず、1024px（列2・アイテム3）は列が余っていないので素通りした

正しい修正は **トラックは `minmax(280px, 1fr)` のままにして、箱の幅だけを `max-width` で絞る**ことだった。カード幅の上限はトラックではなく箱で決める。

3案を幅×枚数で総当たりした実測:

| 案 | 800px | 1024px | 1440px | カード2枚(1440px) | カード1枚 |
|---|---|---|---|---|---|
| `auto-fill` + `1fr` + max-width | 余白0 | 余白0 | 余白0 | **空トラック1** | 空トラック2 |
| **`auto-fit` + `1fr` + max-width（採用）** | 余白0 | 余白0 | 余白0 | 余白0 | 余白0（幅1128pxに伸びる） |
| `auto-fit` + `minmax(280,360)` | **余白328** | **余白168** | 余白0 | **余白384** | 余白768 |

採用案の唯一の弱点はカード1枚のとき1128pxまで伸びることだが、featured記事は25件あり現実には起きない。起きたとしても「右に空白が残る」より害が小さい。

## 結果

- 修正前の `layout.spec.js` は**2件失敗した**（`/` × 1440px・1920px）。検知できることを確認してから `.blog-preview-grid` を直した。
  - 当初これを「4件」と記録していたが、`/venues` は ja にルートが無く `/` にリダイレクトされるため（`config/languages.js` の `LANGUAGE_ONLY_PATHS` で en / zh-TW / ko のみ）、同じページを2回数えていた。テスト対象は実在する `/en/venues` に差し替えた。
- 中央寄せに `justify-content: center` は使わない。**カードが3枚のときしか小見出しと左端が揃わない**（1920pxでカード2枚だと192px、1枚だと384pxずれる。実測）。グリッド自体を `max-width` + `margin: 0 auto` で中央に置き、カードを左詰めにすれば枚数が変わっても揃う。
- 修正後は5軸120テスト全通過。小見出し・グリッド・カードの左端が全幅で一致する。

### 検知ロジックの注意点

- `repeat(auto-fit, ...)` が潰したトラックは、`getComputedStyle().gridTemplateColumns` に **`0px` として残る**（1920pxでは `360px 360px 360px 0px`）。これを列として数えると、正しく中央寄せされたグリッドを誤検知する。実装では幅が0のトラックを除外している。
- レイアウトされていない要素では `gridTemplateColumns` が解決前の指定値（`repeat(auto-fit, minmax(280px, 1fr))` 等）のまま返る。`parseFloat` にかけると `360px))` のような偽のトラックが生まれるため、px値に解決されているものだけを対象にする。
- グリッドを1つも持たないページ（`/accuracy` `/winning-technique` `/faq` `/how-to-use`）では、この検査は通っても何も見ていない。失敗時のメッセージに「検査したグリッド数」を含めて、通過が検査を意味しないことが分かるようにした。

## 検討したが採らなかった案

- **`auto-fill` を全13箇所で機械的に `auto-fit` に置換する**: 左寄せが意図的な箇所もあるため、テストで検知された箇所だけを直す。今回検知されたのは `.blog-preview-grid` のみだった。なお今回の件は「`auto-fill` → `auto-fit` は安全な置換ではない」ことの実例でもある。危険だったのは `auto-fit` 自体ではなく、トラックの上限を固定pxにしたほうだった。
- **`toHaveScreenshot`（視覚回帰テスト）**: トップ・`/today`・`/races` は本番Supabaseの当日データに依存するためベースラインが毎日壊れる。CI(ubuntu)とローカル(macOS)のフォントレンダリング差も避けられない。ただし中間解として、ピクセルではなく幾何量（主要セクションの `left` / `width` / 行数 / トラック構成）をJSONスナップショットで比較する方式は有望で、今回の回帰もそれなら検出できた。次の一手として検討に値する。
- **タップ領域（44px以上）の検証**: 既存UIで大量に引っかかる可能性が高く、最初から無視される検査になりかねない。必要になった時点で別途入れる（YAGNI）。
