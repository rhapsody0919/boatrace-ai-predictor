# ADR 0080: 類似レースの近傍はバッチで事前計算し、pgvector は使わない

## ステータス
提案中（BOA-271 plan.md と同時。Phase U の着手で採用に変える）

## 背景
BOA-271 の FR-2・FR-3 は、今日のレースに近い過去のレース800件を探して決着の分布を出す。MD-6 の検証で、方式は「会場が違うと距離にペナルティを足す k-NN」に決まった（`docs/design/analogy-finder/analysis/md6-result.md`）。

- 母集団は 2019-04〜の約36万レース。距離は発走前の長期の項目だけで作った337次元の重み付きユークリッド
- 表示した近傍は時点固定で残す必要がある（BOA-627）。週次の再学習で近傍の1〜2割が入れ替わるため
- 特徴量は as-of の2段（出走表時点・直前情報時点）。今日のレースの特徴量を作るには、過去走のローリング集計（直近成績・過去ST）が要る
- 既存の ML は学習も推論も GitHub Actions の Python で動いている（`train-poirot.yml`・`generate-poirot.yml`）。Vercel で Python は動いていない。Vercel 関数の上限は300秒（ADR-0066 改訂1）

どこで近傍を計算するかを決める。

## 決定
**GitHub Actions のバッチ（Python）で、今日のレースごとに近傍800件を事前計算し、`analogy_snapshots` に書く。** 画面は RPC `get_analogy_neighbors` で読むだけにする。pgvector は使わない。

- 新しいワークフロー `generate-analogy-neighbors.yml` を JST 8:00〜21:30 に10分ごとに動かす。出走表がそろったレースは出走表時点、展示データが入ったレースは直前情報時点のスナップショットを作る。締切を過ぎたレースは書かない（発走前の結果がそのまま残る）
- 母集団の特徴量行列（約36万×337、float32 で約0.5GB）は週次の学習ジョブが作って Supabase Storage に置き、近傍のジョブは起動時に読み込む。1回に計算するのは数十レースなので、総当たりでも数秒で終わる
- 表示したものの再現は、スナップショットに残した近傍の一覧そのもので行う（BOA-627）

## 却下した選択肢
- **pgvector で表示時に検索する**: 今日のレースの特徴量を DB の中で作る必要がある（過去走のローリング集計を SQL で持つことになり、学習側の Python と二重実装になる）。会場ペナルティは次元の工夫で入れられるが、重みが週次で変わるたびに約36万行のベクトルを作り直してインデックスを張り直す必要がある。近似検索（HNSW）だと800件の順位が厳密でなくなり、検証した方式とずれる。表示時に検索すると、BOA-627 の時点固定のために結局どこかで結果を保存する必要がある
- **Vercel 関数（Edge / Node）で表示時に総当たりする**: 0.5GB の行列を関数ごとに読み込むのは、Edge のメモリとサイズの制約に収まらない。Node 関数でもコールドスタートのたびに読み込みが発生する。特徴量の作成を JS で再実装することになる
- **既存の `generate-poirot.yml`（1日3回）に相乗りする**: 直前情報時点のスナップショットが最大で数時間遅れる。展示データが入ってから発走までは十数分しかないので、3回では足りない

## 影響
- pgvector の導入（spec の「実装開始の前提条件」4）は不要になる。本番 DB で必要な書き込みはマイグレーション 115 の適用だけ
- GitHub Actions の実行回数が1日約80回増える。リポジトリは public なので Actions の実行時間の課金は無いが、cron の遅れ（数分〜十数分）がある。直前情報時点のスナップショットが間に合わないレースは出走表時点を出し、画面に「出走表 ○時○分時点のデータ」と時点を明記する
- 近傍の一覧は1レース・1段あたり約16KB。1日約300行で約5MB、1年で約2GB。180日を過ぎた行は近傍の配列を消す（features と model_version が残るので、Storage のモデルから再計算できる）運用を tasks に入れる
- BOA-635（予想の過去発生率チェック）と BOA-430 は同じ RPC を使う。RPC は決着に加えて、コース順の ST・進入・3連単の払戻も返す
