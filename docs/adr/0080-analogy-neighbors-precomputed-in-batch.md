# ADR 0080: 類似レースの近傍は出走表時点で1日数回バッチ計算し、pgvector は使わない

## ステータス
FR-2 の部分（決定1・2・4、決定3の近傍の起動）は [ADR-0082](./0082-analogy-strata-counted-in-sql.md) で置き換え（2026-10-02、FR-2 が層別 S* に変わったため）。残るのは決定3のうち FR-1 の週次学習を Vercel Cron から workflow_dispatch で起動する部分と、「GitHub Actions の schedule を使わない」「出走表時点」「pgvector を使わない」の判断。以下は経緯として残す

## 背景
BOA-271 の FR-2・FR-3 は、今日のレースに近い過去のレース800件を探して決着の分布を出す。MD-6 の検証で、方式は「会場が違うと距離にペナルティを足す k-NN」に決まった（`docs/design/analogy-finder/analysis/md6-result.md`）。

- 母集団は 2019-04〜の約36万〜39万レース。距離は発走前の長期の項目で作った重み付きユークリッド
- 表示した近傍は時点固定で残す必要がある（BOA-627）。週次の再学習で近傍の1〜2割が入れ替わるため
- 今日のレースの特徴量には、過去走のローリング集計（直近成績・過去ST）が要る
- 既存の ML は学習も推論も GitHub Actions の Python（`train-poirot.yml`・`generate-poirot.yml`）。Vercel で Python は動いていない。Vercel 関数の上限は300秒（ADR-0066 改訂1）
- **GitHub Actions の定時実行（schedule）は、このリポジトリでは当てにならない**。ADR-0066 改訂1 で「2.5〜4.5時間遅れが常態」。設計レビュー（2026-10-01）の実測でも、30分間隔の `campaign-pipeline.yml` が1日36回の予定に対して2〜6回しか起動していない。一方、外から `workflow_dispatch` で起動する `scrape-scheduled.yml` は1日150〜200回安定して起動している
- 展示データが入ってから締切までは中央値20分、5%点12分しかない（2026-09-26〜30 の744R）

どこで・いつ近傍を計算するかを決める。

## 決定
1. **近傍は「出走表時点（前日までの成績）」の1段だけで計算する。** 展示・気象（直前情報）は距離に入れない。設計レビューの測定（test 4,000R）で、展示・気象の8項目を距離から外した k-NN の決まり手の対数損失は 1.28786、全部入りは 1.28703 で、差は約0.0008。どちらも層別に約 −0.023 で勝つ。本番化の前に全 test で同じ比較をして確かめる（tasks T0）
2. **GitHub Actions の Python バッチで、今日のレースごとに近傍800件を計算し `analogy_snapshots` に書く。** 画面は RPC `get_analogy_neighbors` で読むだけ。pgvector は使わない
3. **起動は Vercel Cron から GitHub の `workflow_dispatch` を呼ぶ。** schedule は使わない（障害時の手動起動用に workflow_dispatch だけ残す）。JST 7:30（その日の大半のレース）、10:00・14:00（出走表が後から入る会場・ナイター）の3回。各回は「締切前で、まだスナップショットが無いレース」だけを作る（catch-up）
4. 母集団の特徴量行列は週次の学習ジョブが作り、Supabase Storage に分割して置く（1ファイル50MB以下）。近傍のジョブは起動時に読み込む（actions/cache で再取得を減らす）

## 却下した選択肢
- **10分ごとの schedule で直前情報時点まで作る（当初案）**: schedule が起動しない・数時間遅れる実測があり、展示データが入ってから締切までの20分に間に合わない。直前情報を距離に入れる効果も約0.0008と小さい
- **pgvector で表示時に検索する**: 今日のレースの特徴量を DB の中で作る必要があり（ローリング集計を SQL に持つことになり、学習側の Python と二重実装になる）、重みが週次で変わるたびに全ベクトルを作り直してインデックスを張り直す。近似検索だと800件の順位が厳密でなくなり、検証した方式とずれる。BOA-627 の時点固定のために、結局どこかで結果を保存する必要もある
- **Vercel 関数（Edge / Node）で表示時に総当たりする**: 行列（数百MB）を関数ごとに読み込むのは Edge の制約に収まらず、Node 関数でもコールドスタートのたびに読み込みが発生する。特徴量の作成を JS で再実装することになる
- **cron-job.org から dispatch する**: 既存の `scrape-scheduled.yml` と同じ方法で動くが、外部サービスのジョブ管理が増える。Vercel Cron は ADR-0066 で取得の標準になっており、監視（`scrape_job_state` 等）にも乗せやすい

## 影響
- pgvector の導入（spec の「実装開始の前提条件」4）は不要。本番 DB で要る書き込みはマイグレーション 115 の適用だけ
- **Vercel から GitHub API を呼ぶためのトークン（Actions の write だけを持つ fine-grained PAT）を Vercel の環境変数に足す必要がある。ユーザーの作業**
- 画面のデータ段は「出走表 7:30 時点のデータ（前日までの成績）」になる。FR-2 の「似ている理由」の一行から「展示の差」を外す
- 近傍の一覧は1レースあたり約16KB。1日約150行で約2.4MB、1年で約0.9GB。1年を過ぎた行は近傍の配列を NULL にし、画面にも出さない（再計算はしない）
- BOA-635 と BOA-430 は同じ RPC を使う。RPC は決着に加えて、コース順の ST・進入・3連単の払戻も返す
