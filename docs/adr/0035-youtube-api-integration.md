# ADR 0035: YouTube API連携方式

## ステータス
採用

## 背景
YouTube下書きの承認時、YouTube Data API v3経由で動画・サムネイル・メタデータを自動投稿する（spec.md FR7）。認証方式を決める必要がある。

## 決定
OAuth 2.0のリフレッシュトークン方式を使う。対象YouTubeチャンネルの所有者（ユーザー本人）が一度だけGoogle Cloud ConsoleでOAuth同意画面を通し、取得したリフレッシュトークンをVercel環境変数（`YOUTUBE_CLIENT_ID`・`YOUTUBE_CLIENT_SECRET`・`YOUTUBE_REFRESH_TOKEN`）として保存する。以降はサーバー関数がリフレッシュトークンからアクセストークンを都度取得して`videos.insert`・`thumbnails.set`を呼ぶ。

この初回同意フローはユーザー自身のGoogleログインが必要なため、Claude側では代行できない（未確定事項としてspec.mdに記録済み）。

## 却下した選択肢
**サービスアカウントを使う案**: サーバー間認証で人手を介さず自動化できるという利点はあるが、**個人・ブランドのYouTubeチャンネルはサービスアカウントによる委任をサポートしていない**（Google Workspaceのドメイン全体委任が使える組織アカウントのみ対応）。今回のチャンネルはこの条件に該当しないため、技術的に選択肢として成立しない。

**YouTube公式の自動化ツール（例: TubeBuddy等のサードパーティ連携）を使う案**: 外部SaaSへの依存が増え、既存のRoutine/Supabaseベースの構成と統合しにくい。カスタムのサムネイル生成（Remotion）・下書き承認フロー（sns_drafts）との連携を考えると、直接API連携の方が一貫性を保ちやすい。

## 影響
- リフレッシュトークンは長期間有効だが失効するケースがある（同意の取り消し、一定期間未使用等）。失効時はユーザーが再度同意フローを実施する必要がある——この運用手順を`docs/operation/`に残す
- YouTube Data API v3にはクォータ制限がある（デフォルト1日10,000ユニット、動画アップロード1回あたり約1,600ユニット消費）。1晩1本という運用頻度（spec.md非機能要件）であれば十分な余裕がある
- サムネイルは`thumbnails.set`で動画とは別リクエストになるため、アップロード処理は「動画本体のinsert→動画IDの取得→サムネイルのset」という2段階の実装になる
