# ADR 0065: 会場平均（会場×枠番）は`venues`のjsonb列に事前集計して持つ

## ステータス
採用

## 背景

進入コース遷移傾向の会場別対応（`docs/design/course-entry-tendency-rework/`、FR-6）で、選手の実績（選手×会場×枠番）に添える基準線として、選手を問わない「会場×枠番→進入コース分布」（会場平均）が必要になった。

実データ（2025-09-19以降）では、選手×会場×枠番は中央値2走と薄く、選手値だけでは判断できない。一方、会場×枠番は144組合せすべてで1,484走以上あり、会場差も大きい（6枠の枠外進入率が浜名湖17.6%〜びわこ5.7%）。会場平均は出走表・選手ページ・分析タブの3箇所から参照される。

## 決定

`venues`テーブルにjsonb列`course_entry_baseline`（と更新日時`course_entry_baseline_updated_at`）を追加し、夜間バッチで会場ごとに事前集計して保存する。集計はSQL関数`compute_venue_course_entry_baseline(p_venue_code, p_since)`（会場ごとに呼ぶ）で行い、`scripts/maintenance/update-venue-course-entry-baseline.js`が既存の`aggregate-stats.yml`（JST 23:00）の3つ目のステップとして更新する。

## 却下した選択肢

**専用の新規テーブル（例: `venue_course_entry_stats`）を作る方式**: 24会場×6枠×6コース=最大864行で、参照は「全会場を一括取得」の1パターンのみ。会場単位の値を`venues`の列に置く既存パターン（`update-venue-stats.js`が`venues.avg_first_win_rate`を更新している）と整合し、jsonb列なら追加のJOINも不要。専用テーブルはFK・RLS・マイグレーションの管理対象が増えるだけで得るものが無い。却下。

**表示のたびにDB側で集計する方式（RPCを都度呼ぶ）**: 出走表・分析タブを開くたびに約4万レース×6艇の集計が走る。会場平均は1日に1回しか変わらないため無駄が大きい。却下。

**`racer_aggregated_stats`を全選手で合算して求める方式**: 本番の同テーブルは`venue_code=0`の行しか無く、会場別の内訳も選手ごとの集計期間のずれを含む。会場平均を選手の集計から逆算すると、走数の重みづけが崩れる。却下。

**クライアント側で履歴から集計する方式**: 会場全体の集計には全選手の履歴が必要で、選手ページのような「1選手の履歴を1回取得」の前提が成り立たない。却下。

## 影響

- マイグレーション1本（列2つとSQL関数1つの追加、新規テーブル無し）。適用はユーザーの対話ターミナルで行う
- 会場平均の鮮度は最大1日遅れ（夜間バッチ）。直近12ヶ月の平均なので実害は無い
- `compute_venue_course_entry_baseline`は会場ごとに呼ぶため、1回の集計量が約1/24になり、PostgRESTのタイムアウトを避けられる
- 江戸川のようにほぼ0%の会場が実態か取得由来かは、集計とは別に確認が必要（spec.md FR-6）
