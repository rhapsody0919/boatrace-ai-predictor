# ADR 0083: レースごとの寄与度は、特徴量を Python で朝に作り、SHAP は JS で出走表時点と展示後の2段に計算する

## ステータス
提案中（BOA-271 FR-1 の拡張「レースごとの寄与度」、2026-10-02 ユーザー決定）。FR-1 の学習レーンとの合意（下の「境界」）と、second-opinion-reviewer の検証の後に採用に変える。

## 背景
ユーザー決定（2026-10-02、オーケストレーター経由）:
- 寄与度をレースごとにも出す。朝に出走表時点の値を出し、展示の後に出し直す。FR-2 と同時に公開する
- 展示が間に合わないレースは出走表時点の値のまま「展示前の値」と明示する
- 似たレース（FR-2）は出走表時点のまま。レースごとの寄与度は条件チップの強調にだけ使う（ADR-0082 の混ぜない線）

調べたこと（[perrace-contribution.md](../design/analogy-finder/analysis/perrace-contribution.md)。探索的）:
- 展示（直前情報8列）を入れると、1着の対数損失が +0.0114 [+0.0090, +0.0139] 良くなる（縮小した学習、test 2026-04〜09 28,185R、ablate.json#paired_without_minus_with）。寄与度の ST・直前は、出走表時点専用のモデルで .063、展示ありで .147（#centered_share_mean）。欠損で代用すると .091 になり、出走表時点の値として正しくない
- 展示が DB に入ってから締切まで: 中央値 16.4分、5%点 12.4分、最小 8.4分、締切後 0/912（`scrape_slots.done_at`、2026-09-26〜10-01）
- 展示の取得（`api/cron/exhibition.js`）は、展示を書いたレースだけを同じ起動の中で再計算する仕組みを持っている（`scripts/lib/predictionRefresh.js`、`REFRESH_ON_VERCEL`）
- TreeSHAP の JS 移植の試作（`scripts/analysis/analogy-finder-perrace/treeshap.mjs`、117行）が、LightGBM の pred_contrib と最大差 4.4e-16 で一致（1,008艇、カテゴリ変数と欠損を含む）。1レースの CPU 時間は本番の木 830本換算で約0.11秒
- 選手の過去30走の ST・成績（日単位でずらす）は `features.py`（Python）でしか作れない

## 決定
1. **モデルは1着の2本**: 展示ありの今のモデル（44特徴量）と、直前情報8列を除いた出走表時点専用のモデル（36特徴量）。どちらも週次の学習（`train.py`）が作り、LightGBM の `dump_model()` の JSON をそのまま Storage（`analogy/{版}/`）に置く
2. **特徴量は Python で朝に作って DB に保存する**: 日次の Python ジョブ（Vercel Cron から workflow_dispatch で GitHub Actions、JST 6:40・9:40・13:40）が、今日のレースの36特徴量を `analogy_race_features` に書く。直前情報8列は作らない
3. **SHAP は JS で計算する**（Vercel の Node 関数、モデルは関数のメモリに版ごとに置く）:
   - 出走表時点の段: Vercel Cron（FR-2 のスナップショットと同じ `analogy-snapshots`、JST 7:30・8:30・10:00・14:00）が、特徴量があって段の行がまだ無い締切前のレースについて、専用モデルで計算する
   - 展示後の段: 展示の取得の直後のフック（`runSlotsWithRefresh` の再計算と並べる）が、展示を書いたレースについて、保存した36列＋展示と気象から JS で作った8列で、展示ありのモデルで計算する
   - テーマへの集計（レース内で中心化した |SHAP| のシェア、艇ごと・テーマごとの値）も JS で行う。集計は1か所（JS）だけ
4. **保存は段ごとに1行**（`analogy_race_contributions`、主キー `(race_id, stage)`）。締切前だけ書き、既にあれば書かない（BOA-627 の時点固定）
5. **一致の検査**: 週次の学習が、版ごとに Python の pred_contrib の固定データ（数十レース分）を書き出し、JS の計算と一致すること（最大差 < 1e-9、SHAP の合計＝生スコア）を、切り替え前の品質ゲートとして検査する。リポジトリの CI には、小さな固定モデルで JS の TreeSHAP を検査する verify を置く。直前情報8列の作り方（展示タイムのレース内の差・順位、風の成分、天候の符号化）も、Python の `features.py` と同じ値になることを固定データで検査する

## 却下した選択肢
- **欠損で代用する（展示ありのモデル1本に、出走表時点は直前情報を欠損で入れる）**: ST・直前が .091 と過大になり、出走表時点の値として説明できない
- **展示後の段も GitHub Actions の Python で計算する**: 定時実行は遅れが常態で、dispatch でも起動に数十秒〜分かかる。展示から締切まで5%点 12.4分の中で、既存の Vercel のフックに乗せるほうが確実
- **Vercel の Python 関数**: 依存（lightgbm・numpy・scipy）約187MB は上限内だが、lightgbm が使う libgomp が実行環境にあるか確かめられず、前例も無い
- **Vercel の Edge 関数・Supabase Edge Function**: Edge はコードの上限（gzip 後 1〜2MB）にモデルが収まらない。Supabase は CPU 時間が1リクエスト2秒で、前例が無い
- **36特徴量も JS で作る**: 選手の過去30走のローリング集計を JS と Python の2か所に持つことになる（ADR-0082 の FR-2 の条件と違い、特徴量が多く、日単位のずらし等の約束が多い）
- **出走表時点の段を Python のジョブで計算する**: SHAP のテーマ集計が Python と JS の2か所になる

## 影響
- FR-2 の SQL 化（ADR-0082）で外した「日次の Python ジョブと Vercel → GitHub の dispatch（PAT）」が、FR-1 側に戻る。PAT は FR-1 の週次学習の起動で元々必要なので、それと共用する
- 本番 DB: `analogy_race_features`（1日 約150R×6艇、1艇 約200B）と `analogy_race_contributions`（1日 約150R×2段、1行 約1KB）。どちらも年に約0.1GB 未満
- 展示の取得の関数（maxDuration 300秒）に、寄与度の計算が同居する。1起動で扱うレースは数件で、1レース約0.1秒（CPU）なので収まる見込み。モデルの JSON（約10MB）の読み込みは版ごとに1回（関数のメモリに置く）。取得そのものを遅らせないよう、寄与度の失敗は取得の成否に影響させない
- 失敗したとき: 展示後の段が無ければ出走表時点の段を「展示前の値」として出す。出走表時点の段も無ければ、レースごとの表示を出さない（条件ごとの寄与度は出す）
- モデルの版の切り替え（週次）とレースの段の整合: 行に版を持つ。展示後の段は、そのレースの特徴量の行と同じ版のモデルで計算する（Storage は直近3版を残すので取れる）
- 境界（FR-1 の学習レーンと合意する）: 学習側は2本のモデル・JSON ダンプ・一致検査の固定データ・日次の特徴量ジョブ。推論側（このレーン）は JS の TreeSHAP・テーマ集計・2段の計算・表と API
