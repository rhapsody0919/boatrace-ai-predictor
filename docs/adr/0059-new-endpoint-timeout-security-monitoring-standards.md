# ADR 0059: 新規Vercelエンドポイント・監視の設計標準（BOA-313の知見の横展開）

## ステータス
採用

## 背景

`plan.md`のFR-1（レース特記事項）・FR-4（オッズ全券種・オンデマンド更新）・FR-6（会場個別サイト）を設計する中で、[BOA-313](https://linear.app/boat-ai/issue/BOA-313)（スクレイピング基盤のサーバーレス移行）が既に確立した設計パターン・監視の仕組みを踏襲せず、個別に未設計のまま残していた箇所が複数見つかった（ユーザー指摘「天才エンジニア視点でチェックして」、2026-09-15）。BOA-313の知見を横展開する標準を定める。

## 決定

### 1. 新規Vercel Functionは全て「即時応答＋バックグラウンド継続」パターンを踏襲する

BOA-313 Phase1（展示データ、[PR #639](https://github.com/rhapsody0919/boatrace-ai-predictor/pull/639)）で確定した設計: cron-job.orgのタイムアウト（30秒）に対し、Vercel Function側は`res.status(202)`等で即座に応答を返し、実処理は`waitUntil`でバックグラウンド継続する。

**FR-1（`api/cron/race-notices.js`）にもこのパターンを適用する**。開催中の全会場（最大24会場）を1回の呼び出しで巡回する設計のため、素朴に実装すると30秒を超えるリスクがある。

### 2. オンデマンド更新エンドポイント（公開API）は、cron向けエンドポイントと別のセキュリティモデルにする

FR-4のオンデマンド更新（`api/odds/refresh.js`）は、cron-job.orgからではなく**フロントエンド（不特定多数のブラウザ）から直接呼ばれる**。既存の`CRON_SECRET`（サーバー間の共有シークレット）はこの用途に**適用できない**（フロントエンドに埋め込んだ時点で秘密ではなくなる）。

代わりに以下を実装する:
- **レート制限**: IPアドレス単位、または（ログイン機能があれば）セッション単位で、短時間の連打を制限する（Vercelの[Rate Limiting](https://vercel.com/docs/security/rate-limit) or 簡易的にはSupabase側にレート制限用テーブルを持つ）
- **対象の妥当性検証**: 呼び出しパラメータ（race_id等）が実在する当日レースかを検証し、任意のIDでの濫用を防ぐ
- **多重リクエストの抑制**: 同一レースへの短時間内の重複リクエストは、進行中の取得結果を待たせる（キャッシュ）か、キューイングする

この設計判断がなければ、**自社のVercel Functionが「boatrace.jpへの匿名プロキシ」として悪用され、意図せず攻撃の踏み台になるリスクがある**。

### 3. 会場個別サイト（FR-6）の新規スクレイパーは、既存の`driftHealth.js`を再利用する

[BOA-285](https://linear.app/boat-ai/issue/BOA-285)（Done、[PR #632](https://github.com/rhapsody0919/boatrace-ai-predictor/pull/632)/[#633](https://github.com/rhapsody0919/boatrace-ai-predictor/pull/633)）で、会場公式サイトのHTML構造変化を検知する汎用ロジック（`scripts/lib/venueMotorStats/driftHealth.js`、履歴更新・14日連続失敗での閾値判定）が既に実装済み。ただし**再利用可能なのは履歴更新・閾値判定のコアロジックのみで、reasonコードの分類（`STRUCTURAL_DRIFT_REASONS`）は`venue_motor_stats`固有**（BOA-285のコメントに明記）。

**FR-6の新規スクレイパー（BOA-293進入コース別選手成績、前検ランキング、水面特性、コンピ指数、潮汐、レイアウト変更履歴）は、それぞれ自身のreasonコード分類を定義した上で`driftHealth.js`のコア機構を再利用する**。ゼロから監視の仕組みを作らない。

### 4. 新規T1/T2データパイプラインは、BOA-313と同じ「並走検証→切替」の手順を踏む

BOA-313 Phase1は、新方式を既存方式と並走させ、欠落率が悪化していないことを確認してから切替える手順（`docs/design/scraping-serverless-migration/spec.md`のStep2〜4）を確立した。**FR-1・FR-4（既存`scrape-odds.js`拡張部分）・FR-6のT1〜T2寄りの項目も同じ手順を踏む**: 実装→単体デプロイ確認→（既存方式がある場合は）並走→自動監視での閾値確認→切替。一発切替はしない。

## 却下した選択肢

**各機能を都度違うパターンで実装する（現状のまま）**: 実装は早いが、BOA-313が解決した問題（タイムアウト、監視、段階的検証の欠如）を新しいコードで再現するリスクが高い。今回の指摘のように後から気づいて手戻りするコストの方が大きいため却下。

## 影響

- FR-1・FR-6のタスク分解（`/step3`）に、上記標準への準拠をタスクとして明記する
- FR-4のADR-0057に、オンデマンド更新のセキュリティ設計を追記する（本ADR参照）
- FR-6の各データ項目の実装タスクに「driftHealth.js向けreasonコード定義」を追加する
- 新規パイプラインの実装見積もりに、並走検証期間（3〜7日程度、BOA-313実績を参考）を織り込む
