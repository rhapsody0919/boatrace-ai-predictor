# ADR 0081: 予想の過去発生率は、近傍800件を画面側で数え、予想は端末内に保存する

## ステータス
提案中（BOA-635 plan.md と同時。実装の着手で採用に変える）

## 背景
BOA-635 は、ユーザーが入れた予想（6つの型）が、今日のレースの類似レース（BOA-271 FR-2 の近傍800件）で過去に何回起きたかを見せる。発走後は結果タブで、発走前に入れた予想を振り返る。

- 近傍は BOA-271 のバッチが出走表時点で作り、`get_analogy_neighbors(race_id)` が近い順800件を決着つき（1〜3着・決まり手・進入・コース順の ST・3連単の払戻）で返す（ADR-0080）
- 同じタブの BOA-271 の節（FR-2・FR-3）が同じ800件を既に読む
- 入力は組み合わせが多い（着順の流し、スリット7形×2段×2形、自分で作る 3^6 通り 等）
- 会員登録は無い。BOA-627 の保存項目3（ユーザーの読みと発走前の時刻）は「端末内でも可」とされている
- BOA-430（思考アシスト）の Step2・Step4 に同じ部品を埋め込む予定がある

どこで数えるか、予想をどこに残すかを決める。

## 決定
1. **数えるのは画面側（ブラウザ）の純粋関数。** `get_analogy_neighbors` の800行を、型ごとの判定関数で数える（`src/utils/pastRate/count.js`）。新しい RPC・API・テーブルは作らない
2. **予想は localStorage に保存する**（キー `boatai-user:past-rate-check:v1`。データキャッシュの `boatai:` 名前空間は更新ボタンで全削除されるので重ねない。1レース×1型につき最新1件、入力時刻から30日で消す、締切後は保存しない）。スナップショットとは `(model_version, asof_stage, asof_at)` で紐づける（`analogy_snapshots` の一意制約と同じ組。RPC に `snapshot_id` を足さない）
3. 振り返りの「あなたの予想」の数字は、入力したときに見せた値を保存して出す。決着の行は今の RPC の返り値から数える

## 却下した選択肢
- **RPC（SQL）で数える（入力を引数に渡す）**: 判定式を SQL に持つと、入力の形（流し・2形の AND・自分で作る）を引数で表す API 設計が要り、型を足すたびにマイグレーションが要る。BOA-271 の節が既に同じ800行を画面に持っているので、通信が増えるだけ。BOA-430 に埋め込むときも同じ RPC の改修が要る
- **Edge API で数える**: RPC と同じく通信が増え、判定式が画面と二重になる（画面でも入力の要約・点数を出すため）。800行は画面で数えて十分速い（100ms 以内）
- **予想をサーバー（Supabase のテーブル）に保存する**: 会員登録が無いので、端末ごとの匿名 ID を作る必要があり、匿名の書き込み（RLS で anon に INSERT を許す）を開けることになる。プロジェクトの RLS 規律（匿名は SELECT のみ）に反する。端末をまたいだ振り返りはユーザーの要件に無い
- **sessionStorage / IndexedDB**: sessionStorage はタブを閉じると消え、翌日の振り返りができない。IndexedDB は件数（最大1,000件、数百KB）に対して過剰
- **RPC に `snapshot_id` を足す**: 115 の変更になり BOA-271 側の手間が増える。一意制約の組で同じものを指せる

## 影響
- 判定式は JS が正。定番／レアの線の検証（Python の分析スクリプト）だけ同じ式を Python に持つので、固定データで件数の一致を検査する
- 端末を変えた・ブラウザのデータを消した・30日を過ぎたときは振り返りに「あなたの予想」が出ない（決着の行だけ出る）。仕様として受け入れる
- localStorage が使えない環境では、判定と表示だけ動き、保存と振り返りはしない
- BOA-430 は `PastRateChecker` を props（`types`・`value`/`onChange`・`persist`）で絞って埋め込む。データ取得は BOA-271 のフックを共有する
