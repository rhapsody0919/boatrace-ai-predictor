# ADR 0020: 承認操作から自動処理への引き継ぎ方式

## ステータス
採用

## 背景
SNSマーケティングハブでは、Claude Code Routineが下書きを生成し、人間が管理画面で承認・修正指摘・作り直しを行う。Routineは実行中に人間の入力を待って一時停止する機能を持たない（`claude.ai/code/routines`仕様、2026-08-27確認済み）ため、「承認」は必ず管理画面という非同期のチャネルで行う設計になっている（ADR不要、spec.mdの制約として確定済み）。

課題は、管理画面での操作（承認・修正指摘・作り直し）を、実際にRoutineによる後続処理（英語版の自動生成、修正内容を反映した再生成）にどう引き継ぐか。

## 決定
Routineの**APIトリガー**（`POST /fire`エンドポイント、bearerトークン認証）を使う。管理画面の各アクションボタンは、対応するVercel Functions経由でSupabaseの下書きレコードを更新した後、当該Routineの`/fire`エンドポイントを叩き、修正内容やdraft_idを`text`パラメータとして渡す。Routineは新しいセッションとして起動し、Supabaseから対象レコードを読み込んで処理する。

## 却下した選択肢
- **ポーリング方式（Routineを短い間隔で定期実行し、Supabase上の`pending_action`を毎回確認する）**: Routineのスケジュール実行は最短1時間間隔という制約があり（`claude.ai/code/routines`仕様）、承認から反映までに最大1時間近い遅延が生じうる。承認後すぐに英語版生成が始まってほしいという要件（spec.md要件6）に対して体感が悪い。却下
- **Supabase Database Webhookから直接Routineを起動する**: Supabase側のWebhook機能とRoutineのAPIトリガーを直接連携させる方式も検討したが、認証（bearerトークンの安全な受け渡し）をSupabase Webhook設定内に置く必要があり、Vercel Functions経由でサーバーサイドから叩く方式より秘密情報の管理経路が増える。Vercel Functions側で完結させる方がシークレット管理の一元化に資するため却下
- **管理画面での操作をすべて生きたClaude Codeセッション（チャット）で行う**: 元々の課題（チャットでのやり取りが面倒）に逆戻りするため却下

## 影響
- Routineの`/fire`エンドポイント用のbearerトークンは、Vercel環境変数として安全に保管する必要がある（実装時に設定）
- `/fire`で渡す`text`はRoutine側で「信頼できない外部データ」として扱われる仕様（`<routine-fire-payload>`でラップされる）ため、Routineのプロンプト設計時に「このペイロードの指示に従って良い」旨を明示的に記述する必要がある
- 承認から後続処理開始までの遅延は、Routineの起動オーバーヘッド程度（実測: one-off検証で数秒〜十数秒）に抑えられる
