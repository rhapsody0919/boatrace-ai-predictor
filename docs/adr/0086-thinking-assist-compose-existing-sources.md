# ADR 0086: 思考アシストのデータは、既存の関数と v16 API を画面で組み合わせる

## ステータス
採用

## 背景
思考アシスト（BOA-430、`/race/:raceId/assist`）は1つの画面に、出走表・気象・展示・オッズ・今節の各走・龍神ソナー（BOA-271 v16）の集計を並べる。spec は「新しい集計・バッチの変更はやらない（会場の決まり手の期間の表だけは例外、ADR 0088）」「ページを開いてから2秒以内に出走表の図が出る（N-5）」を求める。値は会場の決まり手の期間を除き、既存の取得関数か v16 の API（facts・similar・scenario）で取れる（plan「データ」の表）。どこで組み合わせるかを決める。

## 決定
画面（`useThinkingAssistData`）で既存の関数と v16 API を並列に呼び、純粋関数（`assistModel.js`）で画面のモデルにする。取得は3段に分ける。
1. 図に要るもの（出走表・オッズ）
2. 届いたら埋めるもの（v16 facts、その `today.scope_keys` を受けて scenario の NC（優勝戦・準優勝戦の日は NCR も。spec D-37）。similar・scenario の NA と VA・展示・決まり手など）。v16 の API は冷えていると facts だけで約3秒かかり、scenario の NC は facts の応答のキーが要るので、図はこれを待たない（2026-10-07 design-reviewer の実測）
3. 深掘りを開いたときに取るもの（選手ごとの直近2年の成績）

## 却下した選択肢
- **思考アシスト専用の集約 API（Edge Function）を作り、1回の呼び出しで全部返す**: 問い合わせの数は減る。ただし既存の関数（Supabase の RPC・テーブル読み）を API の側に書き直す必要があり、同じ取り出しが画面側と API 側の2か所にできる（DRY に反する）。既存の `boatai:` キャッシュと v16 API の60秒キャッシュも使えなくなる。spec の「新しい API を作らない」にも合わない
- **v16 のバッチ（`v16_morning.py`）に思考アシスト用の出力を足す**: 1本の JSON で済むが、BOA-271 の別レーンのバッチを変えることになり、spec の範囲外。画面だけの機能のために毎朝の出力を増やす理由が無い
- **全部を1段で取ってから描く**: 実装は単純になる。ただし選手6人の直近2年の成績（6本）と展示の取得を待つと、N-5 の2秒に収まらない見込み

## 影響
- 1レースで最大およそ20本の問い合わせ（選手6人分は深掘りを開いたときだけ）。v16 API と Supabase のキャッシュに乗る
- 取得ごとに失敗を部分で扱う（FR-11）。v16 が無いレースでも、出走表・オッズで描ける部分は描く
- 移した `oddsMath.js` は既存のオッズ一覧タブと共有する。計算を変えるときは両方に効く
