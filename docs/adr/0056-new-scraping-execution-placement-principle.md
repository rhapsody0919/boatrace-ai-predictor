# ADR 0056: 新規データ項目の実行基盤配置原則（レガシーGitHub Actions拡張 vs 新規Vercel Function）

## ステータス
採用

## 背景

[BOA-313](https://linear.app/boat-ai/issue/BOA-313)は、GitHub Actionsの`concurrency`直列化により処理が詰まると後続トリガーがキャンセルされ、時間に厳しいデータ（展示・結果・オッズ）の取得窓を逃す問題に対処するため、Vercel Serverless Functionsへの段階移行を進めている（Phase 1=展示、完了・並走検証中）。本specで新規に発見したデータ項目（[FR-1](./plan.md#fr-1-レース特記事項ページ)のレース特記事項等）を、どちらの実行基盤に置くべきかの一般原則を決める必要がある。個々のFRごとに都度議論すると判断がぶれるため、原則として1箇所に定める。

## 決定

**タイミング分類（T1〜T5）に応じて機械的に振り分ける**:

- **T1（発走直前ウィンドウ）**: 新規にレガシーGitHub Actionsオーケストレーター（`scrape-scheduled.js`）へ追加しない。既存のVercel Function群（BOA-313のパターン）に統合するか、Phase 2/3の完了を待って統合する（例: FR-4オッズ全券種）
- **T2（当日随時更新、ただし特定の狭い時間窓は無い）**: 新規の軽量Vercel Functionを作る（例: FR-1のレース特記事項、`api/cron/race-notices.js`）。cron-job.orgの間隔はT1より緩やかでよい（30分間隔等）
- **T4/T5（前日〜低頻度・静的）**: 新規のGitHub Actions定期ジョブでよい。BOA-313が問題にしているconcurrency構造の影響を受けない（1日1回〜半年に1回程度の頻度で、既存のレガシーオーケストレーターとは独立したワークフローにする）

## 却下した選択肢

**全て一律で既存レガシーオーケストレーターに追加する案**: 実装は最も簡単だが、T1相当の新規データを追加すると、BOA-313がまさに解決しようとしている「処理が詰まってキャンセルされる」問題を新しい対象で再現し、根本対策を骨抜きにする。却下。

**全て一律で新規Vercel Functionにする案**: T4/T5の低頻度データ（選手期別成績を半年に1回、会場個別サイトを日次〜週次等）まで全てVercel Functionに寄せる必然性は無く、GitHub Actionsの方が実装・監視の手間が小さい（既存のワークフロー管理の仕組みがそのまま使える）。低頻度データにVercel Functionの`CRON_SECRET`認証・cron-job.org側のジョブ管理を追加するのは過剰。却下。

## 影響

- FR-1（T2）は新規Vercel Function、FR-2/FR-5（T5）・FR-6（T4〜T5中心）は新規GitHub Actionsワークフローとして実装する（`plan.md`のFR-8マッピング表参照）
- FR-3当日分・FR-4（いずれもT1〜T2でBOA-313の既存Phase対象と重なる）は、BOA-313自体のPhase 2/3進捗に依存する形になる。他セッションの進捗次第で着手タイミングが変わる
- 将来新たに発見するデータ項目も、まずタイミング分類を行い、本ADRの原則に従って配置先を機械的に決める運用とする
