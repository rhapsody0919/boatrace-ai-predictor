# ADR 0041: 発走前の暫定検知の連続カウント方式

## ステータス
採用

## 背景
BOA-254 FR1で、`update-race-info.js`の「選手情報0人」検出（5分毎、発走1時間前ウィンドウ）を3回連続（15分間）検出した場合にのみ「暫定中止」として確定する方針が決まっている（一時的なスクレイピング失敗との誤検出対策）。この「連続」をどう判定するかを決める。

## 決定
`races.cancellation_check_streak`（SMALLINT、デフォルト0）による回数カウント方式を採用する。選手情報0人を検出するたびに+1し、3に達した時点で`cancellation_status = 'tentative'`に昇格する。選手情報が正常に取得できた場合は`cancellation_check_streak`を0にリセットする（`cancellation_status`が`'tentative'`であっても、正常検知が1回でもあれば`NULL`に戻す誤検出リカバリを行う）。

## 却下した選択肢
- **タイムスタンプ方式**（初回検知時刻を記録し、`now() - 初回検知時刻 >= 15分`かつ直近チェックでも0人、という時間ベース判定）: cron実行間隔がGitHub Actions側の遅延等で厳密に5分でない場合にも対応できる利点はあるが、「直近チェックでも0人」の判定と「経過時間」の判定を両方満たす必要があり実装がやや複雑になる。今回の合意事項（BOA-254）が「3回連続」という回数ベースの表現だったため、素直にカウンタ方式を採用する
- **Supabase RPC（DB側関数）による原子的なincrement**: 複数プロセスが同一レースの行を同時に更新する競合を避ける目的なら有効だが、`update-race-info.js`は同一実行内で1レースにつき1回しか処理せず、次の実行は前回の完了後になる想定のため、JS側での読み取り→計算→書き込みで実用上問題ない。既存の`update-race-info.js`も他の更新処理でRPCを使っておらず、一貫性の観点でも素直な実装を優先する

## 影響
- cron実行が何らかの理由でスキップされた場合（例: GitHub Actions障害）、「3回連続」の実際の経過時間は15分より長くなりうるが、確定を遅らせる方向のズレであり安全側（誤検出を避ける方向）に働くため許容する
- 会場間の処理は`update-race-info.js`内で1秒待機を挟みながら順次実行されるため、同一レースへの書き込みが競合することはない
