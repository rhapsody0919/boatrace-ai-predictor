# ADR 0022: 動画バイナリの長期保持戦略

## ステータス
採用

## 背景
生成した動画ファイルはSupabase Storageに保存される（ADR 0019）。投稿頻度・言語展開が増えるにつれ容量が増加し続けるため、何らかの保持ポリシーが要る。一方で、動画バイナリはデザイン・構成の視覚的な振り返り（AIレビュー・人間によるデザイン改善検討）に必要で、メタデータ（キャプション・指標等）だけでは代替できない。

## 決定
動画ファイルは**完全削除しない**。投稿済み（`posted`）は投稿から30日、却下・アーカイブ済み（`archived`）は7日を経過したら、Supabase Storage上のファイルを**低圧縮・低画質の軽量版に置き換える**定期Routineを新設する。軽量版は「見て振り返る」用途に十分な画質を保ちつつ元ファイルより大幅に小さいサイズとし、長期的に保持する。カバー画像/サムネ・DB上のメタデータは圧縮・削除の対象外で永続保持する。

## 却下した選択肢
- **一定期間経過後に完全削除**: 当初提案したが、視覚的な振り返りができなくなるためユーザー判断で却下（2026-08-27）
- **無期限にオリジナル画質のまま保持**: Supabase Pro（Storage 100GB）の現在の増加ペース（月1〜2GB程度）では数年単位の余裕があり、今すぐ容量問題が起きるわけではない。ただし将来的にYouTube展開・多言語フル展開（Phase 3）で投稿量が増えた際に無策で伸び続けるのは望ましくなく、先回りして軽量化の仕組みを用意する。無期限オリジナル保持は「今は良いが将来の手戻りが大きい」と判断し却下
- **クリーンアップ用Routineの構築をPhase 2以降に先送り**: 他のRoutineと同じ枠組みで作れるため、今作ってしまう方が手戻りが少ないとユーザー判断（2026-08-27）。却下（＝今回のスコープに含める）

## 影響
- 圧縮処理には動画エンコード（ffmpegでのビットレート・解像度削減）が必要。既にRoutine環境でのffmpeg利用は技術検証済み（2026-08-27のone-off spike、`spec.md`制約参照）のため、追加の技術リスクは小さい
- 「オリジナル画質」と「軽量版」を区別するため、`sns_drafts`テーブルに`video_tier`のような列を持たせる必要がある（`docs/design/sns-marketing-hub/plan.md`のデータ設計参照）
- 圧縮後は元の高画質ファイルは失われる（軽量版への置き換えは不可逆）。誤って早すぎるタイミングで軽量化されることのないよう、日数の起算点（`posted_at`/`archived_at`）を正確に記録する必要がある

## 追記（2026-08-31）: 汎用アーカイブ機能との相互作用

管理画面UX改善（`docs/design/sns-hub-admin-ux-improvements/`）で、下書きを任意のステータスから`archived`にできる汎用「非表示にする」ボタンを追加した際、`status='posted'`の下書きを非表示にすると保持期間が本ADRの`posted`用30日ルールから`archived`用7日ルールに意図せず短縮される問題が発覚した（PR #451で対応）。

対応は**フロント側の制限のみ**とした: `DraftCard`（`SnsHubAdmin.jsx`）で`status==='posted'`の場合はボタン自体を表示しない。`archive.js`のAPI自体は引き続きステータス制限を設けない汎用実装のまま（呼び出し元がこのボタンのみであることを確認済み）。将来、別の呼び出し経路が追加される場合はAPI側にも同様のガードを検討すること。
