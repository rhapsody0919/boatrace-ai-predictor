# ADR 0060: モーター単体集計（会場内ランキング・枠番別成績）はライブ計算とする

## ステータス
採用

## 背景

[BOA-301](https://linear.app/boat-ai/issue/BOA-301)（モーター単体の会場内比較・枠番別成績）の実装にあたり、集計をリクエスト時にライブ計算するか、日次バッチで事前集計してキャッシュ列/テーブルに保存するかを判断する必要があった。

[BOA-303](https://linear.app/boat-ai/issue/BOA-303)（`getVenueFirstWinRateRanking()`が全会場×全レースをライブスキャンしていた問題）により、本プロジェクトには「全会場横断の集計は日次バッチで事前集計する」という規約が既に存在する（`docs/design/scraping-full-coverage/plan.md`にも明記済み）。BOA-301の集計もこの規約の対象になるか判断が必要だった。

## 決定

BOA-301のFR-1（会場内ランキング）・FR-2〜4（枠番別・選手×モーター×枠成績）は、**いずれも「1会場×1モーター」に絞り込んだ範囲でのライブクエリとする**。事前バッチ集計は行わない。

理由: BOA-303が問題視していたのは「全24会場×全レース（約42,000行超）を90日分スキャンする」という**全件横断**のクエリだった。BOA-301のクエリはいずれも`WHERE venue_code = ? AND motor_number = ?`で絞り込まれており、対象行数は最大でも1モーターの半年〜1年分の出走数（数十〜数百行程度）に収まる。これは既存の`getRacerVenueStats`（1選手×全会場、同程度の絞り込み規模）と同種のスコープであり、この規模のクエリは本プロジェクトで既にライブ集計が許容されている前例がある。

## 却下した選択肢

**選択肢A: 全モーター×全会場を対象にした日次バッチ事前集計テーブルを新設する**
- 不適合点: 現時点でBOA-301が必要としているのは「特定の1モーターを見ているときのその場の集計」であり、全モーター分を毎日事前計算するのは過剰投資（表示されないモーターの分まで計算することになる）。BOA-303が指摘したパフォーマンス問題も発生しない規模のクエリに対して、事前集計特有のメンテナンスコスト（バッチジョブ・鮮度管理・失敗時のリカバリ）を負う理由がない

**選択肢B: リクエスト時にキャッシュ層（TTL付き）を挟む**
- 不適合点: 却下ではなく将来の拡張余地として保留。実装後、同一モーターへのアクセスが頻発し実際にDB負荷が問題になった場合に導入を検討する。現時点では計測前の最適化（premature optimization）になるため見送る

## 影響

- 新規テーブル・マイグレーション不要（`docs/design/boa-301-motor-venue-waku-stats/plan.md`参照）
- 実装がシンプルになる一方、将来的に「同一モーターへの同時多発アクセス」のような想定外の負荷パターンが出た場合は本ADRを見直す必要がある
- 「単一エンティティ（1選手・1モーター等）に絞り込んだ集計はライブ計算可、全件横断の集計は事前バッチ必須」という判断基準を、本プロジェクトの一般原則としてBOA-303に加えて明文化した（今後同種の判断に再利用できる）
