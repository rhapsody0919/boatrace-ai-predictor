# ADR 0072: 検証スクリプトは台帳で分類し、tier=ci はPRごとにまとめて自動実行する

## ステータス

採用（2026-09-25）

## 背景

「その場限りの修正ではなく恒常的な改修になっているか」をレビューする過程で、`scripts/maintenance/verify-*.js` の実態を測った。

### 実測（2026-09-25、全57本を実際に実行）

| 項目 | 値 |
|---|---|
| `verify-*.js` の本数 | 57本 |
| CIワークフローから実行されていたもの | **2本**（`verify-query-errors.js`＝PR時・パス限定、`verify-morning-digest.js`＝`generate-morning-digest.yml` が日次で実行）。**PRごとに走るのは1本** |
| `package.json` の `verify:*` npm scripts | 57個 |
| 環境変数なしで実行して成功 | 49本（逐次合計 151.8秒） |
| 失敗・タイムアウト | 8本 |

ほとんどのスクリプトは冒頭コメントに「DBにも取得先にも接続しない（フィクスチャ・偽クライアント・時計の差し替え）」と明記されており、**内容としては立派なユニットテストとして書かれている**。にもかかわらず、テストランナーにもCIにも載っておらず、実行されるのは「PRでそのスクリプトを書いた当日、手元で1回だけ」だった。

PRごとに走る検証ワークフローは他に `e2e-smoke-test.yml` と `verify-cache-config.yml`（`scripts/verification/` 配下を実行）があるが、`scripts/maintenance/verify-*.js` を呼ぶものは `verify-query-errors.yml` の1本だけだった。

`.claude/CLAUDE.md` は「実装完了後の自動レビュー」の4番に、該当する変更をしたら `npm run verify:sitemap` / `verify:content-index` / `verify:adr-numbers` / `verify:migration-numbers` / `verify:migration-rls` / `verify:er-diagram` / `verify:query-errors` を手元で実行するよう散文で列挙し、「CI連携はせず、毎回Claude自身が手元で実行する」と明記していた。

### 実際に起きたこと

この方式は実際に破れた。2026-09-25、PR #824 が `063_add_cancellation_status_to_today_races_rpc.sql` を追加した。当時の最大番号は 099 だったので本来は 100 を使うべきで、既存の `063_race_results_actual_course_kfile.sql` と番号が衝突していた。`verify-migration-numbers.js` はまさにこれを検知するために書かれており、実行すれば止まった。CIに載っていなかったため、誰も実行せず、重複したままmasterにマージされた。台帳（`APPLIED.md`）への記載も漏れていた。

失敗8本の内訳も、同じ構造の帰結だった。

| スクリプト | 状態 |
|---|---|
| `verify-migration-numbers.js` | **実在する番号重複を検知していた**（上記） |
| `verify-boatcast-job.js` | マイグレーション091が「未適用」であることを期待値にハードコード。091が適用された時点で壊れていた |
| `verify-pit-report-job.js` | 同上（086が「未適用」であることを期待。2026-09-23に適用されて壊れていた） |
| `verify-data-health-job.js` | 全検証に成功しても PGlite を close しておらずプロセスが終了しない（CIではタイムアウト） |
| 環境依存4本 | 実Supabase接続が必須で、そもそもCIに載せられない |

「壊れていること自体が誰にも気づかれない」ことが、この方式の本質的な問題である。

## 決定

1. **`scripts/maintenance/verify-registry.json` を単一の分類台帳とする。** 全 `verify-*.js` を `ci`（PRごとに自動実行）か `manual`（実DB等が必要で自動実行しない）に分類し、各エントリに「何を守るか」（`guards`）を1行で書く。`manual` には「なぜCIに載せないか」（`reason`）と実行コマンド（`command`）を必須にする。
2. **`npm run verify:ci` が台帳と実ファイルを突き合わせてから、`tier=ci` を並列実行する。** 未登録のスクリプトがあれば失敗する（分類漏れを構造的に止める）。逆に台帳にあってファイルが無い場合も失敗する。
3. **`.github/workflows/quality-gates.yml` が master向けPRごとに、およびmasterへのpush後に `npm run verify:ci` を実行する。** 旧 `verify-query-errors.yml` は統合して削除した。push時にも走らせるのは、masterにブランチ保護が無く "Require branches to be up to date" が効かないため、2つのPRが同じ時点のmasterに対して緑になり、片方のマージ後にもう片方が再検証されずにマージされうるから（063の番号重複はこの経路で入った）。
4. **CLAUDE.md からは個別コマンドの列挙を削除する。** 「該当する変更をしたら手元でこれを実行せよ」という散文の指示は、機械的に実行される仕組みに置き換える。機械検出できない2点（`content-index.json` の新規作成、`APPLIED.md` への行追加）だけを人の判断事項として残す。

### ファイルを移動せずレジストリ方式にした理由

`verify-*.js` を `ci/` `manual/` のサブディレクトリに物理的に分けると、`package.json` の57個のnpm scripts・各設計書・コード内コメントからの参照をすべて追随させる必要がある。得られるものは分類の可視化だけで、台帳1ファイルでも同じ可視化は得られる。KISS/YAGNIに従い、レジストリ方式を採る。

### 2層（ci / manual）にした理由

当初は「役目を終えた一度きりの移行検証」を `archived` として3層にする案だったが、実際に57本を精査すると、移行検証として書かれたもの（`verify-morning-init-refactor.js` など）も、リファクタ後のコードが壊れていないかの回帰テストとして今後も価値がある。現時点で `archived` に入れるべきものが1本も無いため、枠組みだけ先に作らない。

## 結果

- `npm run verify:ci` が52本を実行し、全件成功する状態にした（`manual` は5本）。
- 失敗していた4本（番号重複・台帳期待値のハードコード2本・PGliteのclose漏れ）を修正した。番号重複は `102_add_cancellation_status_to_today_races_rpc.sql` へのリネームと `APPLIED.md` への追記で解消した。
  - `verify-migration-numbers.js` は「既存の重複は `ALLOWED_DUPLICATES` に凍結」と「新規の重複は後発をリネーム」の2つの方針を持ち、今回のファイルは**新規かつ本番適用済み**で両方に当たる。リネームを選んだのは、凍結の理由である「リネームすると docs/design・ADR・コード内コメント・PR履歴からの参照が壊れる」が当てはまらないため（旧ファイル名をリポジトリ全体に grep したところ、参照は1件も無かった）。
  - このリネーム作業中に、当該マイグレーションが068の入れた4フィールド（`seriesDay`・`isFinalDay`・`raceTitle`・`raceStage`）と `LEFT JOIN race_conditions` を落としていることが判明した（本番実測で欠落を確認）。BOA-363と同型の回帰で、復旧は [BOA-431](https://linear.app/boat-ai/issue/BOA-431) で別途対応する。**当初この「適用済み」の判定を `cancellationStatus` の有無で行ったが、068も同じキーを入れるためこの観測では両者を区別できず、根拠として無効だった**（識別力のある `raceStage` を見ていれば、適用確認と同時に回帰も見えていた）。
- 新しい検証スクリプトを書いたら、レジストリに1エントリ足すことが強制される。足さなければCIが落ちる。
- **導入したその日に、この仕組みが実際に番号衝突を1件止めた。** PR #833 のレビュー中、並行して進んでいた PR #830 が `100_data_health_entries_duplicates.sql` をmasterに入れ、本PRの `100_add_cancellation_status_to_today_races_rpc.sql` と衝突した。`npm run verify:ci` がこれを検知して失敗したため、102へリネームして解消した。CI未接続のままなら、#824 と同じ経路でもう1件の重複がmasterに入っていた。**さらにその後、PR #832 が101番を入れたため102へ再度ずらしている。同日中に2回衝突した**ことになり、並行作業の密度に対してこの検査が常時動いている必要性を裏づけている。
- CLAUDE.md の「実装完了後の自動レビュー」4番が大幅に短くなり、AIが読むべき散文ルールが減った。

## 検討したが採らなかった案

- **vitest等のテストランナーへ全面移行する**: 独立レビューから「書き換えは不要で、レジストリを読んで `execFileSync` する薄いテストファイル1つで済む。並列制御・per-testタイムアウト・失敗時の全文表示・junitレポータによるGitHub Actions上の失敗アノテーション・`--changed` によるパス絞りが既製で手に入り、今回自作した3機能（並列キュー・タイムアウト・失敗出力）はすべてその再実装である」という反論を受けた。**この指摘は妥当で、実際に自作したランナーには3つの欠陥があった**（並列度がNaNになると全件スキップ、失敗時に末尾15行で ❌ 行が消える、全体タイムアウトの不整合）。いずれも本PR内で修正したが、同じ品質をゼロから保証し続けるコストは残る。
  それでも本件でランナー自作を選んだのは、(a) 57本は `npm run verify:*` として個別実行される既存の流儀があり、テストランナー経由に変えると手元実行の入口が二重になる、(b) `runner: bash` のような非JSスクリプトも同じ台帳で扱える、(c) 依存を増やさずNode標準だけで完結する、の3点。**ただしこれは強い理由ではない。ci層が100本を超える、あるいはパス絞り（U3）が必要になった時点で、vitestへの移行を再検討する。**新規のユニットテスト（施策C）にvitestを導入する場合は、その時点で本件のランナーも統合を検討する。
- **変更パスに応じて実行対象を絞る**: CI時間が問題になったら検討する。現時点では全件実行の単純さを優先する。
- **`manual` の5本を夜間ワークフローでsecrets付き実行する**: 本番DBへ接続するワークフローを増やすのは影響が大きいため、本件では分類と実行方法の記録に留める。**ただしこの先送りには実害が出た**: `verify-rpc-output-keys.js` は BOA-431（本番RPCからのキー欠落）を検知できる唯一のスクリプトだが、誰も実行していなかった。暫定策として、RPCを変更するマイグレーションを含む変更では本番適用後に手元実行することを CLAUDE.md に明記した。恒久策（読み取り専用の夜間ワークフロー＋Slack通知）は別チケットで検討する。
