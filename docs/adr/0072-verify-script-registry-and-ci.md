# ADR 0072: 検証スクリプトは台帳で分類し、tier=ci はPRごとにまとめて自動実行する

## ステータス

採用（2026-09-25）

## 背景

「その場限りの修正ではなく恒常的な改修になっているか」をレビューする過程で、`scripts/maintenance/verify-*.js` の実態を測った。

### 実測（2026-09-25、全57本を実際に実行）

| 項目 | 値 |
|---|---|
| `verify-*.js` の本数 | 57本 |
| CIワークフローから実行されていたもの | **1本**（`verify-query-errors.js`） |
| `package.json` の `verify:*` npm scripts | 57個 |
| 環境変数なしで実行して成功 | 49本（逐次合計 151.8秒） |
| 失敗・タイムアウト | 8本 |

ほとんどのスクリプトは冒頭コメントに「DBにも取得先にも接続しない（フィクスチャ・偽クライアント・時計の差し替え）」と明記されており、**内容としては立派なユニットテストとして書かれている**。にもかかわらず、テストランナーにもCIにも載っておらず、実行されるのは「PRでそのスクリプトを書いた当日、手元で1回だけ」だった。

`.claude/CLAUDE.md` は「実装完了後の自動レビュー」の4番に、該当する変更をしたら `npm run verify:sitemap` / `verify:content-index` / `verify:adr-numbers` / `verify:migration-numbers` / `verify:migration-rls` / `verify:er-diagram` / `verify:query-errors` を手元で実行するよう散文で列挙し、「CI連携はせず、毎回Claude自身が手元で実行する」と明記していた。

### 実際に起きたこと

この方式は実際に破れた。2026-09-25、PR #824 が `063_add_cancellation_status_to_today_races_rpc.sql` を追加した。当時の最大番号は 099 だったので本来は 100 を使うべきで、既存の `063_race_results_actual_course_kfile.sql` と番号が衝突していた。`verify-migration-numbers.js` はまさにこれを検知するために書かれており、実行すれば止まった。CIに載っていなかったため、誰も実行せず、重複したままmasterにマージされた。台帳（`APPLIED.md`）への記載も漏れていた。

失敗8本の内訳も、同じ構造の帰結だった。

| スクリプト | 状態 |
|---|---|
| `verify-migration-numbers.js` | **実在する番号重複を検知していた**（上記） |
| `verify-boatcast-job.js` | マイグレーション091が「未適用」であることを期待値にハードコード。091が適用された時点で壊れていた |
| `verify-pit-report-job.js` | 同上（086が「未適用」であることを期待。2026-09-23に適用されて壊れていた） |
| `verify-data-health-job.js` | 全検証に成功しても PGlite を close しておらずプロセスが終了しない（CIではタイムアウト） |
| 環境依存4本 | 実Supabase接続が必須で、そもそもCIに載せられない |

「壊れていること自体が誰にも気づかれない」ことが、この方式の本質的な問題である。

## 決定

1. **`scripts/maintenance/verify-registry.json` を単一の分類台帳とする。** 全 `verify-*.js` を `ci`（PRごとに自動実行）か `manual`（実DB等が必要で自動実行しない）に分類し、各エントリに「何を守るか」（`guards`）を1行で書く。`manual` には「なぜCIに載せないか」（`reason`）と実行コマンド（`command`）を必須にする。
2. **`npm run verify:ci` が台帳と実ファイルを突き合わせてから、`tier=ci` を並列実行する。** 未登録のスクリプトがあれば失敗する（分類漏れを構造的に止める）。逆に台帳にあってファイルが無い場合も失敗する。
3. **`.github/workflows/quality-gates.yml` が master向けPRごとに `npm run verify:ci` を実行する。** 旧 `verify-query-errors.yml` は統合して削除した。
4. **CLAUDE.md からは個別コマンドの列挙を削除する。** 「該当する変更をしたら手元でこれを実行せよ」という散文の指示は、機械的に実行される仕組みに置き換える。機械検出できない2点（`content-index.json` の新規作成、`APPLIED.md` への行追加）だけを人の判断事項として残す。

### ファイルを移動せずレジストリ方式にした理由

`verify-*.js` を `ci/` `manual/` のサブディレクトリに物理的に分けると、`package.json` の57個のnpm scripts・各設計書・コード内コメントからの参照をすべて追随させる必要がある。得られるものは分類の可視化だけで、台帳1ファイルでも同じ可視化は得られる。KISS/YAGNIに従い、レジストリ方式を採る。

### 2層（ci / manual）にした理由

当初は「役目を終えた一度きりの移行検証」を `archived` として3層にする案だったが、実際に57本を精査すると、移行検証として書かれたもの（`verify-morning-init-refactor.js` など）も、リファクタ後のコードが壊れていないかの回帰テストとして今後も価値がある。現時点で `archived` に入れるべきものが1本も無いため、枠組みだけ先に作らない。

## 結果

- `npm run verify:ci` が52本を実行し、全件成功する状態にした（`manual` は5本）。
- 失敗していた4本（番号重複・台帳期待値のハードコード2本・PGliteのclose漏れ）を修正した。番号重複は `100_add_cancellation_status_to_today_races_rpc.sql` へのリネームと `APPLIED.md` への追記で解消した。
- 新しい検証スクリプトを書いたら、レジストリに1エントリ足すことが強制される。足さなければCIが落ちる。
- CLAUDE.md の「実装完了後の自動レビュー」4番が大幅に短くなり、AIが読むべき散文ルールが減った。

## 検討したが採らなかった案

- **vitest等のテストランナーへ全面移行する**: 57本はそれぞれ独立したCLIとして書かれており、`check()` 関数・変異検証・出力形式まで各自で持っている。一括で `describe`/`it` に書き換えるのは大工事で、得られるのは実行の集約だけ。集約はランナー1本で達成できる。新規のユニットテストにvitestを使うかは別途判断する（本件のスコープ外）。
- **変更パスに応じて実行対象を絞る**: CI時間が問題になったら検討する。現時点では全件実行の単純さを優先する。
- **`manual` の5本を夜間ワークフローでsecrets付き実行する**: 本番DBへ接続するワークフローを増やすのは影響が大きいため、本件では分類と実行方法の記録に留める。
