# ADR 0057: オッズ取得の時間窓・全通り捕捉範囲の設計

## ステータス
採用

## 背景

[ADR-0054](./0054-odds-all-combinations-storage-format.md)で保存方式（jsonb列）は決めたが、**いつ・どの頻度で・どの券種を全通り捕捉するか**は精査していなかった。ユーザー指摘（2026-09-15）を受けて再検証した。

### 現状（既存`scrape-odds.js`）

`ODDS_WINDOWS = [60, 30, 15, 10, 5]`（分前、各±3分）のうち、**全120通り（`trifecta_all`）を保存するのは最も近い5分前の1窓のみ**（`FULL_ODDS_WINDOW = Math.min(...ODDS_WINDOWS)`）。他の4窓は単勝・複勝・3連単人気上位3つのみ。

### 見落としていた事実

`docs/proposal/DATA_ACQUISITION_STRATEGY.md`の既存分析（2026-09-14）は、日和のオッズ取得タイミング（`shimekiri: [0, 5, 10, 20, 30]`分前）と自社の`ODDS_WINDOWS`を比較し「本質的に同じ、むしろ自社の方が早期の1点を持つ分優れている」と結論していた。しかしこの比較は**「いつ取得するか」（時間窓の位置）のみ**を見ており、**「毎回何を取得するか」（全通りか一部か）**を見落としていた。実際には日和は`shimekiri`の**5点全てで3連単全120通りを保存**している（`各120件`と記録済み）のに対し、自社は5点中1点のみ。時間窓の数では互角以上でも、情報密度では日和の方が高い。

## 決定

**時間窓に0分（締切時点）を追加し、全通り捕捉の範囲を最も近い3窓（10分/5分/0分前）に拡大する**（3連単に加え、FR-4で新規実装する3連複・2連単・2連複・拡連複も同じ範囲で全通り捕捉する）。60分/30分/15分前の遠い窓は、既存通り単勝・複勝・人気上位のみに留める。

```
ODDS_WINDOWS = [60, 30, 15, 10, 5, 0]  （0分＝締切時点を追加）
FULL_ODDS_WINDOWS = [10, 5, 0]  （この3窓で全券種を全通り保存、既存の「1窓のみ」から拡大）
```

理由:
1. **締切直前（0分）のスナップショットが無いのは実務上のギャップ**。ユーザーがオッズ一覧タブを締切間際に見た場合、現状は5分前の値が最新になり、実際の締切時オッズとズレる可能性がある
2. **全通り捕捉を1窓→3窓に拡大することで、日和の「毎回全通り」に近い情報密度に引き上げつつ、6窓全てで全通りにするよりは負荷を抑えられる**。オッズの変動は締切に近いほど大きくなる傾向があるため、直近3窓に絞ることは費用対効果が高い
3. 負荷試算（180レース/日、6窓、5ページ/窓、約50ms/ページのcheerioパース時間換算）: 全通り捕捉を3窓に絞った場合のCPU増分は概算1.1〜1.5時間/月程度（6窓全てで全通りにする場合の半分程度）。既存の0.34時間/月と合わせてもVercel Hobbyの4時間/月枠に収まる見込み

## 却下した選択肢

**案A: 現状維持（全通りは最も近い1窓のみ、既存3連単と同じパターンをFR-4にも適用）**: 実装コストは最小だが、日和と比べて情報密度が明確に劣ったままになる。オッズ一覧タブ（BOA-311）の価値を大きく削ぐため却下。

**案C: 全6窓（60/30/15/10/5/0分）で全券種を毎回全通り捕捉**: 日和と同等以上の情報密度になるが、CPU増分が概算2.25時間/月（既存と合わせ約2.6時間/月、Hobby枠の約65%）に達し、余裕が大きく減る。また、boatrace.jpへのリクエスト数がオッズだけで1日約5,400件（現状の約3倍）に増え、**礼儀正しいスクレイピングの観点で妥当な負荷かが未検証**。将来のデータ蓄積量（jsonb列×6窓×5券種×毎日180レース）も他案より大きくなる。费用対効果が見合わないと判断し却下（ただし将来的にVercel Proへ移行しCPU予算に余裕ができた場合、または実際に「60分前のオッズ推移も見たい」という具体的なユーザー要望が出た場合は再検討の余地を残す）。

## 影響

- `scripts/daily/scrape-odds.js`の`ODDS_WINDOWS`・`FULL_ODDS_WINDOW`（単一値）を`FULL_ODDS_WINDOWS`（複数値の配列）に変更する必要がある
- 既存の3連単（`trifecta_all`）も本ADRの対象に含める（現状の1窓→3窓に拡大）。FR-4の新規4券種と同じタイミングで実装するのが効率的
- 0分窓の追加により、発走直前の取得成功率（レース開始と同時に締切＝ページ取得可能時間が極めて短い可能性）を実データで検証する必要がある。締切直後にページ内容が「投票締切」表示に切り替わるタイミング次第では、0分窓の狙い撃ちが技術的に難しい可能性があり、実装時に要確認（未確定事項として`plan.md`に追記）
- 負荷試算は概算であり、実装後にVercelのActive CPU実測値・boatrace.jp側のレスポンス状況を`docs/proposal/scraping-serverless-migration/investigation.md`と同じ手法で検証すること
