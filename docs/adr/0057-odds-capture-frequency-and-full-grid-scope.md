# ADR 0057: オッズ取得の時間窓・全通り捕捉範囲の設計

## ステータス
採用（2026-09-15改訂: ユーザー指摘により全通り捕捉範囲を3窓→6窓全部に拡大、オンデマンド更新を追加。旧版で却下していた「案C」を採用し直した）

## 背景

[ADR-0054](./0054-odds-all-combinations-storage-format.md)で保存方式（jsonb列）は決めたが、**いつ・どの頻度で・どの券種を全通り捕捉するか**は精査していなかった。ユーザー指摘（2026-09-15）を受けて再検証した。

### 現状（既存`scrape-odds.js`）

`ODDS_WINDOWS = [60, 30, 15, 10, 5]`（分前、各±3分）のうち、**全120通り（`trifecta_all`）を保存するのは最も近い5分前の1窓のみ**（`FULL_ODDS_WINDOW = Math.min(...ODDS_WINDOWS)`）。他の4窓は単勝・複勝・3連単人気上位3つのみ。

### 見落としていた事実

`docs/proposal/DATA_ACQUISITION_STRATEGY.md`の既存分析（2026-09-14）は、日和のオッズ取得タイミング（`shimekiri: [0, 5, 10, 20, 30]`分前）と自社の`ODDS_WINDOWS`を比較し「本質的に同じ、むしろ自社の方が早期の1点を持つ分優れている」と結論していた。しかしこの比較は**「いつ取得するか」（時間窓の位置）のみ**を見ており、**「毎回何を取得するか」（全通りか一部か）**を見落としていた。実際には日和は`shimekiri`の**5点全てで3連単全120通りを保存**している（`各120件`と記録済み）のに対し、自社は5点中1点のみ。時間窓の数では互角以上でも、情報密度では日和の方が高い。

## 決定

**時間窓に0分（締切時点）を追加した上で、全6窓（60/30/15/10/5/0分前）全てで全券種を全通り捕捉する**（3連単に加え、FR-4で新規実装する3連複・2連単・2連複・拡連複も同じ範囲で全通り捕捉する）。日和が5つの時間窓全てで全通り捕捉しているのに対し、自社は6窓（日和より早期の60分を含む）全てで全通り捕捉することになり、情報密度で上回る。

```
ODDS_WINDOWS = [60, 30, 15, 10, 5, 0]  （0分＝締切時点を追加）
FULL_ODDS_WINDOWS = [60, 30, 15, 10, 5, 0]  （全窓で全券種を全通り保存）
```

**加えて、スケジュール捕捉とは別に「オンデマンド更新」を新設する**: BOA-310/311のUI（オッズ検索/オッズ一覧タブ）に更新ボタンを設け、押された時点で該当レースのオッズを即座に取得し直すAPIエンドポイントを用意する。理由:

1. スケジュール捕捉は6窓（60分間隔で見ると最大60分の間隔が空く）だが、ユーザーが「今すぐの最新値」を見たい瞬間はこの間隔と一致するとは限らない
2. オンデマンド更新があれば、スケジュール捕捉の頻度をこれ以上際限なく上げる必要が無くなる（「見たい人はボタンを押せばいい」という設計で、バックグラウンドポーリングの負荷と鮮度要求を分離できる）
3. 日和自身も、出走表ページ読み込み時に`request_odds_shousai.php`へAJAXリクエストを発行する挙動が確認されており（`DATA_ACQUISITION_STRATEGY.md`参照）、同種の「ページアクセス時に最新値を取りに行く」設計を採用している可能性が高い

理由（全窓全通り化について）:
1. **締切直前（0分）のスナップショットが無いのは実務上のギャップ**。ユーザーがオッズ一覧タブを締切間際に見た場合、現状は5分前の値が最新になり、実際の締切時オッズとズレる可能性がある
2. **60分前から全通りで見えないと「見れる範囲が狭すぎる」というユーザー体験になる**。日和は5窓全てで全通りを保存しており、自社が3窓に絞ると明確に見劣りする
3. オンデマンド更新を併設することで、スケジュール捕捉自体は「基本の鮮度」を担保する役割に徹し、「今この瞬間」の要求はオンデマンド側で吸収する設計にできる

## 却下した選択肢

**案A: 現状維持（全通りは最も近い1窓のみ）**: 実装コストは最小だが、日和と比べて情報密度が明確に劣る。オッズ一覧タブ（BOA-311）の価値を大きく削ぐため却下。

**案B（2026-09-15の初回改訂前に採用していた案）: 全通り捕捉を直近3窓（10/5/0分）に限定**: 負荷を抑えつつ改善はできるが、「60分前くらいから全通りで見たい」というユーザー要望に応えられない。オンデマンド更新の追加によりバックグラウンド捕捉の負荷許容度が変わったため、今回不採用に変更。

## 影響

- `scripts/daily/scrape-odds.js`の`ODDS_WINDOWS`・`FULL_ODDS_WINDOW`（単一値）を全窓共通の`FULL_ODDS_WINDOWS`（`ODDS_WINDOWS`と同じ配列）に変更する必要がある
- 既存の3連単（`trifecta_all`）も本ADRの対象に含める（現状の1窓→6窓全部に拡大）。FR-4の新規4券種と同じタイミングで実装するのが効率的
- **新規のオンデマンド更新エンドポイント**（例: `api/odds/refresh.js`）を設計する。UIからの呼び出し頻度に上限を設け、連打による過剰リクエストを防ぐ設計にする。**ファン視点の検証（2026-09-15）により、クールダウンは締切からの残り時間に応じて可変にする**: 締切まで余裕がある時間帯は1分に1回程度で十分だが、**締切直前の数分間はファンが最も頻繁に確認する時間帯**のため、その時間帯だけクールダウンを10〜15秒に短縮する（具体的な閾値・秒数は実装時に確定）
- **セキュリティモデルはcron向けエンドポイントと別に設計する（[ADR-0059](./0059-new-endpoint-timeout-security-monitoring-standards.md)参照、天才エンジニア視点レビューで指摘）**: このエンドポイントはフロントエンドから不特定多数が直接呼び出す公開APIであり、`CRON_SECRET`（サーバー間の共有シークレット）は適用できない。IP単位のレート制限・パラメータ妥当性検証（実在する当日レースのみ受け付ける）を実装し、自社エンドポイントがboatrace.jpへの匿名プロキシとして悪用されることを防ぐ
- **負荷再試算（下記「負荷試算の再検討」参照）**: **2026-09-15確認、Vercelは既にProプランへ移行済み**。Proは従量課金でHobbyのような4時間/月のハード上限が無く、Cron Jobsも1分間隔・分単位精度で使える（cron-job.org依存を将来的に解消できる可能性もある）。そのためCPU予算超過を理由にこの設計を制限する必要は無い
- 0分窓の追加により、発走直前の取得成功率（レース開始と同時に締切＝ページ取得可能時間が極めて短い可能性）を実データで検証する必要がある。締切直後にページ内容が「投票締切」表示に切り替わるタイミング次第では、0分窓の狙い撃ちが技術的に難しい可能性があり、実装時に要確認（未確定事項として`plan.md`に追記）。**フォールバック設計（天才エンジニア視点レビューで指摘）**: 0分窓の取得が失敗した場合、直前の成功スナップショット（通常5分前）を「実質最終値」として扱い、エラーとして握りつぶさない。0分窓の失敗自体も[ADR-0059](./0059-new-endpoint-timeout-security-monitoring-standards.md)の監視対象に含める
- **データ保存期間の方針が未定だった（天才エンジニア視点レビューで指摘）**: 6窓×5券種×毎日約180レースで、年間相当数のレコードが蓄積される。当面は保存期間の上限を設けず運用し、実際のテーブルサイズ・Supabaseのストレージ使用率を監視した上で、必要になった時点でアーカイブ方針（例: 半年以上前の中間窓は0分・5分等の代表的な窓のみ残して間引く）を検討する。現時点でこれを理由に設計を変える必要は無いが、`/step3`のタスクに「ストレージ使用量の監視」を追加する

## 負荷試算の再検討（2026-09-15改訂）

180レース/日、6窓、5ページ/窓（単勝複勝+3連単+3連複+2連単2連複+拡連複、ページ構成は仮定）、約50ms/ページ（既存実測ベース）で概算:

```
180レース × 6窓 × 5ページ × 50ms = 270秒/日 × 30日 = 8,100秒/月 ≈ 2.25時間/月
既存の展示データ等（0.34時間/月）と合わせて ≈ 2.6時間/月 … 3窓案の場合
```

全窓（60/30/15/10/5/0分）で全通り捕捉する場合、上記試算はそのまま6窓分の値であり、**3窓案からの追加分は無い**（上記試算は既に6窓ベースで計算しているため）。ただし当初「3窓に絞った場合」の試算では6窓のうち3窓分しかページ取得しない前提だったため、実際には**当初の3窓案試算の約2倍**のCPU時間になる。

再計算: 3窓案（全通りは10/5/0のみ、60/30/15は単勝複勝＋人気上位のみで軽量）の概算が約1.1〜1.5時間/月だったのに対し、6窓案（全窓で全通り）は約2.25時間/月。既存分（0.34時間/月）と合わせて**約2.6時間/月、Hobbyの4時間/月枠の約65%**。

**訂正**: 当初「6窓全部だと4.8時間/月でHobby超過」とユーザーに伝えたが、上記の再計算では約2.6時間/月に収まる見込み（試算の前提を整理し直した結果）。**さらにVercelは既にProプランへ移行済みと判明したため、そもそもこのCPU予算制約自体が本設計を制限する理由にならない**。Proは従量課金でハード上限が無いため、後述のリクエスト数（礼儀正しさ）の観点だけが実質的な制約として残る。

ただし試算は概算であり誤差は大きいため、実装後の実測（Vercel Active CPU・料金への影響）は引き続き行うこと（`docs/proposal/scraping-serverless-migration/investigation.md`と同じ手法で検証）。リクエスト数（boatrace.jpへの負荷、1日あたり180×6×5=5,400件）は引き続き未検証で、礼儀正しいスクレイピングの観点で実測・監視が必要（Proプランへの移行はこの観点の制約を解消しない）。
