# ADR 0019: racer_profiles テーブルのスクレイピング取得範囲

## ステータス
採用

## 背景
racer-fortune-telling（Step1）は占術計算に生年月日のみを必要とする。一方、同じ`racer_id`をキーに選手基本情報を蓄積する`racer_profiles`テーブルは、racer-news-feature（選手個別ページ）でも支部・出身地・級別等の表示に使う設計を両spec.mdで共有する前提になっている。

boatrace.jp選手検索ページ（`/owpc/pc/data/racersearch/profile?toban={racer_id}`）を実際に取得して構造を確認したところ、`dl.list3`内に以下が1回のリクエストで同時に取得できることが判明した:

```
登録番号(4327) / 生年月日(1983/06/09) / 身長(159cm) / 体重(56kg) /
血液型(A型) / 支部(静岡) / 出身地(静岡県) / 登録期(96期) / 級別(B1級)
```

加えて`racer1_bodyName`（氏名）・`racer1_bodyKana`（カナ）も同ページ内にある。

対象は約1,637人（`race_entries`の distinct `racer_id`件数、2026-08-24時点）。レート制限を踏まえた1リクエストあたり数百ms〜1秒の間隔でも全件処理は十数分で完了する規模のため、「今回は生年月日だけ、支部等はracer-news-feature実装時に再度全1,637人をスクレイピングし直す」という選択肢は、同じ対象・同じページに対して二重にアクセスするだけの無駄なコストになる。

## 決定
生年月日だけでなく、`dl.list3`内で同時に見えている項目（氏名・カナ・身長・体重・血液型・支部・出身地・登録期・級別のスナップショット）もあわせて`racer_profiles`に保存する。ただし**本Step1で使うのは`birth_date`のみ**であり、他カラムは「将来のracer-news-featureのための保存」に留め、Step1のロジック（占術計算・相関検証）はbirth_date以外のカラムを一切参照しない。

## 却下した選択肢
- **A: 生年月日のみ保存し、他項目はracer-news-feature実装時に再取得する** — YAGNI原則には忠実だが、同一対象・同一ページへの再スクレイピングという明確に無駄な二重コストが発生する。1,637件全件へ再度アクセスすることになり、サイト運営者への負荷という点でも望ましくない
- **B: 生年月日以外の項目も含めて今回から`racer_profiles`をUIで使う** — スコープ外。Step1は「画面変更なし・バッチスクリプトのみ」であり、UI実装はracer-news-feature側のタスク。データの保存だけ済ませ、参照・表示はしない

## 影響
- `racer_profiles`のスキーマはracer-news-feature側の`/step2`で「そのまま使う」判断がしやすくなる（テーブルが既に存在し、必要項目も揃っている可能性が高い）
- 級別（`grade`）はスクレイピング時点のスナップショットであり、`race_entries.grade`（レース時点の級別、選手が昇降級すると変わる）とは意味が異なる。将来の混同を避けるため、カラム名は`grade_at_scrape`のように取得時点であることを明示する
- 生年月日以外のカラムがStep1で一切使われないまま保存されるため、取得失敗時の扱い（未確定事項参照）や鮮度管理（登録期・級別は時間が経つと古くなる）はracer-news-feature側の課題として持ち越す
