# ADR 0019: SNSマーケティングハブの運用データ保存先

## ステータス
採用

## 背景
SNSマーケティングハブ（`docs/design/sns-marketing-hub/`）は、Claude Code Routine（クラウド定期実行エージェント）が自律的に下書き（動画・キャプション等）を生成し、人間が管理画面で承認する運用フローを取る。この「運用データ（下書き・承認履歴・リスクチェック結果・エンゲージメント指標）」をどこに保存するかを決める必要がある。

boatAIには「全ての変更はPR経由で行う」という不変のルールがある。Routineはリポジトリの内容を変更する際、`claude/`prefixのブランチにpushする仕組みで、mainへの反映には人間のPRレビューが要る。

## 決定
運用データ（下書き・承認履歴・リスクチェック結果・エンゲージメント指標・テンプレートバリアントレジストリ）は**Supabaseのテーブル・Storageに保存する**。アプリのコード・ドキュメント変更は引き続きgit経由のPRレビューを維持し、日々の運用データはPRレビューを介さないSupabase書き込みとして扱う。

これはboatAIの既存アーキテクチャとも整合する。予測結果・レース結果等、他のランタイムデータも同様にSupabaseで管理されており、運用データをそこに置くことは既存パターンの延長。

## 却下した選択肢
- **git管理下のMarkdown/JSONファイル（現行の`sns-marketing-strategy.md`・`history.json`方式の延長）**: 人間のセッションが手動でファイルを更新する現行運用ではPRレビューを毎回挟むコストが許容できたが、Routineが自律的に高頻度で下書きを生成・更新する設計では、更新のたびにPRレビュー待ちが発生し自律ループが成立しない。却下
- **専用のバックエンドDB（Supabase以外の新規DBサービス）**: 新規インフラの学習・運用コストが発生し、既存のSupabase運用ノウハウ（RLS、マイグレーション運用等）を活かせない。コスト最小化の方針にも反する。却下

## 影響
- アプリのコード変更（Remotionコンポジション、Reactコンポーネント等）は引き続きPRレビューを経る。「デザインの見た目を変える」という判断は人間のレビューを通る一方、「今日は何を投稿するか」「エンゲージメントはどうだったか」という運用データはPRを介さずRoutineが直接読み書きする、という役割分担になる
- Supabaseの新規テーブル群にはRLSでpublicアクセスを許可しない（ADR 0021参照）。既存の公開データ用テーブルとはセキュリティプロファイルが異なる点に注意が必要
