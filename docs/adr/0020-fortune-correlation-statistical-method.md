# ADR 0020: 占術スコアと着順の相関検証手法

## ステータス
採用

## 背景
spec.md（[[racer-fortune-telling]]要件3）は、実データ確認の結果`race_results`に4〜6着データが無いことが判明したため、着順を「複勝圏内（1〜3着）か否か」の二値として扱う方針に変更済み。二値目的変数（複勝圏内フラグ）と占術スコア（数値、4占術間で比較可能な形式）の関係を統計的に検証する具体的な手法を、システム設計として決定する必要がある。

プロジェクトには汎用の統計・回帰ライブラリ（`simple-statistics`等）は導入されていない（`package.json`確認済み）。一方、`scripts/analysis/collect-venue-stats.js`に正規分布近似によるz検定（`binomialPValue`+`normalCDF`のAbramowitz-Stegun近似式）、`scripts/analysis/verify-threshold-logic.js`にPearson相関係数（`correlation`関数）の手書き実装が既に存在し、いずれも小さい自己完結コードで正しく動いている実績がある。

## 決定
以下の2手法を`scripts/lib/statisticalTests.js`に実装する。いずれも上記の既存実装パターン（正規近似・手書き実装、外部ライブラリ非依存）を踏襲する。

1. **占術スコア×複勝圏内フラグ**: スコアを5分位（quintile）でバケット化し、各バケットの複勝率を算出。全体の複勝率（ベースライン）に対して各バケットの複勝率が統計的に有意に異なるかを、二項比率の正規近似z検定（`collect-venue-stats.js`の`binomialPValue`と同一の考え方を汎用化した`proportionZTest`）で検証する
2. **占術スコア×ST（`start_timing`）**: 連続値同士のPearson相関係数を算出し（`verify-threshold-logic.js`の`correlation`と同一実装を`statisticalTests.js`に集約）、相関係数のp値は t統計量 `t = r√((n-2)/(1-r²))` を正規分布で近似して計算する（サンプル数が数万〜十万件規模のため、t分布と正規分布の差は無視できる）

## 却下した選択肢
- **ロジスティック回帰**: 複勝圏内フラグ（二値）に対する本来素直な手法だが、係数推定に反復最適化（Newton-Raphson等）の実装が必要で、収束判定・数値安定性のバグを作り込むリスクがある。今回はStep1の探索的検証（採用可否の一次判定）が目的であり、係数の正確な推定値自体は不要なため、過剰な実装コスト
- **カイ二乗独立性検定（分割表全体に対する検定）**: バケット×複勝有無の分割表全体が「独立でない」ことは示せるが、「どのバケットがどちら方向にどれだけ有意か」を読み取るには結局バケットごとの比率を見る必要があり、レポートとしての分かりやすさでは1バケットずつのz検定に劣る
- **外部統計ライブラリの新規導入**: 実装の正確性は上がるが、依存追加のコストに対してこの検証だけのために導入する理由が薄い。既存コードベースが手書き実装で一貫しているため、それに合わせる

## 影響
- `statisticalTests.js`は`collect-venue-stats.js`/`verify-threshold-logic.js`内の重複ロジックを吸収する形に将来的にはできるが、**既存ファイルの改修は本チケットのスコープ外**（触ると既存の分析結果の再現性を再検証する必要が生じ、過剰）。今回は新規ファイルとして追加するのみ
- サンプル数が少ないバケット（特定の生年月日パターンが稀な場合等）ではz検定の正規近似精度が落ちる可能性がある。レポートには各バケットのサンプル数を必ず併記し、Claudeが解釈を提案する際にサンプル数が少ないバケットの結果は割り引いて評価する
