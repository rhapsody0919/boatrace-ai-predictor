# ADR-0085: アナロジー・ファインダー（v16）の数えた値と類似レースは、朝の Python バッチで今日の分だけ作り Storage に置く

- 状態: 提案（BOA-271。spec の未確定 Q2・Q4 の回答と、design-reviewer の後に確定）
- 置き換えるもの: [ADR-0082](./0082-analogy-strata-counted-in-sql.md)（層別 S* を SQL の RPC で数える）。[ADR-0083](./0083-per-race-contribution-treeshap-in-js.md) のうち、レースごとの寄与度を画面に出す部分（Q2 で「やめる」と決まった場合）
- 関連: [ADR-0080](./0080-analogy-neighbors-precomputed-in-batch.md)（近傍のバッチ。v16 の類似レースは k-NN に戻ったので、考え方は近い）

## 背景
ユーザーがモック Version 16 を承認した（2026-10-04、`docs/design/analogy-finder/mock/APPROVED.md`）。画面の主役は数えた値になり、次の3つを出す。
- 来る艇の条件: 範囲（会場×級別の組み合わせ など）×艇番×項目×6艇中の順位×着順の件数
- 類似レース: そろえる条件の層の中を、寄与度用モデルの重みの距離で近い順に並べた k-NN（展示前・展示後）
- 展開シナリオ: 範囲×進入の型×スリットの形ごとの結果、平均STの手がかりの条件、攻める艇の表

条件に使う値の多くは、選手の過去の走から作る as-of の値（直近30走の1着率・平均ST、今節の平均着順点、コース別の平均ST）で、今は `scripts/ml/analogy/features.py` だけが作れる。ADR-0082 の SQL の母集団は出走表の値だけを条件にしていたので、この形では v16 を数えられない。

## 決定
1. 数える処理は Python（`features.py` と同じデータ。v16 の追加の値は `v16_defs.py`）で行う。SQL・JS に同じ計算を書き直さない
2. 朝のバッチは専用の workflow（`analogy-v16-morning.yml`、workflow_dispatch のみ）で、新しい Vercel Cron（JST 7:10・9:40・13:40、7:40 は拾い直し）から起動する。既存の日次の特徴量ジョブ（レースごとの寄与度用、一度も動いていない）には相乗りしない。今日のレースが使う範囲だけを数え、全範囲の集計表は作らない
3. 出力は非公開の Supabase Storage バケット `analogy-v16`（学習データ・モデルの入った `analogy` とは分ける）に gzip の JSON で、実行ごとの版のパス（`{日付}/{実行ID}/`）に書き、上書きしない。DB には時点の固定のメタデータ（`analogy_v16_snapshots`、レース×段、実行IDを指す）だけを置く。Storage を書き終えてから DB を書く
4. 類似レースの展示後の段は、専用の Vercel Cron（2分ごと。展示の取得の Cron のモードに依存しない）と展示の取得の後のフックから、Vercel の JS が、朝に作った候補（出走表時点の近い順 上位 min(層の件数, 10,000) 件）を、展示の項目の距離を足して並べ直す。距離²は項目の和なので候補の中では厳密に計算できる。候補の K 番目の出走表の距離²が並べ直した800番目の距離²以上なら結果は厳密で、snapshot に記録する。厳密でない近似の一致率は過去のレースで層の大きさ別に測る
5. API は Vercel の Node 関数で、service key で Storage のファイルを読んで返す。艇番・着順・進入・形の切り替えは画面で行う

## 理由
- as-of の値を SQL で作り直すと、`features.py` と2か所になり、ずれの検査（JS・Python・SQL のラウンドの規則で既に3か所あった）が増える
- 範囲×進入×形×結果の全組み合わせは数千万セルになる。今日のレースが使う範囲は1日 数百キーで足りる
- DB の容量・Disk IO を増やさない（1日 約40MB の出力を DB に入れると年 15GB）。Storage は CDN で読める
- Vercel では母集団全体（約40万レース×337次元）の距離計算はできない（メモリ・時間）。展示後に GitHub Actions を起動すると締切に間に合わない（ADR-0080 の検討）
- data-acquisition.md は新規の取得ジョブを Vercel に置くとしているが、これは外部サイトの取得ではなく、全期間の特徴量の計算（Python・数百MB のメモリ）なので、FR-1 の週次の学習と同じく GitHub Actions に置く。起動は Vercel Cron からの dispatch にして、GitHub の schedule の遅れ・欠落を避ける

## 結果
- 朝のバッチが失敗すると、その日の新しいレースは表示できない（拾い直しの 7:20・9:40・13:40 がある）。監視は既存の日次ジョブの Slack 通知と、夜の確認（`verify-analogy-v16.js`）
- 過去のレース（公開前）は表示できない（作り直しの CLI で日付を指定して作れるようにする）
- マイグレーション 120（未適用）は使わない。BOA-635 との行の渡し方は作り直す
- 展示後の段は近似を含みうる（決定4）。design-reviewer の簡易の再現では、候補 3,000件で一致率 平均 84.5%・6,000件で 95.7%（最大の層 58,119件）だったので 10,000件にした
