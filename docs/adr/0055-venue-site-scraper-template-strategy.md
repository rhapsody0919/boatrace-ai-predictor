# ADR 0055: 24会場公式サイトのスクレイパー設計（個別実装 vs CMSベンダー別テンプレート）

## ステータス
採用

## 背景

[BOA-293](https://linear.app/boat-ai/issue/BOA-293)〜[BOA-296](https://linear.app/boat-ai/issue/BOA-296)で24会場の個別公式サイトからデータを取得する必要があるが、24会場は複数のCMSベンダーに分かれていることが判明している（`docs/proposal/competitor-kyoteibiyori/data-coverage-comparison-2026-09-14.md`）: `/modules/`パス構成の共通CMS群（戸田・浜名湖・常滑・三国・尼崎・児島・若松・芦屋・唐津・下関等）と、レガシーな静的HTML/ASP構成群（住之江・桐生・江戸川・大村等）に大別される。24会場分を個別に1つずつスクレイパー実装するか、CMSベンダー単位でテンプレート化するかを決める必要がある。

## 決定

**CMSベンダー単位のテンプレート共有を優先し、テンプレート化できないサイトのみ個別実装する**方針を採用する。

理由:
1. 実装コストの削減。`/modules/`系CMS群は推定10会場前後が同一構造とみられ、1つのパーサーで大部分をカバーできる可能性が高い
2. 保守コストの削減。CMSベンダーがサイトリニューアルした場合、テンプレート単位で1箇所を直せば済む（[BOA-285](https://linear.app/boat-ai/issue/BOA-285)、HTML構造変化の自動検知の仕組みとも相性が良い）
3. 段階実装がしやすい。テンプレート1つを検証してから残りのサイトに展開できるため、リスクを抑えた進め方ができる

## 却下した選択肢

**24会場を個別に実装する案**: サイトごとの細かい差異に確実に対応できる利点はあるが、以下の理由で却下:
- 24個のスクレイパーを個別に保守するコストが高い
- 実際には`/modules/`系のように共通構造を持つサイト群があることが既に分かっており、個別実装は明らかな重複作業になる
- ゼロから全会場を並行実装するより、テンプレート化できる範囲を先に見極める方が手戻りが少ない

## 影響

- Phase 6a（`plan.md`参照）として、実装着手前に全24会場のCMS構造分類調査を行う工程を設ける。この調査結果次第でテンプレート化できる範囲・個別対応が必要な会場数が確定する
- テンプレート化できないサイト（レガシー静的HTML/ASP群）は個別実装が必要になり、当初の想定より工数がかかる可能性がある。Phase 6a完了後にtasks.mdで工数を見積もり直す
- 各会場のToS本文確認（spec.mdの未確定事項）は、CMSベンダー単位ではなく会場単位で必要になる点に注意（同じCMSでも運営主体が異なるためToSは共通ではない）
