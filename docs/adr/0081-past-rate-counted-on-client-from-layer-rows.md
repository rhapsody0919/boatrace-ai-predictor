# ADR 0081: 予想の過去発生率は、同じ条件の過去レースの新しい順最大2,000行を画面側で数え、予想は端末内に保存する

## 背景
BOA-635 は、ユーザーが入れた予想（6つの型）が、今日のレースと同じ条件の過去レースで何回起きたかを見せる。発走後は結果タブで、発走前に入れた予想を振り返る。

- v16 の層は、そろえる条件（1号艇の級別・勝率差の5段階・勝率トップの艇番、優勝戦・準優勝戦ならラウンド、G1・SG なら「G1以上」）が今日と同じ過去レースの全件。会場は含まない。大きさは中央値 7,286件・p90 58,119件
- 龍神ソナーはこの層の中を今日に近い順に並べ、800件まで見る（ADR-0085）。思考アシストは近い順400件で数える（ADR-0087）。どちらも画面で「類似レース」と呼ぶ
- ADR-0087 は思考アシストの数え方で「(B) 新しい順の2,000件（layer API）」を、期間がレースごとに3か月〜3年とばらつき「最近」の意味が一定しないとして却下した
- 発生率の分母が「何件まで見るか」の操作で変わってはいけない（BOA-635 の検証者の推奨）
- v16 の数えた値は Python のバッチで作り、Supabase Storage の非公開バケットに実行ごとのパスで書き、上書きしない（ADR-0085）。layer ファイルは gzip 後で最大約50KB
- 本番 Supabase は小さい計算リソースで、Disk IO Budget の枯渇の警告が出た実績がある（2026-09-19）
- 入力は組み合わせが多い（着順の流し、スリット7形×2段×2形、自分で作る 3^6 通り 等）
- 会員登録は無い。BOA-627 の保存項目3（ユーザーの読みと発走前の時刻）は「端末内でも可」とされている

## 決定
1. **比べる相手は v16 の層の新しい順最大2,000行（layer API）で、画面では「同じ条件の過去レース」と呼ぶ。** 問いが「この予想が過去にどれだけ起きたか」なので、今日に近い順に選ばず、そろえる条件が同じ過去レースを新しい順に数える。ADR-0087 が (B) を却下した理由（「最近」の意味が一定しない）は、最近の傾向を言う思考アシストには当たるが、本機能は最近の傾向を言わない。期間は注記に出す（切り詰めたら数えた行の最古の日〜前日）。龍神ソナー・思考アシストの「類似レース」とは選び方が違うので、呼び名を分ける
2. **数えるのは画面側（ブラウザ）の純粋関数。** 受け取った行を型ごとの判定関数で数える（`src/utils/pastRate/count.js`）。スリットの形は龍神ソナーと共用の `slitForms` に強さの段の引数を足して使う。取得はレースごとに1回で、ボタンを押しても通信しない
3. **取得は既存の layer API を使う。** `status` が `ok` 以外（`not_saved`・`empty_layer`・`absent`）では部品を出さない。切り詰めの判定は `n_returned < n_total`
4. **予想は localStorage に保存する**（キー `boatai-user:past-rate-check:v1`。1レース×1型につき最新1件、入力時刻から30日で消す、締切後は保存しない）。layer とは (raceId, runId) で紐づけ、run_id が違えば「入力したときから、同じ条件の過去レースが変わっています」を出す
5. 振り返りの「あなたの予想」の数字とラベルは、入力したときに見せた値を保存して出す。決着の行は今の layer ファイルの行から数える
6. 層の条件は出走表時点の値なので、展示後も racecard の段の layer ファイルを使う（API が stage を取らない）

## 却下した選択肢
- **龍神ソナーの近い順の上位 N 件（スライダーの件数）を分母にする**: 分母がスライダーで変わる。同じ予想でも、見る件数を変えるだけで「定番」「レア」が入れ替わる
- **思考アシストと同じ近い順400件で数える（ADR-0087）**: 「似ている順」の選び方は距離の重み（学習したモデル）で決まり、モデルを作り直すと同じレースでも分母の中身が変わる。「同じ条件の過去にどれだけ起きたか」という問いには、条件で決まる層の方が説明が単純
- **層の全行を返す**: v16 の層は最大約6万行。応答が数MB になり、モバイルで重い
- **SQL で数える（予想の型と入力を RPC の引数に渡す）**: ボタンを押すたびに層の全行を読む。読み取り量が利用者数×押した回数で増え、Disk IO の予算を圧迫する。v16 の層の条件は選手の過去の走から作る as-of の値を使うので、SQL に同じ計算を書き直すことになる（ADR-0085 の決定1に反する）
- **層の件数が上限以下のときだけ行を返し、超える層では機能を出さない**: 多くのレースで機能が出なくなる。「同じ条件の新しい2,000件」でも比べる意味は残るので、隠すより切り詰めて出す
- **無作為抽出で2,000行**: 新しい順より説明しにくい。新しい順なら「同じ条件の新しいレース」と言える
- **予想をサーバー（Supabase のテーブル）に保存する**: 会員登録が無いので端末ごとの匿名 ID が要り、匿名の書き込み（RLS で anon に INSERT）を開けることになる。プロジェクトの RLS 規律（匿名は SELECT のみ）に反する。端末をまたいだ振り返りはユーザーの要件に無い
- **sessionStorage / IndexedDB**: sessionStorage はタブを閉じると消え、翌日の振り返りができない。IndexedDB は件数（最大1,000件、数百KB）に対して過剰

## 影響
- 層が2,000件を超えるレース（大半のレース）では、割合は層の全体ではなく新しい2,000件（層によって数か月〜約3年分）で数えたものになる。主文は「同じ条件の新しい2,000レース中」と言い（2026-10-02 ユーザー承認）、注記の期間は数えた行の期間を出す。p=15% の標本誤差は N=2,000 で約0.8ポイント
- 層は会場を含まない。会場で 1コース1着率が 43〜63% と違うので、スリット・進入の割合が今日の会場からずれうる。定番／レアの線の検証（spec FR-3）で全国比の上積み（Brier skill）を測り、上積みが無い型はユーザーに戻す
- 同じレースで、龍神ソナー（類似レース）と本機能（同じ条件の過去レース）の割合は一致しない。呼び名を分けたのはそのため
- v16 の公開（2026-10-06 ごろ）より前のレース、締切後に作られたレース、保持期間（2年）を過ぎたレースは `not_saved` で、部品も振り返りも出ない
- 判定式は JS が正。定番／レアの線の検証（Python の分析スクリプト）は同じ式を Python に持つので、固定データで件数の一致を検査する
- 端末を変えた・ブラウザのデータを消した・30日を過ぎたときは、振り返りに「あなたの予想」が出ない（決着の行だけ出る）。仕様として受け入れる
- localStorage が使えない環境では、判定と表示だけ動き、保存と振り返りはしない
- 思考アシスト（BOA-430）には今回埋め込まない。判定・保存は React に依存しない純粋関数なので、後から呼べる
