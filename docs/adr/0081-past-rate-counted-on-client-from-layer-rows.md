# ADR 0081: 予想の過去発生率は、類似レースの層の新しい順最大2,000行を画面側で数え、予想は端末内に保存する

## ステータス
提案中（BOA-635 plan.md と同時。実装の着手で採用に変える）

改訂（2026-10-02）: 初版は BOA-271 FR-2 の k-NN の近傍800件（`get_analogy_neighbors`）を前提にしていた。FR-2 が層別 S*（勝率差5帯→1号艇の級別→会場→勝率1位の艇の4条件が同じ過去レース。使う層の件数は200〜約7万件で、中央値545件。深さ別の中央値は4条件 311・3条件 1,406・2条件 37,626・1条件 72,658。ADR-0082）に作り直され、`get_analogy_neighbors` は作られなくなった。FR-2 レーンと、行を返す RPC `get_analogy_similar_races` を足すことで合意し、本 ADR を書き直した。

## 背景
BOA-635 は、ユーザーが入れた予想（6つの型）が、今日のレースの類似レース（FR-2 の層）で過去に何回起きたかを見せる。発走後は結果タブで、発走前に入れた予想を振り返る。

- FR-2 の RPC `get_analogy_similar` は層の分布（件数）だけを jsonb で返し、行は返さない。予想の型（流し・スリット2形の AND・自分で作る 等）は分布から数えられない
- 層の件数は最大約7万件（2条件・1条件の層）。本番 Supabase は小さい計算リソースで、Disk IO Budget の枯渇の警告が出た実績がある（2026-09-19）
- 入力は組み合わせが多い（着順の流し、スリット7形×2段×2形、自分で作る 3^6 通り 等）
- 会員登録は無い。BOA-627 の保存項目3（ユーザーの読みと発走前の時刻）は「端末内でも可」とされている
- BOA-430（思考アシスト）の Step2・Step4 に同じ部品を埋め込む予定がある

どこで、どの行で数えるか、予想をどこに残すかを決める。

## 決定
1. **RPC `get_analogy_similar_races(p_race_id)`（BOA-271 FR-2 がマイグレーション119 に足す）が、自動の深さの層の過去レースを race_date の新しい順に最大2,000行返す。** 列は判定に要る8列だけ（race_date・1〜3着・決まり手・艇ごとの進入・コース順の ST・3連単の払戻）。行の外に、層の総件数・返した件数・深さ・条件・母集団の期間・スナップショットの有無と作成時刻を1回だけ返す。行の範囲はスナップショット時点の `pool_cutoff` 以前に固定する（発走後も同じ行の集合）。深さは自動に固定し、FR-2 の条件チップには追従しない
2. **数えるのは画面側（ブラウザ）の純粋関数。** 受け取った行を型ごとの判定関数で数える（`src/utils/pastRate/count.js`）。取得はレースごとに1回で、ボタンを押しても通信しない
3. **予想は localStorage に保存する**（キー `boatai-user:past-rate-check:v1`。データキャッシュの `boatai:` 名前空間は更新ボタンで全削除されるので重ねない。1レース×1型につき最新1件、入力時刻から30日で消す、締切後は保存しない）。スナップショットとは (raceId, snapshotAt) で紐づけ、深さ・`pool_cutoff`・層の総件数で行の集合の変化を検知する
4. 振り返りの「あなたの予想」の数字とラベルは、入力したときに見せた値を保存して出す。決着の行は今の RPC の返り値から数える

## 却下した選択肢
- **SQL で数える（予想の型と入力を RPC の引数に渡す）**: ボタンを押すたびに層の全行（最大約7万行）を読む。読み取り量が利用者数×押した回数で増え、Disk IO の予算を圧迫する。判定式が SQL・検証用の Python・画面の JS（要約・点数）の3か所に分かれ、型を足すたびにマイグレーションが要る
- **層の件数が上限（例 5,000）以下のときだけ行を返し、超える層では機能を出さない（FR-2 レーンの初案）**: 2条件・1条件の層（大きい層、全体の数%）で機能が出なくなる。大きい層ほど条件がゆるく、「同じ条件の新しい2,000件」でも比べる意味は残るので、隠すより切り詰めて出す。※初版では「層の中央値が約3.8万件なので大半のレースで出なくなる」と書いたが、3.8万は2条件の層だけの中央値で誤りだった（差分レビュー 2026-10-02 指摘1）
- **層の全行を返す**: 最大約7万行。応答が数MB になり、モバイルで重い
- **無作為抽出で2,000行**: 発走後に同じ行の集合を再現するには乱数の種の固定が要り、新しい順より説明しにくい。新しい順なら「同じ条件の新しいレース」と言える
- **予想をサーバー（Supabase のテーブル）に保存する**: 会員登録が無いので端末ごとの匿名 ID が要り、匿名の書き込み（RLS で anon に INSERT）を開けることになる。プロジェクトの RLS 規律（匿名は SELECT のみ）に反する。端末をまたいだ振り返りはユーザーの要件に無い
- **sessionStorage / IndexedDB**: sessionStorage はタブを閉じると消え、翌日の振り返りができない。IndexedDB は件数（最大1,000件、数百KB）に対して過剰

## 影響
- 層が2,000件を超えるレース（推測で全体の1〜2割）では、割合は層の全体ではなく新しい2,000件（約2〜5か月分）で数えたものになる。その場合の注記の期間は数えた行の期間を出す。p=15% の標本誤差は N=2,000 で約0.8ポイント、層の中央値 N=545 で約1.5ポイント。主文は「同じ条件の新しい2,000レース中」と言う（2026-10-02 ユーザー承認）
- 取得は FR-2 の `get_analogy_similar` と同じく Edge API を通し、CDN にキャッシュさせる（締切前 `s-maxage=300`、締切後 `86400`。NULL・エラーは `no-store`）。部品は AI予想タブの先頭に常に出るので、直接 RPC だと表示のたびに DB に届く（差分レビュー指摘7）。深さ1〜3用の索引は FR-2 レーンが119 に足した（PR #1134）。本番適用後に実行計画を見て、使われない索引は落とす
- 応答は gzip 後で約34KB（FR-2 レーンの試算。本番投入後に実測して gzip 後100KB を超えるなら1,000件に減らす）
- 判定式は JS が正。定番／レアの線の検証（Python の分析スクリプト）だけ同じ式を Python に持つので、固定データで件数の一致を検査する
- cutoff 以前の行が K/B 補完や実進入の後埋めで作り直された場合、振り返りの決着の行は今の値で数える（保存した「あなたの予想」の数字は入力時のまま）
- 端末を変えた・ブラウザのデータを消した・30日を過ぎたときは、振り返りに「あなたの予想」が出ない（決着の行だけ出る）。仕様として受け入れる
- localStorage が使えない環境では、判定と表示だけ動き、保存と振り返りはしない
- BOA-430 は `PastRateChecker` を props（`types`・`value`/`onChange`・`persist`）で絞って埋め込む。データは `useAnalogySimilarRaces` を共有する
