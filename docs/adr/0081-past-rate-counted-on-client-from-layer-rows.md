# ADR 0081: 予想の過去発生率は、類似レースの層の新しい順最大2,000行を画面側で数え、予想は端末内に保存する

## ステータス
提案中（BOA-635 plan.md と同時。実装の着手で採用に変える）

改訂の経緯:
- 初版（2026-10-02）は BOA-271 FR-2 の k-NN の近傍800件（`get_analogy_neighbors`、マイグレーション115）を前提にした
- 第2版（2026-10-02）は FR-2 の層別 S*（マイグレーション119／120 の `get_analogy_similar_races`、会場を含む4条件の自動の深さの層）を前提にした
- 第3版（2026-10-04、本版）: BOA-271 がモック v16 に書き直され（PR #1134、ADR-0085）、120 は本番に適用せず置き換えられた。v16 の朝のバッチが BOA-635 用に層の全件の結果（新しい順最大2,000件）のファイルを作ることで、オーケストレーター経由で合意した

## 背景
BOA-635 は、ユーザーが入れた予想（6つの型）が、今日のレースの類似レースの層で過去に何回起きたかを見せる。発走後は結果タブで、発走前に入れた予想を振り返る。

- v16 の類似レースは、そろえる条件（1号艇の級別・勝率差の5段階・勝率トップの艇番、優勝戦・準優勝戦ならラウンド、G1・SG なら「G1以上」）で絞った層の中を、似ている順に並べる k-NN。画面は件数スライダー（10〜800件）で見る件数を変える
- 発生率の分母が「何件まで見るか」のスライダーで変わってはいけない（BOA-635 の検証者の推奨）。似ている順の上位 N 件を分母にすると、類似度の順位で分母が決まる
- v16 の層は会場を含まない。大きさは中央値 7,286件・p90 58,119件
- v16 の数えた値は Python のバッチで作り、Supabase Storage の非公開バケットに実行ごとのパスで書き、上書きしない（ADR-0085）
- 本番 Supabase は小さい計算リソースで、Disk IO Budget の枯渇の警告が出た実績がある（2026-09-19）
- 入力は組み合わせが多い（着順の流し、スリット7形×2段×2形、自分で作る 3^6 通り 等）
- 会員登録は無い。BOA-627 の保存項目3（ユーザーの読みと発走前の時刻）は「端末内でも可」とされている
- BOA-430（思考アシスト）の Step2・Step4 に同じ部品を埋め込む予定がある

## 決定
1. **v16 の朝のバッチが、今日の各レースについて `layer/{race_id}.json.gz` を作る**（BOA-271 側の作業）。中身は、v16 の層（スライダーではなく、そろえる条件の層）の過去レースを race_date の新しい順（同じ日は race_id の降順）に最大2,000行。列は判定に要る8列だけ（race_date・1〜3着・決まり手・艇ごとの進入・コース順の ST・3連単の払戻）。行の外に、層の総件数・返した件数・母集団の期間・層の条件・run_id を1回だけ持つ
2. **数えるのは画面側（ブラウザ）の純粋関数。** 受け取った行を型ごとの判定関数で数える（`src/utils/pastRate/count.js`）。取得はレースごとに1回で、ボタンを押しても通信しない
3. **予想は localStorage に保存する**（キー `boatai-user:past-rate-check:v1`。データキャッシュの `boatai:` 名前空間は更新ボタンで全削除されるので重ねない。1レース×1型につき最新1件、入力時刻から30日で消す、締切後は保存しない）。スナップショットとは (raceId, runId) で紐づけ、run_id が違えば「類似レースが変わっています」を出す
4. 振り返りの「あなたの予想」の数字とラベルは、入力したときに見せた値を保存して出す。決着の行は今の layer ファイルの行から数える
5. 層の条件は出走表時点の値なので、展示後も racecard の段の layer ファイルを使う

## 却下した選択肢
- **FR-2 の似ている順の上位 N 件（スライダーの件数）を分母にする**: 分母がスライダーで変わる。同じ予想でも、見る件数を変えるだけで「定番」「レア」が入れ替わる
- **層の全行を返す**: v16 の層は最大約6万行。応答が数MB になり、モバイルで重い
- **SQL で数える（予想の型と入力を RPC の引数に渡す）**: ボタンを押すたびに層の全行を読む。読み取り量が利用者数×押した回数で増え、Disk IO の予算を圧迫する。v16 の層の条件は選手の過去の走から作る as-of の値を使うので、SQL に同じ計算を書き直すことになる（ADR-0085 の決定1に反する）
- **層の件数が上限以下のときだけ行を返し、超える層では機能を出さない**: v16 の層は中央値 7,286件で、上限を数千件にすると多くのレースで機能が出なくなる。大きい層ほど条件がゆるいが、「同じ条件の新しい2,000件」でも比べる意味は残るので、隠すより切り詰めて出す
- **無作為抽出で2,000行**: 新しい順より説明しにくい。新しい順なら「同じ条件の新しいレース」と言える
- **予想をサーバー（Supabase のテーブル）に保存する**: 会員登録が無いので端末ごとの匿名 ID が要り、匿名の書き込み（RLS で anon に INSERT）を開けることになる。プロジェクトの RLS 規律（匿名は SELECT のみ）に反する。端末をまたいだ振り返りはユーザーの要件に無い
- **sessionStorage / IndexedDB**: sessionStorage はタブを閉じると消え、翌日の振り返りができない。IndexedDB は件数（最大1,000件、数百KB）に対して過剰

## 影響
- 層が2,000件を超えるレース（v16 の層の大きさから、大半のレース）では、割合は層の全体ではなく新しい2,000件（数か月〜約2年分）で数えたものになる。主文は「同じ条件の新しい2,000レース中」と言い（2026-10-02 ユーザー承認）、注記の期間は数えた行の期間を出す。p=15% の標本誤差は N=2,000 で約0.8ポイント
- 層は会場を含まない。会場で 1コース1着率が 43〜63% と違うので、スリット・進入の割合が今日の会場からずれうる。定番／レアの線の検証（spec FR-3）で全国比の上積み（Brier skill）を測り、上積みが無い型はユーザーに戻す
- 応答の大きさは、2,000件で gzip 後 100KB を超えたら1,000件に下げる（BOA-271 側が初回に実測）
- 取得の経路（BOA-635 の `/api/analogy/layer/[raceId]` か、FR-2 の API への相乗りか）は BOA-271 側が決める。Storage が非公開なので、どちらも service key で読む API を通す
- 判定式は JS が正。定番／レアの線の検証（Python の分析スクリプト）は v16 の `v16_defs.py` と同じ層の選び方で作り、同じ式を Python に持つので、固定データで件数の一致を検査する
- 端末を変えた・ブラウザのデータを消した・30日を過ぎたときは、振り返りに「あなたの予想」が出ない（決着の行だけ出る）。仕様として受け入れる
- localStorage が使えない環境では、判定と表示だけ動き、保存と振り返りはしない
- BOA-430 は `PastRateChecker` を props（`types`・`value`/`onChange`・`persist`）で絞って埋め込む
