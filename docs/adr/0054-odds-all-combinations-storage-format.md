# ADR 0054: オッズ全券種の保存方式（JSON列 vs 正規化テーブル）

## ステータス
採用

## 背景

[BOA-314](https://linear.app/boat-ai/issue/BOA-314)で3連複・2連単・2連複・拡連複の全通りオッズを新規取得する際、保存方式を決める必要がある。1レースあたりの組み合わせ数は券種により異なる（3連単/3連複=120通り、2連単/2連複=15通り、拡連複=15通り）。既存の3連単全120通りは`race_odds.trifecta_all`というJSON列（[BOA-104](https://linear.app/boat-ai/issue/BOA-104)）に保存されている。

## 決定

**既存の`trifecta_all`と同じJSON（jsonb）列方式を新規4券種にも採用する**（`trio_all`/`exacta_all`/`quinella_all`/`wide_all`）。

理由:
1. 既存パターンとの一貫性。`trifecta_all`が既に本番で稼働しており、同じ設計を踏襲することで実装・レビューのコストが下がる
2. 正規化した場合、券種×組み合わせ×レース×スナップショット時刻の全組み合わせで行数が急増する（1レースあたり最大120行×5券種×複数スナップショット）。JSON列なら1レコード（1スナップショット時点）に1券種分をまとめて格納でき、行数の爆発を避けられる
3. オッズ全通りは「その時点のスナップショット」という単位でしか意味を持たず、個々の組み合わせを行として検索する用途（特定の組み合わせだけを頻繁にクエリする等）が現状想定されていない。JSON列で十分

## 却下した選択肢

**正規化テーブル案**（`race_odds_combinations`のような、レースID×券種×組み合わせ×オッズ値×取得時刻を1行とするテーブル）: 個々の組み合わせに対するSQL側でのフィルタ・集計がしやすい利点はあるが、以下の理由で却下:
- 行数がJSON列方式に比べて桁違いに増える（既存の`trifecta_all`導入時にも同じ議論があったと推測され、JSON列が選ばれた実績がある）
- 現状のユースケース（オッズ一覧タブでの表示、[BOA-311](https://linear.app/boat-ai/issue/BOA-311)）はレース単位で全組み合わせを一度に表示するため、JSON列を1回読んでアプリ側で展開する方が素直
- 将来的に組み合わせ単位での横断分析（例: 特定の目の全レース平均オッズ推移）が必要になった場合は、その時点で別途集計テーブルを作る方が、最初から正規化するより要件に即した設計にできる

## 影響

- `scripts/lib/oddsParser.js`に`parseExactaAll`/`parseQuinellaAll`/`parseWideAll`を追加する際、`parseTrifectaAll`/`parseTrioAll`と同じ戻り値形式（組み合わせ文字列をキーにしたオブジェクト）に揃える
- `race_odds`テーブルへのカラム追加はマイグレーションで対応（`docs/db-migration/062_race_odds_all_combinations.sql`草案）
- 将来、組み合わせ単位の横断分析が必要になった場合は改めてADRを起票し直す
