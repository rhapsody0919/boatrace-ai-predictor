# ADR 0082: 類似レース（層別 S*）は、条件の列を持つ母集団を SQL の RPC で数える

## ステータス
提案中（BOA-271 FR-2 の作り直し。設計レビューと BOA-635 のレーンとの合意の後に採用に変える）。[ADR-0080](./0080-analogy-neighbors-precomputed-in-batch.md) の FR-2 の部分（近傍のバッチ・Storage の行列・近傍の起動）を置き換える。ADR-0080 のうち、寄与度（FR-1）の週次学習を Vercel Cron から workflow_dispatch で起動する部分（決定3の学習分）はそのまま残る

## 背景
2026-10-02、FR-2 の方式が k-NN から**層別 S***に変わった（ユーザー決定、spec MD-6・FR-2）。今日のレースと次の4条件がすべて同じ過去レースを集め、決着の分布を出す。

| 順 | 条件 | 定義（`scripts/ml/analogy/features.py` と分析 `scripts/analysis/analogy-finder-fr2-strat/cm2.py`） |
|---|---|---|
| 1 | 1号艇と他艇の勝率差5帯 | 1号艇の全国勝率 − 2〜6号艇の全国勝率の最大。境界 −1.91／−1.14／−0.49／+0.19（`searchsorted(side='right')`＝境界ちょうどは上の帯）。勝率が取れない艇しかいないときは「不明」帯 |
| 2 | 1号艇の級別 | A1／A2／B1／B2（不明は 0） |
| 3 | 会場 | 会場コード |
| 4 | 勝率1位の艇 | 全国勝率が最大の艇番。同率は艇番の小さい方 |

200件未満の層は末尾の条件から外して親の層を使う（m=200）。使う層は 4条件 70.5%・3条件 27.2%・2条件 2.3%（test）。層の大きさは 4条件の中央値 311、3条件 1,406、2条件 37,626、1条件 72,658。

ADR-0080 は「今日のレースの as-of 特徴量（ローリング集計を含む337次元）と全母集団との距離」を前提に、Python のバッチ・Storage の行列・GitHub の dispatch を置いた。層別では距離も順位も要らず、条件の値は出走表の勝率・級別・会場だけで決まる。

読み取りで確かめたこと（本番、2026-10-02）:
- 今日の168レースの4条件を `races`・`race_entries` から SQL で作れた（6艇の勝率がそろわないレース0件、級別は A1〜B2 のみ）。実行 3ms
- 2条件の層に相当する約4万レースの決着の集計（決まり手・1着艇・3連単の組み合わせ120通り）を、結合と全件走査つきで 127ms。条件の列と索引を持つ表なら、これより速い
- 取得済みデータの DB 内集計を Vercel Cron から SQL の RPC で回す前例がある（`api/cron/racer-course-technique-stats.js`、ADR-0066 改訂1。モード off／shadow／live と `scrape_job_state` での監視つき）

## 決定
1. **FR-2 の分布は、表示のたびに SQL の RPC で数える。** 近傍のバッチ（`neighbors.py`・`generate-analogy-neighbors.yml`）、Storage の母集団行列（`pool.py`）、FR-2 用の dispatch は作らない。FR-2 は Python にも GitHub Actions にも依存しない
2. **母集団 `analogy_pool_outcomes` に条件の4列を持たせ、SQL で作る。** 長期分（2019-04〜2025-12-02）は `kb_archive_*` から、以後は本体（`races`・`race_entries`・`race_results`・`race_start_timings`）から、SQL 関数で行を作って upsert する。勝率差の帯は IMMUTABLE な SQL 関数1つ（`analogy_gap_band`）に境界を持たせ、生成列にする。索引は条件の順の複合索引 `(gap_band, b1_class, venue_code, top_boat)` で、どの深さの層も先頭一致で引ける
3. **母集団の更新は Vercel Cron の1ジョブ（`analogy-strata`）で、1日3回（JST 7:30・10:00・14:00）。** 直近7日を作り直して変わった行だけ upsert し（結果の訂正と、K ファイル同期 07:00・12:00 が後から埋める実進入を拾う）、続けて今日のレースのスナップショットを作る。長期分の初回投入は、ユーザーが月ごとに SQL 関数を呼ぶ（本番への書き込みはユーザーが行う）
4. **スナップショット（BOA-627）は、条件の値・使った深さ・深さごとの件数・母集団の最終日（`pool_cutoff`）だけを保存する。** 分布そのものは保存せず、表示のときに `race_date <= pool_cutoff` で数え直す。締切前・中止でない・6艇そろったレースだけを作り、1レース1行（`ON CONFLICT DO NOTHING`）。スナップショットが無いレース（締切までに作れなかった等）は、その場で条件を作り、前日までの母集団で数え、「発走前の保存なし」を返す
5. **母集団の値の約束（BOA-635 の依頼 R1〜R4・D-5・D-6）は ADR-0080 のまま引き継ぐ。** 3連単は本体の `payout_trio` から、F・出遅れ・欠場の ST は NULL、不成立・特払いの払戻は NULL、実進入不明は NULL、不成立と1〜3着に返還艇が入るレースは母集団に入れない、スナップショットは1レース1つ
6. **画面に出す割合は、その層の件数を数えたままの値（件数÷n）にする。** 分析で選んだ親の層への平滑化（α'=50）は表示に使わない。spec の文面ルール4（件数が主役）と、画面の数字を実データの件数で照合できることを優先する。平滑化の有無の精度差は test で有意でない（+0.00073 [−0.00025, +0.00183]）
7. **条件のチップは末尾からだけ外せる**（会場を残して級別だけ外す、のような組み合わせは作らない）。検証したのは条件の順に外す戻し方だけで、索引の先頭一致もこの順で効く

## 却下した選択肢
- **ADR-0080 のまま（近傍を Python のバッチで作り、Storage に行列）**: 層別には不要な距離計算と、遅れの多い起動経路（Vercel→GitHub）・トークン・Storage の版管理を抱える。層の件数は SQL の索引で直接数えられる
- **母集団を週次の学習ジョブ（Python、features.py）で作る**: 条件の定義が features.py と1か所になる利点はあるが、母集団が最大7日古くなり、学習ジョブ（起動の仕組みが未実装）が止まると FR-2 も止まる。SQL と features.py の定義の二重化は、検証スクリプトで両者の行の集合と条件の値を突き合わせて固定する（下の影響）
- **表示のたびに母集団を元テーブルから集計する（条件の列を持たない）**: 1件ごとに約240万艇行から作り直すことになり、2秒以内の要件を満たせない
- **分布をスナップショットに保存する**: 深さごと・組み合わせ（最大120通り）・コールアウト用の表まで持つと1レース約12KB、1年で約0.6GB。数え直しとの差は、後から埋まる実進入（1着の進入コースの分布だけ）と結果の訂正に限られる
- **スナップショットを画面の表示時に匿名の RPC で書く**: 匿名ロールに書き込みを開けることになり、プロジェクトの RLS 規律（匿名は SELECT のみ）に反する
- **4条件の任意の組み合わせを外せるチップ**: 検証していない層（16通り）を出すことになり、「親の層」の意味も崩れる

## 影響
- 本番 DB の書き込みは、マイグレーション（母集団・スナップショット・関数）の適用と、長期分の初回投入。どちらもユーザーが行う。Vercel の環境変数（GitHub のトークン）は FR-2 には要らない（FR-1 の週次学習の dispatch には ADR-0080 どおり要る）
- 条件の定義が SQL と `features.py` の2か所になる。`scripts/maintenance/verify-analogy-pool.js`（manual）で、features.py が作る完全レースの集合と母集団の行の集合、条件4つの値が一致することを本番データで検査する
- 勝率差の帯の境界を変えるときは、生成列を作り直すマイグレーションが要る（境界は分析で確定した値で、変える予定は無い）
- スナップショットの再現は「数え直し」なので、`pool_cutoff` 以前の行が後から変わると件数・分布がずれうる。`verify-analogy-pool.js` でスナップショットの件数と数え直しの件数の一致率を出す
- BOA-635 は近傍800件の行（`get_analogy_neighbors`）を画面で数える前提で設計している（ADR-0081）。層別では層の大きさが 200〜7万件と幅があり、行をそのまま渡せない深さがある。RPC の名前と返り値は BOA-635 のレーンと合意してから確定する（plan.md「RPC」）
- 応答時間は、母集団の投入後に4つの深さそれぞれで実測する（tasks）
