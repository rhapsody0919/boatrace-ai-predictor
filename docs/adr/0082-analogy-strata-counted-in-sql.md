# ADR 0082: 類似レース（層別 S*）は、条件の列を持つ母集団を SQL の RPC で数える

## ステータス
提案中（BOA-271 FR-2 の作り直し）。[ADR-0080](./0080-analogy-neighbors-precomputed-in-batch.md) の FR-2 の部分（近傍のバッチ・Storage の行列・近傍の起動）を置き換える。ADR-0080 のうち、寄与度（FR-1）の週次学習を Vercel Cron から workflow_dispatch で起動する部分（決定3の学習分）はそのまま残る。

採用に変える条件は次の3つ:
- BOA-635 の BOA-635 の ADR 案（PR #1093）（近傍800行を画面で数える）の改訂、または置き換え。下の「影響」を参照
- 決定6（表示の割合）のユーザー確認
- 設計レビュー（design-reviewer）

## 背景
2026-10-02、FR-2 の方式が k-NN から**層別 S***に変わった（ユーザー決定、spec MD-6・FR-2）。今日のレースと次の4条件がすべて同じ過去レースを集め、決着の分布を出す。

| 順 | 条件 | 定義 |
|---|---|---|
| 1 | 1号艇と他艇の勝率差5帯 | 1号艇の全国勝率 − 2〜6号艇の全国勝率の最大。境界 −1.91／−1.14／−0.49／+0.19。1号艇の勝率が無い、または2〜6号艇の勝率がすべて無いときは「不明」帯 |
| 2 | 1号艇の級別 | A1／A2／B1／B2（不明は空） |
| 3 | 会場 | 会場コード |
| 4 | 勝率1位の艇 | 全国勝率が最大の艇番。同率は艇番の小さい方 |

勝率・級別の元は、長期（〜2025-12-02）が `kb_archive_boats.national_win_rate`・`class`、以後が `race_entries.win_rate`・`grade`（`scripts/ml/analogy/features.py` と同じ）。帯と勝率1位の作り方は分析スクリプト `scripts/analysis/analogy-finder-fr2-strat/cm2.py` の `build_axes` にある。

200件未満の層は末尾の条件から外して親の層を使う（m=200）。使う層は 4条件が70.5%、3条件が27.2%、2条件が2.3%（test）。層の大きさの中央値は、4条件 311、3条件 1,406、2条件 37,626、1条件 72,658。

ADR-0080 の前提は、今日のレースの as-of 特徴量と全母集団との距離だった。as-of 特徴量はローリング集計を含む337次元で、これを計算するために Python のバッチ・Storage の行列・GitHub の dispatch を置いた。層別では距離も順位も要らない。条件の値は出走表の勝率・級別・会場だけで決まる。

読み取りで確かめたこと（本番、2026-10-02 15時台）:
- 今日の168レースの4条件を、`races`・`race_entries` から SQL で作れた。実行は 3ms。6艇の勝率がそろわないレースは0件、級別は A1〜B2 のみ
- 2条件の層に相当する約4万レースの決着を集計した（決まり手・1着艇・3連単の組み合わせ120通り）。結合と全件走査つきで 127ms。条件の列と索引を持つ表なら、これより速い
- 本番の race_entries では、2025-12-03〜2026-04 の勝率の NULL は22行、級別の欠け・異常値は0（second-opinion-reviewer の読み取り）
- 取得済みデータの DB 内集計を、Vercel Cron から SQL の RPC で回す前例がある。`api/cron/racer-course-technique-stats.js` で、ADR-0066 改訂1 に基づく。モード off／shadow／live と、`scrape_job_state` での監視が付いている

## 決定
1. **FR-2 の分布は SQL の RPC（`get_analogy_similar`）で数える。** 次のものは作らない:
   - 近傍のバッチ（`neighbors.py`・`generate-analogy-neighbors.yml`）
   - Storage の母集団行列（`pool.py`）
   - FR-2 用の dispatch

   FR-2 は Python にも GitHub Actions にも依存しない。
2. **母集団 `analogy_pool_outcomes` に条件の4列を持たせ、SQL で作る。**
   - 行は SQL 関数で作り、upsert する。長期分（2019-04〜2025-12-02）は `kb_archive_*` から、以後は本体（`races`・`race_entries`・`race_results`・`race_start_timings`・`exhibition_data`）から作る
   - 完全レースの判定は `features.py` の `load_kb`・`load_main`・`add_labels` と同じにする。条件は「6艇」「欠場なし」「結果あり」「中止・不成立でない」「1着が1艇」「1〜3着に返還艇なし」
   - 勝率差の帯は IMMUTABLE な SQL 関数1つ（`analogy_gap_band`）に境界を持たせ、生成列にする。**勝率差は 1/100 単位の数値（numeric）で比べ、境界ちょうどは上の帯とする。これを正とする**。分析は float32 で計算したため、境界ちょうどの勝率差は浮動小数の誤差でどちらの帯にも振れていた。2026-09 の4,656Rで、境界ちょうどのレースは44R、分析と帯が違うのは4R（0.09%）
   - 索引は条件の順の複合索引 `(gap_band, b1_class, venue_code, top_boat, race_date)` にする。どの深さの層も先頭一致で引け、新しい順の一覧にも使える
3. **起動は Vercel Cron で、2つのジョブに分ける**（`racer-course-technique-stats` と同じ形。モードつき）:
   - `analogy-pool`（JST 1:00・12:30）: 直近7日の行を作り直し、変わった行だけ upsert する。結果の確定（result-catchup 23:50・0:30）の後と、K ファイル同期（07:00・12:00）が実進入を埋めた後に走らせる
   - `analogy-snapshots`（JST 7:30・8:30・10:00・14:00）: 今日の締切前のレースのスナップショットを作る。8:30 は 7:30 が失敗したときの補足。10:00・14:00 は出走表が後から入る会場とナイターのため

   母集団の更新が失敗しても、スナップショットは前の母集団で作れる。前日の実進入が 7:30 時点で欠けていても、影響するのは層の中の前日のレースだけ（数件）。
4. **スナップショット（BOA-627）は1レース1行で、次を保存する**:
   - 条件の値
   - 自動で選んだ深さ
   - 深さごとの件数
   - 母集団の期間（`pool_from`・`pool_cutoff`）
   - **自動で選んだ深さの分布**（決まり手・1着艇・1着の進入コース・3連単の全組み合わせ・コールアウト用の進入×決まり手の件数）

   スナップショットがあるレースでは、RPC は自動の深さについて保存した分布をそのまま返す。条件チップで深さを変えたときだけ、`pool_cutoff` 以前の母集団で数え直す（探索用の表示で、時点固定の対象にしない）。スナップショットは締切前・中止でない・6艇の出走表がそろったレースにだけ作り、既にあれば作らない（`ON CONFLICT DO NOTHING`）。スナップショットが無いレース（締切までに作れなかった等）は、その場で条件を作り、その日より前の母集団で数える。この場合は保存なしであることを返す
5. **母集団の値の約束は ADR-0080 から引き継ぐ。** BOA-635 の依頼 R1〜R4・D-5 で決めたもので、次のとおり:
   - 3連単は本体の `payout_trio` から取る
   - F・出遅れ・不明の ST は NULL
   - 実進入が不明なら NULL
   - 不成立と、1〜3着に返還艇が入るレースは母集団に入れない
6. **画面の割合は、件数÷n をそのまま出す（ユーザー確認待ち）。** 理由は見せ方で、件数と%が必ず一致し、実データの件数で照合できる。spec の文面ルール4（件数が主役）にも合う。精度の根拠は無い。分析で選んだ表示（親の層の割合に向けて α'=50 で平滑化）と比べると、生の割合は test で評価しておらず、cal では約0.002悪い（m=200 で α'=1 が 1.3233、α'=50 が 1.3211）。確認で平滑化を採った場合は、RPC の返り値に親の層の件数を足し、画面で平滑化する
7. **条件のチップは末尾からだけ外せる。** 会場を残して級別だけ外す、のような組み合わせは作らない。検証したのは条件の順に外す戻し方だけで、索引の先頭一致もこの順で効く。外せる下限は1条件（勝率差の帯だけ）。深さを決める n は層の行数（決まり手・進入の欠けも数える）

## 却下した選択肢
- **ADR-0080 のまま（近傍を Python のバッチで作り、Storage に行列を置く）**: 層別には要らない距離計算を抱えることになる。さらに、遅れの多い起動経路（Vercel→GitHub）・トークン・Storage の版管理も必要になる。層の件数は、SQL の索引で直接数えられる
- **母集団を週次の学習ジョブ（Python、features.py）で作る**: 条件の定義が1か所で済む利点はある。しかし母集団が最大7日古くなり、学習ジョブ（起動の仕組みが未実装）が止まると FR-2 も止まる。定義の二重化は、参照実装との照合で固定する（下の「影響」）
- **表示のたびに母集団を元テーブルから集計する（条件の列を持たない）**: 1回ごとに約240万艇行から作り直すことになり、2秒以内の要件を満たせない
- **スナップショットに条件と件数だけを保存し、分布は毎回数え直す（この ADR の初版の案）**: ずれる経路が多く、BOA-627 の「見せたものを再現できる」を保証しない（second-opinion-reviewer の指摘）。ずれる経路は次のとおり:
  - 直近7日の作り直し
  - 長期分の投入途中に作ったスナップショット
  - K/B 補完や BOA-523 の実進入の補完
  - 判定の定義の変更

  分布の保存は1レースあたり数KB（3連単の組み合わせ最大120通りと、進入×決まり手の件数）。1日約150レースで年に約0.2GB
- **全深さの分布をスナップショットに保存する**: 1レース約12KB、年に約0.6GB。チップを外した表示は探索用なので、数え直しで足りる
- **スナップショットを、画面の表示時に匿名の RPC で書く**: 匿名ロールに書き込みを開けることになる。プロジェクトの RLS 規律（匿名は SELECT のみ）に反する
- **4条件の任意の組み合わせを外せるチップ**: 検証していない層（16通り）を出すことになり、「親の層」の意味も崩れる

## 影響
- **本番 DB への書き込み**: マイグレーション 119 の適用と、長期分の初回投入。どちらもユーザーが行う。FR-2 には、Vercel の環境変数（GitHub のトークン）は要らない。FR-1 の週次学習の dispatch には、ADR-0080 どおり要る
- **定義の二重化（SQL と Python）**: 照合用の参照実装 `scripts/ml/analogy/strata.py` を置く。中身は、`cm2.py` の `build_axes` の境界を固定し、1/100単位の比較にしたもの。`features.py` の完全レースの判定を使う。`scripts/maintenance/verify-analogy-pool.js`（manual）は、本番の期間を区切って次の3点を照合する:
  - 完全レースの集合
  - 条件4つの値
  - 決まり手・1着艇・1着の進入コースのラベル
- **過去の行が後から変わるとき**: データ取得レーンの K/B 補完や BOA-523 の実進入の補完は、7日より古い行を変える。補完が終わったら、その期間で `refresh_analogy_pool(from, to)` を呼ぶ運用にする（tasks に書く）。`verify-analogy-pool.js` は、元テーブルと母集団の行数・ラベルの差も出す
- **勝率差の帯の境界を変えるとき**: 生成列を作り直すマイグレーションが要る。境界は分析で確定した値で、変える予定は無い
- **BOA-635 の前提が崩れる。** BOA-635 の ADR 案（PR #1093） は次の3つを前提にしており、層別ではどれも成り立たない:
  - ① 画面で800行を数える。層の大きさは200〜7万件で、2条件の層（2.3%、中央値約3.8万件）では行を渡せない
  - ② スナップショットとの紐づけに `(model_version, asof_stage, asof_at)` を使う。FR-2 はモデルの版を持たず、1レース1行になる
  - ③ 定番／レアの線を「近傍800件」で作る

  BOA-635 のレーンと、次のどちらかで合意してから確定する（plan.md「BOA-635 との接続」）:
  - (A) BOA-635 も SQL で数える
  - (B) 行を渡すのは件数が上限以下の層に限る
- **応答時間**: 母集団の投入後に、4つの深さそれぞれで RPC の応答時間を実測する（tasks）。1条件（約7万件）の集計も匿名で走るので、`statement_timeout` 5秒に収まることを確かめる
